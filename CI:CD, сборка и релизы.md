## CI/CD, сборка и релизы

### Q209 (🟢): Что такое CI и CD в контексте iOS, и какие задачи обычно автоматизируют?

**Кратко**
- **CI (Continuous Integration)** — автоматическая проверка каждого изменения: сборка, тесты, статический анализ.
- **CD (Continuous Delivery/Deployment)** — автоматизация доставки сборок: TestFlight/App Store, релизные артефакты, нотификации.
- В iOS чаще: CI + delivery в TestFlight, а “deployment в App Store” часто остаётся полуавтоматическим из‑за ревью и ручных гейтов.

**Развёрнуто**
## 1) CI: цель и что именно автоматизируют
CI отвечает на вопрос: “можно ли безопасно влить изменения в main и не сломать продукт?”

Типичные шаги CI для iOS:
- Проверки репозитория:
  - форматирование/линт (SwiftLint/SwiftFormat),
  - проверка сборочных настроек (warnings as errors при необходимости).
- Сборка:
  - `xcodebuild build` для нужных схем/таргетов,
  - сборка разных конфигураций (Debug/Release), если важно.
- Тесты:
  - unit tests,
  - (опционально) UI tests на симуляторах,
  - отчёты (JUnit, xcresult) и артефакты.
- Аналитика качества:
  - coverage,
  - статанализ (например, clang static analyzer),
  - иногда SAST/secret scanning.
- Артефакты:
  - сохранение `xcresult`, логов, dSYM, билдов для QA.

Смысл:
- быстрый feedback loop,
- детерминированность (одинаковые результаты у всех),
- защита main ветки (quality gates).

## 2) CD: цель и границы в iOS
CD отвечает на вопрос: “как быстро и предсказуемо доставлять сборки туда, где их будут проверять/пользоваться?”

В iOS обычно автоматизируют:
- **Continuous Delivery**:
  - сборка `.ipa`,
  - подпись,
  - выгрузка в **TestFlight**,
  - создание release notes/номер версии,
  - публикация артефактов (dSYM для crash reporting),
  - уведомления в Slack/почту.
- **Continuous Deployment** (в смысле “в прод”):
  - может быть частично автоматизирован (upload + submit), но чаще делают ручной approval:
    - из‑за App Review,
    - из‑за необходимости контроля rollout/hotfix,
    - из‑за комплаенса.

Важно:
- CD не равно “автозаливка в стор каждый коммит”.
- Обычно есть “release pipeline” с гейтами: QA → internal TF → external TF → submit → phased rollout.

## 3) Типовая схема pipelines на практике
- PR pipeline:
  - lint + build + unit tests (быстро, чтобы не тормозить ревью).
- Main pipeline:
  - полный набор тестов + сборка артефактов.
- Release pipeline:
  - bump версий → архив/подпись → TestFlight → теги/релизные заметки → (опционально) submit.

## 4) Частые ожидания от senior-ответа
На уровне senior важно не перечисление инструментов, а понимание:
- какие проверки должны быть “обязательными” на PR,
- что должно быть “релизным” пайплайном,
- как обеспечить воспроизводимость и безопасность (signing, secrets),
- как уменьшить флейки и время исполнения.

## 5) Формулировка на собесе
“CI — это автоматическая проверка изменений: сборка/тесты/линт/качество, чтобы main не ломался. CD — это автоматизация доставки артефактов: подпись, загрузка в TestFlight, публикация dSYM, релизные заметки и гейты. В iOS чаще delivery до TestFlight полностью автоматизируют, а выпуск в App Store обычно проходит через ручные approvals и staged rollout.”

**Самопроверка**
- Оспорено: “CD = автоматический релиз в App Store на каждый коммит” — для iOS это редко практично из‑за гейтов и ревью.
- Неочевидно: ключевая ценность CI — быстрый и детерминированный feedback, а не набор модных тулов.
- Источники, которые стоит освежить: документация Xcode Cloud/GitHub Actions для iOS, Apple про TestFlight и build processing, практики хранения секретов и code signing в CI.


### Q210 (🟢): Из каких шагов обычно состоит pipeline для iOS (lint → build → test → archive → deploy)?

**Кратко**
Типичный iOS pipeline:
1) Checkout + подготовка окружения,
2) зависимости (SPM/CocoaPods),
3) lint/format,
4) build,
5) unit tests,
6) UI tests (опционально),
7) archive + code signing,
8) export `.ipa`,
9) upload (TestFlight/App Store) + артефакты (dSYM) + нотификации.

**Развёрнуто**
## 1) Почему pipeline обычно делят на PR и Release
Одна и та же “труба” редко подходит всем:
- PR pipeline должен быть быстрым (минуты), иначе команда страдает.
- Release pipeline может быть тяжелее (больше тестов, подпись, артефакты).

Поэтому принято:
- **PR**: lint + build + unit
- **main/nightly**: больше тестов, иногда UI tests
- **release**: archive/export/upload

## 2) Базовые шаги (по порядку)
### 1) Checkout + environment
- получить код,
- выбрать Xcode version (фиксированно),
- настроить Ruby/Node/Swift toolchain если нужно.

Ключ:
- фиксировать версии инструментов, иначе “у меня работает, в CI — нет”.

### 2) Dependencies
- SPM: `xcodebuild -resolvePackageDependencies` / кэш,
- CocoaPods: `pod install` (обычно через Bundler).

Важно:
- pinned versions (Podfile.lock, Package.resolved),
- кэширование чтобы не тратить время каждый запуск.

### 3) Lint / Format / Static checks
- SwiftLint/SwiftFormat,
- иногда: danger, linting PR description, checks for secrets.

Цель:
- быстро отсеивать нарушения, не тратить время на сборку.

### 4) Build
- `xcodebuild build` для схемы,
- иногда для нескольких схем/таргетов,
- fail on warnings (если команда приняла правило).

Цель:
- ранний сигнал, что компиляция сломана.

### 5) Unit tests
- `xcodebuild test` на симуляторе,
- генерация отчётов (xcresult, coverage).

Важное:
- стабильность: фиксированный симулятор, чистое окружение.

### 6) UI tests (опционально)
- запуск UI tests часто медленный и флейковый,
- обычно:
  - nightly,
  - или только на release,
  - или на критичные флоу.

Нужно:
- stubs/mocks для сети,
- сброс состояния приложения,
- стабилизация (disable animations, deterministic data).

### 7) Archive + code signing (Release)
- `xcodebuild archive`,
- подпись (profiles/certs),
- export: `xcodebuild -exportArchive` → `.ipa`.

Ключ:
- code signing должен быть воспроизводимым (без ручных “магий” на агенте).

### 8) Upload / Deploy
- TestFlight:
  - upload `.ipa`,
  - релизные заметки,
  - группы тестеров.
- App Store:
  - upload + submit (часто с manual approval).

### 9) Post-steps: артефакты, наблюдаемость
- dSYM upload (Crashlytics/Sentry),
- отчёты тестов/coverage,
- нотификации (Slack),
- теги/релизные заметки, changelog.

## 3) Где чаще всего “сыпется”
- зависимости (SPM caching, pods),
- signing,
- UI tests (флейки),
- различия Xcode версии и симуляторов.

## 4) Как ответить на собесе
“Я разделяю PR и release pipelines. На PR: lint/format, build, unit tests. На release: archive + signing, export ipa, upload в TestFlight/App Store, публикация dSYM и отчётов, уведомления. Критично фиксировать версии инструментов и зависимостей и иметь воспроизводимую подпись.”

**Самопроверка**
- Оспорено: “pipeline = один большой скрипт” — без разделения PR/release вы либо тормозите разработку, либо пропускаете проверки.
- Неочевидно: “post-steps” (dSYM, отчёты, нотификации) — часть зрелого CI/CD, иначе дебаг релизов становится болью.
- Источники, которые стоит освежить: xcodebuild archive/export docs, TestFlight upload tooling, best practices по стабильности UI tests.


### Q211 (🟢): Что такое code signing: certificates, App IDs, provisioning profiles — как это связано со сборкой?

**Кратко**
- **Code signing** — криптографическая подпись приложения, подтверждающая:
  1) кто его подписал (certificate),
  2) что оно не было изменено после подписи.
- **App ID** (Bundle ID + entitlements) определяет “идентичность” приложения.
- **Provisioning Profile** связывает:
  - App ID + entitlements,
  - certificate(ы),
  - разрешённые устройства (для development/ad-hoc),
  - тип распространения (dev, ad hoc, app store, enterprise).
- Без корректного signing:
  - приложение не установится/не запустится на девайсе,
  - архив не экспортируется в `.ipa`,
  - TestFlight/App Store загрузка невозможна.

**Развёрнуто**
## 1) Модель: зачем Apple требует подпись
iOS доверяет только подписанному коду:
- подпись гарантирует целостность бинаря,
- позволяет применить политики безопасности (entitlements),
- связывает приложение с вашим Apple Developer аккаунтом.

## 2) Certificates: что это
Certificate = “удостоверение”, кем подписываем.
На практике есть ключевая пара:
- private key (в Keychain, держится у вас/на CI),
- public key + сертификат от Apple (идентифицирует вас).

Типы по смыслу:
- Development certificate — для сборок на устройства разработчиков.
- Distribution certificate — для распространения (TestFlight/App Store/AdHoc).

Важно:
- сертификат может быть отозван/истечь → сборки сломаются.
- private key — секрет. Если утечёт, подпись можно подделывать (для вашего аккаунта).

## 3) App ID: идентичность приложения
App ID обычно привязан к **Bundle Identifier** (например, `com.company.app`).
Он определяет:
- какие capabilities доступны (push, keychain, iCloud, etc.),
- какие entitlements допустимы.

То есть:
- App ID — это “контракт возможностей” приложения.

## 4) Entitlements: возможности приложения
Entitlements — это “права”, которые вы запрашиваете:
- Push Notifications,
- App Groups,
- Keychain Sharing,
- iCloud и т.д.

Они должны совпадать:
- в project settings,
- в provisioning profile,
- с тем, что разрешено в Developer Portal.

Типовой баг:
- capability включили в Xcode, но профиль/portal не обновили → signing error.

## 5) Provisioning Profile: связующая “склейка”
Provisioning profile — файл, который говорит системе:
- этому bundle ID можно доверять,
- вот с этими entitlements,
- подписанному вот этими сертификатами,
- и (для dev/ad hoc) на вот этих устройствах.

Типы:
- Development: dev cert + devices.
- Ad Hoc: distribution cert + devices (для внешнего теста без TestFlight).
- App Store: distribution cert без списка устройств (для App Store/TestFlight).
- Enterprise (если есть): для внутреннего распространения без App Store.

## 6) Как это связано со сборкой и CI
### На локальной машине
Xcode может “автоматически” управлять подписью:
- подгружает профили,
- выбирает сертификат.

### В CI
Нужно сделать то же, но воспроизводимо:
- импортировать certificates (и private key),
- установить provisioning profiles,
- убедиться, что bundle ID/entitlements совпадают,
- собрать archive и экспортировать ipa.

Ошибки CI чаще всего:
- “No matching provisioning profiles found”,
- “Signing requires a development team”,
- mismatch entitlements,
- истёк/отозван сертификат.

## 7) Как отвечать на собесе
“Code signing — подпись приложения сертификатом, чтобы iOS доверяла бинарю и проверяла целостность. App ID задаёт bundle ID и разрешённые capabilities/entitlements. Provisioning profile связывает App ID + entitlements + сертификаты (и устройства для dev/ad hoc) и тип распространения. Для CI важно иметь воспроизводимую установку certs/profiles и совпадение entitlements, иначе не получится archive/export/upload.”

**Самопроверка**
- Оспорено: “подпись — это просто галочка в Xcode” — в CI и на релизах это отдельная система с сертификатами, профилями, entitlements и сроками.
- Неочевидно: provisioning profile — это не “сертификат”, а контейнер правил: что и кем можно подписывать и куда распространять.
- Источники, которые стоит освежить: Apple Code Signing Guide, устройство provisioning profiles, capabilities/entitlements matching, практики безопасного хранения private keys в CI.


### Q212 (🟢): Чем отличаются Debug / Release конфигурации и Schemes, и зачем нужны разные build settings?

**Кратко**
- **Build configuration** (Debug/Release/Custom) — набор build settings (оптимизации, флаги компилятора, кодоген, strip symbols и т.д.).
- **Scheme** — “сценарий запуска”: какие таргеты, с какой конфигурацией и какие действия (Run/Test/Profile/Archive).
- Разные settings нужны, чтобы:
  - в Debug иметь быструю сборку и дебаг,
  - в Release — оптимизацию и корректный релизный бинарь,
  - а также разные окружения (dev/stage/prod), флаги, endpoints, feature flags.

**Развёрнуто**
## 1) Build configuration: что это на практике
Build configuration — это “переключатель” набора параметров компиляции/линковки.

Типовые отличия:
- Оптимизации:
  - Debug: `-Onone` (или низкие), быстрее компиляция, лучше дебаг.
  - Release: `-O`/`-Osize` (в зависимости), быстрее выполнение, хуже пошаговый дебаг.
- Assertions/logging:
  - Debug: больше assert’ов, debug логов.
  - Release: часть assert выключена или ведёт себя иначе (например, `assert` не срабатывает в релизе).
- Символы/размер:
  - Release часто делает strip symbols, bitcode (исторически), уменьшение бинаря.
- Preprocessor / Swift flags:
  - `SWIFT_ACTIVE_COMPILATION_CONDITIONS` (например, `DEBUG`).

Важно:
- Debug/Release — это не “для симулятора/для девайса”. Это разные наборы настроек. Архив обычно делается на Release, но можно сделать custom.

## 2) Scheme: чем отличается от configuration
Scheme — это набор действий:
- Run
- Test
- Profile
- Analyze
- Archive

И у каждого действия в scheme выбирается:
- какая build configuration используется.

Например:
- Run → Debug
- Test → Debug
- Profile → Release
- Archive → Release

Зачем это нужно:
- вы можете запускать приложение в Debug, но профилировать и архивировать в Release, чтобы профайлинг был релевантен.

## 3) Зачем нужны разные build settings кроме Debug/Release
### A) Разные окружения (dev/stage/prod)
Вместо того, чтобы хардкодить endpoint:
- делают конфигурации `Debug-Dev`, `Debug-Staging`, `Release-Prod`,
или используют `.xcconfig` файлы.

Ключ:
- не превращать это в хаос, где конфигов 20 и никто не понимает, что куда.

### B) Feature flags и поведение приложения
- включить дополнительные проверки в dev,
- отключить экспериментальные фичи в prod,
- включить тестовые SDK ключи.

Требование senior уровня:
- флаги должны быть управляемыми (remote config/feature flags), а build flags — только для окружений и сборочных отличий, а не для “включать фичу навсегда”.

### C) Разные таргеты/white-label
Если несколько приложений из одной кодовой базы:
- schemes помогают собрать конкретный таргет с конкретными настройками.

## 4) Чем это важно для CI
CI использует:
- схему + действие (`test`, `archive`),
- и выбранную конфигурацию.

Типичные проблемы:
- в CI scheme “shared” не включена → `xcodebuild` не видит схему,
- Archive на Debug → неожиданные настройки/оптимизации,
- неправильно выставлены compilation conditions.

## 5) Как отвечать на собесе
“Build configurations — это набор build settings (оптимизация, флаги, символы), Debug для удобного дебага, Release для релиза и производительности. Scheme — это сценарий действий (Run/Test/Profile/Archive) и привязка каждой операции к конфигурации. Разные конфиги/xcconfig позволяют разделять окружения и сборочные параметры без хардкода.”

**Самопроверка**
- Оспорено: “Scheme и configuration — одно и то же” — scheme выбирает действие и какую конфигурацию для него применять.
- Неочевидно: профилирование и архивирование должны идти на релизных настройках, иначе цифры перфа не репрезентативны.
- Источники, которые стоит освежить: Xcode build settings, SWIFT_ACTIVE_COMPILATION_CONDITIONS, xcconfig best practices, xcodebuild scheme sharing в CI.


### Q213 (🟢): Что такое TestFlight и как обычно устроен релизный цикл (internal/external testing → App Store)?

**Кратко**
- **TestFlight** — официальный канал Apple для распространения pre-release сборок:
  - **Internal testing** (внутренние тестеры из команды App Store Connect),
  - **External testing** (внешние тестеры, обычно требует Beta App Review).
- Типичный цикл:
  1) CI собирает и загружает билд в TestFlight,
  2) internal QA проверяет,
  3) external beta (если надо),
  4) сбор release-кандидата,
  5) submit в App Store + (опционально) phased rollout,
  6) мониторинг (crash rate, key metrics) и hotfix при необходимости.

**Развёрнуто**
## 1) Роль TestFlight в процессах
TestFlight закрывает задачу:
- дать тестерам “почти релизную” сборку, подписанную как distribution,
- управлять группами тестеров,
- получать быстрый feedback до App Store.

Это особенно важно, когда:
- нельзя рассылать ad-hoc (ограничение по устройствам),
- нужна централизованная раздача и контроль.

## 2) Internal vs External testing
### Internal testing
- тестеры — пользователи App Store Connect команды,
- обычно быстрее по формальностям,
- подходит для QA/PM/дизайна/разработчиков.

### External testing
- можно приглашать внешних пользователей,
- часто требуется Beta App Review (зависит от состояния и изменений),
- полезно для широкого бета-теста и получения фидбэка “из поля”.

Практическая мысль:
- “external” включают, когда нужен массовый тест или реальные пользователи, иначе обычно хватает internal.

## 3) Типовой релизный цикл: что считается “здоровым”
### A) Build & upload
- CI делает `archive` и upload в TestFlight,
- автоматически прикладывает release notes, номер версии/билда,
- публикует dSYM.

### B) Internal QA (быстрый)
- проверить критичные флоу,
- smoke/regression,
- проверить миграции/авторизацию/платежи,
- зафиксировать acceptance.

### C) External beta (опционально)
- когда нужно:
  - проверить нагрузку,
  - проверить edge cases,
  - собрать UX feedback,
  - проверить совместимость устройств.

### D) Release candidate
- либо тот же билд, либо отдельный RC билд,
- freeze ветки, только hotfix,
- повышенные проверки (analytics, crash-free sessions).

### E) App Store submission
- upload build в App Store Connect,
- заполнить metadata,
- submit for review.

### F) Rollout & monitoring
- phased rollout (если используете),
- мониторинг crash rate, ANR-like симптомов, ключевых метрик,
- быстрый hotfix pipeline.

## 4) Где чаще всего ломается процесс
- “мы тестим только Debug локально” → релизный build отличается.
- нет release candidates → в прод летят “сыроватые” билды.
- нет мониторинга после релиза → баги обнаруживаются поздно.
- нет стратегии hotfix → релиз “стоит”.

## 5) Как отвечать на собесе
“TestFlight — канал для бета распространения. Internal — для команды, external — для внешних тестеров и часто с beta review. Нормальный цикл: CI грузит билд в TF, внутренний QA прогоняет, при необходимости external beta, затем RC и submit в App Store, staged rollout и мониторинг с готовым hotfix потоком.”

**Самопроверка**
- Оспорено: “TestFlight — просто место положить билд” — на практике это ключевой этап контроля качества и управления тестированием.
- Неочевидно: стабильный релиз — это не только upload, но и процессы: RC, мониторинг, rollback/hotfix.
- Источники, которые стоит освежить: App Store Connect/TestFlight docs (internal/external), phased release guidance, best practices release management.



### Q214 (🟠): Как устроить версионирование (CFBundleShortVersionString vs CFBundleVersion) и автоподнятие билд-номера в CI?

**Кратко**
- `CFBundleShortVersionString` (**Version**) — “маркетинговая” версия: `1.4.0`.
- `CFBundleVersion` (**Build**) — номер сборки: обычно монотонно растёт: `345`, `2026.02.01.1`.
- В CI обычно:
  - Version меняют осознанно (по релизу),
  - Build увеличивают автоматически на каждый архив/релиз-кандидат.
- Главное требование App Store:
  - для одной Version Build должен увеличиваться при каждом новом upload.

**Развёрнуто**
## 1) Разница по смыслу
### Version (CFBundleShortVersionString)
- видит пользователь в App Store,
- меняется реже: релизы/минорные версии,
- обычно соответствует семантике: major.minor.patch.

### Build (CFBundleVersion)
- технический идентификатор конкретной сборки,
- должен быть уникальным/монотонным для загрузок,
- удобен для трассировки:
  - “какая конкретно сборка у пользователя”.

## 2) Как это используется в реальном релизном процессе
Обычно:
- на ветке release:
  - выставили Version: `2.3.0`,
- CI на каждый `archive`:
  - инкрементит Build: 501 → 502 → 503,
  - и грузит в TestFlight.

Если нашли баг:
- фикс,
- новый билд (504) с той же Version (2.3.0),
- снова в TestFlight.

В App Store:
- можно выпустить `2.3.0 (build 507)`.

## 3) Стратегии auto-increment build number
### A) Простой инкремент
- хранить build number в репозитории (plist/xcconfig),
- CI увеличивает и коммитит обратно (осторожно: гонки).
Минусы:
- параллельные сборки → конфликты, race.

### B) CI build number как источник правды
- использовать номер билда CI (например, GitHub Actions run number, Jenkins build number).
Плюсы:
- монотонность,
- нет коммитов обратно.
Минусы:
- при смене CI/переносе проекта нужно следить за уникальностью.

### C) Timestamp-based
- `YYYYMMDDHHmm` или `YYYY.MM.DD.<counter>`.
Плюсы:
- почти всегда уникально,
- удобно для отладки.
Минусы:
- нужно соблюдать требования формата (App Store принимает строки из цифр и точек; конкретные ограничения зависят от правил и tooling).

Практичный компромисс:
- CI number (монотонный) +/или timestamp.

## 4) Где хранить и как менять (на уровне проекта)
Пути:
- напрямую в Info.plist,
- через build settings (`MARKETING_VERSION` и `CURRENT_PROJECT_VERSION`),
- через `.xcconfig` для разных конфигов.

Senior практика:
- держать Version/Build в build settings, а не руками в plist,
- чтобы CI мог менять значения без ручных правок plist-файлов по таргетам.

## 5) Важные edge cases (на собесе любят)
- Мульти-таргет (app + extensions):
  - Version/Build должны быть согласованы,
  - иначе при архиве могут быть ошибки или “разъезд” версий.
- Hotfix:
  - Version растёт по политике (например, patch bump),
  - Build — всегда монотонно.
- TestFlight vs App Store:
  - требования к увеличению build применимы к upload в ASC.

## 6) Как отвечать на собесе
“Version (CFBundleShortVersionString / MARKETING_VERSION) — пользовательская версия, меняется по релизу. Build (CFBundleVersion / CURRENT_PROJECT_VERSION) — технический номер сборки, должен увеличиваться при каждом новом upload. В CI я обычно автоставлю build из номера сборки CI (или timestamp), а version меняю на релизных ветках/тегах.”

**Самопроверка**
- Оспорено: “достаточно менять только Version” — App Store/TestFlight требуют уникальные build numbers для загрузок одной версии.
- Неочевидно: коммитить auto-increment обратно в репозиторий опасно при параллельных сборках; лучше использовать номер CI как источник правды.
- Источники, которые стоит освежить: Apple/Xcode build settings `MARKETING_VERSION` и `CURRENT_PROJECT_VERSION`, требования App Store Connect к build numbers и мульти-таргет версиям.


### Q215 (🟠): Как управлять secrets в CI (API keys, signing, tokens) так, чтобы они не утекали в репозиторий и логи?

**Кратко**
- Secrets нельзя хранить в git и нельзя печатать в логи.
- Использовать:
  - секрет-хранилище CI (GitHub Actions Secrets/GitLab CI Variables/Jenkins Credentials),
  - короткоживущие токены (OIDC), least privilege,
  - шифрование файлов (например, signing artifacts) и доступ по ролям,
  - masking в логах + запрет “echo” чувствительных переменных.
- Разделять:
  - “секреты сборки” (signing) и “секреты приложения” (API keys),
  - окружения (dev/stage/prod) с разными секретами.

**Развёрнуто**
## 1) Что считаем секретами в iOS проектах
Типичные:
- Apple signing:
  - `.p12` (certificate + private key),
  - provisioning profiles,
  - App Store Connect API key (JWT key) или credentials.
- Токены внешних сервисов:
  - Crashlytics/Sentry, analytics, feature flags, CDN.
- API keys бэкенда (часто не должны жить в приложении как “секрет”, потому что клиент можно реверснуть).

Сразу оговорка (важная на собесе):
- всё, что лежит в клиенте, не является настоящим секретом.
Можно защитить от случайных утечек, но нельзя считать “безопасным ключом”.

## 2) Базовые принципы безопасности
### A) Не хранить в репозитории
- никакие `.p12`, приватные ключи, токены.
- `.env` файлы — только шаблоны без значений.

### B) Не печатать в логи
- многие утечки происходят из-за `printenv`, `echo $TOKEN`, ошибок скриптов.

### C) Least privilege
- токен/ключ должен давать минимум прав:
  - отдельный ключ для upload в TestFlight,
  - отдельный для crash reporting,
  - разделение по окружениям.

### D) Rotation и отзыв
- иметь процесс смены ключей:
  - срок действия,
  - кто и как ротирует,
  - что происходит при утечке.

## 3) Практика: где хранить secrets
### A) CI secret storage
- Secrets/Variables хранилища CI:
  - значения недоступны в PR из forks (обычно),
  - можно ограничивать по окружениям,
  - есть masking.

### B) Файловые секреты
Если нужен файл:
- `.p12`, `.mobileprovision`, `.json key`.

Подходы:
- хранить зашифрованным (например, GPG/openssl) в репо и расшифровывать в CI через secret key,
- или хранить в CI как secure file/artefact store,
- или генерировать на лету через API (где возможно).

Сеньор-мысль:
- чем меньше “постоянных файлов-секретов” живёт где-то, тем лучше.

### C) OIDC/short-lived tokens
Там, где поддерживается:
- CI получает короткоживущий токен по OIDC,
- без хранения long-lived ключей.

Это уменьшает blast radius и упрощает rotation.

## 4) Защита от утечек в логах
- включить masking (в CI),
- избегать вывода env переменных,
- отключить `set -x` в bash, или включать только для безопасных блоков,
- фильтровать логи артефактов, если они публикуются.

## 5) Pull Requests и fork’и: отдельная зона риска
- PR из forks часто не должен иметь доступ к секретам:
  - иначе злоумышленник может вывести secrets в лог.
Решения:
- разделить pipeline:
  - для PR из forks — только сборка без секретов,
  - release/job с секретами — только на доверенных ветках.
- требовать approvals на jobs, которые используют secrets.

## 6) “Секреты приложения” (API keys) — важное уточнение
Если ключ нужен клиенту:
- его можно извлечь из приложения.

Практики:
- минимизировать значение ключа (scopes),
- делать server-side exchange (клиент получает временный токен),
- привязка к устройству/сессии,
- rate limiting на бэкенде.

На собесе ценят фразу:
- “client secrets не существуют”.

## 7) Как отвечать на собесе
“Я храню secrets только в секрет-хранилище CI или в зашифрованном виде, не в git. Ограничиваю доступ по окружениям и веткам, применяю least privilege и rotation. В логах включаю masking и избегаю печати env. Для PR из forks секреты не выдаю. И отдельно проговариваю, что ключи внутри приложения не являются настоящими секретами — безопасность делается сервером и scopes.”

**Самопроверка**
- Оспорено: “достаточно спрятать ключ в коде” — любой ключ в клиенте извлекаем, нужна серверная модель безопасности.
- Неочевидно: главная угроза утечек в CI — логи и PR из недоверенных источников; нужны гейты и разделение pipelines.
- Источники, которые стоит освежить: CI secrets/masking best practices для вашей платформы (GitHub/GitLab/Jenkins), Apple API key usage для App Store Connect, OIDC short-lived token подходы.



### Q216 (🟠): Как ускорять сборки: кэширование SPM/CocoaPods, derived data, incremental builds, параллельные джобы — что реально работает?

**Кратко**
- Самые “окупаемые” ускорения:
  1) фиксировать Xcode/зависимости → меньше пересборок,
  2) кэшировать зависимости (SPM/CocoaPods) и DerivedData,
  3) разделить pipeline на быстрый PR и тяжёлый release,
  4) прогонять тесты параллельно (шардинг),
  5) избегать лишних archive/export на PR.
- Опасная зона: кэш DerivedData может дать нестабильность — нужен грамотный key и периодическая очистка.

**Развёрнуто**
## 1) Сначала про “что тормозит iOS CI”
Обычно время уходит на:
- resolving dependencies (SPM) / установка pods,
- компиляция (особенно Swift, особенно большие модули),
- запуск тестов на симуляторе,
- archive/export/signing.

Значит ускоряем именно эти куски.

## 2) Кэширование зависимостей
### A) Swift Package Manager
Что кэшировать:
- каталог SourcePackages (SPM build artifacts),
- иногда `.build`/`DerivedData` части (зависит от CI системы).

Что реально помогает:
- caching по ключу:
  - Xcode version,
  - `Package.resolved` hash,
  - архитектура/OS агента.

Ловушка:
- если Xcode version меняется, кэш может стать бесполезным или ломать сборку.

### B) CocoaPods
Что кэшировать:
- `Pods/` и CocoaPods cache (если CI позволяет),
- Ruby gems через Bundler cache (иначе `pod install` сам по себе тормозит).

Ключи кэша:
- `Podfile.lock`,
- версия Ruby/Bundler,
- версия CocoaPods,
- Xcode version.

Плюс:
- сэкономит минуты.

Минус:
- при несовпадении окружений можно получить “mysterious” ошибки линковки/headers.

## 3) DerivedData: ускорение и риски
Кэш DerivedData может:
- сильно ускорить incremental builds,
- но и создать “фантомные” проблемы (особенно если key слишком широкий).

Если кэшируете:
- ключ должен включать:
  - Xcode version,
  - scheme/target,
  - branch/commit (или хотя бы хэш исходников),
  - конфигурацию (Debug/Release).

Практический компромисс:
- кэшировать DerivedData на PR в пределах одной ветки,
- периодически сбрасывать (TTL),
- не тащить DerivedData между разными Xcode.

## 4) Incremental builds и модульность
### A) Настройка проекта
- ограничить “что пересобирается”:
  - меньше зависимостей между модулями,
  - меньше “unity” включений,
  - аккуратный доступ к generated code.

### B) Важный момент для CI
Incremental build реально помогает только если:
- агент не полностью чистый каждый раз,
- или есть кэши (DerivedData).

Если CI всегда “fresh VM/container” без кэшей:
- incremental почти бессмысленен.

## 5) Параллельность: что можно распараллелить
### A) Тесты
- shard unit tests по наборам,
- UI tests по девайсам/симуляторам,
- запускать несколько симуляторов параллельно (осторожно по ресурсам).

Главное:
- тесты должны быть изолированы (нет shared state, нет зависимости от времени/сети).

### B) Matrix builds
- параллельно собирать разные targets/конфиги,
- параллельно прогонять линт и тесты (если линт не зависит от сборки).

## 6) Убирать лишнее из PR pipeline
На PR чаще всего не нужно:
- archive/export/signing,
- TestFlight upload,
- тяжёлые UI tests.

PR pipeline должен:
- давать быстрый сигнал “сломал/не сломал”.
Остальное:
- nightly или release.

## 7) Измерение и контроль регрессий
Senior-подход:
- сначала измерить, где время,
- потом оптимизировать.
Иначе легко “ускорить” не то.

Полезно:
- логировать длительность этапов,
- алерты на деградации,
- держать baseline.

## 8) Как отвечать на собесе
“Я ускоряю CI через кэширование зависимостей (SPM/CocoaPods) и, аккуратно, DerivedData, фиксирую версии Xcode и lock-файлы. Разделяю PR и release pipeline, убираю archive из PR. Тесты шардю и запускаю параллельно, но слежу за изоляцией, иначе флейки. И обязательно измеряю этапы, чтобы видеть эффект.”

**Самопроверка**
- Оспорено: “добавим кэш DerivedData и всё станет быстро” — кэш помогает, но может породить нестабильность без корректного key/TTL.
- Неочевидно: лучшее ускорение часто организационное — разделение pipeline и отказ от archive/signing на PR.
- Источники, которые стоит освежить: caching guides для вашей CI платформы, практики SPM caching, Xcode build performance tips, тестовый шардинг (xcodebuild test-without-building и т.п.).



### Q217 (🟠): Как сделать pipeline надёжным: детерминированные зависимости, pinned versions, reproducible builds, чистые окружения?

**Кратко**
- Надёжный CI = одинаковый результат при одинаковом коде.
- Ключевые практики:
  - фиксировать версии инструментов (Xcode, Ruby, CocoaPods),
  - фиксировать зависимости (Podfile.lock, Package.resolved),
  - изолировать окружение (clean agents/containers + управляемые кэши),
  - не зависеть от внешнего мира (stubs для сети в тестах),
  - иметь явные гейты и артефакты (xcresult, dSYM).

**Развёрнуто**
## 1) Что значит “reproducible build”
Идеал:
- один и тот же commit собирается одинаково:
  - локально у разработчика,
  - на CI,
  - на разных агентах.

Практически это означает:
- отсутствие скрытых зависимостей от машины,
- стабильные версии инструментов и библиотек.

## 2) Детерминированные зависимости
### A) Пиннить версии зависимостей
- CocoaPods: `Podfile.lock` должен коммититься.
- SPM: `Package.resolved` должен коммититься и обновляться осознанно.

Иначе:
- один и тот же commit может собрать разные версии библиотек → разные баги.

### B) Пиннить toolchain
- Xcode version фиксированно.
- Swift version следует из Xcode, поэтому фиксация Xcode критична.

Иногда полезно:
- явно фиксировать командные инструменты (mint, swiftformat, swiftlint versions).

## 3) Чистые окружения vs кэш
### A) Чистое окружение
Плюсы:
- минимум “призрачных” ошибок,
- детерминизм.

Минусы:
- медленно.

### B) Кэш
Плюсы:
- быстрее.

Минусы:
- риск недетерминизма и “битых” кэшей.

Senior-практика:
- кэшировать только то, что приносит большую пользу и легко инвалидировать:
  - зависимости,
  - derived data (осторожно),
  - build artifacts для тестов (test-without-building).

И иметь:
- хорошие cache keys,
- TTL,
- fallback на чистую сборку при проблемах.

## 4) Убрать зависимости от внешнего мира
### A) Сеть в тестах
- UI tests и unit tests не должны зависеть от реального бэкенда:
  - stubs/mocks,
  - local fixtures.

Иначе:
- flakey tests из-за network/latency/данных.

### B) Время, локаль, часовой пояс
- тесты, которые зависят от “текущей даты”, будут флейковыми.
Решение:
- инжектировать clock,
- фиксировать locale/timezone в тестах (или избегать зависимостей).

## 5) Явные артефакты и трассировка
Надёжность повышает:
- хранение `xcresult`,
- логирование версий toolchain,
- прикладывание dSYM,
- фиксирование параметров сборки.

Если сборка упала:
- можно понять почему, а не “перезапусти ещё раз”.

## 6) Гейты и правила веток
- PR не может быть смёржен без успешного CI.
- jobs, которые используют secrets/signing, запускаются только на доверенных ветках.
- release pipeline с ручными approvals (если нужно).

## 7) Как отвечать на собесе
“Я делаю CI воспроизводимым: фиксирую Xcode и версии инструментов, пинню зависимости через lock/resolved, изолирую окружение (clean agent) и аккуратно использую кэш с правильными ключами. Тесты делаю независимыми от сети/времени. Храню артефакты и логи версий, чтобы любые падения можно было диагностировать.”

**Самопроверка**
- Оспорено: “главное — чтобы в CI собралось” — без воспроизводимости вы не сможете стабильно выпускать релизы и чинить редкие CI-баги.
- Неочевидно: кэш — одновременно ускорение и источник нестабильности; зрелость — в правильной инвалидиации и fallback на чистую сборку.
- Источники, которые стоит освежить: best practices reproducible builds, guidance по SPM/CocoaPods lockfiles, документация вашей CI платформы по immutable environments и caching.


### Q218 (🟠): Как организовать автотесты в CI (unit/UI), симуляторы, флейки, параллелизация и стабильность?

**Кратко**
- Unit tests должны быть основой CI: быстрые и стабильные.
- UI tests — дороже и флейковее, поэтому:
  - запускать выборочно (nightly/release/критичные флоу),
  - стабилизировать среду (stubs, reset state),
  - параллелить и шардить.
- Для стабильности:
  - детерминированные данные (без реальной сети),
  - контроль времени/локали,
  - чистое состояние симулятора,
  - артефакты (`xcresult`) для диагностики.

**Развёрнуто**
## 1) Разделить цели unit vs UI tests
### Unit tests
Цель:
- проверка логики, быстрый feedback.
В CI:
- запускать почти всегда на PR.

### UI tests
Цель:
- проверка критичных пользовательских сценариев “сквозняком”.
В CI:
- запускать:
  - на nightly,
  - на релизных ветках,
  - либо subset на PR (smoke suite).

Сеньор-логика:
- не пытаться сделать 100% покрытия UI тестами — вы “убьёте” скорость и получите флейки.

## 2) Управление симуляторами
Что важно:
- фиксированная модель симулятора и iOS версия (насколько возможно).
- перед тестами:
  - `erase all content and settings`,
  - чистить кэш/данные приложения,
  - выставлять разрешения (через launch args/stubs).

Типовая ошибка:
- тесты зависят от “прошлого состояния” симулятора.

## 3) Убрать сеть и нестабильные зависимости
Главный враг стабильности — реальный бэкенд.
Решения:
- network stubbing:
  - URLProtocol stubs,
  - локальный mock server,
  - dependency injection для клиента.
- фикстуры данных:
  - контролируемые ответы,
  - версии.

Это делает UI tests:
- быстрыми,
- детерминированными.

## 4) Параллелизация и шардинг
### A) Шардинг по тест-таргетам/наборам
- split unit tests по группам,
- split UI tests по наборам.

### B) Параллельные симуляторы
Можно запускать несколько симуляторов параллельно, но:
- агент должен быть достаточно мощным,
- иначе всё станет хуже из-за свопа/конкуренции.

### C) test-without-building
Если сборка одинакова, можно:
- один раз build,
- затем запускать `test-without-building` для разных наборов тестов.

Это часто самый эффективный “ускоритель”.

## 5) Флейки: причины и лечение
### Причины
- ожидания по таймингам (анимации, задержки),
- реальные сети/таймауты,
- гонки на main thread,
- неочищенное состояние,
- зависимости от даты/локали,
- слабые селекторы (accessibility identifiers отсутствуют).

### Лечение
- explicit waits вместо sleep,
- отключение/минимизация анимаций (где возможно),
- стабильные accessibility identifiers,
- изоляция данных,
- фиксированная среда (timezone/locale),
- инструменты ретраев:
  - retry только для UI tests и только ограниченно,
  - но при этом обязательно собирать статистику флейков и чинить первопричину.

Важная позиция:
- ретраи — временный костыль, не решение.

## 6) Артефакты и диагностика
Собирать:
- `xcresult`,
- screenshots на фейле,
- логи приложения (если возможно),
- системные логи симулятора.

Это позволяет:
- понять, что реально произошло на CI, а не гадать.

## 7) Как отвечать на собесе
“Unit tests — обязательны на PR. UI tests я делаю короткими, критичными и детерминированными: без реальной сети (stubs), с чистым состоянием симулятора и хорошими identifiers. Для скорости — шардю и параллелю, а также использую test-without-building. Флейки лечу устранением причины, а ретраи использую только как временную меру.”

**Самопроверка**
- Оспорено: “UI тесты достаточно ретраить” — ретраи скрывают проблему, а не решают её; нужны stubs, детерминизм и правильные ожидания.
- Неочевидно: стабильность тестов чаще ломается не “в коде теста”, а в окружении: сеть, симулятор, локаль, состояние.
- Источники, которые стоит освежить: Xcode testing инструменты (xcresult, parallel testing), практики UI test stabilization, test-without-building, network stubbing в UI tests.



### Q219 (🔴): Как спроектировать release train: feature flags, staged rollout, rollback strategy, hotfix flow — чтобы релизы были предсказуемыми?

**Кратко**
- Release train = регулярный, повторяемый процесс выпуска (по расписанию), а не “выпуск по панике”.
- Предсказуемость достигается:
  - **feature flags** (разделяем “деплой кода” и “включение фичи”),
  - **release candidate** + freeze,
  - **staged/phased rollout**,
  - готовым **rollback/hotfix** потоком,
  - мониторингом (crash-free, ключевые метрики) и чёткими stop-правилами.

**Развёрнуто**
## 1) Зачем вообще release train
В зрелом продукте релиз — это риск.
Release train снижает риск за счёт:
- повторяемости шагов,
- дисциплины ветвления,
- автоматизации,
- гейтов качества и мониторинга.

Цель:
- любой участник команды понимает, что будет происходить и когда.

## 2) Базовая модель релиза (пример)
- main всегда в состоянии “готово к релизу” (или близко к этому),
- релизы по расписанию (например, раз в неделю),
- фичи, которые не готовы, сидят за флагом.

## 3) Feature flags: “отделяем код от релиза фичи”
### Почему это важно
- вы можете слить код заранее,
- но включить фичу позже, когда она готова.

Правила (иначе будет хаос):
- флаг — временный (есть дата удаления),
- флаг не должен ломать архитектуру (избегать if-спагетти — выносить в policy/конфиг),
- фичи за флагом должны быть безопасны в выключенном состоянии.

## 4) Release candidate и freeze
Паттерн:
- делаем ветку release/тег RC,
- включаем “заморозку”: только багфиксы, никаких новых фич.

Плюсы:
- меньше неизвестных,
- QA тестит конкретный артефакт.

## 5) Staged / phased rollout
Цель:
- уменьшить blast radius: сначала небольшая доля пользователей.

Подходы:
- phased release (если используете возможности стора),
- внутренние “стейджи” через feature flags (например, включать на 1% по remote config).

Критерии “можно расширять rollout”:
- crash rate,
- ключевые метрики (retention, conversion, payments),
- performance (startup time, memory),
- support tickets.

## 6) Rollback strategy (в iOS это не “kubectl rollback”)
Ограничение:
- App Store релизы не откатываются мгновенно как сервер.

Поэтому rollback в iOS — это:
- выключить фичу флагом (самый быстрый),
- server-side mitigation (если проблема в API/контракте),
- остановить rollout (phased release pause),
- экстренный hotfix релиз.

Вывод:
- feature flags — главный инструмент “быстрого rollback”.

## 7) Hotfix flow
### Когда
- crash spike,
- критичный баг в платежах/логине,
- блокер.

Процесс:
- hotfix ветка от последнего тега релиза,
- минимальный набор изменений,
- быстрый прогон критичных тестов,
- новый build → expedited review (если оправдано),
- выпуск с мониторингом.

Важно:
- не пытаться “впихнуть ещё одну фичу” в hotfix.

## 8) Stop-правила и мониторинг
Предсказуемость невозможна без правил:
- при каких метриках релиз стопится,
- кто принимает решение,
- как эскалировать.

Набор инструментов:
- crash reporting,
- analytics,
- логирование (correlation IDs),
- SLO/пороги.

## 9) Как отвечать на собесе
“Я делаю релизы предсказуемыми через release train: регулярные релизы, RC + freeze, feature flags для отделения деплоя от включения фич, staged rollout и мониторинг. Rollback в iOS — это в первую очередь выключение флагов и остановка rollout, а если нужно — hotfix flow с минимальными изменениями и быстрым прогоном тестов.”

**Самопроверка**
- Оспорено: “в iOS rollback = откатить версию” — это медленно и ограничено стором; реальный быстрый rollback — флаги и server-side mitigation.
- Неочевидно: без stop-правил release train превращается в формальность; нужны метрики и ответственность.
- Источники, которые стоит освежить: практики feature flags lifecycle, phased rollout в App Store Connect, подходы к hotfix/expedited review, наблюдаемость и SLO для мобильных релизов.



### Q220 (🔴): Как сделать подписанный build полностью в CI без “ручной магии”: managed signing, match-like подход, rotation, multiple targets/extensions?

**Кратко**
- Цель: чтобы любой агент CI мог собрать **архив и ipa** без ручных шагов на локальной машине.
- Основные подходы:
  1) **Managed signing** (Xcode/ASC управляют профилями и сертификатами),
  2) **Match-like** подход (единый источник правды для certs/profiles, автоматическая установка в CI).
- Обязательные элементы зрелого решения:
  - централизованное хранение/доступ к signing материалам,
  - разделение окружений (dev/stage/prod),
  - rotation/отзыв сертификатов,
  - поддержка всех targets (app + extensions) и их entitlements,
  - безопасность (secrets, ACL, audit).

**Развёрнуто**
## 1) Проблема, которую решаем
“Ручная магия” обычно означает:
- на чьей-то машине есть нужный сертификат и профиль,
- CI падает из-за отсутствия private key или mismatch entitlements,
- новый разработчик не может собрать релиз.

Это ломает:
- воспроизводимость,
- безопасность,
- скорость релизов.

## 2) Подход №1: Managed signing
Идея:
- Xcode/Apple автоматически создают и обновляют profiles,
- вы меньше управляете вручную.

Плюсы:
- меньше ручных файлов и “знаний шамана”,
- проще вход новым людям.

Минусы/риски:
- сложнее контролировать, что именно произошло (кто создал профиль/сертификат),
- при сложных сетапах (много таргетов, extensions, enterprise policy) становится трудно дебажить,
- всё равно нужен безопасный доступ CI к аккаунту/ключам.

Когда подходит:
- небольшие/средние проекты,
- не супер-жёсткие требования к audit.

## 3) Подход №2: Match-like (единый источник правды)
Идея:
- сертификаты/профили централизованы,
- CI получает их предсказуемо и устанавливает автоматически.

Ключевые элементы:
- один “репозиторий/хранилище” signing артефактов (обычно шифрованное),
- один механизм установки на агент (скрипт),
- один набор правил, как создавать/обновлять.

Плюсы:
- воспроизводимость,
- контроль и аудит,
- лучше для команд и сложных проектов.

Минусы:
- нужно настроить и поддерживать,
- нужен процесс rotation.

## 4) Безопасность: что важно, чтобы это было “senior”
### A) Private keys — только в защищённом виде
- хранить в secret storage CI или шифрованном хранилище,
- доступ по минимальным правам,
- аудит доступа.

### B) Минимизация blast radius
- отдельные сертификаты/ключи под окружения или под приложения (если политика позволяет),
- ограничить, кто может выпускать distribution.

### C) Rotation
Процесс должен быть:
- плановым (например, при истечении или по политике),
- с понятными шагами: выпустить новый cert, обновить profiles, обновить CI secrets,
- с планом “что делать если утечка”.

## 5) Multiple targets/extensions: где чаще всего боль
В iOS почти всегда есть:
- app target,
- push notification service extension,
- share extension,
- widgets, intents и т.п.

Каждый таргет имеет:
- свой bundle id,
- свои entitlements,
- может требовать отдельный provisioning profile.

Системная причина фейлов:
- mismatch entitlements между таргетом и профилем.

Практика:
- документировать список таргетов + bundle IDs,
- централизованно управлять capabilities в портале,
- в CI валидировать, что для каждого таргета есть профиль нужного типа.

## 6) Как выглядит “полностью в CI”
Минимальный рецепт:
1) CI получает signing secrets (p12 + пароль, profiles, ASC API key).
2) Импортирует p12 в временный keychain (эпhemeral).
3) Устанавливает provisioning profiles.
4) Архивирует и экспортирует ipa.
5) Удаляет keychain/очищает после себя.
6) Загружает билд и публикует dSYM.

Ключ:
- агент должен быть “stateless”: всё создаётся на лету и чистится.

## 7) Как отвечать на собесе
“Я делаю signing воспроизводимым: либо managed signing, либо централизованный match-like подход. В CI импортирую cert в ephemeral keychain, ставлю профили, архивирую и экспортирую ipa. Для нескольких targets держу явную матрицу bundle IDs/entitlements и проверяю наличие профилей. Отдельно — безопасность: secrets в CI vault, least privilege, audit и rotation сертификатов.”

**Самопроверка**
- Оспорено: “достаточно один раз настроить подпись на ноутбуке” — это ломает воспроизводимость и масштабирование команды.
- Неочевидно: самая частая причина падений — extensions и entitlement mismatch, а не “сломанный CI”.
- Источники, которые стоит освежить: практики managed signing в Xcode, подходы match-like управления signing, Apple docs по capabilities/entitlements и распределению по targets, принципы эпhemeral keychain в CI.



### Q221 (🔴): Как внедрить quality gates: coverage thresholds, performance baselines, static analysis, security scanning — без превращения CI в “ад”?

**Кратко**
- Quality gates полезны только если:
  - они **точно измеримы**,
  - дают **мало false positives**,
  - и не тормозят команду до нуля.
- Практика “без ада”:
  1) разделить быстрые PR-гейты и тяжёлые nightly/release,
  2) вводить гейты постепенно (warn → soft fail → hard fail),
  3) держать baseline и “no regression” вместо абсолютных цифр,
  4) инвестировать в снижение флейков и ложных срабатываний,
  5) показывать результат разработчику (понятный отчёт, а не “упало где-то”).

**Развёрнуто**
## 1) Сначала о предпосылке: больше гейтов ≠ лучше
Неправильные гейты:
- превращают CI в “кладбище красных билдов”,
- побуждают “обходить”, а не “улучшать” качество,
- замедляют цикл разработки.

Поэтому задача senior — “минимум гейтов, максимум эффекта”.

## 2) Разделить уровни контроля (tiered CI)
### Tier 1: PR gates (быстро и строго)
Обычно:
- lint/format,
- build,
- unit tests,
- простые статические проверки (например, запрещённые API),
- secret scanning.

Цель:
- быстрый feedback, 5–15 минут (условно).

### Tier 2: nightly (дольше, но шире)
- расширенные тесты,
- UI tests,
- coverage отчёты,
- статанализ глубже.

### Tier 3: release gates (самые строгие)
- полный набор тестов,
- performance baselines,
- security scanning,
- артефакты, подпись, upload.

## 3) Coverage thresholds: как не убить команду
Проблема абсолютного порога:
- старый проект с 20% покрытия никогда не станет 80% мгновенно.

Рабочая стратегия:
- “no regression”:
  - покрытие не должно падать,
  - или порог только для нового кода/изменённых модулей.
- постепенное повышение:
  - 20 → 25 → 30 с планом.

Ловушка:
- гонка за цифрой может привести к бесполезным тестам.

## 4) Performance baselines
Проблема:
- перф-тесты флейковы из-за окружения.

Как сделать полезно:
- измерять только ключевые метрики:
  - cold start / time-to-interactive,
  - scroll FPS (или surrogate),
  - память на критичных экранах,
  - время выполнения ключевых use cases.
- baseline как “коридор”:
  - допускается небольшая вариативность,
  - важны регрессии, а не идеальная стабильность.

Где запускать:
- чаще nightly/release, а не на каждый PR.

## 5) Static analysis
Слои:
- компилятор warnings,
- SwiftLint/SwiftFormat,
- clang static analyzer,
- специальные проверки архитектуры (например, запрет импорта UI в domain).

Как избежать ада:
- ограничить правила и поддерживать их (rule ownership),
- не включать 200 правил “потому что можно”,
- auto-fix где возможно (format).

## 6) Security scanning
Что реально полезно для iOS:
- secret scanning (токены/ключи в репо),
- dependency vulnerability scanning (где доступно),
- бинарные проверки (например, запрещённые symbols, jailbreak-detection политики — если требуется),
- лицензии (license compliance), если продукт в корп-среде.

Важно:
- security tool не должен спамить ложными тревогами.
Нужен triage и suppress/allowlist процесс.

## 7) Плавное внедрение (change management)
Стратегия:
1) собрать метрики “как сейчас”,
2) включить отчётность без падения билда (informational),
3) потом “soft fail” (падает, но можно override с причиной),
4) потом “hard fail”.

Это предотвращает сопротивление команды.

## 8) Как отвечать на собесе
“Я строю quality gates tiered: быстрые PR-гейты и тяжёлые nightly/release. Ввожу правила постепенно: сначала отчёты, потом soft/hard fail. Для coverage использую no-regression или пороги для изменённого кода. Для performance — baselines с коридором и запуск не на каждый PR. Статанализ и security scanning держу минимальным и поддерживаемым, иначе будет много false positives и CI станет шумом.”

**Самопроверка**
- Оспорено: “давайте поставим 80% coverage и всё” — это ломает процесс, если проект не готов; лучше no-regression и поэтапность.
- Неочевидно: главный риск quality gates — ложные срабатывания и шум; без triage/ownership они быстро деградируют.
- Источники, которые стоит освежить: практики gradual rollout quality gates, performance testing на CI, инструменты secret/dependency scanning вашей платформы.



### Q222 (🔴): Как организовать многомодульные/мультибрендовые сборки (white-label): разные bundle IDs, конфиги, assets, локализации, env — без копипасты?

**Кратко**
- White-label лучше строить вокруг:
  - **нескольких targets** (или packages/modules) + общей кодовой базы,
  - **конфигов** (`.xcconfig`, build settings, Info.plist per target),
  - **ресурсной стратегии** (asset catalogs per brand, strings),
  - **окружений** (dev/stage/prod через схемы/конфиги),
  - чётких границ: “Core” (общий) и “Brand layer” (переопределения).
- Главная цель: чтобы добавление нового бренда = добавление конфигов и ресурсов, а не форк кода.

**Развёрнуто**
## 1) Сначала о рисках “быстрого” white-label
Плохие варианты:
- форк репозитория под каждого клиента,
- `if brand == ...` по всему коду,
- копии asset’ов и storyboards/экраны “слегка разные”.

Цена:
- релизы ломаются,
- багфиксы приходится переносить N раз,
- продукт деградирует.

Поэтому надо проектировать “вариативность” как слой, а не как размазанные if’ы.

## 2) Модель: что обычно отличается между брендами
- bundle id, display name, app icon,
- deep links и URL schemes,
- endpoints (или env),
- дизайн (цвета/шрифты/картинки),
- часть функциональности (фичи, paywall, подписки),
- локализации (часто общие + брендовые).

Значит — нужны:
- конфиги,
- ресурсы,
- feature flags/remote config,
- точки расширения.

## 3) Организация targets/schemes/configs
### A) Targets
Часто делают:
- один общий framework/package (Core),
- несколько app targets (BrandAApp, BrandBApp),
- shared extensions (если одинаковые) или брендовые (если нужно).

Плюсы:
- bundle IDs и Info.plist разные по таргетам,
- ресурсы можно изолировать по таргету,
- проще подписывать и выпускать.

### B) Schemes
Schemes управляют:
- какой таргет запускаем,
- какой конфиг/окружение используем.

Практика:
- для каждого бренда:
  - BrandA-Debug, BrandA-Release, (опционально Staging),
- чтобы CI мог собирать матрицей.

### C) .xcconfig и build settings
Смысл:
- вынести “переменные бренда” в конфиги:
  - bundle id prefix,
  - endpoints,
  - ключи (не секреты, а identifiers),
  - флаги компиляции.

Плюсы:
- минимизируем ручные клики в Xcode,
- можно менять из CI.

## 4) Ресурсы и дизайн: как избежать дублирования
### A) Assets
- отдельные asset catalogs:
  - `Assets-BrandA.xcassets`,
  - `Assets-BrandB.xcassets`,
- подключать их на уровне target membership.

### B) Локализация
Подходы:
- общий `Localizable.strings`,
- брендовые override-файлы (приоритет таргета),
- либо отдельные tables per brand.

Ключевой принцип:
- строки по ключам одинаковые, но значение может отличаться (override).

### C) Design system
Правильно:
- абстракции (colors/fonts/images) через “provider”:
  - `Theme`/`BrandConfig`.
Не правильно:
- `if brand ==` в 200 местах.

## 5) Конфигурация окружений (env)
Различия dev/stage/prod:
- лучше делать как “окружение”, а не “бренд”.
Итого:
- Brand × Env матрица (BrandA-Dev, BrandA-Prod, BrandB-Prod…).

Важно не взорваться в количестве конфигов:
- выделить “общие” .xcconfig,
- и маленькие overlay-файлы для бренда/окружения.

## 6) Логика различий: feature flags и dependency injection
Если функциональность отличается:
- не делаем `if brand` в доменной логике.
Вместо этого:
- вводим протоколы/интерфейсы на границах:
  - `PaywallProviding`, `AnalyticsProviding`, `FeatureFlagsProviding`,
- и даём разные реализации в composition root для каждого бренда.

Это даёт:
- тестируемость,
- минимальный разброс по коду,
- прозрачные точки расширения.

## 7) CI: сборка и подпись white-label
CI должен:
- уметь собирать матрицей (brand × env),
- иметь signing для каждого bundle id/extension,
- уметь выгружать в разные TestFlight apps (если они отдельные),
- иметь понятные артефакты.

## 8) Как отвечать на собесе
“Я делаю white-label через отдельные app targets на общую кодовую базу (Core). Различия выношу в .xcconfig/Info.plist per target и отдельные asset catalogs/локализации. В коде различия идут через Theme/BrandConfig и DI в composition root, а не через if по всему проекту. Для окружений использую overlay конфиги и feature flags, а CI собирает матрицей brand×env.”

**Самопроверка**
- Оспорено: “проще форкнуть репо под каждого клиента” — это быстро только один раз, потом технический долг становится экспоненциальным.
- Неочевидно: самая опасная часть white-label — размазанные if’ы; правильнее — конфиги + точки расширения через DI.
- Источники, которые стоит освежить: Xcode multi-target best practices, xcconfig overlays, resource target membership, подходы к modularization и composition root для white-label.



### Q223 (🔴): Как расследовать и устранять флейки и недетерминизм в CI (UI tests, network stubs, timeouts, race conditions, simulator state) системно?

**Кратко**
- Флейки лечатся не “ретраями”, а системной локализацией причины:
  1) классифицировать тип флейка,
  2) сделать воспроизводимость,
  3) собрать максимум артефактов,
  4) устранить источник недетерминизма (сеть/время/состояние/гонки),
  5) поставить наблюдаемость (метрики флейков) и регрессионные гейты.
- Ретраи допустимы только временно и только для UI tests.

**Развёрнуто**
## 1) Что такое флейк в контексте CI
Флейк = один и тот же тест/джоб:
- то проходит, то падает без изменения кода.

Это признак:
- недетерминизма в тестах или окружении,
- скрытых гонок,
- зависимости от внешнего мира.

## 2) Системный подход: этапы расследования
### Этап A: Сбор данных (не гадать)
Нужно иметь:
- `xcresult`,
- скриншоты/видео (если UI tests),
- логи приложения,
- логи симулятора,
- версию Xcode/OS/девайса,
- seed/конфиг тестового окружения.

Без артефактов вы будете “лечить по наитию”.

### Этап B: Классификация (где искать)
Частые классы:
1) **UI timing**: элементы не успели появиться, анимации, неправильные ожидания.
2) **Network**: реальный бэкенд, таймауты, нестабильные данные.
3) **State leakage**: симулятор/кейчейн/юзер-дефолты не очищены.
4) **Race conditions**: фоновые задачи, конкурирующие запросы, async.
5) **Environment**: локаль/часовой пояс/разрешения/доступность сервисов.
6) **Resource contention**: CI агент перегружен, симуляторы тормозят, OOM.

### Этап C: Минимизация и воспроизведение
Цель:
- получить минимальный тестовый сценарий, который падает чаще.

Инструменты:
- многократный прогон одного теста (stress-run),
- запуск в изолированном окружении,
- фиксированные конфиги (один симулятор, одна версия iOS).

### Этап D: Фикс причины + защита от регрессии
После фикса:
- добавить “guard”:
  - лучшее ожидание,
  - stubs,
  - reset state,
  - синхронизация,
  - выключение недетерминизма.
- добавить метрику/алерт: флейк не должен вернуться.

## 3) UI tests: типовые ошибки и решения
### A) Sleep вместо ожиданий
Проблема:
- sleep либо слишком короткий (падает), либо слишком длинный (медленно).

Решение:
- использовать явные ожидания:
  - `XCTNSPredicateExpectation`,
  - `waitForExistence(timeout:)`,
  - ожидание “стабильного состояния” (например, исчез лоадер).

### B) Слабые селекторы
- искать по тексту или hierarchy — нестабильно.
Решение:
- accessibility identifiers.

### C) Анимации и переходы
- анимации создают нестабильность.
Решение:
- минимизировать/отключать (где возможно), ждать завершения переходов.

## 4) Network stubs: обязательный инструмент стабильности
Почему:
- сеть и бэкенд — самый большой источник флейков.

Решение:
- URLProtocol stubs,
- локальные fixtures,
- mock server.

Принцип:
- UI tests должны проверять UI/флоу, а не доступность продового API.

## 5) Timeouts и лимиты
Если тест часто падает по timeout:
- это либо реальная проблема производительности,
- либо неправильное ожидание/сеть.

Подход:
- сначала убрать сеть и стабилизировать ожидания,
- потом уже подкручивать timeout.

Важно:
- “увеличить timeout” почти всегда маскирует проблему.

## 6) Race conditions и async
Частая причина:
- тест проверяет состояние до завершения async операций.

Решения:
- синхронизация через observable signals (например, ожидать событие “данные загружены”),
- dependency injection + controllable schedulers,
- убрать параллельность в тестовом режиме.

## 7) Simulator state: чистота окружения
Нужно:
- сбрасывать симулятор/приложение,
- контролировать permissions,
- избегать влияния прошлых запусков.

Иначе:
- тест “иногда” видит другой экран/попап/логин.

## 8) Метрики флейков и политика команды
Senior уровень — это процесс:
- измерять “flake rate” по тестам,
- заводить bug tickets на top offenders,
- иметь SLO: например, UI suite не может иметь >X% флейков,
- запрет мерджей, если флейк-рейт растёт.

## 9) Как отвечать на собесе
“Я лечу флейки системно: собираю артефакты, классифицирую, делаю воспроизведение стресс-ранами, затем устраняю недетерминизм. Для UI tests: stable identifiers, явные ожидания вместо sleep, stubs вместо реальной сети, чистое состояние симулятора. Ретраи допускаю временно, но параллельно чиню причину. И ввожу метрики флейков как часть качества CI.”

**Самопроверка**
- Оспорено: “добавим ретрай и забудем” — это скрывает боль и ухудшает доверие к CI.
- Неочевидно: флейки чаще не “в тесте”, а в окружении и недетерминизме (сеть/время/состояние/гонки).
- Источники, которые стоит освежить: XCTest best practices (expectations/waits), network stubbing подходы, инструменты анализа `xcresult`, практики test isolation и flake monitoring.

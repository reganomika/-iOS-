## Управление памятью

### Q24 (🟢): Разница между `weak` и `unowned`

**Кратко**
- `weak` — **не удерживает** объект и **обнуляется в `nil`** при деинициализации объекта → всегда `Optional`.
- `unowned` — **не удерживает** объект, но **не обнуляется**; предполагает, что объект жив дольше ссылки → не `Optional`.
- Если обратиться к `unowned` (checked) после деинициализации объекта → **крэш** (runtime trap).
- `unowned(unsafe)` не делает никаких проверок → dangling pointer и undefined behavior.
- `weak` безопаснее, `unowned` (checked) быстрее/проще по API, но требует строгого инварианта жизненного цикла.

**Развёрнуто**
Оба модификатора решают одну проблему: не создавать сильную ссылку и тем самым избегать retain cycle. Разница — в том, **как ссылка ведёт себя после смерти объекта** и какие гарантии требует от кода.

## 1) `weak`
- Хранится как "слабая" ссылка, которая регистрируется в runtime.
- Когда объект деинициализируется, runtime **обнуляет** все `weak` ссылки на него.
- Поэтому `weak` всегда `Optional`: значение может стать `nil` в любой момент после того, как объект перестал удерживаться сильными ссылками.

```swift
final class Owner {
    var child: Child?
}

final class Child {
    weak var owner: Owner?
}
```

Плюсы:
- безопасно: после смерти объекта ссылка станет `nil`, можно сделать `if let`/`guard let`.

Минусы:
- есть накладные расходы на механизм weak-таблиц/обнуление,
- приходится писать `Optional`-обработку.

## 2) `unowned` (два вида)
Ссылка "не владеет" объектом и **не зануляется**. Бывает двух видов:

### `unowned` (checked)
- При обращении к мёртвому объекту runtime выполняет **проверку** и вызывает trap (крэш).
- Это "fail fast" поведение — ошибка проявляется детерминированно.
- Требует минимальных накладных расходов на проверку при доступе.

### `unowned(unsafe)`
- Никаких проверок нет.
- После смерти объекта ссылка становится **dangling pointer** → undefined behavior: мусор, краши, коррупция памяти.
- Используется только в критичных низкоуровневых сценариях, где lifetime доказан формально.

```swift
final class Parent {
    let child: Child
    init() { child = Child(parent: self) }
}

final class Child {
    unowned let parent: Parent  // checked unowned
    init(parent: Parent) { self.parent = parent }
}
```

Плюсы `unowned` (checked):
- не `Optional`, меньше шума,
- дешевле `weak` (нет zeroing и side table механизма, только проверка при доступе).

Минусы:
- если инвариант нарушен — **крэш**.

## 3) Как выбирать в проде (короткая эвристика)
- **По умолчанию** для обратных ссылок и closures: `weak`.
- `unowned` (checked) — когда жизненный цикл гарантирован архитектурой:
  - child строго живёт внутри parent,
  - объект A создаёт B и B никогда не переживёт A,
  - это закреплено контрактом (например, `let`-связью и инициализацией в `init`).
- `unowned(unsafe)` — только в низкоуровневом коде с формально доказанным lifetime.

## 4) Типовая ловушка на собесе
- "`unowned` всегда безопасен, если не Optional" — нет: он безопасен только при правильном инварианте времени жизни; checked `unowned` хотя бы крашится предсказуемо, `unowned(unsafe)` — нет.
- "`weak` всегда лучше" — не всегда: `weak` может быть избыточен там, где гарантии железные, и усложняет код.

**Самопроверка**
- Оспорено: "разница только в optional" — ключевое различие в поведении после деинициализации (nil vs trap vs UB) и в требуемых гарантиях жизненного цикла.
- Оспорено: "`unowned` бесплатен в отличие от `weak`" — checked `unowned` требует runtime-проверки при доступе; только `unowned(unsafe)` полностью без overhead.
- Источники: Swift Language Guide (ARC), Apple docs про memory management, практические кейсы retain cycles.

### Q25 (🟢): Как работает ARC? В контексте `weak` / `unowned`

**Кратко**
- ARC автоматически вставляет операции **retain/release** для reference-типов, чтобы освободить объект, когда сильных ссылок становится 0.
- `strong` увеличивает счётчик удержаний; `release` уменьшает; при 0 вызывается `deinit`.
- `weak` не увеличивает счётчик и **обнуляется в `nil`** при деинициализации объекта (runtime поддерживает список weak-ссылок).
- `unowned` не увеличивает счётчик и **не обнуляется**; доступ после `deinit` приводит к **крэшу**.
- Цикл сильных ссылок удерживает счётчик > 0 навсегда → утечка до разрыва цикла.

**Развёрнуто**
ARC — это механизм управления временем жизни объектов классов. Компилятор анализирует код и вставляет вызовы “удержать/отпустить” так, чтобы объект жил ровно столько, сколько на него есть сильные ссылки.

## 1) Базовая модель
- Каждый объект имеет “количество сильных удержаний” (концептуально, реализация сложнее, но на собесе достаточно).
- Когда ты присваиваешь объект в сильную ссылку или передаёшь/захватываешь так, что он должен жить — компилятор вставляет `retain`.
- Когда сильная ссылка выходит из scope/перезаписывается/обнуляется — вставляется `release`.
- Когда сильных ссылок становится 0 → объект деинициализируется (`deinit`) и память освобождается.

```swift
final class Foo {
    deinit { print("deinit") }
}

do {
    let a = Foo()   // +1 strong
    let b = a       // +1 strong
}                   // -1, -1 → 0 → deinit
```

## 2) Как `weak` влияет на время жизни
`weak`:
- не удерживает объект (не участвует в strong count),
- регистрируется как слабая ссылка в runtime,
- когда объект умирает, runtime **зануляет** weak-ссылки.

```swift
final class Owner {}
final class Child {
    weak var owner: Owner?
}

var owner: Owner? = Owner()
let child = Child()
child.owner = owner

owner = nil          // Owner deinit → child.owner станет nil
print(child.owner)   // nil
```

Следствие: `weak` всегда `Optional`, потому что ссылка может обнулиться вне твоего контроля.

## 3) Как `unowned` влияет на время жизни
`unowned`:
- не удерживает объект,
- не зануляется,
- предполагает, что объект живёт дольше ссылки.

```swift
final class Parent {
    let child: Child
    init() { child = Child(parent: self) }
}

final class Child {
    unowned let parent: Parent
    init(parent: Parent) { self.parent = parent }
}
```

Если `Parent` освободится раньше, чем `Child` перестанет обращаться к `parent`, будет crash при доступе к `unowned`.

## 4) Retain cycle и почему `weak/unowned` его ломают
```swift
final class A { var b: B? }
final class B { var a: A? }  // если strong → цикл

let a = A()
let b = B()
a.b = b
b.a = a // strong-strong → цикл
```

Если сделать одну сторону `weak` или `unowned`, strong count сможет упасть до 0 и объекты освободятся.

## 5) Почему ARC “автоматический”, но не “магический”
ARC не решает логические циклы владения за тебя. Он механически освобождает объект только когда strong references = 0. Поэтому дизайн графа владения (owner/child) — ключевой навык.

**Самопроверка**
- Оспорено: “ARC сам избавляется от циклов” — нет, retain cycle нужно разрывать архитектурно (`weak/unowned`, делегаты, separate owner).
- Неочевидно: точные внутренние детали счётчиков/side tables сложнее, но для собеса важны семантика и последствия (`weak` nil, `unowned` crash).
- Источники: Swift Language Guide (ARC), Apple docs про memory management, практические материалы по retain cycles.

### Q26 (🟢): Что делает `autoreleasepool` и когда он реально нужен в iOS?

**Кратко**
- `autoreleasepool { ... }` создаёт область, где **autoreleased** объекты будут освобождены в конце блока.
- В Swift это чаще всего актуально при взаимодействии с **Objective‑C/Foundation** API, которые возвращают autoreleased объекты.
- В обычном UIKit run loop есть “верхнеуровневый” autorelease pool, который очищается каждый тик; поэтому часто он не нужен.
- Реально полезен, когда внутри короткого периода создаётся **очень много временных ObjC‑объектов** (большие циклы, обработка изображений/строк, парсинг), и ты хочешь освободить их раньше, не дожидаясь конца итерации run loop.

**Развёрнуто**
## 1) Что такое autorelease и зачем пул
В Objective‑C (и bridging‑слоях Foundation) есть концепция autoreleased объектов: объект помечается на “освободить позже”, а конкретный момент освобождения привязан к **autorelease pool**. Когда пул дренится (drain), он отправляет `release` всем объектам, которые в него попали.

Swift напрямую не использует `autorelease` как основной механизм (там ARC и строгие правила), но при вызове ObjC‑API и мостинге (`NSString`, `NSData`, `UIImage`, `NSError` и т.п.) autorelease встречается.

## 2) Что делает `autoreleasepool { ... }`
- Создаёт/пушит новый пул (вложенный относительно текущего).
- Всё autoreleased, созданное внутри блока, будет освобождено при выходе из блока.

```swift
for i in 0..<10_000 {
    autoreleasepool {
        let s = NSString(format: "item-%d", i) // пример ObjC объекта
        _ = s
    } // здесь пул дренится, временные autoreleased освобождаются
}
```

## 3) Почему “обычно не нужно”
- В iOS вокруг каждого прохода run loop система обычно держит autorelease pool.
- Если ты не создаёшь огромный объём autoreleased объектов в одном тикe, они и так освободятся достаточно быстро.

## 4) Когда реально нужно
1) **Большие циклы на фоне**
- Парсинг, генерация/обработка изображений, конвертация больших текстов, работа с CoreGraphics, где много временных Foundation объектов.

2) **Непрерывные batch‑операции**
- Ты хочешь, чтобы пик памяти не рос до конца всей операции.

3) **Bridging-heavy код**
- Частые переходы Swift ↔ ObjC (например, `String` ↔ `NSString`, `Data` ↔ `NSData`) в tight loop могут накапливать autoreleased временные объекты.

## 5) Что `autoreleasepool` НЕ делает
- Не “форсит деинициализацию” чисто Swift‑структур и не управляет памятью value‑типов.
- Не решает retain cycles.
- Не гарантирует момент освобождения всех объектов (только тех, что реально попали в autorelease pool).

**Самопроверка**
- Оспорено: “autoreleasepool нужен всегда для экономии памяти” — обычно системного пула достаточно; нужен в специфичных hot/batch местах.
- Неочевидно: какие именно объекты в твоём коде autoreleased — зависит от вызванных ObjC API и мостинга; проверяется профилем (Allocations/VM Tracker).
- Источники: Apple docs по Autorelease Pool, ARC/Objective‑C runtime, практические кейсы Instruments (Allocations).

### Q27 (🟠): Чем отличается управление памятью в Swift и Objective-C?

**Кратко**
- И Swift, и Objective-C на Apple платформах используют **ARC**, но модель и “видимость” деталей различаются.
- Swift ARC тесно интегрирован с типовой системой: value-типы без ARC, строгие правила `inout`, exclusivity, предсказуемые `deinit`.
- Objective-C исторически связан с message dispatch, dynamic runtime, `autorelease` и более широким использованием `nil`-семантики.
- В Swift меньше `autorelease`, но при bridging с Foundation/ObjC он остаётся и управляется autorelease pools.
- Swift даёт больше compile-time гарантий и оптимизаций, ObjC — больше runtime динамики и “магии” (KVC/KVO, swizzling).

**Развёрнуто**
## 1) Общая база: ARC есть в обоих
- В обоих языках ARC вставляет retain/release для объектов (reference-types).
- Основные проблемы одинаковые: retain cycles, неправильные strong/weak, удержания closures/blocks.

## 2) Value types и семантика копирования
- Swift активно использует `struct/enum` (value types): они не управляются ARC как сущности.
- Objective-C почти полностью class-oriented: большинство сущностей — reference objects.

Следствие:
- в Swift можно проектировать модели без shared state и без ARC-нагрузки,
- в ObjC это чаще достигается копированием объектов или дисциплиной владения.

## 3) Autorelease и run loop
- В ObjC autorelease — часть повседневной модели: много API возвращают autoreleased.
- В Swift “чистый” код обычно не думает про autorelease, но:
  - при взаимодействии с Foundation и при bridging часто создаются autoreleased объекты,
  - `autoreleasepool {}` в Swift нужен в основном для ObjC-heavy batch-операций.

## 4) Runtime динамика и её влияние на память
Objective-C:
- message dispatch (`objc_msgSend`), dynamic features, swizzling, KVC/KVO;
- lifetime часто “размазан” по runtime; бывают неожиданные удержания через ассоциированные объекты, KVO-обсерверы и т.д.

Swift:
- больше статической типизации и предсказуемости,
- чаще static dispatch/специализация,
- более строгая модель доступа к памяти (exclusivity) уменьшает класс ошибок.

## 5) Weak/unowned и нуллинг
- В ObjC `weak` зануляется при `dealloc` (zeroing weak).
- В Swift `weak` тоже zeroing, но дополнительно есть `unowned`/`unowned(unsafe)` как часть языка и семантики.
- Swift делает `weak` всегда optional, ObjC — `__weak` по сути тоже “может стать nil”, но типовая система это не заставляет так же явно.

## 6) Interop нюансы
- Swift object может быть bridged в ObjC и наоборот; при этом:
  - появляются autorelease pools,
  - меняются “места” удержаний (например, block/closure bridging),
  - иногда возникают неожиданные retain cycles на границах.

## 7) Практический вывод для собеса
- Оба языка под ARC, но Swift даёт сильнее compile-time гарантии и стимулирует value-oriented дизайн.
- ObjC чаще требует понимания autorelease, runtime динамики и паттернов “ручного” контроля владельцев.

**Самопроверка**
- Оспорено: “Swift и ObjC одинаковы, раз оба ARC” — различия существенны: value types, autorelease, runtime динамика, типовая система.
- Неочевидно: конкретные детали bridging/retain в смешанном проекте зависят от API и runtime; лучше подтверждать инструментами (Memory Graph/Instruments).
- Источники: Apple docs по ARC (Swift и ObjC), docs по Autorelease Pools, материалы по Swift/ObjC interop и runtime.

### Q28 (🟠): Как ARC определяет, где нужно вставить retain/release?

**Кратко**
- ARC — это **compile-time** анализ: компилятор строит граф времени жизни ссылок и вставляет retain/release так, чтобы объект жил, пока на него есть сильные ссылки.
- Вставки зависят от:
  - границ scope,
  - присваиваний/перезаписей,
  - передачи аргументов/возврата значений,
  - захватов в closures,
  - оптимизаций (например, eliminate retain/release, move/releases, SSA).
- Компилятор стремится минимизировать операции, но сохранять семантику (чтобы не освободить объект раньше).
- При bridging с ObjC добавляются `autorelease`/`retainAutoreleasedReturnValue` и похожие оптимизации ABI.

**Развёрнуто**
ARC в Swift — не runtime сборщик мусора, а набор трансформаций компилятора. Концептуально процесс можно объяснить так:

## 1) Анализ ownership на уровне IR
Компилятор (через SIL/LLVM pipeline) анализирует:
- где создаётся объект и кто им владеет,
- где появляются новые сильные ссылки,
- где ссылки исчезают (scope end, overwrite, nil assignment),
- какие пути выполнения возможны (ветвления, early return, throw).

На основе этого он размещает:
- `retain` при появлении владения,
- `release` при уходе владения.

## 2) Простой пример: присваивание и выход из scope
```swift
final class Foo { deinit { print("deinit") } }

func f() {
    let a = Foo()   // +1 retain (owner a)
    let b = a       // +1 retain (owner b)
    // ...
}                   // -1 release (b), -1 release (a) → 0 → deinit
```

## 3) Overwrite/обнуление
```swift
var x: Foo? = Foo() // +1
x = Foo()           // release старого, retain нового
x = nil             // release
```
ARC должен гарантировать, что старый объект будет отпущен, когда ссылка на него заменяется.

## 4) Ветвления и исключения
ARC вставляет удержания/освобождения на всех путях:
```swift
func g(_ flag: Bool) {
    let obj = Foo()
    if flag { return } // release всё равно должен произойти
    // ...
} // release
```
Компилятор размещает release так, чтобы он отработал независимо от пути (включая `throw`).

## 5) Closures и захваты
Если closure захватывает объект сильно, ARC продлевает его жизнь до конца жизни closure:
```swift
func h() -> () -> Void {
    let obj = Foo()
    return { print(obj) } // obj удерживается closure → release произойдёт, когда closure освободится
}
```
Если `[weak obj]`, то удержания нет (и добавляется механизм zeroing weak).

## 6) Оптимизации ARC
Компилятор и оптимизаторы пытаются:
- убирать пары retain/release, которые взаимно компенсируются,
- перемещать release раньше (early release), если доказано, что объект больше не нужен,
- объединять операции, сокращать трафик ARC.

Но он не может нарушить семантику: если объект используется дальше — release нельзя “подвинуть” раньше.

## 7) Нюанс про ObjC interop
При вызовах ObjC API используются оптимизации вроде “retain/autorelease return value” (тема ObjC ARC optimizations), и значение может быть autoreleased с последующим “fast retain”. В Swift это проявляется особенно на границах bridging.

**Самопроверка**
- Оспорено: “ARC решает в runtime” — основная работа делается compile-time, runtime лишь выполняет вставленные операции и weak-механику.
- Неочевидно: точные места вставок зависят от оптимизаций и версии компилятора; на собесе важно объяснить принцип и факторы (scope/overwrite/closures/branches).
- Источники: Swift docs про ARC, материалы Swift compiler/SIL ownership, ObjC ARC optimization docs, WWDC про performance/ARC.

### Q29 (🟠): Могут ли быть циклы ретейна без closure?

**Кратко**
- Да. Retain cycle — это любой цикл в графе **сильных ссылок** между объектами, и closures не обязательны.
- Классика: `A -> B -> A` через stored properties.
- Часто встречается через делегаты/обратные ссылки, которые ошибочно сделаны `strong`.
- Бывает “скрытый” цикл через `NotificationCenter`, `Timer`, KVO, ассоциированные объекты, кеши/синглтоны, графы моделей.

**Развёрнуто**
Retain cycle появляется, когда объекты удерживают друг друга так, что их strong count не может упасть до 0. Closures — лишь один из источников, но не единственный.

## 1) Простейший цикл: два объекта
```swift
final class A {
    var b: B?
    deinit { print("A deinit") }
}

final class B {
    var a: A?
    deinit { print("B deinit") }
}

var a: A? = A()
var b: B? = B()

a?.b = b
b?.a = a

a = nil
b = nil
// deinit не вызовется: A <-> B strong cycle
```

Лечение: разорвать цикл `weak`/`unowned` на одной из сторон:
```swift
final class B {
    weak var a: A?
}
```

## 2) Делегаты и обратные ссылки
Типовой источник:
- `owner` хранит `child` сильно,
- `child` хранит `owner` как delegate тоже сильно → цикл.
Решение: delegate почти всегда `weak` (или `unowned`, если гарантирован lifetime).

## 3) Циклы через контейнеры и графы
- Узлы дерева/графа с двунаправленными ссылками.
- Parent удерживает children, children удерживают parent.
Часто делают `parent` как `weak/unowned`.

## 4) “Скрытые” циклы без closures
### `Timer`
`Timer.scheduledTimer` может удерживать target:
- если target удерживает timer → цикл.
Решение: invalidate timer, или использовать weak proxy.

### `NotificationCenter`
Если использовать block-based API и хранить token неправильно, можно удержать цепочку.
(Даже без closure-обработчика можно получить удержания через observer/owner зависимости.)

### KVO / ассоциированные объекты
- KVO может удерживать наблюдателя/наблюдаемый объект в неожиданных комбинациях.
- Associated objects легко создают сильные связи, особенно если вешать “менеджеры” на объекты.

### Синглтоны/кеши
Если singleton держит объект сильно, а объект держит singleton (или держит что-то, что держит singleton) — можно получить цикл/утечку по времени жизни приложения.

## 5) Главный принцип
Retain cycle — это не про “closure”, а про **граф владения**. Вопрос на собесе проверяет, понимаешь ли ты владение и умеешь ли проектировать “направление” strong-ссылок.

**Самопроверка**
- Оспорено: “retain cycle — это только `[weak self]` в замыканиях” — цикл бывает вообще без замыканий.
- Неочевидно: конкретная механика удержаний у `Timer/NotificationCenter/KVO` зависит от конкретного API и паттерна использования; в спорных кейсах подтверждать Memory Graph/Instruments.
- Источники: Swift ARC docs, Apple docs по Timer/NotificationCenter/KVO, практический опыт отладки через Memory Graph/Instruments.

### Q30 (🟠): Может ли closure быть `nil`?

**Кратко**
- Да, если closure хранится в **опциональном** типе: `(() -> Void)?`.
- Не может быть `nil`, если свойство/переменная не optional: `let f: () -> Void`.
- В UIKit часто делают optional callbacks (`var onTap: (() -> Void)?`), чтобы подписка была необязательной.
- Важно: “closure = nil” не освобождает автоматически всё, что удерживается где-то ещё; но если именно эта closure удерживала объекты, то обнуление может разорвать удержания.

**Развёрнуто**
Closure в Swift — это значение (обычно heap-объект/контекст), и как любое значение может быть опциональным.

## 1) Пример: optional closure
```swift
final class Cell {
    var onTap: (() -> Void)?

    func tap() {
        onTap?()
    }
}

let cell = Cell()
cell.onTap = { print("tap") }
cell.tap()

cell.onTap = nil     // ✅ теперь колбэк отсутствует
cell.tap()           // ничего не произойдёт
```

## 2) Пример: non-optional closure
```swift
let f: () -> Void = { print("hi") }
// f = nil // ❌ нельзя
```

## 3) Зачем это нужно в архитектуре
- Делать callback необязательным (ячейка/вью может жить без подписчика).
- Разрывать удержания: если closure захватила `self` сильно, то `onTap = nil` может убрать retain cycle.

## 4) Частые ошибки
1) Забыть вызвать через `?()`:
```swift
onTap() // ❌ если optional
onTap?() // ✅
```

2) Думать, что `nil` всегда “лечит” утечки:
- если retain cycle не через эту closure, обнуление не поможет,
- если closure хранится где-то ещё (например, подписка/таск), утечка останется.

**Самопроверка**
- Оспорено: “closure не может быть nil, это же функция” — в Swift это значение, которое может быть optional.
- Неочевидно: где именно хранится closure (свойство, подписка, task) и что она удерживает; обнуление помогает только если это место владения разрывает цепочку.
- Источники: Swift Language Guide (Closures, Optionals), практические паттерны UIKit callbacks и ARC.

### Q31 (🟠): Бывают ли сильные референсы без циклов ретейна?

**Кратко**
- Да. Сильная ссылка (`strong`) — это обычное владение объектом и она **нормальна** сама по себе.
- Retain cycle появляется только если сильные ссылки образуют **цикл** (A удерживает B, B удерживает A, или более длинный цикл).
- Большинство объектов в приложении живут за счёт сильных ссылок без каких-либо циклов (владение “деревом”: root → children).
- Проблема не в strong-ссылке, а в **неправильном графе владения** (отсутствие “одного владельца” или неверная направленность ссылок).

**Развёрнуто**
Сильные ссылки — это механизм “кто отвечает за жизнь объекта”.

## 1) Нормальный случай: дерево владения
Самая здоровая модель — ownership tree:
- есть корневые владельцы (например, UIWindow/Coordinator/Root VC),
- они держат дочерние объекты сильно,
- дочерние держат родителей слабо/не держат вовсе.

```swift
final class Owner {
    let service = Service()
}

final class Service {
    // не держит Owner сильно
}
```

Здесь strong-ссылка `Owner -> Service` удерживает `Service` ровно столько, сколько живёт `Owner`. Цикла нет.

## 2) Пример: сильная ссылка без цикла, но с “долгой жизнью”
Сильная ссылка может быть источником “утечки” по смыслу, даже без цикла, если:
- объект удерживается глобально (singleton),
- объект кладётся в кэш и не удаляется,
- кто-то держит его “слишком долго”.

Это не retain cycle, но эффект похож: `deinit` не вызывается.

```swift
final class Cache {
    static let shared = Cache()
    var items: [String: AnyObject] = [:] // если не чистить — держит объекты вечно
}
```

## 3) Почему вопрос важен
Он проверяет, путаешь ли ты:
- “strong ссылка” (нормальный ownership),
- “retain cycle” (патологический цикл ownership),
- и “lifetime bug” (объект удерживается дольше, чем нужно, но без цикла).

## 4) Практический критерий
- Если можно построить путь сильных ссылок от объекта обратно к нему самому — это cycle.
- Если пути обратно нет, но объект всё ещё жив — ищи владельца (root, singleton, кэш, подписка, таск).

**Самопроверка**
- Оспорено: “любая strong ссылка опасна” — нет, без strong невозможно управление временем жизни.
- Неочевидно: “утечка” в смысле продукта часто означает “живёт слишком долго” (логическая утечка), даже без retain cycle; важно различать эти классы проблем.
- Источники: Swift ARC docs, практики проектирования ownership (coordinators, dependency graphs), инструменты Memory Graph/Instruments.

### Q32 (🟠): Чем отличается capture list и что он даёт?

**Кратко**
Capture list (`[ ... ]`) — это явное описание того, **что и как захватывает** closure:
- позволяет захватывать `self` как `weak`/`unowned` и тем самым разрывать retain cycle,
- позволяет “снять слепок” значения на момент создания closure (value capture),
- позволяет переименовать захваченные значения,
- управляет тем, что будет храниться в capture context (и, косвенно, временем жизни объектов).

**Развёрнуто**
## 1) Базовый смысл: что такое захват
Closure может использовать переменные из внешнего scope. Тогда компилятор создаёт capture context, который хранит эти значения/ссылки.

Без capture list захват происходит по правилам языка:
- для reference-типов это захват ссылки (strong по умолчанию),
- для value-типов — захват значения (копия) либо оптимизированная форма, но семантически значение.

```swift
final class VC {
    func setup() {
        let x = 10
        let f = {
            print(x)       // захват x
            print(self)    // захват self (strong по умолчанию)
        }
        _ = f
    }
}
```

## 2) Разрыв retain cycle: weak/unowned self
Самая частая причина использования capture list:
```swift
final class VC {
    var onDone: (() -> Void)?

    func bind() {
        onDone = { [weak self] in
            self?.finish()
        }
    }

    func finish() {}
}
```
Если `onDone` хранится в `self`, то без `[weak self]` будет цикл:
`self -> onDone(closure) -> self`.

`unowned` вариант:
```swift
onDone = { [unowned self] in
    finish()
}
```
Он уместен только если гарантировано, что `self` жив, пока closure может быть вызвана.

## 3) “Снимок значения” (value capture) и freeze
Capture list позволяет захватить выражение в момент создания closure:
```swift
var count = 0

let f = { [count] in
    print(count) // напечатает значение count на момент создания f
}

count = 42
f() // 0
```

Без capture list closure прочитала бы актуальный `count` (в зависимости от семантики переменной и оптимизаций, но на уровне модели — “видит изменения”).

## 4) Переименование и ясность
```swift
let url = URL(string: "https://example.com")!
let f = { [u = url] in
    print(u)
}
```

## 5) Тонкости, которые важно понимать
- `[weak self]` делает `self` внутри closure опциональным; нужно `self?`/`guard let`.
- При `guard let self` внутри closure создаётся **сильная** ссылка на время выполнения блока (это обычно правильно).
- Захват значения через capture list может увеличить копирование (полезно как “freeze”, но не всегда нужно).
- Capture list не “ускоряет” автоматически — он управляет семантикой владения и моментом захвата.

**Самопроверка**
- Оспорено: “capture list нужен только для weak self” — он также нужен для value snapshot, переименования и явного контроля захвата.
- Неочевидно: как именно переменные захватываются (по значению/по ссылке) зависит от их природы (value/reference) и контекста; на собесе безопаснее объяснять на примерах.
- Источники: Swift Language Guide (Closures: Capturing Values), ARC docs, типовые паттерны UIKit/async callbacks.

### Q33 (🟠): Что такое side tables и зачем они нужны?

**Кратко**
- Side table — это внешняя структура данных, где runtime хранит "дополнительное" состояние объекта, которое не хочется/нельзя держать прямо в объекте.
- В Swift runtime side table (`HeapObjectSideTableEntry`) создаётся **не при создании объекта**, а **при первом создании `weak` ссылки** на этот объект.
- В ObjC runtime side tables используются также для associated objects.
- Нужны, чтобы:
  - не раздувать размер каждого объекта "на всякий случай",
  - хранить данные только для тех объектов, которым это нужно,
  - обеспечить zeroing weak без изменения layout классов.

**Развёрнуто**
Термин "side table" не всегда строго формализован в пользовательской документации, но смысл один: runtime ведёт **внешние структуры**, создаваемые по требованию, чтобы хранить служебную информацию.

## 1) Почему нельзя хранить всё внутри объекта
Если бы для каждого объекта заранее выделяли место под:
- списки weak-ссылок,
- ассоциированные объекты,
- дополнительные флаги синхронизации,
то каждый объект стал бы тяжелее, даже если ему это не нужно.

Side tables позволяют:
- держать "пустой" объект компактным,
- создавать записи в таблице только при первом использовании фичи.

## 2) Когда именно создаётся side table в Swift
В Swift runtime (`SwiftObject`/`HeapObject`) side table **не создаётся при инициализации объекта**.

Она создаётся **при первом создании `weak` ссылки** на объект:
- до этого момента объект хранит в своём заголовке только strong count и unowned count,
- при создании первой `weak` ссылки runtime аллоцирует `HeapObjectSideTableEntry`,
- заголовок объекта обновляется: в нём хранится указатель на side table,
- все дальнейшие weak-ссылки регистрируются через side table.

При `deinit`:
- runtime через side table находит все weak-ссылки,
- зануляет их (zeroing weak),
- освобождает side table после завершения уничтожения.

## 3) Side tables и associated objects (ObjC)
Associated objects позволяют "прикрепить" произвольные данные к объекту без изменения его класса:
- runtime хранит глобальную таблицу вида `(object, key) -> value`.
Это тоже "side table" подход, но уже в ObjC runtime.

## 4) Что важно сказать на собесе
- Side table в Swift создаётся **лениво** — только при первой `weak` ссылке, а не сразу.
- `weak` почти всегда дороже `unowned`/strong, потому что требует участия runtime, side table и zeroing механизма.
- Объекты без `weak`-ссылок никогда не получают side table и остаются компактными.

**Самопроверка**
- Оспорено: "side table создаётся при создании каждого объекта" — нет, она создаётся лениво при первой weak-ссылке.
- Оспорено: "side table — это часть каждого объекта" — нет, это внешняя структура, создаваемая по требованию.
- Неочевидно: точные внутренние структуры (`HeapObjectSideTableEntry`) могут меняться между версиями runtime; на собесе лучше держаться концепта (lazy creation + weak registration + zeroing), а не байтовых деталей.
- Источники: Swift runtime source (HeapObject.h), материалы по ObjC runtime (associated objects, weak references), WWDC/performance talks про ARC/weak overhead.

### Q34 (🟠): Что такое `weak`, как он устроен под капотом

**Кратко**
- `weak` — ссылка, которая **не удерживает** объект и **автоматически становится `nil`**, когда объект деинициализируется (zeroing weak).
- Реализуется при участии runtime:
  - ссылка хранится как “weak entry”,
  - runtime ведёт таблицу/регистрацию weak-ссылок на объект (side table),
  - при `dealloc/deinit` объекта runtime зануляет все weak-ссылки.
- `weak` всегда `Optional`, потому что может стать `nil` в любой момент после исчезновения strong-владельцев.
- Операции записи/чтения weak обычно дороже strong/unowned (из-за таблиц, синхронизации, barrier’ов).

**Развёрнуто**
## 1) Семантика
`weak` нужен, чтобы:
- не создавать strong ownership,
- безопасно ссылаться на объект, который может умереть раньше.

```swift
final class Child {
    weak var parent: Parent?
}
```

Если `Parent` освобождается, `child.parent` станет `nil`, а не “висячей ссылкой”.

## 2) Что происходит при установке weak-ссылки
Когда ты делаешь `child.parent = parent`, runtime:
- регистрирует факт “вот эта weak-переменная указывает на этот объект”,
- чтобы позже можно было занулить её при освобождении объекта.

Концептуально:
- для объекта создаётся запись в side table (если её ещё нет),
- в ней хранится список/хэш weak-референсов.

## 3) Что происходит при деинициализации объекта
При `deinit`/`dealloc`:
- runtime находит все weak-ссылки, зарегистрированные на этот объект,
- присваивает им `nil` (zeroing),
- очищает записи.

Поэтому `weak` безопасен: после смерти объекта ты не получишь dangling pointer.

## 4) Почему `weak` дороже
- Нужен lookup/обновление записей в таблице weak-референсов.
- Часто есть синхронизация, чтобы корректно работать в присутствии конкуренции (хотя это не делает код thread-safe).
- Чтение weak может требовать “проверки, жив ли объект” и корректного получения ссылки.

## 5) Практические следствия
- `weak` — типичный выбор для:
  - делегатов,
  - обратных ссылок child→parent,
  - захвата `self` в closures, если lifetime не гарантирован.
- В горячих местах (tight loops) большое количество weak-операций может быть заметно — тогда лучше пересмотреть дизайн.

**Самопроверка**
- Оспорено: “weak — это просто не-retain” — нет, важная часть: zeroing при деинициализации через runtime таблицы.
- Неочевидно: точные детали реализации (структуры таблиц, атомарность) зависят от runtime/версии; на собесе важнее корректная модель: регистрация weak + зануление.
- Источники: Apple docs по ARC/weak, материалы ObjC runtime про zeroing weak, обсуждения Swift runtime/ABI, performance материалы про стоимость weak.

### Q35 (🟠): Что такое `unowned`, как он устроен под капотом

**Кратко**
- `unowned` — не удерживает объект, **не зануляется**, предполагает, что объект жив дольше ссылки.
- При обращении к `unowned` после деинициализации объекта → **крэш** (trap), потому что ссылка становится “недействительной”.
- В отличие от `weak`, `unowned` обычно не требует zeroing-механизма и таблиц weak-ссылок, поэтому дешевле по обслуживанию.
- Есть нюанс: в Swift есть `unowned` (checked) и `unowned(unsafe)` (без проверки).

**Развёрнуто**
## 1) Семантика `unowned`
`unowned` подходит для обратных ссылок, когда жизненный цикл гарантирован:
- child никогда не переживёт parent,
- или ссылка используется только в промежутке, где владелец точно жив.

```swift
final class Parent {
    let child: Child
    init() { child = Child(parent: self) }
}

final class Child {
    unowned let parent: Parent
    init(parent: Parent) { self.parent = parent }
}
```

## 2) Что “под капотом”
Концептуально `unowned` хранит “ссылку без владения”:
- не увеличивает strong count,
- не участвует в weak-таблицах и не зануляется.

Для checked `unowned` runtime обычно способен обнаружить обращение к уже освобождённому объекту и аварийно завершить (trap), вместо того чтобы продолжать с повреждённой памятью. Это ключевое отличие от `unowned(unsafe)`.

Важно для собеса: не нужно утверждать “это просто сырой указатель” — checked `unowned` обычно имеет проверку валидности/статуса объекта (реализация может меняться), но по поведению: **крэш при обращении после смерти**.

## 3) Чем отличается от `weak`
- `weak` безопасен: становится `nil`.
- `unowned` небезопасен при нарушении инварианта: краш.
- `weak` требует runtime zeroing и side tables; `unowned` — нет (обычно).

## 4) Где `unowned` реально уместен
- relationship “owner/owned”: объект-ребёнок строго живёт внутри владельца (например, создаётся и удерживается `let`-ссылкой).
- performance-чувствительный код, где `weak`-оверход заметен, и есть железная гарантия lifetime.

## 5) Типовой антипример
`unowned` в callbacks/async, где время жизни непредсказуемо:
- запрос в сеть,
- таймер,
- completion в другом объекте,
где `self` может умереть раньше → это кандидат на `weak`.

**Самопроверка**
- Оспорено: “unowned = безопаснее weak, потому что не optional” — наоборот: он безопасен только при строгих гарантиях, иначе краш.
- Неочевидно: точная реализация checked `unowned` может отличаться по версиям runtime; на собесе лучше описывать наблюдаемое поведение и trade-offs.
- Источники: Swift Language Guide (ARC), обсуждения Swift runtime про unowned references, практические кейсы retain cycles и crashes.

### Q36 (🟠): Чем отличается `unowned` от `unowned(unsafe)`?

**Кратко**
- `unowned` (checked) — не удерживает объект и **падает (trap)** при обращении после освобождения объекта.
- `unowned(unsafe)` — не удерживает объект и **не делает проверок**; после освобождения объекта это **dangling pointer** → UB-подобные эффекты: краши, чтение мусора, коррупция памяти.
- `unowned(unsafe)` используют крайне редко: обычно только для низкоуровневых оптимизаций/interop, где lifetime гарантирован внешним контрактом.
- По умолчанию выбирают `weak` или `unowned` (checked), а не `unowned(unsafe)`.

**Развёрнуто**
## 1) Семантика и поведение при ошибке
### `unowned`
- Предполагает, что объект жив.
- Если нет — runtime останавливает программу (trap). Это “fail fast” и помогает поймать баг.

### `unowned(unsafe)`
- Тоже предполагает, что объект жив.
- Если нет — никакой страховки: обращение идёт по недействительному адресу.

```swift
final class A { deinit { print("deinit") } }
final class B {
    unowned(unsafe) var a: A
    init(a: A) { self.a = a }
}
```

Если `A` освобождён раньше, чем `B` обратится к `a`, поведение непредсказуемо.

## 2) Почему вообще существует `unowned(unsafe)`
Это инструмент “на крайний случай”:
- когда ты точно знаешь, что lifetime гарантирован, и хочешь убрать проверки/overhead,
- или когда работаешь с low-level runtime/interop и хочешь явно выразить “сырость” ссылки.

Но в обычной iOS разработке это почти всегда плохая идея:
- слишком легко нарушить инвариант временем жизни,
- баги проявляются нестабильно и плохо диагностируются.

## 3) Практическая эвристика выбора
- Непредсказуемый lifetime (async, callbacks, timers) → `weak`.
- Гарантированный lifetime по архитектуре → `unowned` (checked).
- `unowned(unsafe)` — только если можешь формально доказать lifetime и готов принять риск “сложных крашей”.

## 4) Как объяснить это на собесе кратко и чётко
“`unowned` — это невладеющая ссылка с проверкой: если объект умер, будет trap. `unowned(unsafe)` — без проверки: после смерти объекта получаешь висячий указатель и undefined behavior.”

**Самопроверка**
- Оспорено: “unsafe просто быстрее и норм” — скорость не стоит риска UB в приложенческом коде.
- Неочевидно: конкретные механизмы проверок у `unowned` могут меняться; важно различать проверяемое vs непроверяемое поведение.
- Источники: Swift Language Guide (ARC), Swift reference manual про ownership qualifiers, обсуждения Swift runtime о `unowned(unsafe)`.

### Q37 (🟠): Что такое `strong`, как он устроен под капотом

**Кратко**
- `strong` — обычная сильная ссылка, которая **владеет** объектом и увеличивает его lifetime.
- При присваивании в strong-ссылку ARC вставляет **retain**, при выходе из владения — **release**.
- Когда суммарное владение (strong references) падает до 0 → вызывается `deinit`, память освобождается.
- Внутренне это не “магическое поле”, а результат вставок компилятора + runtime поддержка reference counting.

**Развёрнуто**
## 1) Семантика
Сильная ссылка означает: “я удерживаю объект живым”.

```swift
final class Foo {
    deinit { print("deinit") }
}

do {
    let a = Foo() // strong owner
    _ = a
} // a выходит из scope → release → deinit
```

## 2) Что происходит “под капотом”
### Compile-time часть
Компилятор анализирует ownership и вставляет:
- `retain` при появлении владения,
- `release` при уходе владения.

Это происходит при:
- присваивании,
- передаче в функции (когда нужно продлить жизнь),
- возврате,
- захвате в closures.

### Runtime часть
Runtime обеспечивает:
- корректное изменение счётчиков,
- уничтожение объекта при достижении 0,
- работу `weak`/`unowned` механизмов вокруг (side tables и т.п. — уже дополнительно).

На уровне модели: strong count (reference count) увеличивается/уменьшается.

## 3) Strong в свойствах / локальных переменных / захватах
- Свойство класса по умолчанию strong:
```swift
final class A {
    var b: B? // strong
}
```

- Захват `self` в closure по умолчанию strong:
```swift
onTap = {
    self.doSomething() // self удерживается closure
}
```

Это сильные ссылки, но проблемой становятся только при циклах или слишком длинном lifetime.

## 4) Важные нюансы
- “Strong count” — упрощение: реальная реализация может включать дополнительные счётчики/флаги, оптимизации, side tables.
- ARC может делать оптимизации: убирать лишние retain/release, сдвигать release раньше и т.д.

## 5) Типовая проверка мышления на собесе
- Strong — это норма владения.
- Неправильно направленные strong-ссылки превращаются в retain cycle.
- Даже без цикла strong может держать объект слишком долго (кэш/синглтон/таск).

**Самопроверка**
- Оспорено: “strong — это просто ‘сильное поле’ в объекте” — это поведение владения, обеспеченное вставками ARC и runtime.
- Неочевидно: детали реализации счётчиков (например, где хранятся флаги/side tables) могут отличаться; на собесе важнее объяснить lifecycle и операции retain/release.
- Источники: Swift Language Guide (ARC), Apple docs по ARC, материалы про ARC optimizations и runtime.

### Q38 (🟠): Как удалить объект из памяти?

**Кратко**
- В Swift ты “удаляешь объект” не вручную, а **убирая все сильные ссылки** на него.
- Когда strong references становятся 0, ARC вызывает `deinit` и освобождает память.
- Практически это значит:
  - присвоить `nil` опциональным strong-полям,
  - разорвать retain cycles (`weak/unowned`, invalidate timers, cancel tasks),
  - удалить из кэшей/синглтонов/коллекций,
  - отписаться от наблюдений/notifications, где ты удерживаешься.
- Нельзя “форснуть” освобождение, если где-то ещё остаётся strong-владелец.

**Развёрнуто**
## 1) Основной принцип: убрать владельцев
Объект живёт, пока его удерживают strong-ссылки. Поэтому “удаление” — это сведение count к 0.

```swift
final class Foo { deinit { print("deinit") } }

var x: Foo? = Foo()
x = nil // release → deinit (если больше никто не держит)
```

## 2) Типовые источники “почему не удаляется”
### A) Retain cycle
Классика:
- VC хранит closure,
- closure хранит VC (self) → цикл.
Решение: `[weak self]`, или разнести владение.

### B) Таймеры / дисплейлинки
- `Timer`/`CADisplayLink` могут удерживать target.
Если target удерживает timer → цикл.
Решение: `invalidate()` в `deinit`/`viewWillDisappear`, weak-proxy.

### C) Notifications / observers
- Если ты держишь token/observer и не удаляешь его, цепочки могут жить дольше.
Решение: удалять observer/token в нужный момент.

### D) Долгоживущие коллекции/кэши/синглтоны
- Объект добавили в массив/кэш и забыли удалить.
Решение: remove/evict.

### E) Async задачи и подписки
- `Task`, Combine subscriptions, операции, completion handlers могут удерживать `self` и граф объектов.
Решение: `cancel()`, `store(in:)` с контролируемым lifetime, `[weak self]` где уместно.

## 3) Как убедиться, что объект реально освобождается
- Добавить `deinit { print(...) }` (или логгер).
- Проверить Memory Graph в Xcode: кто удерживает объект.
- Instruments (Leaks/Allocations): живые объекты и удерживающие ссылки.

## 4) Важное уточнение
ARC освобождает память “когда может”, но иногда освобождение происходит после выхода из текущего scope или после оптимизаций; главное — убрать strong-владельцев. Если кто-то держит объект сильной ссылкой, принудительно “удалить” нельзя (кроме как удалить этого владельца).

**Самопроверка**
- Оспорено: “в Swift есть delete/free для объектов” — нет, управление через ARC: освобождение при отсутствии владельцев.
- Неочевидно: долгоживущие системные механизмы (таймеры, подписки, асинхронщина) часто выглядят как “утечка”, но это удержания по дизайну; надо уметь их отменять.
- Источники: Swift ARC docs, Apple docs по Timer/NotificationCenter/Combine/Concurrency, инструменты Xcode Memory Graph и Instruments.

### Q39 (🟠): Почему `weak` всегда `Optional`, и что происходит с `weak`-ссылкой при деинициализации объекта?

**Кратко**
- `weak` всегда `Optional`, потому что объект может быть освобождён **в любой момент**, и ссылка обязана уметь стать “пустой”.
- При деинициализации объекта runtime выполняет **zeroing**: все weak-ссылки на этот объект автоматически присваиваются `nil`.
- Это предотвращает dangling pointers и “use-after-free”.
- Следствие: всегда нужно безопасно разворачивать `weak` (`self?`, `guard let self`).

**Развёрнуто**
## 1) Почему нельзя сделать `weak` не-Optional
Если бы `weak` был не-Optional, он должен был бы всегда указывать на валидный объект. Но `weak` специально **не удерживает** объект, значит в любой момент может наступить ситуация:
- все strong references исчезли,
- объект освобождён,
- `weak` всё ещё “смотрит” туда же.

Чтобы не получить висячую ссылку, язык делает `weak` только как `Optional`, и runtime гарантирует, что после смерти объекта там будет `nil`, а не мусор.

```swift
final class Owner {}

final class Child {
    weak var owner: Owner?
}

var o: Owner? = Owner()
let c = Child()
c.owner = o

o = nil               // Owner deinit
print(c.owner == nil) // true
```

## 2) Что происходит при деинициализации (zeroing weak)
Под капотом runtime:
- отслеживает weak-ссылки на объект,
- в момент `deinit/dealloc` обходит их,
- зануляет (`nil`) и снимает регистрацию.

Это “zeroing weak references”.

## 3) Почему это важно для безопасности
Если бы runtime не занулял `weak`, то после освобождения объекта `weak` стала бы dangling pointer.
Такие баги — самые неприятные: нестабильные краши, коррапция памяти.

`weak` делает поведение детерминированным:
- либо объект жив и ссылка не nil,
- либо объект умер и ссылка nil.

## 4) Практические последствия в коде (особенно closures)
```swift
someAsync { [weak self] in
    guard let self else { return }
    self.updateUI()
}
```
Здесь:
- `[weak self]` предотвращает удержание VC задачей,
- `guard let self` безопасно прекращает работу, если VC уже освобождён.

## 5) Частые ошибки
- Считать, что `weak` “почти как strong, но не держит” — он может стать nil в любой момент после потери владельцев.
- Разворачивать `weak` один раз и использовать долго — лучше ограничивать область сильной ссылки через `guard let self`.

**Самопроверка**
- Оспорено: “weak можно сделать non-optional и всё равно безопасно” — нет, без владения нет гарантии существования, поэтому нужна возможность `nil`.
- Неочевидно: конкретные структуры runtime (где хранятся weak-entries) меняются; на собесе важнее семантика zeroing weak и последствия для кода.
- Источники: Swift Language Guide (ARC, Optionals), материалы ObjC runtime про zeroing weak, практики использования `[weak self]` в async/UI коде.

### Q40 (🟠): Какие типичные краши/баги создаёт неправильный выбор `weak` vs `unowned`?

**Кратко**
- Ошибка в сторону `unowned`:
  - **Crash** при обращении после деинициализации объекта (dangling unowned → trap).
  - Часто проявляется в async/callback/timer сценариях, где lifetime `self` не гарантирован.
- Ошибка в сторону `weak`:
  - “Тихие” баги: код **не выполняется**, потому что `self` стал `nil`, UI не обновился, состояние не сохранилось.
  - Неочевидные race/логические проблемы: разные ветки могут увидеть `self` nil/не nil.
- И то и другое:
  - может маскировать архитектурную проблему владения (кто должен владеть кем).

**Развёрнуто**
## 1) `unowned` там, где lifetime не гарантирован → крэши
Самый типичный сценарий: VC запускает асинхронную операцию, а пользователь уходит назад.

```swift
final class VC {
    func load() {
        api.fetch { [unowned self] result in
            self.updateUI(result) // ❌ если VC уже deinit → crash
        }
    }
}
```

Почему это происходит:
- `unowned` не удерживает VC,
- callback может прийти позже,
- VC к этому моменту уже освобождён.

Правильнее:
```swift
api.fetch { [weak self] result in
    guard let self else { return }
    self.updateUI(result)
}
```

## 2) `weak` там, где нужна гарантия выполнения → “тихие” баги
Если операция должна обязательно завершиться (например, запись важного состояния), `weak self` может привести к тому, что блок просто не выполнит финализацию:

```swift
final class Saver {
    func save(_ data: Data, completion: @escaping () -> Void) {
        completion()
    }
}

final class VC {
    let saver = Saver()
    func commit() {
        saver.save(Data()) { [weak self] in
            self?.showSuccess() // ⚠️ может не сработать, если VC уже нет
        }
    }
}
```

Это не краш, а “поведение исчезло”.

Как лечат:
- переносить ответственность за действие в объект, который гарантированно жив (координатор/сервис),
- или временно удерживать `self` (иногда допустимо), если UX требует.

## 3) Классическая ошибка: “guard let self” как будто делает strong навсегда
```swift
task { [weak self] in
    guard let self else { return }
    // self тут strong только на время выполнения блока
}
```
Это правильно, но важно понимать:
- ты не “передумал” и не сделал цикл,
- ты просто держишь `self` локально, чтобы она не исчезла посреди выполнения.

## 4) Где чаще всего ошибаются
- Network callbacks (completion handlers).
- Timers / display links.
- Animations completion blocks.
- Combine subscriptions / async Task closures.
- Долгоживущие closures, хранящиеся как свойства.

## 5) Быстрая эвристика выбора
- Не можешь доказать lifetime → `weak`.
- Можешь доказать lifetime формально (child не переживёт parent) → `unowned`.
- Если цена “тихого пропуска” высока — перепроектировать владение/ответственность, а не насиловать `unowned`.

**Самопроверка**
- Оспорено: “unowned просто удобнее, потому что не optional” — удобнее, но опаснее; в async почти всегда неверно.
- Неочевидно: иногда `weak` действительно ломает логику (не должен “молчаливо” отменять обязательные действия); правильное решение — менять архитектуру (кто владеет задачей).
- Источники: Swift ARC docs, практики iOS async/callback владения, реальные отладки через Crash logs + Memory Graph.

### Q41 (🔴): Что такое `autoreleasepool`, как он устроен

**Кратко**
- `autoreleasepool` — механизм ObjC runtime: объекты, помеченные как *autoreleased*, добавляются в текущий пул и получают `release`, когда пул “дренится”.
- Под капотом пул — это структура/стек “контекстов”, куда записываются ссылки на autoreleased объекты.
- В iOS обычно есть системный autorelease pool на каждом проходе run loop; `autoreleasepool {}` создаёт вложенный пул и дренит его раньше.
- Нужен для контроля пиков памяти в batch-операциях с ObjC/Foundation/bridging.

**Развёрнуто**
## 1) Зачем вообще существует autorelease
Исторически в Objective-C было (и есть) управление временем жизни через reference counting. Чтобы не заставлять разработчика вручную балансировать retain/release в каждом месте, появился паттерн:
- объект создаётся и “помечается на release позже” (`autorelease`),
- конкретный момент “позже” — когда очистится autorelease pool.

Это удобно для фабрик, временных объектов, возвращаемых из функций, и для случаев, когда сложно заранее определить владельца.

## 2) Как это выглядит на уровне модели
- В потоке есть **стек autorelease pools** (вложенные области).
- Когда создаётся autoreleased объект, runtime помещает его в **верхний** пул.
- Когда пул “drain”:
  - он проходит по записанным объектам,
  - делает им `release`,
  - затем пул уничтожается.

В Swift:
- чисто Swift-объекты не “autorelease” по умолчанию,
- но bridging с ObjC может создавать autoreleased временные `NSObject`-сущности.

## 3) Что делает `autoreleasepool { ... }` в Swift
Он:
- пушит новый autorelease pool,
- выполняет блок,
- дренит пул по выходу.

```swift
for i in 0..<100_000 {
    autoreleasepool {
        let s = NSString(format: "item-%d", i) // autoreleased ObjC
        _ = s
    } // освобождение autoreleased внутри итерации
}
```

Без внутреннего пула autoreleased могли бы копиться до конца внешнего системного пула (например, до конца тика run loop), увеличивая пик памяти.

## 4) Как устроен “под капотом” (интервью-уровень)
На практике пул реализован как:
- структура данных, связанная с текущим потоком,
- с быстрым добавлением записей (часто stack-like),
- где каждая запись — указатель/ссылка на объект, которому надо отправить release.

Нюанс, который важно сказать: конкретная реализация — внутренность runtime и может меняться, но концепт “stack of pools + list of objects to release on drain” стабилен.

## 5) Где встречается системный пул
- В UIKit/AppKit вокруг обработки событий и run loop обычно создаются/дренятся autorelease pools автоматически.
- В фоновом потоке, особенно в manual loops, иногда надо создавать пул вручную, если там генерируются autoreleased объекты.

## 6) Что `autoreleasepool` НЕ решает
- Не лечит retain cycles.
- Не “форсит” освобождение объектов, которые удерживаются strong-ссылками.
- Не управляет Swift value types.

**Самопроверка**
- Оспорено: “autoreleasepool — это Swift-фича” — это механизм ObjC runtime, Swift лишь предоставляет удобную обёртку.
- Неочевидно: какие объекты в твоём коде попадают в autorelease pool — зависит от Foundation/ObjC API и bridging; это лучше подтверждать Instruments (Allocations).
- Источники: Apple docs по Autorelease Pools, ObjC runtime материалы, WWDC/performance talks.

### Q42 (🔴): Как “работает под капотом” `weak self` внутри closure

**Кратко**
- `[weak self]` в capture list означает: closure захватывает `self` **слабой ссылкой**, то есть **не удерживает** объект.
- Под капотом создаётся weak-ячейка/entry, зарегистрированная в runtime (zeroing weak). Если `self` умрёт, ссылка в closure станет `nil`.
- При выполнении closure обычно делают `guard let self`:
  - это создаёт **временную strong-ссылку** на время выполнения блока, чтобы `self` не исчезла посреди работы.
- Это разрывает retain cycle `self -> closure -> self`, если closure хранится в `self` (или в объекте, который `self` удерживает).

**Развёрнуто**
## 1) Что именно захватывает closure
Closure хранит capture context. Когда ты пишешь:
```swift
someAsyncCall { [weak self] in
    self?.doWork()
}
```
компилятор делает так:
- в capture context кладётся **weak reference** на `self` (не strong),
- то есть closure не увеличивает strong count `self`.

## 2) Почему `self` становится Optional внутри
Потому что weak может быть занулён runtime в любой момент после освобождения объекта:
- поэтому внутри closure `self` имеет тип `Self?`.

## 3) Что происходит при выполнении closure
Вариант A (часто в коде):
```swift
{ [weak self] in
    guard let self else { return }
    self.doWork()
}
```

Здесь важный момент:
- `guard let self` создаёт **локальную сильную ссылку** `self` (shadowing) на время выполнения.
- Это предотвращает ситуацию “`self` была не nil в начале, но стала nil посередине”.

Это не создаёт retain cycle, потому что:
- strong-ссылка живёт только внутри выполнения closure,
- closure всё ещё хранит `self` weak.

Вариант B:
```swift
{ [weak self] in
    self?.doWork()
}
```
Тоже ок, но:
- `self` может стать nil между обращениями, если их несколько,
- часто менее читаемо, если нужно много вызовов.

## 4) Что происходит, если `self` уже деинициализирована
- weak в capture context уже занулён → `self` будет `nil` → блок либо ранний return, либо ничего не сделает.
Это “тихое” поведение, в отличие от `unowned self`, который бы упал.

## 5) Зачем это всё в контексте ARC
Классический цикл:
- `self` хранит `closure` как property,
- `closure` захватывает `self` сильно,
→ `self` никогда не освободится.

`[weak self]` делает связь `closure -> self` слабой и цикл исчезает.

## 6) Нюанс про производительность/механику
- Weak требует участия runtime (таблицы weak, zeroing), поэтому операции с weak дороже сильных ссылок.
- Но в UI/async callbacks это почти всегда правильный trade-off ради корректности.

**Самопроверка**
- Оспорено: “`[weak self]` просто делает self optional” — важнее то, что closure перестаёт удерживать `self` и runtime зануляет ссылку при deinit.
- Неочевидно: exact runtime-детали (как хранится weak-entry) меняются; на собесе держаться модели: weak capture + zeroing + optional unwrap + временный strong внутри блока.
- Источники: Swift Language Guide (Closures: Capturing Values), ARC/weak docs, материалы runtime про zeroing weak.

### Q43 (🔴): Как устроена память в iOS приложении (Stack/Heap/Static etc.)

**Кратко**
- **Stack**: быстрые LIFO-кадры вызовов функций (локальные переменные, адреса возврата). Живёт по scope/вызову.
- **Heap**: динамические аллокации (объекты классов, буферы, большие структуры, многие runtime-объекты). Живёт пока не освобождена (ARC/free).
- **Static/Global**: глобальные переменные, `static`, данные модуля. Живут весь процесс.
- **Text (Code)**: машинный код приложения и системных библиотек (обычно read-only + executable).
- **Data сегменты**:
  - `.data` (инициализированные глобальные),
  - `.bss` (неинициализированные/нули),
  - `__const`/rodata (константы).
- **Heap-мэппинги** включают: malloc zones, ObjC/Swift runtime, JIT нет, но есть mmap для файлов/фреймворков.
- В iOS всё это — виртуальная память; реальные страницы подгружаются по demand paging.

**Развёрнуто**
Нужно понимать, где что живёт, чтобы объяснять:
- почему class обычно heap,
- почему рекурсия может переполнить stack,
- почему глобальные singletons живут "вечно",
- как memory spikes связаны с heap/VM.

## 1) Stack
Stack — это память потока (thread):
- каждая функция создаёт stack frame,
- в нём: локальные переменные (маленькие), временные значения, служебные данные,
- освобождение "автоматическое" при выходе из функции.

Свойства:
- очень быстрый аллок/деаллок (движение указателя стека),
- ограниченный размер (stack overflow возможен при глубокой рекурсии/больших локальных массивах),
- отдельный stack на поток.

## 2) Heap
Heap — общий пул динамической памяти процесса:
- `class` объекты и большинство runtime-структур лежат на heap,
- большие буферы (`Array`, `Data`, `String` storage) часто на heap,
- время жизни контролируется ARC/free/malloc.

Свойства:
- аллокации дороже, возможна фрагментация,
- требует управления временем жизни,
- именно здесь чаще всего видны утечки, retain cycles, spikes.

## 3) Static/Global memory
Глобальные и `static` переменные:
- размещаются в data-сегментах процесса,
- живут весь срок жизни приложения (процесса).

Примеры:
- `static let shared = ...` (сам объект может быть на heap, но ссылка — static),
- таблицы метаданных типов, константы.

Важно: `static` переменная хранит значение/ссылку глобально → может продлевать lifetime объектов.

## 4) Code/Text segment
Сегмент кода (`__TEXT` в Mach-O) содержит:
- исполняемый код,
- таблицы символов, строки, константы и т.п. (часть может быть read-only).
Обычно memory-mapped и шарится между процессами для системных библиотек (в зависимости от условий).

## 5) Data сегменты: `.data`, `.bss`, `__const`
- `.data`: инициализированные глобальные/статические переменные.
- `.bss`: неинициализированные (логически нули), ОС выделяет виртуально, физически — по demand.
- `__const`/rodata: константы, часто read-only.

## 6) Виртуальная память и mmap
iOS использует виртуальную память:
- страницы памяти выделяются "виртуально" и подгружаются/выделяются физически при обращении.
- фреймворки и ресурсы могут быть memory-mapped (mmap), что видно в Instruments как VM regions.

## 7) Swift-специфика (интервью-уровень)
- Value-типы (`struct/enum`) могут лежать на stack или inline внутри других объектов.
- Однако value types **могут оказаться на heap** в нескольких случаях:
  - при упаковке в existential контейнер (`any P`) — если значение не помещается в 3-словный буфер контейнера, происходит boxing и значение переезжает на heap,
  - при захвате closure — если closure создаёт capture context на heap, значения захваченных переменных хранятся внутри него,
  - как stored property объекта-класса — само поле является частью heap-объекта.
- Это частая причина неожиданных heap-аллокаций в Swift при работе с протоколами и замыканиями.
- `Copy-on-write` делает так, что копируется не весь буфер, пока нет мутации.

**Самопроверка**
- Оспорено: "все структуры на стеке, все классы на куче" — классы почти всегда heap, а структуры могут быть и на heap (boxing в existential, захват closure, хранение внутри класса).
- Оспорено: "value types всегда дешевле class, потому что на стеке" — при боксинге или захвате closure value type уходит на heap и теряет это преимущество.
- Неочевидно: точные Mach-O секции/VM regions зависят от билда и загрузчика; на собесе важно объяснить модель (stack/heap/text/data) и последствия.
- Источники: Apple docs по Virtual Memory, Mach-O/segments overview, материалы по Swift memory model и CoW, existential boxing, Instruments (VM Tracker).

### Q44 (🔴): Можешь рассказать про retain cycle и как его находить?

**Кратко**
- Retain cycle — цикл в графе **сильных ссылок**, из-за которого ARC не может освободить объекты (strong count не падает до 0).
- Самые частые источники:
  - `self` ↔ closure (closure хранится в `self` и захватывает `self` strongly),
  - parent ↔ child (двунаправленные strong свойства),
  - `Timer`/`CADisplayLink` target циклы,
  - подписки (Combine/Rx), async tasks, делегаты, кеши.
- Находят через:
  - `deinit` логирование,
  - Xcode Memory Graph,
  - Instruments (Leaks/Allocations),
  - анализ цепочки “кто держит кого”.

**Развёрнуто**
## 1) Что именно происходит
ARC освобождает объект, когда сильных ссылок на него 0. В retain cycle сильных ссылок по кругу остаётся > 0, поэтому:
- `deinit` не вызывается,
- память не освобождается,
- часто растёт потребление памяти и количество живых объектов.

## 2) Классические примеры
### A) Два объекта
```swift
final class A { var b: B?; deinit { print("A deinit") } }
final class B { var a: A?; deinit { print("B deinit") } }

var a: A? = A()
var b: B? = B()
a?.b = b
b?.a = a

a = nil
b = nil
// deinit не будет, если обе ссылки strong
```
Лечение: одна сторона `weak`/`unowned` (обычно обратная ссылка).

### B) Closure как property
```swift
final class VC {
    var onTap: (() -> Void)?
    func bind() {
        onTap = { self.doWork() } // ❌ self удерживается closure
    }
    func doWork() {}
    deinit { print("VC deinit") }
}
```
Лечение:
```swift
onTap = { [weak self] in self?.doWork() }
```

### C) Timer/DisplayLink
Если объект держит timer, а timer держит объект как target — цикл.
Лечение: `invalidate()` + weak proxy или блоки с weak self.

## 3) Как находить retain cycle системно
### Шаг 1: поставить “детекторы”
- Добавить `deinit` лог в подозреваемый класс.
- Воспроизвести сценарий (push/pop VC, показать/закрыть экран).

Если `deinit` не сработал — объект удерживается.

### Шаг 2: Xcode Memory Graph
- Debug → View Memory Graph.
- Найти объект (часто VC), посмотреть “Retained By”.
- Пройти по ссылкам, найти цикл.

### Шаг 3: Instruments
- Allocations: увидеть, что количество объектов растёт и не падает.
- Leaks: иногда подсветит утечки (но retain cycle не всегда “leak” на уровне malloc, просто долгоживущие объекты).
- VM Tracker: полезен для больших буферов (изображения/данные).

### Шаг 4: локализовать владельца
Спросить себя:
- кто должен владеть объектом?
- где ownership должен завершаться?
- что держит объект после ухода со сцены?

Типовые “держатели”:
- singleton/cache,
- subscription bag,
- task/operation queue,
- timer/notification tokens,
- closure property в другом объекте.

## 4) Как чинить (принципы)
- Правильный граф владения: owner → child strong; child → owner weak/unowned.
- Для callbacks/async: `[weak self]` по умолчанию, но подумать, не нужен ли другой владелец задачи (сервис/координатор).
- Инвалидировать/отменять долгоживущие штуки:
  - `timer.invalidate()`,
  - `task.cancel()`,
  - `cancellable.cancel()`.

**Самопроверка**
- Оспорено: “retain cycle = утечка памяти всегда” — это утечка времени жизни: объект живёт бесконечно, но может быть освобождён при разрыве цикла.
- Неочевидно: иногда объект удерживается не циклом, а валидным владельцем (кэш/синглтон/таск); важно различать “cycle” и “legit long-lived”.
- Источники: Xcode Memory Graph docs, Instruments (Allocations/Leaks), Swift ARC docs, Apple docs по Timer/Combine/Concurrency.

### Q45 (🔴): Как искать retain cycle на практике: Instruments / Memory Graph / стратегия локализации?

**Кратко**
- Начни с гипотезы “объект должен был умереть, но не умер” → ставь `deinit` и воспроизводи сценарий.
- **Memory Graph** — лучший быстрый инструмент: показывает, кто удерживает объект (Retained By) и позволяет увидеть цикл.
- **Instruments**:
  - Allocations — рост/непадение количества объектов,
  - Leaks — иногда ловит утечки, но retain cycle может не быть “leak” в терминах malloc,
  - VM Tracker — если проблема в больших буферах/мэппингах.
- Стратегия локализации: бинарный поиск по владельцам (подписки, timers, notifications, tasks, caches), временно отключая/обнуляя их, пока `deinit` не начнёт срабатывать.

**Развёрнуто**
## 1) Золотое правило: измерять, а не гадать
Если retain cycle есть, это проявляется так:
- объект не деинициализируется после ожидаемого момента (например, pop VC),
- память/количество объектов растут или не падают.

Первое, что делаем:
```swift
deinit { print("Deinit \(Self.self)") }
```

## 2) Memory Graph (Xcode) — самый быстрый путь к “кто держит”
### Как работать
1) Запусти приложение в Debug.
2) Воспроизведи сценарий: открой экран → закрой.
3) Debug → View Memory Graph.
4) Найди нужный объект (часто `UIViewController`).
5) Открой “Retained By” и пройди по ссылкам.

### Что искать
- сильные ссылки (solid arrows),
- цепочки `self -> something -> self`,
- property closures, timers, subscriptions, caches.

Memory Graph часто сразу покажет “точку удержания”: например, `__NSMallocBlock__` (closure), `NSTimer`, `AnyCancellable`, `NotificationCenter` token.

## 3) Instruments: когда Memory Graph недостаточно
### Allocations
Используй, чтобы:
- увидеть рост количества объектов конкретного класса,
- понять “когда” они создаются и не освобождаются,
- сравнить до/после фикса.

### Leaks
Полезно, если есть реальная утечка malloc (потерянные указатели).
Но retain cycle может не появиться как leak, потому что память достижима (просто “никогда не отпускается”).

### VM Tracker
Если утечка/рост связаны с:
- `Data`/images,
- mmap regions,
- кешами и буферами.

## 4) Стратегия локализации (workflow)
### Шаг A: определить “подозреваемых владельцев”
Когда VC не умирает, почти всегда виновато одно из:
- closure property (колбэки в view/manager),
- timer/displaylink,
- notification observer/token,
- Combine/Rx subscriptions,
- async tasks/operations,
- singleton/cache/DI-container,
- delegate, который случайно strong.

### Шаг B: бинарный поиск по удержаниям
Идея: временно “вырезать” целые классы удержаний:
- закомментировать подписки,
- `invalidate()` timers,
- `cancel()` tasks,
- обнулить closures,
- убрать добавление в кэш,
и проверять, появился ли `deinit`.

Как только `deinit` начинает срабатывать — у тебя “виновник” локализован.

### Шаг C: отследить конкретную ссылку
Когда найден виновный механизм:
- посмотреть, кто держит его,
- кто он держит дальше,
- где должна быть точка разрыва (`weak`, cancel, invalidate, removal).

## 5) Типовые “паттерны удержания” и как их распознать
- `__NSMallocBlock__` → closure удерживает `self`.
- `AnyCancellable` в property `Set` → подписка держит цепочку.
- `NSTimer`/`CADisplayLink` → target/selector.
- `NotificationCenter` → observer/token/closure.
- `Swift.Task`/continuation → async удержание.

**Самопроверка**
- Оспорено: “Leaks инструмент всегда показывает retain cycle” — нет, cycle часто не является leak для Instruments, потому что память достижима.
- Неочевидно: в Debug сборке поведение/оптимизации отличаются; но для lifetime-багов Debug обычно даже удобнее, потому что Memory Graph доступен.
- Источники: документация Xcode Memory Graph, Instruments user guide (Allocations/Leaks/VM Tracker), Swift ARC/Concurrency/Combine docs.

### Q46 (🔴): Как ARC взаимодействует с closures и async-задачами (`Task`, `async let`): где возникают неожиданные удержания?

**Кратко**
- Closure по умолчанию **сильно захватывает** reference-типы (включая `self`) → может продлить lifetime и создать retain cycle.
- Async-задачи (`Task { ... }`) удерживают всё, что захвачено в их замыкании, **пока задача не завершится или не будет отменена** (но отмена не гарантирует немедленного освобождения, если код не проверяет cancellation и не выходит).
- `async let` при отсутствии точки `await` (ранний throw/выход) **автоматически отменяет** незавершённые дочерние задачи — это гарантия structured concurrency.
- Частые источники "неожиданных удержаний":
  - `self` захвачен strongly в `Task`/completion/Combine/Rx,
  - бесконечные/долгие задачи (polling, `while true`, long await цепочки),
  - хранение `Task` в свойстве `self` + strong capture `self` внутри → цикл,
  - actor/isolated контекст и очереди, которые продлевают жизнь объектов через захваты.

**Развёрнуто**
## 1) Closures и ARC: базовая модель
Если closure использует `self`:
- по умолчанию `self` захватывается **strong**.

```swift
final class VC {
    var onDone: (() -> Void)?

    func bind() {
        onDone = {
            self.finish()   // ❌ self captured strongly
        }
    }

    func finish() {}
}
```

Если `onDone` хранится в `self`, получаем цикл:
`self -> onDone(closure) -> self`.

Лечение: `[weak self]` или перенос владения.

## 2) `Task {}` удерживает захваты до завершения задачи
```swift
final class VC {
    func load() {
        Task {
            await self.fetchAndUpdate() // ❌ self captured strongly
        }
    }

    func fetchAndUpdate() async {}
}
```

Даже если VC "закрыли", задача может продолжать жить и удерживать `self`.
Это не обязательно цикл, но это "lifetime prolongation" — объект живёт дольше, чем ожидают.

### Правильный шаблон (часто)
```swift
Task { [weak self] in
    guard let self else { return }
    await self.fetchAndUpdate()
}
```

## 3) Retain cycle через хранение Task в `self`
Опасный паттерн:
```swift
final class VC {
    var task: Task<Void, Never>?

    func start() {
        task = Task {
            await self.runLoop() // ❌ self strong, task strong
        }
    }

    func runLoop() async {
        while true {
            try? await Task.sleep(nanoseconds: 1_000_000_000)
        }
    }

    deinit { print("deinit") }
}
```

Цикл:
- `self.task` удерживает `Task`,
- `Task` удерживает closure,
- closure удерживает `self`.

Лечения:
- `[weak self]` в Task,
- `task?.cancel()` и выйти из цикла,
- не хранить task в `self`, если не нужно, или хранить в объекте-владельце другого уровня.

## 4) Отмена не всегда освобождает
`task.cancel()`:
- ставит флаг cancellation,
- но если внутри нет `try await`/проверок `Task.isCancelled`, код может продолжать удерживать захваты.

Правильная практика:
- в long-running тасках регулярно проверять cancellation и выходить,
- использовать `try await Task.sleep(...)` (он бросает `CancellationError`),
- избегать бесконечных циклов без точки выхода.

## 5) `async let` и автоматическая отмена (ключевая гарантия)
`async let` запускает дочернюю задачу и удерживает контекст до `await`:
```swift
func f() async {
    async let a = heavy()
    async let b = heavy()
    // пока не await — результаты удерживаются
    _ = await (a, b)
}
```

Если внутри `heavy()` захвачены большие объекты/буферы, пик памяти может быть выше, чем ожидают.

**Важная гарантия structured concurrency**: если функция завершается досрочно (через `throw`, `return` или при отмене родительской задачи) до достижения точки `await`, Swift **автоматически отменяет** все незавершённые `async let` дочерние задачи. Это фундаментальное свойство structured concurrency — дочерние задачи не могут "утечь" за пределы своей области.

```swift
func g() async throws {
    async let a = heavy()
    async let b = heavy()
    throw SomeError()
    // ✅ Swift автоматически отменяет a и b
    // _ = await (a, b) // эта строка никогда не выполнится
}
```

## 6) Где чаще всего ловят баги
- VC стартует Task в `viewDidAppear`, но не отменяет в `viewWillDisappear`.
- Service держит completion closures в массиве "до ответа".
- Combine: `sink { self... }` + `store(in: &cancellables)` в `self` → цикл, если не `[weak self]`.
- Long polling/streaming: задача живёт часами, удерживая граф объектов.

## 7) Практические правила
- Async/callback по умолчанию: `weak self`, если `self` не обязан жить ради выполнения.
- Если обязан — пусть живёт **другой владелец** (координатор/сервис), а не VC.
- Храни `Task` только если реально надо управлять её жизненным циклом, и обязательно отменяй.
- В длинных задачах поддерживай cancellation.
- `async let` безопасен по lifetime (structured), но может создавать пики памяти при больших буферах.

**Самопроверка**
- Оспорено: "Task не влияет на ARC, это просто async" — влияет через захваты: задача держит closure и всё внутри, продлевая lifetime.
- Оспорено: "`async let` может оставлять 'висячие' задачи при throw" — нет, structured concurrency гарантирует автоматическую отмену дочерних `async let` при любом досрочном выходе из scope.
- Неочевидно: где граница "надо weak self" vs "надо удержать self" — это продуктовая семантика; часто правильнее переносить работу в слой, который не связан с жизнью VC.

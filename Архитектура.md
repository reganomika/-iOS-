## Архитектура и дизайн системы iOS-приложения

### Q119 (🟢): Что такое архитектура приложения и чем она отличается от “структуры папок”?

**Кратко**
- **Архитектура** — это набор **правил и границ ответственности**: какие компоненты существуют, кто от кого зависит, где живут решения (бизнес-логика, данные, навигация), как течёт data/control flow, какие инварианты соблюдаются.
- **Структура папок** — это способ разложить файлы в проекте. Она может отражать архитектуру, но сама по себе **не гарантирует** ни правильных зависимостей, ни тестируемости, ни масштабируемости.

**Развёрнуто**
## 1) Что именно включает “архитектура”
Архитектура отвечает на вопросы:
- Какие **слои/модули** есть (например UI → Domain → Data)?
- Кто имеет право знать о ком (**направление зависимостей**)?
- Где принимаются решения:
  - бизнес-правила (Domain/UseCases),
  - отображение состояния (UI/Presentation),
  - сетевые/локальные детали (Data/Infrastructure)?
- Как проходит запрос:
  - UI событие → use case → repository → API/DB → результат → маппинг → состояние → UI.
- Как обрабатываются “сквозные” штуки:
  - логирование, аналитика, конфиг, ошибки, авторизация.
- Как код **эволюционирует**: добавление фичи без переписывания старых.

## 2) Почему “папки” не равны архитектуре
Можно сделать идеальные папки:
- `ViewModels/`
- `Services/`
- `Managers/`
…и всё равно получить:
- циклические зависимости,
- бизнес-логику в UI,
- сервисы, которые тащат UIKit,
- невозможность мокать зависимости.

Папки — это **косметика**, архитектура — **инварианты**.

## 3) Что значит “архитектура работает”
Набор признаков, что архитектура действительно есть:
- Можно заменить транспорт (REST → GraphQL) **без переписывания UI**.
- Можно тестировать бизнес-правила без запуска приложения.
- Команда понимает, куда класть код, и в PR легко проверять “попал ли в слой”.
- Новая фича добавляется “по шаблону”, а не через копипасту.

## 4) Минимальный пример архитектурных правил (на словах)
Например:
- UI знает только про `UseCase`/`Repository` интерфейсы.
- Data слой реализует репозитории и знает про `URLSession`, `Realm`, кеши.
- Domain слой не знает про UIKit/Realm/URLSession и содержит правила и модели домена.

Визуально:
```
UI (View/VC/VM)  ->  Domain (UseCases, Models, Protocols)  ->  Data (API, DB, Cache)
         ^                                                             |
         |---------------------- зависимость только по протоколам ------|
```

## 5) Частая ловушка на собесе
“У нас MVVM, значит архитектура есть”.
MVVM — это форма организации presentation-слоя, но без:
- явных границ слоёв,
- правил зависимостей,
- стратегии навигации/данных/ошибок,
получается просто “MVVM с God-VM”.

**Самопроверка**
- Оспорено: “архитектура = папки/паттерн” — нет, архитектура = границы + зависимости + инварианты.
- Неочевидно: хороший маркер архитектуры — лёгкость подмены деталей (сеть/хранилище) и тестируемость домена.
- Источники, которые стоит освежить: Apple/WWDC про модульность и separation of concerns, практики Clean Architecture (слои/направление зависимостей), гайды по тестируемости и DI в Swift.

### Q120 (🟢): Какие проблемы решает разделение на слои (UI / Domain / Data)?

**Кратко**
- Слои нужны, чтобы управлять **зависимостями и изменениями**:
  - UI меняется часто (дизайн, состояния),
  - Data меняется часто (API, формат, кеши),
  - Domain должен быть стабильным (правила, модели, use cases).
- Разделение снижает:
  - связность,
  - риск “потянуть UIKit в сервисы”,
  - стоимость изменений и тестирования.
- Цель — чтобы детали (сеть/БД/фреймворки) не протекали в бизнес-логику и UI.

**Развёрнуто**
## 1) Что считается “слоем” в нормальной модели
### UI / Presentation layer
- отображение состояния,
- обработка пользовательских событий,
- маппинг доменных ошибок/состояний в UI.
Тут живут: VC/Views, ViewModels/Presenters, coordinators/routers (часто тоже здесь).

### Domain layer
- бизнес-правила,
- use cases / interactor’ы,
- доменные модели и контракты (протоколы репозиториев).
Не знает про UIKit/URLSession/Realm.

### Data / Infrastructure layer
- реализация репозиториев,
- API-клиенты, маппинг DTO,
- кеш, БД, файловая система,
- политика ретраев/таймаутов/дедупликации.

## 2) Какие проблемы реально решаются
### A) Управление изменениями
- Меняем API → правим Data слой, но Domain/UI остаются стабильными (если контракт не изменился).
- Меняем UI → не трогаем бизнес-правила.
- Меняем хранилище (Realm → CoreData/SQLite) → не трогаем Domain/UI.

Это главный practical win.

### B) Тестируемость
- Domain тестируется без UI и без сети.
- Data тестируется как интеграция (mock server/DB).
- UI тестируется с mock use cases/repositories.

### C) Контроль зависимостей и “грязи”
Без слоёв появляются:
- `URLSession` вызовы из ViewModel/VC,
- `Realm` объекты, которые утекли в UI,
- `DispatchQueue.main.async` повсюду,
- “менеджеры” которые знают обо всём.

Слои вводят “ограждения”.

### D) Параллельная разработка
Разные люди могут работать:
- UI над состояниями и экраном,
- Data над API,
- Domain над правилами,
не блокируя друг друга.

## 3) Нюанс: слои не должны быть “три папки”
Типичная ошибка:
- сделать папки UI/Domain/Data,
- но разрешить любые импорты между ними.

Слои работают только если соблюдено правило:
- зависимости направлены в одну сторону,
- детали зависят от абстракций (протоколов).

## 4) Критерии правильного разреза
- Domain не импортирует UIKit/Foundation-networking specifics.
- UI не знает про DTO/DB schemas.
- Data может импортировать всё, но общается с Domain через протоколы.

## 5) Ловушка: “слишком чисто”
Можно перегнуть:
- 10 абстракций на один экран,
- “use case на каждый тап”.
Слои должны снижать стоимость изменений, а не умножать ceremony.
Правило: добавляй уровень, когда есть реальная вариативность/сложность.

**Самопроверка**
- Оспорено: “слои = про красоту и порядок” — нет, это про контроль изменений и зависимостей.
- Неочевидно: слои бесполезны без enforcement (зависимости/правила модулей), иначе это просто папки.
- Источники: Clean Architecture (границы и направление зависимостей), практики modularization в iOS, гайды по тестируемости слоёв (unit/integration).

### Q121 (🟢): Что такое “границы ответственности” и почему это важнее паттерна (MVC/MVVM/VIPER)?

**Кратко**
- **Границы ответственности** — это чёткое разделение “кто за что отвечает” и “кто о ком может знать”.
- Паттерн (MVC/MVVM/VIPER) — лишь один из способов организовать код, но без границ ты получишь:
  - бизнес-логику в UI,
  - сервисы, зависящие от UIKit,
  - “God Object” (VC/VM/Interactor).
- Границы важнее, потому что они определяют:
  - тестируемость,
  - заменяемость компонентов,
  - масштабирование команды,
  - устойчивость к изменениям.

**Развёрнуто**
## 1) Что значит “границы” на практике
У каждого компонента есть:
- **входы** (что он принимает),
- **выходы** (что он отдаёт),
- **инварианты** (что он гарантирует),
- и ограничения на зависимости.

Примеры границ:
- View/VC: не ходит в сеть и не знает о DTO.
- ViewModel/Presenter: не импортирует UIKit (или минимально), отдаёт state/outputs.
- UseCase: не знает про UI, только про доменные модели/контракты.
- Repository: контракт в Domain, реализация в Data.
- API client: знает только про transport и DTO.

## 2) Почему паттерны без границ не работают
### “Мы на MVVM”
Но ViewModel:
- хранит токены,
- делает запросы,
- парсит JSON,
- маппит ошибки,
- кеширует,
- и ещё знает про navigation.
Это не MVVM, это God-VM.

### “Мы на VIPER”
Но Interactor:
- трогает UIKit,
- Entity = DTO,
- Router делает бизнес-решения.
Это тоже “название”, а не архитектура.

Паттерн помогает, если границы соблюдаются.

## 3) Что дают границы senior’у (и команде)
- Можно менять UI без переписывания домена.
- Можно менять API/хранилище без переписывания экрана.
- Появляется единый “контракт” в PR: куда класть код.
- Тесты становятся естественными:
  - домен — unit,
  - data — integration,
  - UI — snapshot/UI.

## 4) Как формулировать границы в проекте
Лучший формат — короткие правила:
- UI не импортирует Data.
- Domain не импортирует UIKit/Realm.
- Навигация не в ViewModel (или наоборот, но выбрано и одинаково).
- Все side effects (сеть/диск) — только через интерфейсы.
- Ошибки маппятся на границе (например, Data → Domain).

## 5) Типовой вопрос на собесе: “Где бы ты положил эту логику?”
Твой ответ должен опираться на границы:
- Это бизнес-правило? → Domain/use case.
- Это маппинг из API? → Data/mapper.
- Это форматирование под UI? → Presentation.
- Это навигация? → Coordinator/Router.
- Это кэш/ретраи/дедуп? → Data/infrastructure policy.

**Самопроверка**
- Оспорено: “достаточно выбрать MVVM/VIPER” — нет, без границ это только ярлык.
- Неочевидно: границы — это не только “классы”, но и правила зависимостей/импортов; без enforcement границы размываются.
- Источники: Clean Architecture (boundaries, dependency rule), опыт крупных iOS codebases (modularization), гайды по layering и PR-энфорсменту (lint/build rules).

### Q122 (🟢): Чем отличается “модуль” от “слоя”?

**Кратко**
- **Слой** — это логическое разделение ответственности по уровню абстракции (UI/Domain/Data). Он задаёт **направление зависимостей**.
- **Модуль** — это единица сборки/поставки/границы кода (Swift Package, framework, target). Он задаёт **физическую границу**: что экспортируется публично, что импортируется.
- Слои отвечают “какие правила”, модули — “как это зафиксировать технически”.

**Развёрнуто**
## 1) Слой = концептуальная архитектурная граница
Слой — это про:
- **уровень абстракции**,
- **правила зависимостей**,
- **куда течёт знание**.

Например:
- UI слой зависит от Domain,
- Data слой реализует Domain-протоколы,
- Domain не зависит ни от UI, ни от Data.

Слой может существовать даже в одном target’е, но тогда он “на честном слове”.

## 2) Модуль = физическая граница и механизм энфорсмента
Модуль даёт:
- отдельный target (компиляция),
- отдельные imports,
- контроль `public/internal`,
- возможность запретить прямые зависимости (через build settings/graph).

То есть модуль — это способ **заставить** соблюдать архитектуру.

## 3) Типичные комбинации
### A) Слои без модулей
- Весь проект одним target’ом, но есть папки UI/Domain/Data.
Плюсы:
- быстро стартовать.
Минусы:
- границы легко нарушаются, потому что любой файл может импортировать что угодно.

### B) Модули без слоёв
- Много targets по фичам, но каждый содержит UI+Data+Domain вперемешку.
Плюсы:
- изоляция фич.
Минусы:
- дублирование логики, нет общего домена/контрактов, тяжело менять инфраструктуру.

### C) Идея “слои × фичи”
Популярный подход:
- Core modules (Domain, Networking, Analytics),
- Feature modules (каждая фича),
и внутри фичи тоже выдерживаются границы (Presentation/Domain/Data локально или через Core).

## 4) Зачем различать на собесе
Если сказать “у нас модульная архитектура”, могут спросить:
- по какому принципу режете (слои или фичи)?
- как не допускаете циклов?
- что лежит в публичном API модулей?
- где живут модели и протоколы?
Тут важно уверенно развести:
- “логика слоёв” vs “механика модулей”.

## 5) Практическое правило
- Слои задают дизайн зависимости,
- Модули помогают это enforce’ить и масштабировать сборку/команду.

**Самопроверка**
- Оспорено: “модуль = слой” — нет: слой логический, модуль физический.
- Неочевидно: можно иметь один слой в нескольких модулях (например, Domain разбит на пакеты) и одну фичу, растянутую по слоям; это разные оси.
- Источники: практики modularization iOS (targets/SPM), Clean Architecture dependency rule, гайды по dependency graph и циклам.

### Q123 (🟢): Что такое dependency inversion и зачем он нужен в iOS?

**Кратко**
- Dependency inversion (DIP) — принцип: **высокоуровневые политики (бизнес-логика) не зависят от низкоуровневых деталей (сеть/БД/UI)**; оба зависят от **абстракций**.
- В iOS это обычно означает:
  - домен/проектная логика зависит от протоколов,
  - инфраструктура (URLSession/DB) реализует эти протоколы.
- Зачем:
  - тестируемость (моки),
  - заменяемость (смена API/DB),
  - снижение связности,
  - стабильный domain при частых изменениях UI/Data.

**Развёрнуто**
## 1) Что “инвертируется”
Интуитивная (плохая) зависимость:
- UseCase/VM напрямую вызывает `URLSession`, `Realm`, `FileManager`.

Тогда высокоуровневый код знает:
- детали транспорта,
- формат DTO,
- схемы хранения.

При DIP:
- high-level код зависит от контракта:
  - `UserRepository`, `AuthService`, `PaymentsGateway` (протоколы),
- low-level код подставляется реализацией:
  - `RemoteUserRepository(URLSession...)`,
  - `RealmUserRepository(...)`.

## 2) Почему это особенно важно в iOS
iOS код часто сталкивается с:
- UI-изменениями,
- A/B/feature flags,
- сменой backend API,
- offline/кеш,
- тестами под много устройств.

Без DIP обычно получается:
- “сеть в ViewModel”,
- сложно мокать,
- сложно переиспользовать бизнес-логику.

## 3) Как выглядит минимально (идея без архитектурной религии)
Domain:
```swift
protocol UserRepository {
    func loadUser(id: String) async throws -> User
}
```

Data:
```swift
final class RemoteUserRepository: UserRepository {
    func loadUser(id: String) async throws -> User { /* URLSession + DTO mapping */ }
}
```

UseCase/VM принимает `UserRepository`:
- не знает, remote оно или cache.

## 4) Частая ошибка: “у нас DIP, потому что протоколы”
Если протокол объявлен рядом с реализацией и:
- протокол экспортирует детали инфраструктуры (DTO, URLRequest),
то DIP формально есть, но смысл потерян.

Правильная абстракция:
- выражает доменную потребность,
- не тащит детали транспорта.

## 5) Цена DIP
- больше сущностей (протоколы/моки),
- риск “протокол ради протокола”.
DIP оправдан, когда есть:
- вариативность реализаций,
- необходимость тестов,
- рост проекта/команды.

**Самопроверка**
- Оспорено: “DIP = DI” — нет: DIP про направление зависимостей (политики → абстракции), DI — техника внедрения.
- Неочевидно: ключ DIP — качественная абстракция; протокол, протекающий DTO/URLSession, нарушает идею.
- Источники: SOLID (DIP), Clean Architecture dependency rule, практики протокольных границ в Swift (repositories/gateways).

### Q124 (🟢): Что такое dependency injection и какие есть способы внедрения зависимостей (инициализатор, property, service locator)?

**Кратко**
- Dependency Injection (DI) — способ передать объекту его зависимости **снаружи**, а не создавать их внутри.
- Основные способы:
  - **Constructor injection** (через init) — предпочтительный.
  - **Property injection** (через свойства) — когда init неудобен, но риск “не установили”.
  - **Method/parameter injection** — зависимость передаётся в конкретный метод.
  - **Service Locator** — объект сам запрашивает зависимость из контейнера; удобно, но скрывает зависимости и усложняет тесты.

**Развёрнуто**
## 1) Зачем DI вообще нужен
Без DI класс делает:
- `let api = APIClient()` внутри,
и ты получаешь:
- жёсткую связанность,
- невозможность подменить зависимость в тестах,
- сложность расширений (кеш, ретраи).

DI позволяет:
- мокать/подменять,
- конфигурировать на уровне composition root,
- контролировать lifetime (singleton/per-screen/per-request).

## 2) Constructor injection — базовый “правильный” вариант
Плюсы:
- зависимости видны в сигнатуре,
- объект всегда валиден после init,
- проще тестировать.

```swift
final class ProfileViewModel {
    private let repo: UserRepository
    init(repo: UserRepository) { self.repo = repo }
}
```

Минусы:
- длинные init’ы при большом числе зависимостей (это сигнал к рефакторингу, а не повод уходить в locator).

## 3) Property injection — компромисс
Используют, когда:
- объект создаётся системой (например, storyboard),
- или зависимость циклична (чаще признак плохого дизайна).

Минусы:
- можно забыть установить → runtime crash/неявные баги,
- объект какое-то время “полуинициализирован”.

Частичная защита:
- делать зависимость required перед использованием,
- или использовать фабрику, чтобы не было “пустого” состояния.

## 4) Method/parameter injection
Передавать зависимость только туда, где она нужна:
```swift
func load(repo: UserRepository) async throws -> User { ... }
```
Плюс:
- минимальная область видимости зависимости.
Минус:
- может засорять сигнатуры, если использовать везде.

## 5) Service Locator — удобно, но опасно
```swift
final class ProfileViewModel {
    private let repo: UserRepository = Container.shared.resolve()
}
```
Плюсы:
- быстро подключить, меньше параметров.
Минусы:
- зависимости скрыты (не видно по init),
- сложнее тестировать (нужно подменять глобальный контейнер),
- легко получить “магические” singletons и неуправляемые lifetimes.

Service locator часто превращается в анти-паттерн, если им закрывают архитектурные проблемы.

## 6) Composition Root
Здоровая практика:
- все конкретные зависимости собираются в одном месте (App/Scene/Feature factory),
- дальше внутрь фичи проталкиваются через init.

Это снижает “DI расползся по всему коду”.

## 7) Как отвечать на собесе
- “Предпочитаю constructor injection; property — только когда объект создаётся системой; locator использую осторожно, потому что он скрывает зависимости.”
- “Если init стал огромным — это сигнал: компонент делает слишком много, надо дробить.”

**Самопроверка**
- Оспорено: “DI = контейнер” — нет, DI возможен без контейнера; контейнер — лишь инструмент.
- Неочевидно: service locator часто воспринимается как DI, но он наоборот прячет зависимости; это важно уметь проговорить.
- Источники: SOLID/DI, практики composition root, примеры DI без фреймворков в iOS, обсуждения анти-паттерна service locator.

### Q125 (🟢): В чём смысл протоколов на границах слоёв?

**Кратко**
- Протоколы на границах слоёв фиксируют **контракт**, позволяя:
  - домену/презентации не зависеть от деталей (сети/БД),
  - подменять реализации (remote/cache/mock),
  - тестировать слой изолированно.
- Протокол — это не “абстракция ради абстракции”, а способ выразить потребность слоя более высокого уровня.

**Развёрнуто**
## 1) Что такое “граница слоя”
Граница — место, где высокоуровневый код должен сказать:
- “мне нужно получить/сохранить X”,
но не должен говорить:
- “сходи по URL, распарсь JSON, положи в Realm”.

Поэтому контракт на границе описывает:
- операции,
- доменные модели,
- доменные ошибки (или их категории).

## 2) Пример границы: Domain ↔ Data
Domain объявляет:
```swift
protocol UserRepository {
    func user(id: String) async throws -> User
    func save(_ user: User) async throws
}
```

Data предоставляет реализации:
- `RemoteUserRepository`,
- `CachedUserRepository`,
- `MockUserRepository`.

UI/Domain не знают, какая реализация сейчас используется.

## 3) Что дают протоколы в реальности
### A) Заменяемость деталей
- REST → GraphQL,
- Realm → CoreData,
- URLSession → WebSocket,
— высокоуровневые слои не должны “переехать”.

### B) Тестируемость
- Domain use case тестируется с мок-репозиторием.
- UI VM тестируется с мок-use case/репозиторием.

### C) Снижение связности
Если UI импортирует конкретный `APIClient`:
- он знает про сеть и DTO,
- изменения в API “бьют” по UI.

С протоколом:
- UI зависит от интерфейса, который меняется реже.

## 4) Главная ошибка: “протокол, который протекает деталями”
Плохие признаки:
- протокол возвращает `URLRequest`, `Data`, `RealmObject`, DTO,
- протокол требует “endpoint”/“headers” на уровне домена.

Такой протокол формально абстракция, но смысл DIP ломается: деталь протекла вверх.

Хороший протокол:
- возвращает доменную модель (`User`, `Order`),
- принимает доменные параметры,
- скрывает транспорт/формат.

## 5) Где располагать протоколы
Часто лучше, чтобы контракт жил:
- в более высоком слое (Domain), потому что он выражает потребность,
а реализация — в Data.

Это естественная инверсия зависимостей.

## 6) Цена и критерий “нужно ли”
Не нужно делать протоколы “на всё”.
Оправдано, когда:
- есть вариативность (remote/cache/mock),
- нужно тестирование,
- ожидаются изменения деталей.

Если компонент точно один и не будет меняться:
- протокол может быть лишним.

**Самопроверка**
- Оспорено: “протоколы нужны всегда” — нет, они должны окупать сложность.
- Неочевидно: правильное место протокола — там, где формулируется потребность (обычно в домене), а не рядом с реализацией.
- Источники: DIP/Clean Architecture, практики repository pattern, guidelines “design protocols around needs, not implementations”.

### Q126 (🟢): Что такое “use case / interactor” и когда он оправдан?

**Кратко**
- Use case (interactor) — объект/функция, которая реализует **конкретный сценарий пользователя** (business action): “загрузить профиль”, “оформить заказ”, “обновить подписку”.
- Он сидит между UI/Presentation и Data:
  - принимает намерение (input),
  - вызывает репозитории/сервисы,
  - применяет бизнес-правила,
  - возвращает результат (output) или ошибку.
- Оправдан, когда:
  - сценарии нетривиальны,
  - бизнес-логика должна быть переиспользуемой,
  - нужно тестировать правила отдельно от UI.

**Развёрнуто**
## 1) Зачем нужен use case, если есть ViewModel/Service?
Без use case часто появляется:
- бизнес-правила в ViewModel,
- сетевые детали в ViewModel,
- повтор сценариев в нескольких экранах.

Use case выносит “политику”:
- что считаем валидным,
- как обрабатываем ошибки,
- когда делаем ретрай/кеш,
- как склеиваем несколько источников.

## 2) Типовая структура
- `LoadProfileUseCase`
- `UpdateUserNameUseCase`
- `PurchaseSubscriptionUseCase`

Внутри:
- валидация input,
- вызовы зависимостей (репозитории),
- маппинг/агрегация,
- бизнес-решения (например, “если токен протух — рефреш”).

UI видит:
- простую операцию.

## 3) Когда use case точно полезен
- Сценарий затрагивает несколько репозиториев (API + кеш + аналитика).
- Есть правила/валидации (пороговые значения, ограничения, политики).
- Один сценарий используется в нескольких местах (экран + виджет + фон).
- Нужны unit-тесты бизнес-правил.
- Нужно разгрузить ViewModel, чтобы она была про presentation, а не про домен.

## 4) Когда use case может быть лишним
- Экран делает один простой запрос без правил.
- Приложение маленькое и не растёт.
- Сценарий не переиспользуется, и бизнес-правил почти нет.

В таких случаях use case добавит ceremony:
- больше файлов,
- больше абстракций,
без ощутимой выгоды.

## 5) Как не скатиться в “use case на каждый чих”
Плохой знак:
- use case = тонкая прокладка “repo.get()”.
Правило:
- use case должен добавлять ценность (правила/оркестрация), иначе держи логику проще.

## 6) Хорошая формулировка на собесе
“Use case — это unit бизнес-логики, выражающий действие пользователя. Я выношу туда сценарии с правилами/оркестрацией, чтобы ViewModel оставалась про состояние UI. Но не делаю use case ради абстракции, если это один простой запрос.”

**Самопроверка**
- Оспорено: “use case нужен всегда” — нет, это инструмент для сложности/переиспользования, иначе лишний слой.
- Неочевидно: граница между use case и ViewModel — это ‘business rules vs presentation rules’; важно уметь разделять.
- Источники: Clean Architecture (use cases as application-specific business rules), практики “thin VM / fat domain”, unit-тестирование сценариев.

### Q127 (🟢): Что такое repository и чем он отличается от service / gateway?

**Кратко**
- **Repository** — абстракция доступа к данным домена: “дай/сохрани `User`”. Он скрывает источник (API/DB/cache) и возвращает **доменные модели**.
- **Service** — более общий термин. Часто это:
  - инфраструктурная штука (например, `AnalyticsService`, `PushService`),
  - или доменный сервис, если логика не помещается в entity/use case.
- **Gateway** (в Clean Architecture) — адаптер на границе: интерфейс, через который use case общается с внешним миром (API, DB, платежи). По сути, repository — частный случай gateway для данных.

**Развёрнуто**
## 1) Repository: смысл и границы
Repository отвечает на вопросы:
- какие данные нужны домену,
- как ими оперировать,
не раскрывая:
- откуда они пришли,
- как кешируются,
- какие DTO/таблицы/эндпоинты используются.

Главное:
- repository говорит на языке домена (`User`, `Order`), а не на языке транспорта.

## 2) Что внутри repository (обычно)
- выбор источника: кеш vs сеть,
- политика обновления: stale-while-revalidate,
- маппинг DTO ↔ domain,
- дедупликация запросов,
- сохранение в локальное хранилище.

При этом repository не должен:
- знать про UI,
- тащить UIKit,
- держать presentation state.

## 3) Service: почему термин опасен
“Service” часто превращается в свалку:
- `UserService`, который делает всё: сеть, кеш, бизнес-правила, форматирование.

Чтобы избежать:
- либо уточнять назначение (NetworkingService, AnalyticsService),
- либо использовать более конкретные паттерны (Repository, UseCase, Mapper).

Но “service” может быть уместен как:
- доменный сервис (например, `PriceCalculator`, `EligibilityService`),
когда правило не принадлежит одной entity.

## 4) Gateway: взгляд Clean Architecture
Use case зависит от интерфейсов:
- репозиториев (данные),
- платежного шлюза,
- пуш-отправки,
- хранилища токена,
— всё это “gateways”.

Разница чаще терминологическая:
- Gateway шире,
- Repository обычно про хранение/чтение агрегатов домена.

## 5) Как отвечать на собесе без религии
- Repository: “я хочу скрыть источник данных и вернуть доменную модель”.
- Service: “или инфраструктура (analytics), или доменная логика (calculator)”.
- Gateway: “контракт на границе домена и внешнего мира; repository — частный случай”.

## 6) Красные флаги
- repository возвращает DTO/RealmObject → протекают детали data слоя.
- repository принимает `URLRequest` → протекает транспорт.
- “service” делает всё подряд → нужно разрезать на роли.

**Самопроверка**
- Оспорено: “repository = просто сеть” — нет, repository скрывает источники и политики доступа, часто включает кеш/мердж.
- Неочевидно: service — слишком размытый термин; важно уметь переопределить в контексте проекта и не превращать в God-service.
- Источники: repository pattern, Clean Architecture (gateways), практики data layer в iOS (caching, mapping, policies).

### Q128 (🟢): Что такое DTO vs domain model и зачем разделять?

**Кратко**
- **DTO (Data Transfer Object)** — модель для транспорта/хранения: соответствует API/БД схеме, удобна для сериализации.
- **Domain model** — модель предметной области: выражает смысл и инварианты, удобна для бизнес-логики.
- Разделять нужно, чтобы:
  - изменения API/схемы не ломали домен и UI,
  - не тащить optional’ы и “грязные” поля в бизнес-логику,
  - держать инварианты и валидацию в домене.

**Развёрнуто**
## 1) Что не так, если DTO = Domain
Если ты используешь DTO как доменную модель, часто получаешь:
- кучу `Optional`, потому что “API может не прислать”,
- странные нейминги и структуры, продиктованные backend’ом,
- поля для совместимости/версий, не нужные бизнесу,
- leakage деталей (например, `snake_case`, `raw` статусы).

И главное:
- любое изменение API требует массовых правок по приложению.

## 2) Что делает domain model лучше
Domain model:
- минимальна и выражает смысл,
- хранит только нужные поля,
- может держать инварианты:
  - “цена не может быть отрицательной”,
  - “статус заказа ограничен enum”,
  - “email валиден”.

Domain модель должна быть стабильнее, чем DTO.

## 3) Как связаны DTO и domain
Обычно есть слой маппинга:
- `DTO -> Domain` (и иногда `Domain -> DTO`).
Этот слой:
- нормализует данные,
- решает дефолты,
- обрабатывает несовместимости,
- конвертирует raw строки в enum,
- маппит ошибки.

## 4) Где живёт маппинг
Чаще всего:
- в Data слое (потому что это адаптация транспорта к домену),
или в отдельном “Mapping” модуле.

Важно:
- не размазывать маппинг по UI/VM.

## 5) Практический пример “зачем”
API даёт:
- `first_name`, `last_name`, `status: "ok"|"blocked"`, `age: null`.

Domain хочет:
- `User(name: String, status: UserStatus, age: Int?)` или даже без age,
- гарантии, что `status` всегда валиден.

DTO позволяет “принять мир как есть”, Domain — “работать с миром как нужно бизнесу”.

## 6) Цена разделения
- больше кода (DTO + domain + mapper),
- но окупается, когда:
  - API меняется,
  - приложение растёт,
  - важна тестируемость и стабильность домена.

**Самопроверка**
- Оспорено: “разделение DTO/domain — оверинжиниринг” — для небольших приложений может быть, но для long-lived продукта это снижает стоимость изменений.
- Неочевидно: домен — это не “модель экрана”; домен должен быть независимым от API и UI.
- Источники: DDD/clean architecture подходы к моделям, практики mapping DTO↔domain в мобильных клиентах, примеры борьбы с optional-адом.

### Q129 (🟢): Что такое mapper и где он должен жить?

**Кратко**
- Mapper — компонент, который переводит модели между слоями/представлениями:
  - DTO ↔ Domain,
  - DB Entity ↔ Domain,
  - Domain ↔ UI Model (реже и осторожно).
- Его задача — **адаптация формы данных**, а не бизнес-решения UI.
- Обычно mapper живёт:
  - в Data/Infrastructure (для DTO/DB → Domain),
  - иногда отдельным “Mapping” модулем,
  - но не размазан по VC/VM.

**Развёрнуто**
## 1) Зачем нужен mapper как отдельная роль
Без явного mapper’а часто происходит:
- маппинг в `init(domain:)` у UI моделей,
- маппинг внутри репозитория вперемешку с сетью/кешем,
- маппинг в ViewModel “на коленке”.

Это приводит к:
- дублированию,
- рассинхрону при изменениях API,
- сложным тестам,
- “грязным” слоям.

Mapper отделяет:
- транспортную/хранилищную форму данных
от
- доменной модели.

## 2) Что mapper должен делать
- переименовывать/переструктурировать данные,
- конвертировать типы (String → enum, timestamps → Date),
- подставлять дефолты,
- отфильтровывать “мусорные” поля,
- валидировать на уровне адаптации (например, если поле критично и отсутствует — ошибка mapping).

## 3) Что mapper НЕ должен делать
- принимать бизнес-решения уровня продукта (“если premium, то…”),
- лезть в UI (цвета, строки локализации),
- дергать сеть/БД,
- иметь сайд-эффекты.

Если mapper начинает “умничать” — это сигнал, что границы размылись.

## 4) Где его размещать (самое частое)
### DTO ↔ Domain
- Data слой: потому что это адаптация внешнего мира к домену.

### DB Entity ↔ Domain
- тоже Data слой.

### Domain ↔ UI Model
Варианты:
- держать UI Model прямо в presentation и строить его в VM,
- или иметь mapper в presentation.
Главное — не смешивать UI mapping с Data mapping.

## 5) Реализация: static vs instance
- Если mapper чистый и без состояния → часто делают `static func map(...)`.
- Если нужен конфиг/locale/форматтеры → instance + DI.

Важно:
- не тащить в mapper глобальные singleton форматтеров без контроля (иначе тесты/потоки).

## 6) Вопрос “а почему не в init модели?”
Можно, но опасность:
- модель начинает знать про “чужую” модель (DTO),
- возникают нежелательные зависимости слоя.
Лучше:
- domain не должен импортировать DTO типов.

**Самопроверка**
- Оспорено: “mapper = лишний слой” — нет, это чёткая точка адаптации, которая уменьшает ripple-effect изменений API/DB.
- Неочевидно: маппинг Domain↔UI — отдельная история; не стоит смешивать с DTO↔Domain, иначе UI начинает зависеть от data особенностей.
- Источники: Clean Architecture (adapters), практики “mapping layer” в мобильных клиентах, DDD anti-corruption layer идея.

### Q130 (🟢): Чем отличается бизнес-логика от presentation-логики?

**Кратко**
- **Бизнес-логика (domain logic)** — правила предметной области: что допустимо/недопустимо, как считаются значения, какие инварианты должны соблюдаться. Она не зависит от UI.
- **Presentation-логика** — как представить состояние пользователю: форматирование, локализация, выбор текстов/иконок, маппинг доменных состояний в UI-state, управление loading/empty/error.
- Разделение важно, чтобы:
  - бизнес-правила переиспользовались,
  - UI менялся без переписывания домена,
  - тесты были проще и стабильнее.

**Развёрнуто**
## 1) Примеры бизнес-логики
- “Скидка применяется только если сумма > X.”
- “Пользователь не может купить подписку, если аккаунт заблокирован.”
- “Order можно отменить только в статусе pending.”
- “Формула расчёта итоговой цены/налогов.”
- “Правила валидации input (не пусто, формат, ограничения).”

Характеристики:
- выражается через доменные модели/enum,
- не содержит UIKit,
- не знает про строки/цвета.

## 2) Примеры presentation-логики
- Как показать статус:
  - `OrderStatus.pending` → “Ожидаем оплату” + жёлтая иконка.
- Форматирование:
  - `Double` → “1 234,50 ₽” (Locale),
  - `Date` → “Сегодня / Вчера / 12 янв.”
- Сбор UI-state:
  - loading/empty/content/error,
  - выбор плейсхолдеров.

Характеристики:
- зависит от UX/дизайна,
- меняется чаще,
- может жить в VM/Presenter.

## 3) Где проводить границу
Удобное правило:
- Если ответ должен быть одинаковым в:
  - приложении,
  - виджете,
  - фоне,
  - серверной части (в теории),
то это бизнес-логика.

Если ответ зависит от:
- языка,
- дизайна,
- конкретного экрана,
то это presentation.

## 4) Частая ошибка
Смешать:
- “когда можно отменять заказ” (business)
и
- “какой текст и цвет показывать” (presentation)
в одном месте (обычно в VM).

Это делает:
- VM толстым,
- домен “тонким”,
- тесты хрупкими (текст/формат меняется).

## 5) Практический паттерн разделения
- Domain возвращает “чистые” состояния и ошибки:
  - `Result<Order, DomainError>`.
- Presentation слой маппит их:
  - `DomainError.paymentFailed` → `UIErrorState(title, message, action)`.

## 6) Сигнал, что граница нарушена
- Domain возвращает локализованные строки.
- Domain знает про цвета/иконки.
- Use case решает, какой экран открыть.
- VM реализует валидацию с доменными правилами, которые повторяются в других местах.

**Самопроверка**
- Оспорено: “всё можно держать в VM” — можно, но это плохо масштабируется: доменные правила становятся не переиспользуемыми и растёт стоимость изменений.
- Неочевидно: часть “валидации” бывает смешанной: формат (presentation) vs правило (business). Важно уметь разделить.
- Источники: Clean Architecture (domain vs presentation), практики UI state mapping, примеры unit-тестов домена отдельно от UI.

### Q131 (🟢): Как определить, что ViewModel стала “толстой” и что делать?

**Кратко**
- ViewModel “толстая”, если она:
  - делает сеть/БД напрямую,
  - содержит бизнес-правила и оркестрацию нескольких сценариев,
  - управляет кешами/ретраями/дедупликацией,
  - знает про навигацию слишком много,
  - разрослась по зависимостям и стала “мини-приложением”.
- Что делать:
  - вынести бизнес-правила в use cases,
  - вынести data-политики (кеш/ретраи) в repositories/infrastructure,
  - вынести навигацию в coordinator/router,
  - разделить VM на feature sub-VM или state reducers.

**Развёрнуто**
## 1) Признаки “толстой” VM
### A) Слишком много ролей
VM одновременно:
- грузит данные,
- парсит/маппит DTO,
- решает правила,
- форматирует UI,
- хранит глобальное состояние,
- управляет навигацией.

Это нарушение SRP.

### B) “Пахнет” инфраструктурой
- `URLSession`, `Realm`, `FileManager` в VM,
- обработка заголовков/endpoint’ов,
- работа с токенами/refresh,
- retry/backoff.

VM должна говорить на языке “loadProfile”, а не “GET /user”.

### C) Плохая тестируемость
- чтобы протестировать один кейс, надо поднять полмира,
- тесты становятся flaky из-за таймингов/сетевых моков, потому что VM делает слишком много.

### D) Длинные init и сильная связанность
- 10+ зависимостей,
- каждая фича тянет новые сервисы.

Это сигнал, что VM агрегирует слишком много ответственности.

## 2) Типовые “правильные” рефакторы
### A) Вынести сценарии в use cases
VM должна вызывать:
- `LoadProfileUseCase`,
- `UpdateAvatarUseCase`,
а не делать orchestration внутри.

### B) Вынести data-политики в репозитории
Дедуп, кеш, stale-while-revalidate, retry:
- это не задача VM.

### C) Навигацию вынести из VM
- Coordinator/Router может слушать output events:
  - `didTapSettings`,
  - `didFinishOnboarding`.

VM не должна импортировать конкретные VC.

### D) Разделить presentation state
Если VM стала “store”:
- вынести reducer/state machine,
- или поделить VM на подкомпоненты (например, HeaderVM, ListVM).

## 3) Как не перепилить
Ошибка: “разнесли на 20 объектов и стало хуже”.
Правило:
- выноси только то, что:
  - переиспользуется,
  - сложно тестируется внутри VM,
  - относится к другому слою (Domain/Data),
  - растёт и будет расти.

## 4) Практичная формулировка
“ViewModel должна отвечать за преобразование доменных данных в UI state и обработку UI событий. Как только появляются бизнес-правила, кеш, ретраи и orchestration — это сигнал выносить в use cases и repositories.”

**Самопроверка**
- Оспорено: “толстая VM — это нормально, лишь бы работало” — на senior уровне важно думать о цене изменений и тестируемости; толстая VM делает проект хрупким.
- Неочевидно: навигация — частый скрытый источник разрастания VM; перенос в coordinator часто даёт большой выигрыш.
- Источники: MVVM best practices (thin VM), Clean Architecture (use cases), примеры разделения responsibilities и state management.

### Q132 (🟢): Что такое “single source of truth” для состояния?

**Кратко**
- Single Source of Truth (SSOT) — принцип: у каждого факта состояния в системе есть **одно авторитетное место**, из которого остальные части читают/на которое подписываются.
- Цель — убрать рассинхрон:
  - “UI показывает одно, модель хранит другое, кеш третье”.
- SSOT не означает “всё в одном глобальном синглтоне” — это про **единственность владения**, а не про глобальность.

**Развёрнуто**
## 1) Зачем SSOT нужен
Без SSOT обычно появляются баги:
- статус загрузки живёт и в VC, и в VM, и в сервисе,
- список элементов обновили в одном месте, но не в другом,
- одно событие приводит к разным представлениям данных на разных экранах.

SSOT снижает класс багов “рассинхронизация”.

## 2) Как выглядит SSOT на разных уровнях
### Внутри экрана
- VM владеет `State` (loading/content/error),
- View читает state и рендерит.
View не хранит “вторую копию” данных.

### Внутри фичи
- Feature store/VM владеет состоянием фичи (например, корзина),
- другие экраны читают из этого источника.

### Внутри приложения
- Состояние сессии/авторизации хранится в SessionStore (или actor/store),
- UI подписывается на изменения.

## 3) SSOT ≠ “одна модель для всего”
Частая ошибка:
- пытаться сделать одну гигантскую модель состояния приложения.
Это приводит к:
- сильной связанности,
- огромным диффам,
- тяжёлой поддержке.

SSOT лучше делать по доменам/фичам:
- один источник на область ответственности.

## 4) SSOT и кеши
Важно различать:
- источник истины для UI (например, локальная БД),
- vs источник истины для “мира” (сервер).

Offline-first часто делает SSOT UI = локальная БД, а сервер — источник синка.
Это нормальная модель, если она чётко проговорена.

## 5) Практические механики SSOT
- наблюдаемое состояние (Combine/Rx/async sequence),
- immutable state + reducer,
- или хотя бы один владелец mutable state (actor/serial queue).

Ключ:
- избегать “обратных записей” из UI в разные места без центра.

## 6) Типовые анти-паттерны
- Дублирование массива: `items` в VM и `items` в VC.
- Два независимых кеша (например, service cache + DB) без политики приоритета.
- Несколько источников правды для auth state (Keychain + singleton + user defaults), которые могут расходиться.

**Самопроверка**
- Оспорено: “SSOT = глобальный стор” — нет, SSOT про единственность владения в рамках области, а не про глобальность.
- Неочевидно: в offline-first SSOT для UI часто локальный storage; сервер — источник синка, а не “прямая правда” для отрисовки.
- Источники: state management практики (unidirectional data flow), оффлайн архитектуры, документация Combine/Rx/Swift Concurrency sequences.

### Q133 (🟢): Как бы ты организовал обработку ошибок и отображение ошибок в UI (без копипасты)?

**Кратко**
- Я разделяю:
  1) **инфраструктурные ошибки** (network, decoding, db),
  2) **доменные ошибки** (business rules),
  3) **UI-ошибки** (что показать пользователю).
- На границе слоёв делаю маппинг:
  - Data error → DomainError (или ErrorCategory),
  - DomainError → UIErrorState (title/message/action).
- Для переиспользования:
  - единый error mapping / presenter,
  - стандартизированные UI состояния (loading/empty/error),
  - типизированные recover actions (retry, open settings, login).

**Развёрнуто**
## 1) Почему “просто показывать error.localizedDescription” плохо
- тексты не предназначены пользователю,
- нет локализации/консистентности,
- теряется контекст и действия (retry/login),
- UI начинает зависеть от низкоуровневых деталей.

## 2) Структура ошибок по слоям
### Data (низкоуровневые)
- timeout, no internet, 500, decode failed, db write failed.

### Domain
- “нет прав”, “аккаунт заблокирован”, “лимит превышен”, “товар закончился”.
Доменные ошибки выражают правила, не транспорт.

### UI
- что показать:
  - заголовок/текст,
  - кнопка (Retry / Go to Settings),
  - тип (toast / alert / full-screen state).

## 3) Где происходит маппинг
### Data → Domain
В Data слое (или адаптере):
- HTTP 401 → `AuthError.unauthorized`,
- timeout/noInternet → `NetworkError.unreachable`,
- decode → `DataError.invalidResponse`.

Цель: домен не должен знать про HTTP/URLSession.

### Domain → UI
В presentation:
- `NetworkError.unreachable` → экран “No Internet” + кнопка “Try again”,
- `AuthError.unauthorized` → “Session expired” + action “Login”.

## 4) Как избежать копипасты
### A) Единый `UIErrorMapper`
- вход: `Error`/`DomainError`,
- выход: `UIErrorState`.

`UIErrorState` содержит:
- title, message,
- action (enum): `.retry`, `.openSettings`, `.login`, `.contactSupport`,
- стиль отображения.

### B) Единый протокол для экранов со state machine
- `ScreenState = loading | content | empty | error(UIErrorState)`.
Тогда каждый экран рендерит state единообразно.

### C) Политики retry
Retry лучше не в UI:
- “сколько раз ретраить, когда” — инфраструктурная политика.
UI получает уже “не получилось” + возможность вручную повторить.

## 5) Важный нюанс: recoverable vs non-recoverable
- recoverable: сеть, временная ошибка → retry.
- non-recoverable: бизнес-ограничение → показать объяснение, не ретраить.

Это снижает бессмысленные “попробуйте снова”.

## 6) Как отвечать на собесе
“Я не показываю raw ошибки. Я мапплю низкоуровневые ошибки в доменные категории, а затем в UIErrorState. UI получает стандартизированный state и action, поэтому нет копипасты alert’ов и одинаковых обработчиков ошибок по всему приложению.”

**Самопроверка**
- Оспорено: “ошибка — это просто текст” — нет, ошибка должна быть типизирована, иметь категорию и recover strategy.
- Неочевидно: retry-политика не должна жить в UI; иначе на разных экранах будет разное поведение.
- Источники: best practices error handling (domain errors), API design (typed errors), UX гайды по error states, подходы UDF/state machine.

### Q134 (🟠): Как ты выбираешь архитектурный стиль (MVC/MVVM/Clean/VIPER/TCA-подобное) под продукт и команду?

**Кратко**
- Я выбираю не “самый модный паттерн”, а минимальный набор практик, который снижает стоимость изменений:
  1) сложность продукта (много состояний/офлайн/синк/платежи),
  2) размер команды и параллельная разработка,
  3) требования к тестированию/качество,
  4) срок жизни проекта,
  5) опыт команды.
- База почти всегда: слои + границы + DI. Дальше добавляю “механики” (use cases, reducers, coordinators) по мере необходимости.

**Развёрнуто**
## 1) Что я считаю “архитектурным стилем”
Не ярлык (MVVM/VIPER), а ответы на вопросы:
- где живёт состояние,
- как течёт data flow,
- где side effects,
- как устроены зависимости,
- как делаем навигацию.

Если эти ответы не зафиксированы — паттерн не спасёт.

## 2) Критерии выбора по ситуации
### A) Небольшой продукт / быстрая разработка / маленькая команда
- Обычно хватает:
  - MVC или MVVM-lite,
  - строгих границ: UI ↔ Services/Repositories,
  - DI через init,
  - минимум абстракций.
Риск: VM/VC могут стать “толстыми”, поэтому нужны правила ревью.

### B) Средний продукт / много экранов / несколько разработчиков
- MVVM + coordinators + слой use cases/repositories (частично Clean).
Причина:
- легче параллелить работу по фичам,
- проще тестировать бизнес сценарии,
- навигация перестаёт жить в VC.

### C) Сложный продукт / много состояний / офлайн / синк / реальное “state explosion”
- Clean Architecture (слои + use cases) и/или UDF (TCA-подобные идеи):
  - единый state,
  - события (actions),
  - reducer,
  - эффекты отдельно.
Почему:
- сложные состояния проще держать детерминированными,
- удобно тестировать сценарии,
- меньше “рассыпавшихся” подписок и гонок.

### D) VIPER
Я рассматриваю VIPER, когда:
- команда уже сильна в нём,
- нужна жёсткая изоляция и очень большой проект,
но он дорог по ceremony (много сущностей на экран) и часто проигрывает аккуратному MVVM+Clean/UDF по отношению сигнал/шум.

## 3) Что является “красными флагами”
- “Мы выбрали паттерн, но у нас нет правил зависимостей”.
- “В проекте 5 стилей на разные фичи”.
- “У нас DI-контейнер, но всё через service locator”.
- “Тестов нет, но архитектура супер сложная”.

## 4) “Эволюционный” подход (мне нравится как senior)
- стартуем проще,
- добавляем уровни там, где появляется:
  - переиспользование,
  - сложные сценарии,
  - множественные источники данных,
  - боль от тестов,
  - проблемы с навигацией.
Это лучше, чем сразу пилить TCA на приложение из 5 экранов.

## 5) Как объяснить выбор на собесе
Хороший ответ звучит как tradeoffs:
- “Я выбрал MVVM+use cases, потому что у нас сложная бизнес-логика и нужно тестировать сценарии отдельно, а также несколько команд параллельно”.
или
- “Я не тащу heavy архитектуру в небольшой проект: важнее правила границ и качественный data layer”.

**Самопроверка**
- Оспорено: “есть лучший универсальный паттерн” — нет, есть компромисс под контекст (сложность/команда/тесты).
- Неочевидно: архитектура должна быть эволюционной; слишком ранняя “идеальная” архитектура часто ухудшает скорость и качество.
- Источники: опыт крупных iOS codebases, практики Clean Architecture/UDF, материалы по coordinating/navigation, engineering management (tradeoff подход).

### Q135 (🟠): Как ты проектируешь “границы” фичи: что входит в Feature Module, что в Core?

**Кратко**
- Я разделяю по принципу: **Core = стабильные общие абстракции и инфраструктура**, Feature = конкретная бизнес-фича и её UI.
- В Feature Module держу всё, что специфично для фичи:
  - экраны/VM/координатор,
  - локальные use cases,
  - локальные мапперы/модели, если они не нужны другим.
- В Core выношу то, что:
  - переиспользуется несколькими фичами,
  - задаёт общие контракты (Domain),
  - является инфраструктурой (Networking, Persistence, Analytics),
  - должно быть единым (Design System, Session/Auth, Remote Config).

**Развёрнуто**
## 1) Зачем вообще делить Feature и Core
Цели:
- параллельная разработка фич без конфликтов,
- контроль зависимостей и предотвращение “монолита”,
- ускорение сборки (в идеале),
- понятные публичные API между частями.

## 2) Что обычно лежит в Feature Module
- Presentation:
  - VC/Views/SwiftUI Views,
  - ViewModel/Presenter,
  - локальные UI-компоненты, специфичные для фичи,
  - Coordinator/Router (если навигация локальна фиче).
- Application/Domain (внутри фичи, если нужно):
  - use cases, которые обслуживают именно эту фичу,
  - state machine/reducer (если UDF),
  - доменные правила фичи, не пригодные другим.
- Data adapters:
  - реализация репозиториев, если источник данных специфичен для фичи (или glue-код).

Важно: Feature не должен экспортировать “внутренности” наружу — обычно наружу отдаётся один вход: `FeatureFactory`/`FeatureEntryPoint`.

## 3) Что обычно лежит в Core
### CoreDomain (контракты и модели)
- базовые доменные модели (если общие),
- протоколы репозиториев/gateways,
- общие ошибки/категории ошибок (если единообразно).

### CoreInfrastructure
- Networking (HTTP client, interceptors, retry policies),
- Persistence (DB, migrations, file storage),
- Auth/Session (token storage, refresh),
- Observability (logging, analytics, crash breadcrumbs),
- Remote Config / Feature flags SDK wrapper.

### CoreUI / Design System
- компоненты, токены, темы, типографика,
- общие UI утилиты (но осторожно, чтобы не стал “dump module”).

## 4) Критерии “выносить в Core или оставить в Feature”
Выносить в Core, если:
- используется ≥ 2 фичами и будет расти,
- нужна единая политика (auth, networking, analytics),
- это фундаментальная абстракция (Domain контракт).

Оставить в Feature, если:
- специфично,
- нестабильно/часто меняется,
- есть риск “засорить Core” и начать тащить туда всё подряд.

## 5) Частые ошибки и как их избегать
- **God Core**: всё общее складывают в Core → Core становится монолитом.
  - Лекарство: строгие правила: Core содержит только действительно shared или foundational вещи.
- **Кросс-импорты фич**: FeatureA импортирует FeatureB.
  - Лекарство: общие контракты в Domain/Core, общение через публичные entry points или события.
- **Циклы зависимостей**:
  - Лекарство: dependency graph, lint/build rules, отсутствие “обратных” импортов.

## 6) Практическая формулировка
“Я стараюсь, чтобы фичи зависели от Core, но не друг от друга. Наружу фича показывает один entry point. В Core держу контракты и инфраструктуру, а всё специфичное — внутри фичи.”

**Самопроверка**
- Оспорено: “Core должен содержать всё общее” — нет, это путь к монолиту; Core должен быть минимальным и стабильным.
- Неочевидно: то, что сегодня используется в двух местах, завтра может стать “случайным совпадением”; выносить стоит только при реальной зрелости/вариативности.
- Источники: практики iOS modularization (targets/SPM), dependency rule (слои), опыт крупных проектов (feature entry points, dependency graph enforcement).

### Q136 (🟠): Как организовать навигацию так, чтобы экраны были независимыми: Coordinator/Router — критерии выбора.

**Кратко**
- Цель: экраны не должны:
  - создавать друг друга напрямую,
  - знать о “соседях” иерархии,
  - держать в себе логику переходов и сборки зависимостей.
- Coordinator/Router выносит:
  - построение графа экранов,
  - переходы,
  - deeplink входы,
  - lifetime навигационных сценариев.
- Критерий выбора:
  - **Coordinator** хорош, когда есть сценарии/флоу и нужен lifecycle.
  - **Router** — более лёгкий термин/роль: “как перейти”, без управления жизненным циклом флоу.

**Развёрнуто**
## 1) Проблема “навигация в VC”
Если VC делает:
- `navigationController?.pushViewController(NextVC(), animated: true)`
то он:
- знает конкретный тип следующего экрана,
- знает способ презентации,
- начинает заниматься сборкой зависимостей,
- усложняет тесты и переиспользование.

Это превращает VC в “director” приложения.

## 2) Что делает Coordinator
Coordinator обычно:
- создаёт и держит navigation controller (или получает),
- создаёт экраны через фабрики,
- реагирует на выходные события экранов,
- управляет флоу: onboarding, auth, checkout.

Принцип:
- экраны эмитят события (“tap login”, “finish”), координатор решает, что дальше.

## 3) Что делает Router
Router часто проще:
- предоставляет методы навигации:
  - `showDetails(id:)`,
  - `presentPaywall()`,
- инкапсулирует детали push/present/transition style.

Router может быть:
- per-feature (внутри модуля),
- или общий (если есть единый навигационный слой).

Если роутер не управляет флоу и lifecycle — это просто навигационный адаптер.

## 4) Критерии выбора: когда Coordinator
- Есть “поток” из нескольких экранов (wizard, onboarding, checkout).
- Нужно хранить состояние флоу и его lifetime.
- Нужны ветвления: разные шаги в зависимости от условий.
- Нужна изоляция фичи: entry point запускает coordinator.

Coordinator особенно удобен в modular architecture:
- “фича экспортирует coordinator как entry point”.

## 5) Критерии выбора: когда Router
- Переходы простые и локальные, без сложного флоу.
- Хочется минимум сущностей.
- Нужно убрать зависимости на конкретный UI-переход из VM/VC, но без “флоу-менеджера”.

## 6) Как сделать экраны независимыми (конкретно)
- Экран/VM отдаёт наружу “выходы”:
  - делегат,
  - closure outputs,
  - Combine publisher / async stream событий.
- Координатор/роутер подписывается и выполняет навигацию.
- Сборка зависимостей делается в одном месте (factory/composition root), а не в VC.

## 7) Подводные камни
- Координаторы легко превращаются в God-координатор, если сделать один на всё.
  - Решение: дерево координаторов (app → feature → subflow).
- Утечки: coordinator держит child, child держит coordinator.
  - Решение: weak outputs / правильный ownership / завершение child flow.

## 8) Формулировка для собеса
“Я выношу навигацию из VC/VM в координаторы или роутеры. Для сложных потоков — coordinator с управлением жизненным циклом. Для простых переходов — router. Экраны общаются наружу через outputs, а сборка зависимостей и решение ‘что дальше’ живёт в одном месте.”

**Самопроверка**
- Оспорено: “MVVM решает навигацию” — MVVM не про навигацию; навигация — отдельная ответственность, иначе VM раздувается и течёт знание о UI графе.
- Неочевидно: главный выигрыш координатора — управление флоу и lifetime, а не просто “push вынесли из VC”.
- Источники: паттерн Coordinator (iOS), практики routing/deeplinks, modular feature entry points, memory management в навигации.

### Q137 (🟠): Как бы ты спроектировал deeplink routing, чтобы он был расширяемым и тестируемым?

**Кратко**
- Делай deeplink routing как отдельный слой:
  1) **Parse**: URL/NSUserActivity → типизированный `DeepLink` (enum/struct).
  2) **Resolve**: `DeepLink` → навигационное действие (feature entry point/flow).
  3) **Execute**: координатор/роутер выполняет переходы.
- Не парси URL внутри VC.
- Для расширяемости: таблица/реестр хендлеров по паттернам.
- Для тестируемости: парсер и резолвер — чистые функции, навигация — мокаемая.

**Развёрнуто**
## 1) Почему deeplink — это архитектурная задача
Deeplink:
- это вход “в середину” приложения,
- часто требует:
  - восстановить контекст (auth, onboarding, выбранный аккаунт),
  - открыть правильный flow,
  - дождаться зависимостей (например, сессии),
  - обработать “невозможно открыть сейчас” (fallback).

Если парсить и пушить экраны прямо в AppDelegate/SceneDelegate без структуры:
- получится хаос и регрессии.

## 2) Разделение на этапы
### A) Parse
Парсер превращает URL в доменный объект:
- `DeepLink.product(id:)`
- `DeepLink.profile(userID:)`
- `DeepLink.paywall(source:)`

Важно:
- типизированный результат вместо “строк и if”.

### B) Resolve (контекстно)
Резолвер решает:
- можно ли открыть сейчас,
- нужен ли login/onboarding,
- какой аккаунт/тенант активировать,
- какой feature owner отвечает.

Результат — навигационное действие/команда:
- `.start(AuthFlow, then: openTarget)`
- `.open(FeatureEntryPoint)`

### C) Execute
Execution выполняет:
- coordinator/router,
- без парсинга и бизнес-решений.

Это отделяет “что открыть” от “как открыть”.

## 3) Handler registry (расширяемость)
Вместо огромного switch можно сделать:
- список хендлеров (паттерн → builder),
- или мапу схем/хостов/путей на feature.

Пример идеи:
- `DeepLinkHandler` протокол:
  - `canHandle(url)`
  - `parse(url) -> DeepLink?`

Добавление нового deeplink:
- добавил новый handler,
- написал тесты парсинга,
- подключил в registry.

## 4) Тестируемость
### Что тестировать
- Парсер:
  - URL → DeepLink (happy/edge cases).
- Резолвер:
  - DeepLink + AppState(auth/onboarding) → Action.
- Исполнитель:
  - проверка, что вызвал правильный coordinator/feature entry (моки).

Критично:
- навигация не должна быть жёстко привязана к конкретным VC внутри парсера.

## 5) Очередь deeplink и readiness
Частый реальный кейс:
- приложение стартует, а сессия ещё не готова.
Тогда:
- складываем deeplink в очередь,
- выполняем после readiness (auth loaded, main UI готов),
- при необходимости вставляем pre-flow (login).

## 6) Безопасность
- валидировать вход:
  - whitelist схем/хостов,
  - проверка форматов id,
  - игнорировать неизвестные/подозрительные параметры.
- не исполнять “команды” из query напрямую (например, навигацию по arbitrary class names).

## 7) Собеседовательная формулировка
“У меня deeplink routing — отдельный слой: парсер делает типизированный DeepLink, резолвер учитывает состояние приложения и решает flow, а координатор выполняет. Это расширяемо (registry handlers) и тестируемо (чистые функции на parse/resolve).”

**Самопроверка**
- Оспорено: “deeplink = просто открыть экран” — нет, это вход в flow с контекстом (auth/onboarding/readiness) и он требует архитектуры.
- Неочевидно: резолвер должен быть контекстным (учитывать app state), иначе deeplink будет ломаться на холодном старте/без авторизации.
- Источники: Apple docs Universal Links/NSUserActivity, практики coordinator-based routing, опыт больших приложений (deeplink queue, readiness gates).

### Q138 (🟠): Где хранить состояние экрана: VC, VM, store, coordinator? Как решить?

**Кратко**
- Я разделяю “состояния” по их природе:
  - **UI ephemeral** (scroll offset, фокус, текущая анимация) — в View/VC.
  - **Presentation state** (loading/content/error, данные для отображения, выбранные фильтры) — в VM/Presenter/Store.
  - **Flow state** (на каком шаге onboarding, параметры флоу, pending deeplink) — в Coordinator/Flow controller.
  - **App-wide state** (auth/session, active account) — в отдельном store/actor.
- Решение: состояние живёт там, где оно имеет корректный ownership и lifetime, без дублирования (SSOT).

**Развёрнуто**
## 1) Ключевые оси выбора
### A) Ownership (кто владеет и изменяет)
Если UI должен только рендерить, а не “владеть” бизнес-состоянием — держим state вне VC.

### B) Lifetime (как долго должно жить)
- только пока экран на экране → VC/VM,
- между экранами внутри флоу → coordinator/flow state,
- между сессиями → persistence (UserDefaults/DB/Keychain).

### C) Reuse/Sharing
Если состояние нужно нескольким экранам:
- либо общий store (по фиче),
- либо источник истины в data layer (например, локальная БД),
но не “копия в каждой VM”.

### D) Testability
Состояние, которое нужно тестировать (deterministic transitions), лучше держать в VM/store (pure-ish), а не в VC.

## 2) Что оставлять в View/VC (и не стесняться)
- состояния “представления”, которые не являются частью бизнес-сценария:
  - `contentOffset`,
  - выделение текста/фокус,
  - текущий `UIResponder`,
  - состояние анимации/gesture recognizer.
Их перенос в VM часто делает архитектуру хуже (слишком много шума).

## 3) Что держать в ViewModel/Presenter
- всё, что определяет, *что видит пользователь* как содержимое:
  - список элементов,
  - выбранные фильтры/сортировки,
  - loading/empty/error,
  - derived UI state (enabled/disabled, секции).
VM должна быть SSOT для экрана.

## 4) Что держать в Store/Reducer (если UDF)
Когда:
- много событий,
- сложные переходы состояния,
- нужны детерминированные тесты,
- есть эффекты/отмена.
Store владеет state и принимает actions, VM/VC только отправляет события/рендерит.

## 5) Что держать в Coordinator
Coordinator — не место для “данных экрана”, но место для:
- состояния флоу:
  - текущий шаг,
  - параметры, которые передаются между экранами,
  - pending target (deeplink),
  - решение “куда дальше”.
Сильный сигнал держать в coordinator:
- если state влияет на переходы между экранами.

## 6) Типичные ошибки
- Дублирование: state хранится и в VC, и в VM (“на всякий случай”).
- “Coordinator как data store”: координатор начинает держать бизнес-данные и превращается в God-object.
- Persist “всё подряд”: сохраняют ephemeral состояния (scroll offset) как будто это доменные данные.

## 7) Практичная формулировка
“UI-эфемерное — в VC, отображаемое состояние — в VM/store, состояние флоу — в coordinator, глобальная сессия — в отдельном store/actor. Критерий — ownership + lifetime + кто является SSOT.”

**Самопроверка**
- Оспорено: “вся state должна быть в VM” — нет, часть состояния чисто UI и перенос в VM увеличивает сложность.
- Неочевидно: координатор не должен становиться моделью данных; его зона — навигация и flow state.
- Источники: MVVM/UDF практики state ownership, coordinator pattern, принципы SSOT и lifecycle-based state placement.

### Q139 (🟠): Как проектировать слой данных, чтобы можно было менять транспорт (REST/WebSocket/GraphQL) без переписывания UI?

**Кратко**
- UI/Domain должны зависеть от **контрактов** (репозитории/гейтвеи), а транспорт — быть деталью Data слоя.
- Разделяю:
  1) Domain контракт: `ChatRepository`, `OrdersRepository`,
  2) Transport clients: `RESTClient`, `WebSocketClient`, `GraphQLClient`,
  3) Adapters: реализации репозиториев, которые используют нужный client,
  4) Mapping: DTO ↔ Domain,
  5) Policies: retry/backoff, caching, deduplication.
- Тогда смена транспорта = замена/добавление адаптера, UI не трогаем.

**Развёрнуто**
## 1) Проблема “UI зависит от сети”
Если VM знает:
- эндпоинт, HTTP коды, query, DTO,
то смена REST → GraphQL заставит переписать presentation и тесты.

Цель — чтобы UI говорил:
- “загрузи список сообщений”, а не “выполни запрос”.

## 2) Контракт на границе (Domain)
Domain определяет:
- что нужно бизнесу:
  - `func messages(for chatID: ...) async throws -> [Message]`
  - `func send(message: ...) async throws`
без упоминаний:
- REST/GraphQL схем,
- подписок WebSocket,
- HTTP headers.

## 3) Реализация в Data: адаптеры
Data слой содержит:
- `RESTChatRepository: ChatRepository`
- `WebSocketChatRepository: ChatRepository`
- `GraphQLChatRepository: ChatRepository`

Каждый адаптер:
- маппит response в доменные модели,
- переводит ошибки,
- может агрегировать источники (кеш + сеть),
- скрывает детали (pagination/cursors/subscriptions).

## 4) Общий транспортный слой vs “наивные клиенты”
Хорошо иметь общий слой:
- request building,
- interceptors (auth, headers),
- retries/backoff,
- logging/tracing,
но важно:
- чтобы он не протекал наружу (UI его не знает).

## 5) Streaming / subscriptions (WebSocket/GraphQL)
Чтобы UI не зависел от конкретного транспорта:
- контракт выражает поток как абстракцию:
  - `AsyncStream<Message>` / `AnyPublisher<Message, Error>`,
- Data слой выбирает, чем наполнять поток:
  - WS events, GraphQL subscriptions, polling.

UI просто подписывается на “messages stream”.

## 6) Caching и consistency
При смене транспорта часто ломается:
- консистентность и дедуп,
- порядок событий,
- reconnection.
Поэтому политики должны быть вынесены:
- в репозиторий/инфраструктуру, а не в UI.

## 7) Что именно менять при переходе, чтобы UI не трогать
- заменить DI binding (composition root):
  - `ChatRepository = RESTChatRepository(...)` → `ChatRepository = WebSocketChatRepository(...)`.
- добавить новый адаптер, не меняя контракт.
Если контракт не хватает (например, нужен stream), меняем контракт в домене один раз — это уже осознанная API эволюция.

## 8) Практичная формулировка
“Я держу доменные репозитории как контракты. Транспорт — это деталь data layer. REST/WS/GraphQL — разные реализации одного репозитория. В домен возвращаю domain models или поток абстракции (AsyncSequence). Тогда смена транспорта — это смена реализации и DI wiring.”

**Самопроверка**
- Оспорено: “достаточно заменить URL’ы” — нет, меняются semantics (пагинация, подписки, reconnection); поэтому нужен контракт и адаптеры.
- Неочевидно: потоковые API лучше выражать абстракцией (AsyncStream/Publisher), чтобы UI не зависел от WS/GraphQL механики.
- Источники: Clean Architecture gateways/repositories, практики data layer abstraction, Swift Concurrency AsyncSequence/streams, опыт migration REST↔GraphQL/WS.

### Q140 (🟠): Как организовать кэширование (memory/disk) так, чтобы оно не протекало в UI слой?

**Кратко**
- UI не должен знать “где лежат данные” и “кешировать ли их”.
- Кеширование — это часть **data/infrastructure policy**:
  - реализуется внутри репозитория или отдельного Cache слоя,
  - скрыто за контрактом (`Repository`),
  - управляется стратегией (TTL, stale-while-revalidate, eviction).
- UI получает либо доменные модели, либо stream обновлений, а не “cache hit/miss”.

**Развёрнуто**
## 1) Почему “кеш в UI” — плохая идея
Если VM/VC знает про кеш:
- появляется ветвление “если есть кеш — покажи, если нет — загрузи” в каждом экране,
- инвалидация/TTL размазываются по коду,
- разные экраны начинают вести себя по-разному,
- тесты усложняются, потому что логика доступа к данным смешалась с presentation.

Правильный слой для кеша:
- data layer, где и решается политика получения данных.

## 2) Абстракция: репозиторий как “точка правды” для доступа
Контракт:
- `func loadProfile(id:) async throws -> Profile`
UI просто вызывает use case/repo.
Repo внутри решает:
- отдать memory cache,
- или disk cache,
- или сеть,
- или комбинацию.

## 3) Два уровня кеша: memory и disk
### Memory cache
- быстрый,
- живёт в RAM,
- сбрасывается при memory pressure/перезапуске.
Подходит:
- изображения,
- часто используемые объекты,
- результаты запросов с коротким TTL.

### Disk cache
- медленнее,
- переживает перезапуск,
- требует управления размером и очисткой.
Подходит:
- большие payloads,
- offline-first,
- результаты запросов с долгим TTL.

## 4) Политики кеширования (важнее, чем место хранения)
### TTL (time-to-live)
- данные считаются валидными N секунд/минут.

### Stale-while-revalidate
- сразу отдаём “старое” (stale),
- параллельно обновляем из сети,
- при успехе пушим обновление в поток/notify.

### Cache invalidation
- по TTL,
- по событиям (logout, смена аккаунта),
- по версии схемы/формата,
- по server hints (ETag/Cache-Control).

UI не должен знать детали инвалидации.

## 5) Как не “протекать” кешом через API
### Плохой API
- `loadProfile(useCache: Bool, forceRefresh: Bool, cachePolicy: ...)`

UI начинает принимать решения, которые должен принимать data слой.

### Хороший API
- два явных сценария (если нужно):
  - `profile()` (обычная политика),
  - `refreshProfile()` (явный пользовательский pull-to-refresh),
и оба по-прежнему внутри репозитория, но сценарий называется бизнес-термином, а не “кеш-политикой”.

## 6) Инструменты реализации (идея)
- Cache интерфейс:
  - `get(key)`, `set(key, value, ttl)`, `invalidate(key/prefix)`.
- Репозиторий использует cache + network:
  - всё маппит в domain model.
- Для потоков:
  - `AsyncStream<Profile>` или `Publisher` как “единый источник обновлений”.

## 7) Важные edge cases
- Мульти-аккаунт: ключи кеша должны включать account/tenant.
- Конкурентные запросы: коалесинг/дедуп, чтобы 10 экранов не били сеть одновременно.
- Согласованность: когда писать в кеш, когда читать, и что считать “истиной” для UI (часто локальная БД при offline-first).

## 8) Формулировка на собесе
“Кеширование — часть data layer. UI вызывает use case/repo и получает доменные модели. Repo скрывает memory/disk кеш, TTL, stale-while-revalidate и инвалидацию. UI может инициировать refresh как бизнес-событие (pull-to-refresh), но не управляет кеш-политикой напрямую.”

**Самопроверка**
- Оспорено: “удобнее передавать cachePolicy из UI” — это создаёт протекание деталей и копипасту политики; лучше выражать намерение пользователя (refresh) и держать политику в data layer.
- Неочевидно: дедупликация и ключи кеша (account/locale/flags) — частая причина багов при “правильной” архитектуре.
- Источники: практики caching (TTL, stale-while-revalidate), repository pattern, Apple URL loading system caching (ETag/Cache-Control) как концепт, но применённый через слой данных.

### Q141 (🟠): Как правильно решать проблему “параллельных запросов”: дедупликация, коалесинг, кэш-на-лету.

**Кратко**
- Проблема: один и тот же ресурс запрашивают несколько потребителей одновременно → лишняя сеть/нагрузка/гонки.
- Решения (обычно в Data слое):
  1) **Dedup / request coalescing**: несколько запросов объединяем в один in-flight, остальные ждут его результат.
  2) **Cache-on-flight**: как только запрос стартовал, кладём “промис”/task в таблицу in-flight, чтобы следующие подписались.
  3) **Caching**: после завершения кладём результат в memory/disk/DB.
- Важно: корректная отмена, таймауты и ключи (account/locale/params).

**Развёрнуто**
## 1) Чем дедуп отличается от кеша
- Кеш решает “повторный запрос после завершения”.
- Дедуп решает “одновременные запросы, пока первый ещё выполняется”.

Можно иметь кеш и всё равно страдать от 10 одинаковых запросов, которые стартовали “в одну секунду”.

## 2) Где должна жить дедупликация
Почти всегда:
- в репозитории или инфраструктурном слое (networking/cache),
а не в UI:
- иначе каждый экран решает по-своему, и баги неизбежны.

## 3) Как это обычно реализуют (идея)
### In-flight таблица
Ключ = идентичность запроса:
- endpoint + params + auth context (+ locale/feature flags при необходимости).

Значение = выполняющаяся операция:
- `Task<Value, Error>` или promise/future.

Псевдо-логика:
- если in-flight есть → await существующий,
- если нет → создать, сохранить, выполнить, удалить после завершения.

Это и есть coalescing.

## 4) Cancellation: главный подводный камень
Если “все подписались на один Task”:
- отмена одного потребителя не должна обязательно отменять общий запрос.
Иначе “один ушёл со страницы — всем отменили”.

Подходы:
- оборачивать task и считать refcount,
- или не пробрасывать cancellation наружу, а использовать явную отмену только когда никто не ждёт,
- или создавать отдельный слой (share/replay) с управлением подписчиками.

На собесе важно проговорить:
- cancellation semantics и ownership.

## 5) Cache-on-flight и “negative caching”
### Cache-on-flight
- положили in-flight сразу → следующий запрос мгновенно присоединяется.

### Negative caching
Иногда полезно кешировать ошибки кратковременно:
- чтобы не долбить сервер при повторяющихся ошибках (например, 404/403),
но осторожно:
- transient ошибки (timeout) кешировать опасно.

## 6) Консистентность и гонки при записи
Если после запроса идёт запись в DB/кеш:
- нужны атомарные правила:
  - записываем только последний ответ,
  - или используем versioning.
Иначе можно:
- получить устаревшие данные, если второй запрос закончился раньше первого.

## 7) Как объяснить tradeoffs
- Dedup снижает нагрузку и ускоряет UI,
- но усложняет cancellation и ключи.
Сильный ответ:
- “делаю дедуп на уровне репозитория по ключу запроса, храню in-flight task, управляю отменой через refcount/ownership, и после успеха кеширую результат”.

**Самопроверка**
- Оспорено: “кеш решает параллельные запросы” — нет, кеш решает повторные после завершения; in-flight дедуп решает одновременные.
- Неочевидно: cancellation semantics — ключевая сложность; важно не отменять общий запрос при отмене одного подписчика.
- Источники: паттерны request coalescing, reactive share/replay концепты, Swift Concurrency Task sharing, практики networking layers.

### Q142 (🟠): Как организовать глобальные зависимости приложения (network, analytics, remote config), чтобы не получить God-object?

**Кратко**
- Я избегаю “AppManager, который знает всё”.
- Подход:
  1) **Composition Root**: сборка зависимостей в одном месте (App/Scene/Feature factories).
  2) **Мелкие сервисы по ответственности**: `Analytics`, `Logging`, `RemoteConfig`, `Networking`.
  3) **Абстракции на границах**: протоколы там, где нужна подмена/тесты.
  4) **Контроль lifetime**: singleton только для truly-global (например, session store), остальное — scoped.
  5) **Изоляция состояния**: глобальные mutable store’ы (auth/session/cache) — через actor/serial queue.

**Развёрнуто**
## 1) Откуда берётся God-object
Когда пытаются “упростить доступ”:
- `AppServices.shared` содержит 20 сервисов,
- все берут зависимости оттуда,
- никакой явной зависимости в сигнатурах,
- сложно тестировать и менять.

Это по сути service locator + глобальный мешок.

## 2) Что делать вместо
### A) Composition Root
Одна точка, где создаются concrete реализации:
- `AppAssembly` / `SceneAssembly` / `FeatureAssembly`.

Правило:
- внутри бизнес-кода не должно быть `resolve()`.

### B) Scoping зависимостей
- Global (на приложение): логирование, аналитика, remote config client, session store.
- Per-feature/per-flow: coordinators, use cases, repositories фичи.
- Per-screen: view models.

Это снижает риск утечек и неконтролируемых связей.

### C) Разделение по ответственности
Вместо `AppManager`:
- `AnalyticsTracking` (протокол),
- `RemoteConfigProviding`,
- `NetworkClient`,
- `AuthSessionStoring`.

Каждый сервис маленький и понятный.

## 3) Где оправдан singleton
Singleton — не зло, но:
- он должен быть действительно глобальным и безусловно один.
Обычно оправданы:
- session store (источник истины),
- logging/metrics pipeline,
- remote config cache (если единый),
но и тут лучше:
- инжектить интерфейсы, а не дергать `shared` повсюду.

## 4) Как не превратить DI контейнер в service locator
Если используешь контейнер:
- контейнер живёт в composition root,
- приложение создаёт граф объектов,
- дальше зависимости передаются через init.

Запрещённый паттерн:
- `Container.shared.resolve()` внутри VM/use case.

## 5) Плагины/сквозные зависимости (analytics, logging)
Хорошая практика:
- иметь один слой “Observability”:
  - логирование,
  - метрики,
  - трейсинг,
и давать наружу маленький API:
- `logger.info(...)`,
- `metrics.increment(...)`,
- `tracker.track(event)`.

Внутри можно менять провайдера (Firebase/Datadog/Sentry) без касания фич.

## 6) Контроль глобального состояния
Глобальное mutable состояние (auth/session/cache) должно:
- иметь единственного владельца (SSOT),
- быть thread-safe (actor/serial queue),
- быть наблюдаемым (Combine/AsyncStream).

Иначе: гонки, рассинхрон, странные баги.

## 7) Формулировка на собесе
“Я держу сборку зависимостей в composition root, избегаю глобального мешка сервисов. Делаю сервисы маленькими и типизированными, чётко задаю lifetime scopes и не использую service locator внутри фич. Глобальное mutable состояние изолирую (actor/store).”

**Самопроверка**
- Оспорено: “singleton проще, значит лучше” — проще краткосрочно, но убивает тестируемость и приводит к скрытым зависимостям и God-object’ам.
- Неочевидно: DI контейнер может быть полезен, но только если его не дергать из бизнес-кода; иначе это тот же service locator.
- Источники: DI/composition root практики, SOLID (DIP), опыт больших проектов (scoping/lifetime), Swift Concurrency для изоляции глобального состояния.

### Q143 (🟠): Как проектировать shared компоненты (design system) без превращения в монолитный “UIKitCore”?

**Кратко**
- Shared UI нужен, чтобы обеспечить консистентность и ускорить разработку, но опасность — “свалка всего”.
- Принципы:
  1) **Design tokens** (цвета/типографика/отступы) отдельно от компонентов.
  2) Компоненты — **атомарные** и композиционные, без бизнес-логики.
  3) Разделять по уровням:
     - Tokens → Primitives → Components → Feature UI.
  4) Жёсткие правила публичного API и депенденси.
  5) Не класть туда “утилиты на все случаи” без владельца.

**Развёрнуто**
## 1) Откуда берётся “UIKitCore монолит”
Когда команда начинает “делать всё общее”:
- любой helper,
- любой extension,
- любой специфичный компонент,
попадает в общий модуль.

Итоги:
- сложно понимать, что можно использовать,
- зависимости расползаются,
- модуль разрастается и замедляет сборку,
- изменения в одной фиче ломают другую.

## 2) Правильная структура: слои UI
### A) Tokens
- цвета, шрифты, радиусы, размеры, spacing.
Без UIKit-логики, по сути данные.

### B) Primitives
- базовые building blocks (кнопка, текст, контейнер),
- минимальные зависимости,
- параметризуемые стилем.

### C) Components
- более “собранные” элементы (card, list cell skeleton, error state view),
- всё ещё без бизнес-правил,
- конфигурируются данными.

### D) Feature UI
- экраны, композиции, которые уже завязаны на домен/сценарии,
- живут в фичах, не в design system.

## 3) Гайдлайны, чтобы не засорять
- Каждый компонент имеет:
  - owner (кто поддерживает),
  - пример использования,
  - ограничения.
- Запрещать:
  - компоненты, которые знают про network/auth/paywall и т.п.
- Запрещать:
  - “универсальные” helpers без ясной ответственности.

## 4) API design
- маленький публичный API:
  - `ButtonStyle`, `TextStyle`, `CardView`.
- не экспортировать внутренние детали.
- не делать “магические синглтоны темы” без контроля.

## 5) Тема/брендинг/белая маркировка
Если нужен theming:
- абстракция темы + токены,
- переключение темы на composition root,
- компоненты читают токены (в идеале без глобального mutable state).

## 6) Тесты и регрессии
- snapshot tests для компонентов,
- визуальные тесты на типографику/Dynamic Type,
- accessibility baseline.

Иначе design system становится источником визуальных регрессий.

## 7) Формулировка на собесе
“Я строю дизайн-систему слоями: tokens → primitives → components. В общий модуль не кладу бизнес-логику и не превращаю его в свалку утилит. У каждого компонента есть owner и публичный API. Фича-специфичный UI остаётся внутри фич.”

**Самопроверка**
- Оспорено: “всё общее надо выносить” — нет, иначе общий модуль становится монолитом и тормозит проект.
- Неочевидно: tokens/primitives/components — важное разделение, чтобы дизайн-система оставалась стабильной и переиспользуемой.
- Источники: практики design systems (tokens), опыт modular UI, snapshot testing, accessibility/dynamic type гайды.

### Q144 (🟠): Как бы ты организовал обработку “состояний” экрана: loading/empty/content/error — архитектурно.

**Кратко**
- Я делаю явную модель состояния экрана (state machine):
  - `loading`, `content`, `empty`, `error`.
- Источник истины — VM/store.
- UI “рендерит” state (idempotent render), не держит дубликатов.
- Ошибка — не строка, а типизированный `UIErrorState` с action.
- Для переиспользования: общий подход/протокол рендера или базовые view-компоненты для состояний.

**Развёрнуто**
## 1) Почему важно моделировать состояния явно
Если состояния не моделировать, появляется:
- куча флагов: `isLoading`, `hasError`, `items` и они могут быть несовместимы,
- гонки: загрузка закончилась, но error не сбросили,
- UI “подвис” в полусостоянии.

Явный state устраняет “невозможные состояния”.

## 2) Типичная модель состояния
- `Loading` (в т.ч. initial vs refresh),
- `Content(data)`,
- `Empty(reason)`,
- `Error(UIErrorState)`.

Полезно различать:
- initial load vs pull-to-refresh,
- empty “по данным” vs empty “по фильтру/поиску”.

## 3) Кто владеет state
- VM/store владеет и обновляет state.
- UI подписывается/наблюдает и рендерит:
  - show skeleton,
  - show list,
  - show empty view,
  - show error view/alert.

UI не должен принимать решение “что показывать” по кускам данных — он должен следовать state.

## 4) Рендер как функция состояния
Паттерн:
- `render(state)` должен быть идемпотентным:
  - вызвали 10 раз — результат тот же.
Это снижает баги от “забыли скрыть loader”.

## 5) Как избежать копипасты между экранами
### A) Единые UI компоненты состояний
- `LoadingView` (skeleton),
- `EmptyStateView` (иконка+текст+CTA),
- `ErrorStateView` (retry/open settings).

### B) Единый тип `UIErrorState`
- title/message,
- CTA (retry/login/settings),
- presentation style (inline/fullscreen/toast).

### C) Базовый протокол для VM outputs
Например:
- `state: Published<ScreenState>`
Тогда экраны работают одинаково.

## 6) Где решать “пусто/ошибка/контент”
Это обязанность:
- use case/repository + VM:
  - VM решает, что `items.isEmpty` = empty state,
  - или use case отдаёт уже доменное “пусто по причине”.

Но UI не должен решать это заново.

## 7) Как отвечать на собесе
“Я моделирую состояние экрана явно как enum/state machine и делаю UI рендером этого состояния. Это исключает невозможные состояния и уменьшает копипасту. Ошибки типизированы и маппятся в UIErrorState с действиями.”

**Самопроверка**
- Оспорено: “достаточно isLoading/isError” — набор флагов создаёт несовместимые комбинации; enum/state machine проще и надёжнее.
- Неочевидно: empty state часто не “просто пусто”, а имеет причины (нет данных/нет результатов поиска), и это лучше моделировать.
- Источники: state management практики (UDF), UI state modeling, подходы render(state) в UIKit/SwiftUI.

### Q145 (🟠): Как организовать пагинацию и обновления списка: где логика, как избегать гонок и дублей?

**Кратко**
- Логика пагинации должна жить в VM/store/use case, а не в VC.
- Нужны:
  - явное состояние пагинации (`isLoadingNext`, `hasMore`, `cursor/page`),
  - защита от параллельных `loadNext`,
  - дедуп/merge элементов по идентификатору,
  - корректное поведение при refresh (reset vs append).
- Источник истины один (SSOT), UI рендерит snapshot.

**Развёрнуто**
## 1) Типовая проблема
Без архитектуры пагинации появляются:
- двойные запросы при быстром скролле,
- дубли в списке,
- “перепрыгивание” курсора,
- гонки: refresh и loadNext одновременно,
- невозможность повторить (retry) для одной страницы.

## 2) Где должна жить логика
### Presentation (VM/store)
- принимает события UI:
  - “дошли до конца”,
  - “pull-to-refresh”,
  - “повторить после ошибки”.
- держит state пагинации и список.
- решает, когда дергать use case.

### Domain/Data
- знает, как загружать страницы (page/cursor),
- маппит в доменные модели,
- может делать дедуп in-flight запросов.

UI слой:
- только триггеры (prefetch/willDisplay) и рендер.

## 3) Явная модель состояния пагинации
Минимально:
- `items: [Item]`
- `nextCursor` или `currentPage`
- `isLoadingInitial`
- `isLoadingNext`
- `hasMore`
- `errorInitial` / `errorNext` (разные!)

Разделять initial error и next-page error важно:
- initial error = полноэкранный error state,
- next error = inline “не удалось загрузить ещё” + retry.

## 4) Защита от гонок
### A) Gate для loadNext
Если `isLoadingNext == true` → игнорировать повторный триггер.

### B) Refresh vs LoadNext
Правило:
- refresh отменяет in-flight loadNext или делает “reset token”.
Иначе можно:
- получить результаты старой страницы после refresh и испортить список.

Подход:
- “generation id”: каждый refresh увеличивает generation, ответы старых generation игнорируются.

### C) Параллельные запросы и дедуп
На уровне repository:
- in-flight по ключу (cursor/page) коалесится.

## 5) Дедуп и merge элементов
Серверы и курсоры часто дают:
- пересекающиеся элементы.
Поэтому:
- элементы должны иметь стабильный id,
- merge делаем по id (set/ordered dictionary),
- обновляем существующий элемент (если пришла новая версия).

## 6) Prefetching и триггеры
Триггер “дошли до конца” лучше делать заранее:
- например, когда показываем элемент за N до конца.
Это уменьшает “дырку” при подгрузке.

Важно:
- не завязывать логику на конкретный метод таблицы, а передавать “index reached threshold” как событие.

## 7) Формулировка на собесе
“Пагинация — это state machine в VM/store. Я явно храню cursor/page и флаги загрузки, блокирую параллельные loadNext, разделяю initial/next error, делаю дедуп по id и защищаюсь от гонок refresh/loadNext через generation id или отмену in-flight.”

**Самопроверка**
- Оспорено: “пагинация = просто page++” — на практике важны гонки, разные типы ошибок и дедуп.
- Неочевидно: server может присылать пересечения, поэтому дедуп по id и merge — must, иначе дубли неизбежны.
- Источники: практики cursor pagination, state management для списков, UIKit prefetching/diffable как инструменты рендера, но логика всё равно должна быть вне UI.

### Q146 (🟠): Как проектировать фоновую синхронизацию/refresh данных (background fetch, push, periodic sync) в архитектуре?

**Кратко**
- Я отделяю:
  1) **Sync engine** (domain/application слой): сценарии синхронизации и правила.
  2) **Data layer**: репозитории, транспорт, хранение, маппинг.
  3) **Triggers**: iOS механизмы (BGTaskScheduler, push, app launch, pull-to-refresh).
- UI не инициирует “как синкать”, UI инициирует “обновить” как намерение.
- Нужны:
  - идемпотентность,
  - дедуп запросов,
  - управление сетью/энергией,
  - наблюдаемое состояние (progress/errors),
  - стратегии конфликтов (если есть локальные изменения).

**Развёрнуто**
## 1) Почему background sync — отдельная подсистема
Она пересекает:
- жизненный цикл приложения,
- сеть/энергию,
- хранение и консистентность,
- конфликтующие источники данных (сервер/локально),
- ретраи и backoff.

Если “синк” размазан по экранам, получаешь:
- дубли логики,
- неконсистентные данные,
- непредсказуемые ретраи.

## 2) Архитектурный разрез
### A) Triggers (платформенные)
- BGTaskScheduler (background processing/refresh),
- push notifications (silent push),
- app became active,
- user pull-to-refresh.

Их задача:
- вызвать “start sync” и сообщить системе о завершении (success/failure),
но не содержать бизнес-правила.

### B) Sync engine (оркестрация)
- какие сущности синкать,
- в каком порядке,
- какие зависимости между шагами,
- retry/backoff политика (на уровне сценариев),
- обработка ошибок и частичного успеха.

### C) Data layer
- конкретные репозитории и клиенты,
- сохранение в локальную БД,
- дедуп in-flight,
- маппинг DTO→domain.

## 3) Идемпотентность и дедуп
Критично, потому что triggers могут сработать несколько раз.
Подходы:
- sync run id,
- in-flight lock (actor/serial queue),
- дедуп запросов и операций по ключам.

## 4) Консистентность и конфликты
Если есть локальные правки:
- нужна стратегия:
  - server wins,
  - client wins,
  - merge по версии,
  - CRDT/операции (редко на мобиле, но принцип).

Для большинства apps:
- optimistic updates + server reconciliation,
- или offline-first с локальной БД как SSOT и фоновым push изменений.

## 5) Наблюдаемость и диагностика
- логирование шагов синка,
- метрики (сколько времени, сколько ошибок),
- возможность воспроизвести проблему.

UI может показывать:
- “последнее обновление”,
- индикатор синка,
но не должен управлять механикой.

## 6) Ограничения iOS
- фон ограничен временем,
- сеть/энергия: уважать условия (Wi‑Fi/charging, если требуется),
- корректно завершать BGTask и не держать задачи бесконечно.

Архитектурно это значит:
- синк должен уметь останавливаться и продолжаться,
- иметь маленькие шаги.

## 7) Собеседовательная формулировка
“Я делю background sync на три части: triggers (iOS), sync engine (оркестрация сценариев), data layer (транспорт/хранилище). Sync idempotent, дедупит запуск, пишет в локальную БД как SSOT и публикует состояние. UI лишь отражает и может инициировать refresh.”

**Самопроверка**
- Оспорено: “синк можно делать прямо в AppDelegate” — триггер можно, но бизнес-логика и оркестрация должны быть вынесены, иначе это не масштабируется.
- Неочевидно: идемпотентность — ключевой инвариант, иначе background triggers приводят к дублированию и гонкам.
- Источники: Apple background tasks (BGTaskScheduler) концепты, оффлайн архитектуры (local DB SSOT), практики sync engine (оркестрация, retries, conflicts).

### Q147 (🔴): Как спроектировать “composition root” и dependency graph в большом iOS-приложении, чтобы избежать циклов и ускорить сборку?

**Кратко**
- Composition Root — единственное место, где связываются конкретные реализации и протоколы, и строится граф объектов.
- Для большого приложения:
  - фиксирую dependency directions (Core → Features),
  - режу модули по слоям и/или фичам,
  - ограничиваю public API,
  - запрещаю service locator внутри бизнес-кода,
  - визуализирую и проверяю dependency graph (скрипты/линтеры),
  - изолирую “тяжёлые” зависимости, чтобы уменьшить пересборки.
- Цель: нет циклов, меньше recompilation, параллельная работа команд.

**Развёрнуто**
## 1) Что такое composition root в iOS (практически)
Это место, где:
- создаются singletons/scoped services,
- выбираются реализации (remote vs mock vs offline),
- собираются feature entry points,
- настраиваются cross-cutting системы (analytics, logging, config).

Обычно:
- `App`/`SceneDelegate`,
- или отдельный `AppAssembly`,
- или набор `FeatureAssembly` + `AppAssembly`.

Важно:
- только здесь разрешено знать про concrete типы и их wiring.

## 2) Как избежать циклов зависимостей
### A) Два “направления”
- Core/Domain/Infrastructure — фундамент.
- Features зависят от Core, но не друг от друга напрямую.

Если FeatureA нужна FeatureB:
- общение через:
  - протоколы/entry points,
  - события/координаторы,
  - shared domain contracts,
а не через импорт FeatureB.

### B) “Контракты вверх, реализации вниз”
- протоколы живут в более высоком слое (Domain/Core),
- реализации — внизу (Data/Feature).
Это убирает обратные зависимости.

### C) Публичные API минимальны
- наружу модуль отдаёт только entry point и нужные типы,
- остальное `internal`.

Чем меньше `public`, тем меньше непреднамеренных связей.

## 3) Как ускорить сборку архитектурой
### A) Минимизировать “горячие” зависимости
Если модуль зависит от большого модуля, он будет пересобираться чаще.
Поэтому:
- тяжёлые SDK wrappers и инфраструктуру держать отдельно,
- дизайн систему тоже модульно: tokens/primitives/components.

### B) Использовать SPM/targets разумно
- Много маленьких модулей = не всегда быстрее (overhead),
- но правильно выделенные модули уменьшают invalidation и позволяют параллельную компиляцию.

### C) Стабилизировать Core
Core должен меняться редко.
Если Core постоянно меняют под фичи — сборка страдает.
Решение:
- не тащить фича-специфичное в Core.

## 4) Практическая структура dependency graph
Один из рабочих вариантов:
- `CoreDomain` (модели/контракты),
- `CoreInfrastructure` (networking/persistence/observability),
- `CoreUI` (design system),
- `FeatureX` (entry point + UI + local domain),
- `App` (composition root, wiring).

Граф:
- App зависит от всех Feature,
- Feature зависит от Core*,
- CoreInfrastructure зависит от CoreDomain,
- CoreUI зависит от tokens/core.

## 5) Anti-patterns, которые ломают всё
- Service locator (внутри VM/use case) → скрытые зависимости → циклы.
- “Utils” модуль, который импортят все → становится центром цикла.
- Большие `public` модели, которые все шарят → coupling.

## 6) Как проверять и держать граф в порядке
- скрипты/инструменты, которые строят dependency graph и падают на циклах,
- правила ревью: “feature не импортит другую feature”,
- периодический аудит public API,
- static analysis для forbidden imports.

## 7) Хорошая формулировка на собесе
“У меня есть composition root, где собирается граф. Я держу dependency rule: features зависят от core, но не друг от друга. Контракты объявляю в домене, реализации ниже. Минимизирую public API и использую модульность, чтобы сократить rebuilds. Циклы предотвращаю правилами графа и автоматическими проверками.”

**Самопроверка**
- Оспорено: “больше модулей = быстрее” — не всегда; важно правильно разрезать и стабилизировать базовые модули, иначе будет overhead и больше пересборок.
- Неочевидно: главный источник циклов — скрытые зависимости (service locator, shared utils); их надо управлять архитектурно и организационно.
- Источники: практики modularization iOS/SPM, dependency graph tooling, Clean Architecture dependency rule, build performance гайды (incremental builds).

### Q148 (🔴): Как спроектировать offline-first архитектуру: локальная БД как SSOT, синк, конфликты, UX?

**Кратко**
- Offline-first = UI работает от **локального источника истины** (обычно DB), а сеть — механизм синхронизации.
- Архитектура:
  1) UI подписан на локальную БД/хранилище (SSOT).
  2) Репозитории пишут/читают из DB, а сетевой слой обновляет DB.
  3) Sync engine управляет очередью операций, ретраями, backoff.
  4) Конфликты решаются политикой (server wins / client wins / merge) и версионированием.
- UX: явные статусы синка, optimistic updates, понятные ошибки.

**Развёрнуто**
## 1) Главная идея offline-first
Не “кешируем ответы сети”.
А:
- локальная БД — первичный источник данных для UI,
- сеть — вторичный источник, который приводит локальную БД к актуальному состоянию.

Это даёт:
- быстрый UI,
- стабильность при плохой сети,
- единый SSOT,
- более предсказуемое состояние.

## 2) Поток данных (data flow)
### Read
- UI/VM читает из DB (observed results, stream, fetch + subscribe).
- Нет ветвления “если нет сети” — просто показываем то, что есть локально.

### Write (optimistic)
- пользователь делает действие → пишем изменение в DB сразу (optimistic),
- ставим “pending operation” в очередь синка,
- sync engine отправляет на сервер,
- при успехе — подтверждение/обновление,
- при ошибке — стратегия rollback/пометки.

## 3) Очередь операций (outbox pattern)
Часто нужен “outbox”:
- таблица локальных операций (create/update/delete),
- сериализация и дедуп (например, несколько update на один объект объединять),
- ретраи с backoff,
- устойчивость к перезапуску приложения.

Это важнее, чем “кеш ответов”.

## 4) Конфликты и версии
Конфликт возникает, когда:
- локально изменили,
- а сервер изменился параллельно.

Стратегии:
- server wins (просто перезатереть локальное),
- client wins (перезаписать сервер),
- merge (по полям или через операции),
- last-write-wins по timestamp (осторожно, часы могут врать).

Практичный подход:
- использовать server-side version/etag и при конфликте:
  - запросить актуальную версию,
  - применить merge policy.

## 5) UX и продуктовые решения
Offline-first требует UX-ответов:
- показываем ли “pending” бейджи?
- что делаем при ошибке синка?
- разрешаем ли редактировать объект в конфликте?
- как пользователь узнает, что данные устарели?

Хорошие практики:
- не блокировать UI без нужды,
- показывать статусы (syncing / offline),
- давать ручной retry,
- аккуратно делать rollback (не терять ввод пользователя).

## 6) Инварианты и тестирование
Инварианты:
- локальная БД — SSOT для UI,
- синк идемпотентен,
- операции упорядочены,
- дедуп/коалесинг запросов,
- при перезапуске система продолжает синк.

Тестирование:
- unit тесты merge/conflict policy,
- integration тесты outbox/sync engine,
- симуляция плохой сети.

## 7) Как ответить на собесе
“Offline-first — это локальная БД как SSOT: UI читает из неё, а сеть обновляет её через sync engine. Записи — optimistic с outbox очередью операций. Конфликты решаю через versioning и явную policy. UX включает статусы и retry, чтобы пользователь не терял данные.”

**Самопроверка**
- Оспорено: “offline-first = просто кешировать ответы” — нет, ключ в SSOT и outbox/операциях, иначе будут гонки и несогласованность.
- Неочевидно: offline-first — это не только архитектура, но и UX решения по pending/errors/conflicts; без них получится “работает, но пользователю непонятно”.
- Источники: offline-first/outbox pattern, практики sync engines, DDD consistency подходы, опыт мобильных клиентов с локальной БД как SSOT.

### Q149 (🔴): Как проектировать API и архитектуру так, чтобы избежать “massive refactor” при росте требований?

**Кратко**
- Я проектирую систему так, чтобы изменения локализовались:
  - стабильные контракты на границах (repositories/use cases),
  - разделение DTO/domain/UI models,
  - composition root,
  - единые политики ошибок/кеша/ретраев,
  - feature entry points (модули не знают друг о друге).
- Я избегаю premature abstractions, но закладываю “место для расширения”:
  - enum/strategies вместо if-ов,
  - “policy objects” вместо флагов,
  - versioned APIs и миграции.

**Развёрнуто**
## 1) Почему происходят “massive refactors”
Обычно из-за:
- протекания деталей (DTO/транспорт/DB) в UI/Domain,
- отсутствия границ и контрактов,
- скрытых зависимостей (service locator, shared singletons),
- размазанной навигации и state,
- “сервисов-свалок” и God-объектов,
- отсутствия тестов и наблюдаемости.

Т.е. не из-за “не того паттерна”, а из-за слабых границ.

## 2) Принцип локализации изменений
Я спрашиваю:
- “Если завтра меняется backend/UX/бизнес-правило, сколько слоёв я трону?”
Цель:
- менять максимум один слой/модуль.

Примеры:
- поменяли API → меняется DTO+mapper+data adapters, domain UI трогаем минимально.
- поменяли UX → меняется presentation, домен/репо трогаем минимально.
- добавили кеш/оффлайн → меняется repo/data policies, UI почти не трогаем.

## 3) Стабильные контракты и явные сценарии
### A) Контракты на границах
- репозитории/гейтвеи,
- use cases как сценарии.

Это снижает ripple-effect: UI не знает деталей.

### B) Не протекать “параметрами политики”
Не делать:
- `loadX(cachePolicy:force:retry:)`.
Иначе UI становится “конфигуратором инфраструктуры” и изменения растекаются.

Вместо этого:
- выражать намерение сценариями:
  - `refresh()`, `loadMore()`, `retry()`.

## 4) Versioning и миграции
Рост требований часто бьёт по:
- storage schema,
- API contracts.

Нужны:
- миграции DB,
- versioned endpoints/DTO mapping,
- backward compatible parsing,
- feature flags/remote config, чтобы катить изменения постепенно.

## 5) Evolving architecture без “религии”
Не строить “идеальную” архитектуру с первого дня.
Но держать инварианты:
- DIP/DI,
- разделение моделей,
- SSOT,
- навигация вне VC,
- тестируемые use cases.

Дальше:
- когда появляется “state explosion” — вводить store/reducer,
- когда растёт команда — модульность,
- когда растёт синк — sync engine.

## 6) Тесты как страховка от refactor disaster
Massive refactor страшен, когда:
- нет тестов.
Я закладываю:
- unit тесты доменных правил и маппинга,
- integration тесты data layer критичных сценариев,
- snapshot/UI тесты для компонентов.

Тогда можно менять внутренности без переписывания всего.

## 7) Наблюдаемость
Без логов/метрик:
- любые изменения = “сломалось где-то”.
Я строю:
- централизованные логи и error reporting,
- трассировку ключевых сценариев.
Это позволяет рефакторить безопаснее.

## 8) Формулировка на собесе
“Чтобы не делать massive refactor, я строю архитектуру с чёткими границами и стабильными контрактами. Детали (транспорт/БД) изолированы в data layer, UI работает с use cases и domain моделями. Плюс: тесты, миграции, versioning и постепенные rollout’ы через флаги.”

**Самопроверка**
- Оспорено: “массовые рефакторы из-за выбора паттерна” — чаще из-за протекания зависимостей и отсутствия границ/тестов.
- Неочевидно: premature abstractions тоже приводят к боли; важно держать минимальный набор инвариантов и эволюционировать.
- Источники: Clean Architecture (границы), практики modularization, опыт versioning/migrations/feature flags, инженерные практики тестов и observability.


### Q150 (🔴): Как спроектировать межфичевое взаимодействие без прямых зависимостей: events, contracts, feature entry points?

**Кратко**
- Цель: FeatureA не импортит FeatureB и не знает её типов.
- Подходы:
  1) **Feature Entry Point**: фича наружу экспортирует один интерфейс (factory/coordinator) и принимает зависимости через протоколы.
  2) **Контракты в CoreDomain**: общие модели/протоколы (минимум).
  3) **События/шина** (event bus) — осторожно: удобно, но риск скрытых связей.
  4) **Navigation-based composition**: одна фича запускает другую через coordinator и публичный entry point.
- Критерий: взаимодействие должно быть явным, тестируемым и не создавать циклов.

**Развёрнуто**
## 1) Почему прямые зависимости между фичами — проблема
Если FeatureA импортит FeatureB:
- возникают циклы (A → B → A),
- фичи нельзя переиспользовать/удалять из приложения,
- сборка и ревью усложняются,
- изменения в B ломают A (ripple-effect),
- сложнее параллельная работа команд.

Правило: **фичи не зависят друг от друга напрямую**.

## 2) Паттерн Feature Entry Point
Каждая фича экспортирует один публичный “вход”:
- `FeatureXEntryPoint` / `FeatureXFactory` / `FeatureXCoordinator`.

Снаружи виден только контракт:
- что можно открыть,
- какие параметры нужны,
- какие события фича отдаёт наружу.

Внутренности (VC/VM/модели) — скрыты `internal`.

## 3) Контракты через CoreDomain
Если нужно обмениваться данными/возможностями:
- контракт живёт в CoreDomain (или отдельном Contracts модуле),
- реализации — в фичах.

Важно:
- не превращать Contracts в “общий склад типов”,
- выносить только то, что реально стабильно и shared.

## 4) Событийная модель: когда уместна и чем опасна
### Когда уместна
- cross-cutting события:
  - `didLogout`,
  - `subscriptionChanged`,
  - `appDidBecomeActive`,
  - `trackingEvent`.
- один отправитель → много подписчиков.

### Риски (existential trap архитектуры)
- скрытые зависимости: подписчик не очевиден,
- тяжело отлаживать “кто съел событие”,
- порядок доставки и thread-safety проблемы,
- memory leaks (подписки) и гонки.

Если используешь event bus:
- типизируй события,
- держи строгие правила владения подписками,
- избегай использования как “RPC между фичами”.

## 5) Альтернатива event bus: явные callback/outputs
Для навигационных сценариев:
- FeatureB отдаёт outputs наружу:
  - `onFinished`, `onSelected(itemID)`.
FeatureA не подписывается на глобальную шину — она получает событие через явный output.

Это делает взаимодействие:
- явным,
- локализованным,
- тестируемым.

## 6) Взаимодействие через “shared state” (осторожно)
Иногда нужно общее состояние:
- auth/session,
- active account,
- feature flags.
Это может быть отдельный store/actor (SSOT).
Но:
- он не должен превращаться в “глобальную шину данных” для всего подряд.

## 7) Практичная формулировка на собесе
“Я не связываю фичи импортами. Каждая фича имеет entry point. Общие контракты лежат в core contracts/domain. Для кросс-фичевых реакций использую типизированные события или общий session store, но не делаю из event bus универсальный способ общения — навигационные и бизнес-события передаю через явные outputs.”

**Самопроверка**
- Оспорено: “event bus решает всё” — он часто скрывает связи и усложняет отладку; предпочтительнее явные контракты и outputs.
- Неочевидно: contracts модуль легко превратить в свалку; выносить стоит только стабильные интерфейсы и минимальные типы.
- Источники: modular architecture (feature entry points), coordinator-based navigation, event-driven patterns (pub/sub) и их tradeoffs, практики dependency rule.

### Q151 (🔴): Как ты проектируешь безопасность и хранение секретов (Keychain, tokens), чтобы не протекало по слоям?

**Кратко**
- Секреты (tokens, refresh tokens, credentials) — это инфраструктура и политика безопасности, не задача UI.
- Я делаю:
  1) `SecureStorage` интерфейс (в домене/контрактах или core),
  2) реализацию на Keychain в infrastructure,
  3) `SessionStore/AuthManager` как SSOT для auth state,
  4) сетевой слой читает токен через `TokenProvider`/interceptor,
  5) UI работает с use cases (“login/logout/refresh”), а не с Keychain.
- Важны: минимизация доступа, clear-on-logout, миграции и тестируемость.

**Развёрнуто**
## 1) Что означает “не протекать”
Плохая архитектура:
- ViewModel читает/пишет Keychain,
- сеть напрямую шарит `UserDefaults` с токеном,
- разные места имеют разные копии auth state.

Хорошая:
- один владелец (SSOT) для auth/session,
- слои общаются через контракты.

## 2) Роли компонентов
### A) SecureStorage
Контракт:
- `saveToken`, `loadToken`, `deleteToken`.
UI не знает, что это Keychain.

### B) SessionStore (SSOT)
- держит текущее состояние сессии:
  - `isAuthenticated`,
  - `accessToken` (в памяти),
  - user identity,
- публикует изменения (Combine/AsyncStream),
- при старте восстанавливает из SecureStorage.

### C) TokenProvider / AuthInterceptor
Сетевой слой:
- не знает про UI и use cases,
- получает токен через provider,
- делает refresh при 401 (по политике),
- обновляет session store.

## 3) Политики безопасности
- clear-on-logout: удалять токены и связанные данные,
- scoping: разные аккаунты → разные keys/containers,
- минимальный доступ: не давать “всем” сервисам читать токен,
- избегать логирования секретов,
- обрабатывать “keychain unavailable” и миграции.

## 4) Ошибки, которые часто ловят в проде
- race conditions при одновременном refresh,
- бесконечные refresh loops,
- stale token в памяти после logout,
- хранение токена в UserDefaults,
- утечки токена через логи/краши.

Архитектурно лечится:
- дедуп refresh (in-flight),
- единый session store,
- строгие границы доступа.

## 5) Тестируемость
- SecureStorage — мокается,
- SessionStore — тестируется на переходы состояния,
- AuthInterceptor — тестируется на сценарии 401/refresh.

UI тестирует только:
- что на `logout` состояние поменялось,
а не детали Keychain.

## 6) Формулировка на собесе
“Keychain — инфраструктура. Я прячу его за SecureStorage, а состояние авторизации держу в SessionStore как SSOT. Сеть получает токен через provider/interceptor и делает refresh дедуплицированно. UI работает с use cases и не трогает секреты напрямую.”

**Самопроверка**
- Оспорено: “достаточно хранить токен в Keychain и всё” — важно ещё управлять жизненным циклом, дедуп refresh, и не допустить протекания по слоям.
- Неочевидно: concurrency вокруг refresh — главный источник багов; без in-flight дедуп и правильного ownership будут гонки и лупы.
- Источники: best practices token handling, архитектура auth/session store, Keychain usage patterns, network interceptors и refresh strategies.

### Q152 (🔴): Как спроектировать наблюдаемость (logging/metrics/tracing) так, чтобы помогало дебажить и не засоряло код?

**Кратко**
- Observability — сквозная инфраструктура: логи, метрики, трассировка.
- Архитектурно:
  1) общий интерфейс `Logger/Metrics/Tracer`,
  2) реализации (Sentry/Datadog/OSLog) спрятаны внутри,
  3) correlation id / trace id проходит через сценарии и сеть,
  4) события уровня домена (use case started/finished) и ошибки фиксируются централизованно,
  5) логирование не должно протекать в UI и не должно быть “print” повсюду.

**Развёрнуто**
## 1) Цель observability в мобильном приложении
- понять “что произошло” у пользователя,
- быстро локализовать место и причину,
- видеть деградации (latency, error rates),
- воспроизводить цепочки событий.

Если логирование хаотичное:
- много шума,
- нет контекста,
- невозможно связать сетевой запрос с пользовательским действием.

## 2) Три составляющих
### A) Logging (события и контекст)
- структурированные логи (категория, уровень, контекст),
- минимум PII,
- redaction секретов.

### B) Metrics (числа)
- длительность сценариев,
- количество ошибок,
- количество ретраев,
- время рендера/скролла (если измеряете),
- cache hit ratio.

### C) Tracing (цепочки)
- trace/span: user action → use case → repo → network → db,
- correlation id помогает связать разрозненные логи.

## 3) Архитектура без “засорения”
### A) Обёртки и интерфейсы
- `Logger` протокол:
  - `info/warn/error`,
  - принимает `context` (dictionary).
- `Metrics` протокол:
  - `timer`, `counter`, `histogram`.
- `Tracer` протокол:
  - `startSpan(name, context)`.

Фичи используют абстракции, не конкретный SDK.

### B) Точки логирования
Не нужно логировать “везде”.
Лучшие точки:
- границы use case (start/finish + duration),
- ошибки (с категорией и контекстом),
- network layer (request id, status, duration),
- sync engine шаги,
- critical user flows (purchase, login).

UI обычно логирует только high-level события:
- “tap purchase”, “open screen” (и то через analytics/trackers).

## 4) Контекст и корреляция
- создаём `CorrelationID` на входе сценария (например, при нажатии кнопки),
- протаскиваем его через use case/repo,
- добавляем в заголовки запросов (если можно),
- сеть логирует тот же id.

Тогда можно собрать историю:
- почему пользователь увидел ошибку (и где).

## 5) Гигиена и безопасность
- не логировать токены/пароли,
- редактировать PII (email/телефон),
- соблюдать политики (GDPR/комплаенс).

## 6) Тестирование и dev ergonomics
- в debug: больше логов, локальный вывод,
- в release: семплинг, уровни, throttling.

Иначе:
- логи начнут убивать производительность и стоимость отправки.

## 7) Формулировка на собесе
“Я делаю observability как отдельный infrastructure слой: logger/metrics/tracer протоколы, конкретные SDK внутри. Логирую на границах use case и в data layer, использую correlation id/trace для связывания событий, соблюдаю redaction и семплинг. Это помогает дебажить, и код не превращается в ‘print везде’.”

**Самопроверка**
- Оспорено: “логов много — значит хорошо” — нет, важнее структура, контекст и правильные точки; иначе шум и бесполезность.
- Неочевидно: correlation/trace id — главный множитель пользы; без него логирование часто не помогает связать причины и эффекты.
- Источники: observability практики (logs/metrics/tracing), Apple OSLog, коммерческие SDK (Sentry/Datadog) как примеры, инженерные практики семплинга и redaction.

### Q153 (🔴): Как проектировать “потоки” (onboarding/auth/checkout) так, чтобы они были переиспользуемыми и легко менялись?

**Кратко**
- Я моделирую flow как самостоятельный объект:
  - coordinator/flow controller,
  - со своим состоянием (flow state),
  - с явными входами и выходами (inputs/outputs).
- Экраны внутри флоу не знают “что дальше”.
- Переиспользование достигается:
  - отделением flow state от UI state,
  - конфигурацией (feature flags/remote config),
  - шагами как стратегии/состояния state machine.

**Развёрнуто**
## 1) Почему потоки нужно проектировать отдельно
Onboarding/auth/checkout:
- длинные, ветвящиеся,
- зависят от условий (страна, подписка, эксперимент),
- часто меняются продуктом,
- требуют корректного lifecycle (start/cancel/finish).

Если логика потока размазана по VC:
- изменения превращаются в “везде поправить if”,
- растут баги и циклы навигации.

## 2) Flow как координатор + state
### Coordinator
- отвечает за навигацию и сборку экранов.

### Flow state
- хранит:
  - текущий шаг,
  - накопленные данные (например, выбранный тариф),
  - pending deeplink,
  - результаты шагов.

Это flow state, а не data модели всего приложения.

## 3) Шаги как state machine
Практично представлять flow как:
- `enum Step { case welcome, permissions, paywall, finish }`
и переходы:
- `on(event) -> nextStep`.

Тогда:
- ветвления (условия) централизованы,
- легко тестировать переходы.

## 4) Конфигурация и вариативность
Flow должен быть конфигурируемым:
- AB-тесты,
- remote config,
- локаль/регион,
- подписка.

Подход:
- `FlowConfig` + `FlowPolicy`,
- coordinator строит шаги по конфигу.

Важный момент:
- экраны не должны знать про эксперименты, они просто показывают свой UI.

## 5) Переиспользование flow
Если auth flow нужен:
- на старте,
- при 401,
- при попытке открыть защищённый deeplink,
то его нужно запускать как модуль:
- `AuthFlowCoordinator.start(from:)`.

Выход:
- “успех/отмена/ошибка” через output, чтобы вызывающая сторона решала, что дальше.

## 6) Частые ошибки
- Один гигантский AppCoordinator, который держит все флоу.
  - Решение: дерево координаторов + child coordinators.
- Flow state хранит слишком много “данных экрана”.
  - Решение: UI state остаётся в VM, flow state — только то, что нужно между шагами.
- Экраны делают навигацию сами.
  - Решение: outputs/делегаты.

## 7) Как отвечать на собесе
“Я делаю потоки отдельными coordinator’ами со state machine: шаги и переходы централизованы. Экраны отдают события наружу, координатор решает следующий шаг. Потоки имеют вход/выход и конфигурируются флагами, поэтому их можно переиспользовать и менять без переписывания экранов.”

**Самопроверка**
- Оспорено: “достаточно storyboard segues/пушей в VC” — для ветвящихся и часто меняющихся flow это приводит к хаосу и высокой цене изменений.
- Неочевидно: разделение flow state и UI state — ключ к переиспользованию; иначе координатор становится хранилищем всех данных экрана.
- Источники: coordinator pattern, state machine подходы к flows, практики AB-testing/remote config в navigation, опыт крупных приложений.

### Q154 (🔴): Как проектировать A/B эксперименты и feature flags так, чтобы они не разносили if’ы по всему коду?

**Кратко**
- Feature flags — это конфигурация поведения, но если распылить `if flag { ... }` по коду — получится хрупко.
- Подход:
  1) централизованный `FeatureFlagService` (read-only API),
  2) “policy objects”/strategies вместо if,
  3) конфигурируемая сборка фич/флоу (composition root),
  4) флаги не должны проникать в domain правила без явной причины,
  5) тестируемость: фиксировать значение флагов в тестах и снапшотах.

**Развёрнуто**
## 1) В чём вред “флагов повсюду”
- код становится ветвистым и трудно читаемым,
- сложно удалить эксперимент (ветки остаются),
- баги на стыке флагов (комбинаторный взрыв),
- тесты не покрывают все комбинации.

## 2) Централизация доступа
`FeatureFlagService`:
- умеет вернуть типизированные флаги:
  - `isEnabled(.newPaywall)`
  - `variant(.onboardingFlow)` → `.A/.B`
- скрывает remote config провайдера.

Правило:
- фичи не читают “сырые ключи строками”.

## 3) Убрать if’ы через стратегии и конфигурацию
### A) Strategy/Policy
Вместо:
- `if flags.newLayout { renderNew() } else { renderOld() }`
делаем:
- `LayoutPolicy` протокол,
- две реализации,
- выбираем реализацию в composition root по флагу.

Плюсы:
- меньше ветвлений в месте использования,
- эксперимент отключается удалением одной реализации/биндинга.

### B) Конфигурируемая сборка flow
Для onboarding:
- шаги и переходы выбираются `FlowConfig`,
- не нужно “if на каждом экране”.

## 4) Где флаги должны жить по слоям
- Presentation: часто уместно (варианты UI).
- Application/Flow: уместно (варианты сценариев).
- Domain: осторожно, только если это реально “правило продукта”, иначе domain становится нестабильным.

Идея:
- domain должен быть максимально стабильным и не зависеть от экспериментов UI.

## 5) Life-cycle флагов (важно на senior)
Нужна дисциплина:
- флаг имеет owner и дату удаления,
- эксперимент завершён → код ветки удалён,
- иначе “кладбище флагов” навсегда.

## 6) Тестирование
- Для unit/integration тестов:
  - `FeatureFlagService` мокается,
  - фиксируются варианты A/B.
- Для UI snapshot:
  - снимаем снапшоты для A и B (или критичных комбинаций),
- для аналитики:
  - логировать, какой вариант увидел пользователь.

## 7) Формулировка на собесе
“Я не размазываю if’ы по коду. Доступ к флагам централизован, а вариативность реализуется через стратегии и сборку в composition root: выбираем нужные реализации/флоу по флагу. Доменные правила стараюсь не делать зависимыми от экспериментов. Есть дисциплина удаления флагов и тесты по вариантам.”

**Самопроверка**
- Оспорено: “if флагов — нормально” — на масштабе это приводит к комбинаторному взрыву и сложности удаления; лучше инкапсулировать вариативность стратегиями.
- Неочевидно: флаги в domain — риск сделать домен нестабильным; чаще флаги должны жить в presentation/flow.
- Источники: feature flag best practices, strategy/policy patterns, remote config архитектуры, engineering practices по “flag lifecycle”.

### Q155 (🔴): Как проектировать “сложное состояние” (state explosion) в UIKit: когда вводить reducer/store и как не переписать всё?

**Кратко**
- “State explosion” — когда экран/фича имеет много взаимосвязанных состояний и событий, и набор флагов перестаёт работать.
- Сигналы:
  - много флагов (`isLoading`, `isRefreshing`, `isEditing`, `isSelecting`, …) и они конфликтуют,
  - много источников событий (UI + сеть + таймер + notifications),
  - гонки и “невозможные состояния”.
- Решение:
  - вводим явный `State` и `Action`,
  - обновляем state через reducer (детерминированно),
  - side effects выносим отдельно.
- Миграция инкрементальная: сначала моделируем state enum, потом выделяем reducer, потом эффекты.

**Развёрнуто**
## 1) Почему флаги ломаются
Флаги создают множество комбинаций:
- 2 флага → 4 состояния,
- 6 флагов → 64 состояния,
и многие из них “некорректны”.

В результате:
- баги, которые сложно воспроизвести,
- сложные if/else,
- UI “залипает”.

## 2) Когда reducer/store оправдан
- экран похож на mini-app (редактор, чат, корзина, карта),
- есть:
  - сложная интерактивность,
  - асинхронные эффекты,
  - отмена/повтор,
  - параллельные запросы,
  - необходимость строгой последовательности.

Если экран простой — reducer добавит ceremony.

## 3) Минимальная модель UDF
### State
Один объект, описывающий всё, что нужно UI:
- данные,
- режимы,
- под-состояния (pagination, selection, error).

### Action
События:
- UI events (tap, scroll threshold),
- system events (didAppear),
- async results (response, failed).

### Reducer
Функция:
- `(inout State, Action) -> Effect?`
которая:
- детерминированно меняет state,
- возвращает эффекты (запросы, таймеры) как “описания”.

### Effects
Исполняются отдельно:
- выполняют сеть/DB,
- диспатчат обратно actions с результатом.

## 4) Как мигрировать без “переписать всё”
### Step 1: Свести флаги в enum/state
Даже без reducer:
- `ScreenState = loading | content | error`
и внутри content — под-состояния.

Это уже убирает несовместимые комбинации.

### Step 2: Централизовать обновления state
Вместо обновлений из 10 мест:
- один метод `handle(event)` меняет state.

### Step 3: Выделить reducer
Перевести `handle(event)` в чистый reducer:
- меньше side effects внутри.

### Step 4: Вынести эффекты
Вынести сеть/таймеры/уведомления в отдельный слой.

Это можно делать поэтапно.

## 5) Что делать с UIKit
UIKit остаётся:
- подписка на state (Combine/closure),
- `render(state)` (идемпотентно),
- отправка actions (tap/scroll).
То есть:
- UIKit — “view”, а не “controller”.

## 6) Tradeoffs (нужно проговорить)
Плюсы:
- предсказуемость,
- тестируемость (reducer тесты),
- меньше гонок,
- проще reasoning.

Минусы:
- больше “структуры” и кода,
- нужна дисциплина,
- не надо тащить на простые экраны.

## 7) Формулировка на собесе
“Когда количество состояний и асинхронных событий растёт, флаги становятся источником багов. Тогда я ввожу единый State и Action, обновляю его через reducer и выношу эффекты отдельно. Мигрирую по шагам: сначала enum/state, потом централизованный handle, потом reducer, потом эффекты.”

**Самопроверка**
- Оспорено: “reducer/store всегда лучше” — нет, он оправдан при state explosion; на простых экранах увеличит ceremony.
- Неочевидно: миграция должна быть инкрементальной, иначе риск “переписать всё” и сломать продукт.
- Источники: unidirectional data flow практики, TCA/Redux концепты, state machine modeling, опыт внедрения reducer в UIKit экраны.

### Q156 (🔴): Как проектировать тестируемость архитектуры: что тестировать на каком уровне и как не утонуть в моках?

**Кратко**
- Я делю тесты по слоям:
  - **Unit**: доменные правила, reducer/state transitions, маппинг, форматирование.
  - **Integration**: репозиторий + транспорт/DB (контрактные тесты), синк, кеш-политики.
  - **UI/Snapshot**: визуальные регрессии и критические пользовательские сценарии.
- Чтобы не утонуть в моках:
  - мокать только границы (repositories/gateways),
  - использовать fakes/in-memory implementations,
  - избегать чрезмерного протоколирования “внутри слоя”,
  - держать контракты крупнее (use case level).

**Развёрнуто**
## 1) Ошибка №1: пытаться покрыть всё unit-тестами
На мобиле много интеграционных проблем:
- сериализация, кеш, миграции, конкуренция, ретраи.
Unit тесты этого не ловят.

Нужна пирамидка:
- много unit,
- меньше integration,
- немного UI.

## 2) Что тестировать где
### A) Domain / Business rules
- чистые функции, правила валидации, расчёты,
- ошибки и edge cases,
- use case orchestration (если он чистый).

Цель:
- быстро, детерминированно.

### B) Presentation (VM/store)
- state transitions:
  - given State + Action → new State,
- форматирование (date/price),
- правила enable/disable кнопок,
- пагинация state logic.

### C) Data layer
- маппинг DTO ↔ domain,
- error mapping (401/timeout → DomainError),
- caching policies (TTL, stale-while-revalidate),
- дедуп in-flight запросов.

### D) Integration
- репозиторий с реальным HTTP stub / локальной DB,
- контрактные тесты API (schema changes),
- sync engine сценарии.

### E) UI/Snapshot
- дизайн-система компоненты,
- критичные экраны и состояния (loading/empty/error),
- accessibility snapshots (Dynamic Type).

## 3) Как не утонуть в моках
### A) Мокать только на границах
VM тестируем с мокнутыми use cases/repositories.
Use case тестируем с мокнутыми repositories.
Не мокать “внутренние” приватные детали.

### B) Prefer fakes вместо mocks где уместно
- InMemoryRepository,
- StubNetworkClient,
- FakeClock (для TTL),
- TestScheduler.

Fakes дают:
- меньше хрупкости,
- ближе к реальности.

### C) Контракты должны быть достаточно “толстыми”
Если контракты слишком мелкие:
- нужно мокать 20 методов.
Лучше:
- use case-level интерфейсы,
- или репозитории по агрегатам.

### D) Тестировать поведение, а не реализацию
Не проверять “сколько раз вызвали метод X”, если это не важно.
Проверять:
- итоговое состояние,
- возвращаемый результат,
- side effects на уровне контракта.

## 4) Контрактные тесты для репозиториев
Полезный паттерн:
- один набор тестов проверяет контракт `UserRepository`,
- прогоняем для:
  - `RemoteUserRepository`,
  - `CachedUserRepository`,
  - `MockUserRepository`.
Это даёт уверенность, что разные реализации совместимы.

## 5) Формулировка на собесе
“Я строю тестовую пирамиду: доменные правила и state transitions — unit, data layer политики — integration/contract tests, UI — snapshots для регрессии. Мокую только границы и предпочитаю fakes, чтобы не было хрупких тестов, завязанных на имплементацию.”

**Самопроверка**
- Оспорено: “unit тесты достаточно” — нет, проблемы часто интеграционные (кеш/сеть/конкуренция); нужны contract/integration тесты.
- Неочевидно: fakes часто лучше mocks, потому что дают более реалистичное поведение и меньше хрупкости.
- Источники: testing pyramid, контрактные тесты, практики тестирования data layers и reducers/state machines, snapshot testing.

### Q157 (🔴): Как проектировать миграции данных (Realm/CoreData/files) так, чтобы обновления приложения были безопасными?

**Кратко**
- Миграции — часть data layer и release процесса.
- Принципы:
  1) versioned schema и миграции “вперёд”,
  2) идемпотентность и возможность повторного запуска,
  3) тесты миграций на реальных/сэмпл данных,
  4) постепенные изменения (expand → migrate → contract),
  5) план отката: совместимость и корректное поведение при partial migration.
- UI не должен знать про миграции, максимум — показать “обновляем базу” при долгой операции.

**Развёрнуто**
## 1) Почему миграции ломают прод
- у пользователей база разных версий,
- миграция может занять время (большие данные),
- могут быть краши из-за несовместимых моделей,
- могут быть прерывания (app killed, low storage).

Нужно проектировать под “грязную” реальность.

## 2) Versioning и стратегия изменений
### A) Expand → Migrate → Contract
Чтобы не ломать обратную совместимость:
1) Expand: добавить новые поля/таблицы без удаления старых.
2) Migrate: заполнить новые поля на основе старых.
3) Contract: удалить старые поля в следующем релизе, когда уверены.

Это снижает риск, особенно когда есть server sync.

## 3) Идемпотентность и прерывания
Миграция должна:
- быть безопасной при повторном запуске,
- не полагаться на “всё выполнится за один раз”.

Подходы:
- миграционные флаги/метки версии,
- атомарные шаги,
- checkpoints.

## 4) Производительность миграции
- ленивые миграции: мигрировать сущности по мере доступа (если возможно),
- батчи (chunking),
- минимизация аллокаций,
- перенос тяжёлой работы из main thread (если технология позволяет),
- прогресс и возможность показать UI.

## 5) Files и storage вне DB
Часто данные = DB + файлы (PDF, изображения).
Миграции должны учитывать:
- переименование путей,
- перемещение директорий,
- чистку orphan files,
- согласованность DB ↔ filesystem.

Это часто забывают, и появляются “битые ссылки”.

## 6) Тестирование миграций
Нужны:
- фикстуры баз старых версий (реальные dump/seed),
- автотест, который:
  - запускает миграцию,
  - проверяет инварианты,
  - проверяет сохранность данных,
  - проверяет скорость (хотя бы грубо).

## 7) Rollout и наблюдаемость
- feature flags/remote config для включения новых моделей поведения,
- логирование времени миграции и ошибок,
- crash reporting с тегом “migration”.

Иногда полезно:
- “мягкий запуск” миграции (мигрировать только часть данных, если возможно).

## 8) Формулировка на собесе
“Я делаю схемы версионными и использую стратегию expand→migrate→contract. Миграции идемпотентны, тестируются на фикстурах старых версий и учитывают файловое хранилище. Для больших баз — батчи/ленивые миграции и UI-индикатор. Плюс наблюдаемость и безопасный rollout.”

**Самопроверка**
- Оспорено: “миграция — это один скрипт и готово” — реальность включает прерывания, performance и сочетание DB+filesystem; нужна стратегия и тесты.
- Неочевидно: expand→migrate→contract снижает риск и позволяет выпускать изменения поэтапно, а не “всё сразу”.
- Источники: практики миграций (DB schema evolution), опыт Realm/Core Data migrations, release engineering, observability при миграциях.

### Q158 (🔴): Как ты проектируешь обработку ошибок “сквозь слои”: network → domain → UI, чтобы не терять смысл и не делать “String everywhere”?

**Кратко**
- Я не передаю `Error.localizedDescription` как единственную “модель ошибки”.
- Деление:
  1) Infrastructure errors (HTTP/timeout/decoding) → маппятся в `DomainError`.
  2) DomainError → маппится в `UIErrorState` (текст + action + presentation style).
- Маппинг делаю в одном месте (policy/mapper), чтобы поведение было единым.
- UI получает готовую модель для отображения и ретрая, а не детали транспорта.

**Развёрнуто**
## 1) Почему “String everywhere” ломает продукт
Если ошибки — строки:
- нельзя единообразно обрабатывать,
- нельзя локализовать нормально,
- невозможно отличить retryable vs non-retryable,
- аналитика ошибок становится мусором,
- теряется причина (network vs auth vs validation).

## 2) Слои ошибок
### A) Infrastructure
Ошибки типа:
- HTTP status, URLSession error,
- decoding error,
- connectivity.

### B) Domain
DomainError описывает смысл:
- `.unauthorized`
- `.rateLimited(retryAfter:)`
- `.notFound`
- `.validationFailed(field:)`
- `.offline`
- `.unknown`

Важно:
- domain не должен содержать URL/эндпоинты.

### C) UI
UIErrorState — это “как показать”:
- title/message (локализуемые ключи),
- CTA:
  - retry,
  - login,
  - open settings,
  - contact support,
- presentation:
  - inline,
  - fullscreen,
  - toast.

## 3) Где делать маппинг
- infra → domain: в data layer (repository/adapters).
- domain → UI: в presentation layer (VM) или отдельный UIErrorMapper.

Главное:
- единая точка, а не 20 раз `switch error` в разных экранах.

## 4) Retry policy как часть модели
Не все ошибки нужно ретраить:
- timeout → да,
- 400 validation → нет,
- 401 → запустить auth flow,
- offline → показать offline UI и попробовать позже.

Если сделать это через типы:
- UI знает “какое действие предложить”, не вникая в детали.

## 5) Сохранение контекста (не терять смысл)
Иногда полезно иметь:
- `underlying` (для логирования),
- `requestId/correlationId` (для поддержки),
- “debug info” только для observability, не для UI.

Т.е.:
- смысл в domain,
- детали в логах.

## 6) Формулировка на собесе
“Я делю ошибки по слоям. Инфраструктурные ошибки мапплю в доменные типы, которые отражают смысл и позволяют принять решение (retry/login/etc). Затем доменные ошибки мапплю в UIErrorState, который задаёт текст и действие. Это избегает ‘String everywhere’ и делает поведение единообразным и тестируемым.”

**Самопроверка**
- Оспорено: “достаточно localizedDescription” — это теряет тип и смысл, мешает ретраям/аналитике/локализации и приводит к копипасте обработчиков.
- Неочевидно: важно не только “показать текст”, но и закодировать action/presentation; иначе логика ретраев расползётся по UI.
- Источники: layered error handling practices, mapping patterns (DTO→domain аналогия), retry policies, локализация ошибок.

### Q159 (🔴): Как спроектировать networking layer (клиент), чтобы поддерживать retries, interceptors, cancellation и тестируемость?

**Кратко**
- Я разделяю networking на уровни:
  1) **Endpoint/Request description** (типизированное описание запроса),
  2) **HTTP client** (исполнение, URLSession),
  3) **Interceptors/Middleware** (auth, headers, logging, retry, caching hints),
  4) **Decoding & error mapping** (infra → domain),
  5) **Cancellation & dedup** (in-flight, таймауты).
- Снаружи networking даёт маленький API: `execute(endpoint) -> Decoded`.
- Тестируемость: протокол `HTTPTransport` + стабы/record-replay, детерминированные ретраи.

**Развёрнуто**
## 1) Типичные боли “наивного” networking
- в каждом запросе копипаста: headers/auth/logging,
- хаос с 401 refresh,
- ретраи неуправляемы (дубли запросов),
- cancellation работает странно,
- тесты упираются в URLSession и реальные тайминги.

Поэтому нужен слой политики, а не просто “метод fetch”.

## 2) Разделение ответственности
### A) Endpoint как типизированное описание
Endpoint содержит:
- method/path/query/body,
- expected response type,
- требования:
  - auth required,
  - cache policy hint,
  - idempotent (для safe retries),
  - timeout.

Это позволяет:
- централизовать построение URLRequest,
- иметь единый ключ для дедупа (endpoint key).

### B) HTTP client
- принимает `Endpoint`,
- строит `URLRequest`,
- вызывает transport,
- возвращает `Data/Response` или mapped error.

### C) Transport (абстракция над URLSession)
`HTTPTransport`:
- `func send(_ request: URLRequest) async throws -> (Data, HTTPURLResponse)`
Реализации:
- URLSessionTransport,
- StubTransport (тесты),
- RecordingTransport (для отладки/реплея).

### D) Interceptors/Middleware
Цепочка, которая может:
- модифицировать request (auth headers),
- логировать/трейсить,
- обрабатывать 401 (refresh + retry),
- делать retries/backoff по политике,
- добавлять correlation id.

Важно:
- interceptors не должны знать про UI.

## 3) Retry policy (ключевой дизайн)
Не все запросы ретраим:
- safe (GET) чаще можно,
- non-idempotent (POST) — осторожно, иначе дубли операций.
Решение:
- endpoint описывает idempotency,
- policy решает:
  - какие ошибки retryable (timeout, 5xx),
  - сколько раз,
  - backoff/jitter,
  - circuit breaker (если нужно).

## 4) Cancellation и таймауты
- Cancellation должна:
  - отменять конкретный запрос,
  - не ломать других подписчиков, если есть дедуп/coalescing.
- Таймаут:
  - на endpoint уровне (per request),
  - и общий (session).

Если используешь in-flight дедуп:
- cancellation одного await’ера ≠ отмена общего запроса (нужно ownership/refcount или “не propagate”).

## 5) Dedup in-flight (опционально, но сильно помогает)
- in-flight table по ключу запроса,
- коалесинг одинаковых запросов.
Это снижает:
- нагрузку,
- “шторма” в момент открытия экрана.

## 6) Error mapping
Networking возвращает:
- инфра-ошибки (status, decoding, connectivity),
Data layer (repo) маппит в:
- DomainError.
UI видит:
- UIErrorState (через маппер).

Так не протекают HTTP детали.

## 7) Тестируемость без боли
- transport мокается,
- retry policy тестируется отдельно (на fake clock),
- interceptors тестируются “как pipeline”:
  - на вход request,
  - на выход side effects (например, added header, number of attempts).

## 8) Формулировка на собесе
“Я строю networking как pipeline: endpoint описывает запрос, transport исполняет, interceptors добавляют auth/logging/retry, есть политика retries с учетом idempotency и корректная cancellation. Всё тестируемо через transport abstraction и отдельные тесты для policy/interceptors.”

**Самопроверка**
- Оспорено: “URLSession достаточно” — URLSession исполняет, но политика (auth/retry/logging/dedup) должна быть архитектурно выделена, иначе будет копипаста и баги.
- Неочевидно: retries без учёта idempotency могут привести к дублям операций; это нужно кодировать в endpoint/policy.
- Источники: практики HTTP middleware/interceptors, идемпотентность и retry policies, Swift Concurrency cancellation semantics, опыт построения testable networking layers.

### Q160 (🔴): Как проектировать “границы модулей” и публичный API фичи (SPM/targets), чтобы команда могла работать параллельно?

**Кратко**
- Я проектирую фичу как модуль с минимальным публичным API:
  - `FeatureEntryPoint` (factory/coordinator),
  - contracts (inputs/outputs),
  - иногда — UI components, если они реально shared.
- Внутри модуля всё `internal` по умолчанию.
- Зависимости направлены: Core → Features, фичи не импортят друг друга.
- Параллельная работа = стабильные контракты + независимая сборка + тесты на контракт.

**Развёрнуто**
## 1) Почему “границы модулей” — это про скорость команды
Если границы слабые:
- фичи начинают тянуть типы друг друга,
- любая правка ломает компиляцию в соседних местах,
- появляется “невидимый coupling”,
- сборка замедляется из-за огромных targets.

Правильные границы позволяют:
- разным людям менять разные модули без конфликтов,
- делать релизы безопаснее.

## 2) Публичный API фичи: что можно экспортировать
### A) Entry point
Единственный “вход”:
- `FeatureXEntryPoint`:
  - `makeRoot(...) -> UIViewController`
  - или `start(from:)`.

### B) Inputs/Outputs
- входные параметры (минимум),
- outputs/callbacks для событий наружу:
  - `onFinished`, `onSelected`.

### C) Contracts (если нужно)
Если другие фичи должны обращаться:
- экспортировать только протоколы/минимальные типы в отдельном Contracts/CoreDomain модуле.

Важно:
- не экспортировать внутренние VC/VM/DTO.

## 3) Что должно быть `internal`
- ViewControllers, ViewModels,
- DTO и мапперы,
- внутренние helpers,
- внутренние модели, которые не являются domain.

Правило: “internal by default” — лучший способ не допустить протекания.

## 4) Управление зависимостями
### A) Dependency direction
- FeatureX зависит от CoreDomain/CoreInfra/CoreUI,
- App зависит от всех features,
- features не зависят друг от друга напрямую.

### B) Если нужно “вызвать” другую фичу
Через:
- entry point другой фичи, который прокинул app/coordinator,
а не через импорт и прямое создание VC.

## 5) Контрактные тесты на публичный API
Чтобы контракты не ломались незаметно:
- тесты, которые проверяют вход/выход entry point,
- API evolution через deprecation и версионирование, если нужно.

## 6) Сборка и скорость
- меньше публичных символов → меньше recompilation и меньше coupling,
- небольшие модули позволяют параллельную компиляцию,
но:
- слишком мелкая модульность может добавить overhead.
Поэтому модульность должна следовать границам домена/команды, а не “по папкам”.

## 7) Формулировка на собесе
“Я делаю фичи отдельными модулями с entry point и минимальным публичным API. Внутренности — internal. Контракты живут в core/contracts, зависимости направлены (features → core). Межфичевые взаимодействия через entry points/outputs. Это даёт независимую разработку, меньше конфликтов и быстрее сборку.”

**Самопроверка**
- Оспорено: “можно просто всё сделать public ради удобства” — это разрушает границы и делает проект неуправляемым на масштабе.
- Неочевидно: модульность ради модульности не спасёт; важно правильно выбрать границы (feature/team boundaries) и держать dependency rule.
- Источники: modular architecture практики, Swift access control и его роль, build performance и dependency graphs, feature entry points.

### Q161 (🔴): Как ты принимаешь решение “монолит vs модульность” в iOS и как объясняешь tradeoffs?

**Кратко**
- Модульность — инструмент, а не цель.
- Я выбираю модульность, когда она решает конкретную боль:
  - параллельная работа команд,
  - долгие сборки и высокая связность,
  - необходимость переиспользовать/изолировать фичи,
  - разные циклы релизов/экспериментов.
- Я избегаю чрезмерной модульности, когда:
  - команда маленькая,
  - продукт быстро меняется и границы ещё не стабилизировались,
  - overhead SPM/targets/пакетов превышает пользу.
- Критерии: coupling, build invalidation, ownership, dependency graph.

**Развёрнуто**
## 1) Почему “модульность” не всегда выигрывает
Модульность добавляет:
- overhead на поддержку графа зависимостей,
- усложнение навигации/DI wiring,
- необходимость контрактов и дисциплины public API,
- время на инфраструктуру (SPM, CI, линтеры, versioning пакетов).

Если команда маленькая и продукт в поиске:
- цена поддержки может превысить выгоду.

## 2) Когда монолит оправдан
- 1–3 разработчика,
- ранняя стадия, фичи часто переезжают,
- высокий темп экспериментов,
- сборки уже быстрые,
- нет потребности шарить код между приложениями.

Но даже в монолите важно:
- держать границы в коде (слои/фичи), чтобы потом можно было резать.

## 3) Когда модульность приносит реальную пользу
### A) Командная масштабируемость
- разные команды/подкоманды отвечают за разные фичи,
- меньше конфликтов и зависимостей.

### B) Build performance
- тяжёлые зависимости изолируются,
- меньше recompilation при изменениях в одной области.

### C) Управляемость зависимости и границ
- dependency rule становится enforceable,
- легче предотвратить “протекание” типов.

### D) Переиспользование
- shared design system,
- shared infra (networking, observability),
- возможно переиспользование фич.

## 4) Как оценивать “нужно ли резать”
Я смотрю на признаки:
- “изменил один файл → пересобралось всё”,
- много cross-imports и shared utils,
- сложно удалить/заменить фичу,
- onboarding нового разработчика тяжёлый,
- модули уже логически существуют (владельцы, домены).

Если есть эти симптомы — модульность становится выгодной.

## 5) Как резать безопасно (инкрементально)
Не делать “big bang”.
Шаги:
1) выделить `CoreDomain` (контракты/модели) и `CoreInfrastructure`,
2) выделить `CoreUI` (tokens/primitives),
3) вынести одну фичу как пилот (FeatureX),
4) ввести entry points и правило “features не импортят features”,
5) автоматизировать проверки графа.

## 6) Как объяснить tradeoffs на собесе
Важно говорить не “я люблю модульность”, а “я выбираю по боли”.
И проговорить риски:
- слишком мелкие модули → overhead и сложность,
- слишком крупные → нет эффекта.

## 7) Формулировка на собесе
“Я принимаю решение по критериям: размер команды, скорость сборки, связность и ownership. Если модульность решает конкретную боль (build invalidation, параллельная работа, границы), я режу инкрементально: core modules → пилотная фича → правила dependency graph. Если нет — держу монолит, но с явными слоями и границами, чтобы позже резать было безопасно.”

**Самопроверка**
- Оспорено: “модульность всегда лучше” — нет, она имеет цену; в маленькой команде и на ранней стадии монолит часто эффективнее.
- Неочевидно: правильный ответ — про критерии и инкрементальную стратегию, а не про “религию” SPM/архитектуры.
- Источники: iOS modularization практики, build performance и incremental compilation принципы, dependency graph management, опыт масштабирования команд.

### Q162 (🔴): Как бы ты спроектировал “антипод” Massive ViewController: правила разделения UI/Presentation/Domain в UIKit проекте?

**Кратко**
- Massive VC возникает, когда VC делает: навигацию, бизнес-логику, сеть, хранение, форматирование, state и UI одновременно.
- Я придерживаюсь правил:
  1) VC = только UI wiring + render(state) + user events → VM.
  2) VM/store = состояние экрана + преобразование domain → UI + orchestration.
  3) Use cases = бизнес-сценарии (композиция репозиториев).
  4) Repositories = доступ к данным (кеш/сеть/DB) и маппинг.
  5) Навигация = координатор/роутер.
- Цель: каждый слой тестируем и заменяем без цепной реакции.

**Развёрнуто**
## 1) Чёткое распределение ответственности
### UIViewController
- создание/настройка UI,
- подписка на state,
- отправка user actions:
  - `didTap`, `didScroll`, `didSelect`.
- минимум логики: “как отрендерить”.

Нельзя:
- ходить в сеть,
- писать в БД,
- хранить бизнес-состояние.

### ViewModel/Store
- хранит `State`,
- решает, что показывать (loading/empty/content/error),
- форматирует для UI (date/price),
- запускает use cases,
- обрабатывает результаты и ошибки,
- управляет пагинацией/дедупом UI событий.

### Use case / Interactor
- отражает бизнес-сценарий:
  - “загрузить ленту”,
  - “купить подписку”,
  - “сохранить документ”.
- знает, какие репозитории дергать и в каком порядке,
- возвращает доменные модели/результаты.

### Repository
- скрывает детали:
  - сеть/кеш/БД,
  - дедуп in-flight,
  - маппинг DTO ↔ domain,
  - retry policies.

### Coordinator/Router
- навигация и flow,
- dependency injection и сборка экранов,
- deeplinks.

## 2) Как не скатиться обратно
### A) Не давать VC доступ к инфраструктуре
- VC не должен иметь `NetworkClient` или `Realm`.
Если доступ есть — он будет использоваться.

### B) Явные входы в VM
- VM принимает use cases и navigator протоколы.
Это ограничивает “что можно сделать” на уровне кода.

### C) Render как функция состояния
- VC не принимает решений “что показать” по флагам.
Он рендерит state, который даёт VM.

## 3) Что делать с “маленькими” экранами
Правило масштаба:
- можно упрощать, но инварианты сохранять.
Например:
- use case может быть тонким,
- repository простым,
но:
- VC всё равно не должен знать транспорт/хранилище.

## 4) Признаки, что VC снова стал massive
- VC > 300–500 строк и растёт,
- много async calls,
- куча private методов “business” характера,
- сложное состояние и флаги,
- прямые зависимости на сервисы.

Лечение:
- вынести state в VM,
- вынести навигацию в coordinator,
- вынести data access в repo,
- выровнять модели (DTO/domain/UI).

## 5) Формулировка на собесе
“Я делаю VC максимально тонким: он рендерит state и отправляет события. Состояние и orchestration — в VM/store, бизнес-сценарии — в use cases, доступ к данным — в repositories, навигация — в coordinator. Так Massive VC не появляется, потому что у каждого слоя чёткая ответственность и ограниченные зависимости.”

**Самопроверка**
- Оспорено: “достаточно вынести часть методов в extensions” — это косметика; massive VC — проблема ответственности, а не файлов.
- Неочевидно: архитектура держится на ограничении зависимостей (VC не должен иметь доступ к data layer), иначе границы быстро разрушатся.
- Источники: MVVM/Clean layering практики, coordinator pattern, опыт больших UIKit проектов и анти-паттерн Massive ViewController.

### Q163 (🔴): Как проектировать интеграцию сторонних SDK (analytics/payments/ads) так, чтобы можно было заменить провайдера без переписывания фич?

**Кратко**
- Я не даю фичам импортировать SDK напрямую.
- Делается слой адаптеров:
  1) `AnalyticsTracking`, `PaymentsService`, `AdsServing` — протоколы,
  2) конкретные адаптеры (Firebase/Amplitude, StoreKit/Apphud, AdMob…) в infrastructure,
  3) внедрение через DI в composition root,
  4) домен/фичи общаются через стабильные контракты.
- Для логирования/ошибок/метрик — общий observability слой.

**Развёрнуто**
## 1) Почему прямой импорт SDK в фичах — дорого
- vendor lock-in,
- сложно мокать в тестах,
- SDK диктует модели/ошибки и протекает по коду,
- обновление SDK ломает много модулей,
- сложно разделять ownership в команде.

## 2) Контрактный слой (facade)
Делаю маленькие интерфейсы:
- `AnalyticsTracking.track(event:)`
- `PaymentsProviding.purchase(productID:)`
- `RemoteConfigProviding.value(for:)`
- `CrashReporting.record(error:)`

Контракты должны:
- использовать доменные/нейтральные типы,
- не протекать vendor-типами.

## 3) Адаптеры (adapter) и фасады (facade)
### Adapter
- маппит наши типы в типы SDK,
- обрабатывает ошибки SDK,
- применяет политики (например, throttling).

### Facade
- скрывает “комплексность” нескольких SDK:
  - analytics + crash + logs,
  - payments + receipt validation.

Фича не знает, что под капотом 2–3 SDK.

## 4) Замена провайдера без переписывания
Если завтра Firebase → Amplitude:
- меняется только реализация `AnalyticsTracking`,
- фичи остаются на контракте.

Это работает только если:
- контракт не протёк vendor-specific возможностями.
Поэтому:
- не включать в контракт “экзотические” API SDK без необходимости,
- или делать расширения как отдельные capability протоколы.

## 5) Capability-based дизайн
Если часть фич требует особых возможностей:
- `AnalyticsTracking` базовый,
- `AttributionTracking` дополнительный capability,
- фича, которой нужно, зависит от capability, а не от всего SDK.

Это уменьшает “всезнание” и coupling.

## 6) Тесты
- SDK адаптеры можно покрыть контрактными тестами,
- в фичах использовать fakes/stubs контрактов,
- важно тестировать:
  - что события трекаются,
  - что purchase flow корректно маппит статусы,
а не детали SDK.

## 7) Формулировка на собесе
“Я интегрирую сторонние SDK через слой адаптеров и контрактов. Фичи знают только протоколы вроде AnalyticsTracking/PaymentsProviding. Конкретные провайдеры создаются в composition root. Это упрощает замену SDK, тестирование и ограничивает протекание vendor-типов.”

**Самопроверка**
- Оспорено: “проще импортировать SDK прямо в фичу” — краткосрочно да, но потом это создаёт vendor lock-in, проблемы тестирования и сложные миграции.
- Неочевидно: важно проектировать контракты нейтрально; если контракт отражает особенности SDK, замена всё равно будет дорогой.
- Источники: adapter/facade patterns, DI best practices, опыт миграций analytics/payments SDK, capability-based интерфейсы.

### Q164 (🔴): Как проектировать API слоя домена так, чтобы он был удобен для async/await и cancellation?

**Кратко**
- Доменные API должны выражать **намерение**, быть **детерминированными** и **без привязки к платформенным деталям**.
- Для Swift Concurrency:
  - `async throws` для единичного результата,
  - `AsyncSequence/AsyncStream` для потоков,
  - принимать `Cancellation` как *семантику*, а не как “ручку отмены”.
- Отмена должна:
  - корректно “пробрасываться вниз” в data layer,
  - быть **идемпотентной** (отменили дважды — всё ок),
  - не оставлять систему в полусостоянии.

**Развёрнуто**
## 1) Что значит “удобный доменный API”
Удобный API в домене:
- не требует от UI знать про `URLSession`, кэш, ретраи,
- не заставляет таскать “политику” параметрами (`cachePolicy`, `retryCount`, …),
- легко комбинируется (compose) и тестируется.

Хорошая формулировка методов:
- `refreshFeed()`
- `loadNextPage()`
- `observeSession()`

Плохая:
- `loadFeed(forceNetwork: Bool, retry: Int, queue: DispatchQueue, completion: ...)`

## 2) Модели асинхронности в домене
### A) Один результат
Используй:
- `func execute(...) async throws -> Output`

Где `Output` — доменная модель или доменный результат:
- `Result<Value, DomainError>` обычно не нужен, если есть `throws`.

### B) Поток значений / подписка
Если домен “стримит”:
- `AsyncSequence` (лучше) или `AsyncStream`.

Примеры, где поток уместен:
- состояние сессии,
- прогресс синка/загрузки,
- наблюдение за изменениями данных (если домен так спроектирован).

Важно:
- домен не обязан “стримить UI-частоты”; поток должен отражать доменную семантику.

## 3) Cancellation: что должно быть истинно (инварианты)
- Отмена — нормальная ветка выполнения, а не “ошибка”.
- Отмена должна:
  - не ломать инварианты данных,
  - не оставлять “висящие” ресурсы (таймеры, подписки),
  - корректно освобождать “in-flight” (если дедуп/коалесинг).

Типичная семантика:
- доменный метод при отмене завершает `throw CancellationError()` (или пробрасывает отмену как есть).

## 4) Где “живет” cancellation и как пробрасывается вниз
### Правило
**Домен не должен изобретать свой механизм отмены** (типа custom token), если проект на Swift Concurrency.

Проброс вниз:
- use case → repository → transport.
Transport (например, URLSession) должен реально отменять запрос, если Task отменили.

Если есть коалесинг одинаковых запросов:
- отмена одного “подписчика” не обязана отменять общий in-flight запрос.
Нужна политика:
- “shared request” живет пока есть хотя бы один consumer.

## 5) Не протаскивай “политики инфраструктуры” в домен
Частая ошибка: доменный API принимает параметры типа:
- `timeout`, `retryPolicy`, `cachePolicy`.

Это создаёт:
- протекание инфраструктуры в домен,
- взрыв параметров,
- поломку границ.

Вместо этого:
- домен выражает **намерение** (refresh vs load),
- политики живут ниже (data layer / infra),
- а вариативность в домене решается сценариями (разные use cases), а не “flags параметрами”.

## 6) Тестируемость доменных async API
- Use cases должны быть тестируемы через моки/фейки репозиториев.
- Для cancellation тестов:
  - использовать controlled fakes, которые “подвисают” и проверять, что отмена приводит к корректному завершению,
  - проверять инварианты (ничего не записалось, если отменили до commit).

## 7) Как отвечать на собесе
“Я делаю доменные методы `async throws` для единичных операций и `AsyncSequence` для наблюдения. Отмена — часть семантики: Task cancellation пробрасывается вниз до transport, use case при отмене не должен оставлять систему в полусостоянии. Инфраструктурные политики (retry/timeout/cache) не протаскиваю в домен — домен выражает намерение, а политики реализуются ниже.”

**Самопроверка**
- Оспорено: “домену нужно знать про timeout/retry” — это протекание инфраструктуры; домен должен выражать намерение и инварианты.
- Неочевидно: cancellation в присутствии коалесинга/in-flight дедупа — нужен явный выбор политики (отмена одного consumer ≠ отмена запроса).
- Источники, которые стоит освежить: Swift Concurrency cancellation semantics, AsyncSequence/AsyncStream, URLSession отмена через Task, практики layered architecture (границы домена и инфраструктуры).

### Q165 (🔴): Как строить policy для ретраев/таймаутов/бекоффа, где она живёт?

**Кратко**
- Retry/timeout/backoff — это **инфраструктурная политика**, не задача UI и не часть доменных правил.
- Политика должна быть:
  - централизованной,
  - тестируемой (fake clock),
  - учитывающей идемпотентность запросов,
  - различающей типы ошибок (retryable vs non-retryable),
  - поддерживающей jitter и лимиты.
- Живёт обычно:
  - в networking pipeline (interceptors),
  - частично в repository (если зависит от сценария),
  - но не в VC/VM.

**Развёрнуто**
## 1) Почему policy нельзя “размазать”
Если в каждом месте:
- `retry 3 times with 1s delay`,
получаем:
- разные поведения для одинаковых ошибок,
- невозможность быстро поменять стратегию,
- скрытые ретраи (удвоение нагрузки),
- сложность дебага.

Policy должна быть в одном месте.

## 2) Что включает policy
### A) Timeout policy
- global timeout по умолчанию,
- per-endpoint override (но не из UI),
- разные таймауты для:
  - download,
  - upload,
  - auth refresh.

### B) Retry policy
Определяет:
- какие ошибки retryable:
  - connectivity,
  - timeouts,
  - 5xx,
  - 429 (rate limit) — с `Retry-After`.
- какие НЕ retryable:
  - 4xx validation,
  - unauthorized (обычно не retry, а refresh/login),
  - decoding error (чаще баг/контракт).

### C) Backoff policy
- exponential backoff:
  - `base * 2^attempt`,
- jitter (случайность), чтобы не устроить синхронный “шторм” запросов,
- max delay cap.

## 3) Ключевой критерий: идемпотентность
Ретраить безопасно только если:
- запрос идемпотентен (GET, PUT при корректной семантике),
- или сервер поддерживает idempotency keys для POST.

Иначе:
- рискуешь дублями операций (двойная покупка, двойное создание).

Поэтому:
- endpoint должен иметь флаг `isIdempotent`,
- policy учитывает его.

## 4) Где именно “живёт” policy (практическая схема)
### A) Networking layer (лучшее место)
- interceptor/middleware:
  - применяет таймаут,
  - решает retry/backoff,
  - делает logging/metrics.

Плюс:
- единообразие.

### B) Repository layer (когда нужно)
Если retry зависит от доменной семантики:
- например, “если refresh feed — можно stale data, если checkout — нельзя”.
Тогда репозиторий может выбирать:
- разные endpoint/policies,
или разные сценарии (use cases).

Важно:
- repository не должен реализовывать backoff вручную; он выбирает политику/конфиг, а исполняет инфраструктура.

### C) UI/VM — запрещено
UI может инициировать:
- `retry` как намерение пользователя,
но не задавать:
- “сколько раз” и “как” ретраить.

## 5) Circuit breaker и rate limiting (если зрелый уровень)
Если сервис падает:
- бесконечные ретраи вредны.
Механизмы:
- circuit breaker (open/half-open/closed),
- global throttle,
- cooldown.

Это тоже часть infrastructure policy.

## 6) Тестирование policy
Нужно тестировать:
- decision matrix: (error, attempt, idempotency) → action,
- backoff timing через fake clock,
- 429 `Retry-After` поведение,
- cap и jitter (jitter тестируется как “в диапазоне”).

## 7) Формулировка на собесе
“Retry/timeout/backoff — инфраструктурная политика. Я реализую её в networking interceptor: определяю retryable ошибки, учитываю идемпотентность, использую exponential backoff с jitter и лимитами, поддерживаю 429 с Retry-After. UI лишь инициирует retry как действие пользователя, но не содержит политику.”

**Самопроверка**
- Оспорено: “ретраи можно просто добавить где удобно” — это приводит к разным стратегиям, удвоению нагрузки и проблемам дебага.
- Неочевидно: идемпотентность — критический предохранитель; без неё ретраи могут создавать дубли операций.
- Источники, которые стоит освежить: HTTP semantics (idempotency), best practices retry/backoff/jitter, handling 429 Retry-After, Swift Concurrency cancellation + retry interplay.

### Q166 (🔴): Как сделать модуль фичи “подключаемым”: публичные интерфейсы, сборка, ресурсы, локализация?

**Кратко**
- “Подключаемая фича” = модуль, который можно добавить/убрать, не ломая остальное.
- Требования:
  1) минимальный public API (entry point),
  2) отсутствие прямых зависимостей на другие features,
  3) ресурсы/локализация внутри модуля (bundle),
  4) явные зависимости через DI (inputs),
  5) устойчивость к отсутствию фичи (fallback/guards).
- Реально реализуется через SPM target (или framework) + entry point + resource bundle.

**Развёрнуто**
## 1) Что значит “подключаемый”
Фичу можно:
- вынести в отдельный пакет/таргет,
- отключить флагом или вообще не включать в сборку,
- при этом приложение компилируется и работает (с деградацией функционала).

## 2) Публичный интерфейс (entry point)
Экспортировать наружу:
- `FeatureXEntryPoint` / `FeatureXFactory`:
  - `makeRoot(dependencies:) -> UIViewController`
  - или `start(from:dependencies:)`.

Inputs:
- только то, что реально нужно:
  - `SessionProvider`,
  - `AnalyticsTracking`,
  - `FeatureFlags`,
  - `Navigator` (если нужно).

Outputs:
- callbacks/делегаты:
  - `onFinished`,
  - `onSelected(id:)`.

Правило:
- наружу не торчат VC/VM/DTO.

## 3) Как устроить ресурсы и локализацию в модуле
### A) Resources
Если SPM:
- объявлять ресурсы в `Package.swift` через `.process("Resources")`.
Получать bundle:
- через `Bundle.module`.

Если framework:
- иметь отдельный resource bundle (или использовать `Bundle(for:)` и искать bundle ресурсов).

Важно:
- не использовать `Bundle.main` внутри модуля для ресурсов.

### B) Localization
- `Localizable.strings` кладём в resources модуля.
- доступ к строкам через helper, который берёт bundle модуля, не main:
  - `NSLocalizedString(key, bundle: .module, ...)`.

Если есть общий механизм локализации:
- он должен уметь принимать bundle (или иметь “resolver”).

## 4) Сборка и регистрация фичи
### A) Composition root
`AppAssembly` решает:
- включать фичу или нет,
- отдаёт entry point.

### B) Feature registry (опционально)
Если фич много:
- registry “ключ → entry point”.
Но осторожно:
- не превращать registry в God-object.
Лучше:
- типизированный набор фич, или DI контейнер на верхнем уровне.

## 5) Безопасная “отсутствующая” фича
Если фичу можно отключить:
- вызывающая сторона не должна падать.
Подходы:
- optional entry point,
- no-op implementation,
- fallback экран (“feature unavailable”).

## 6) Версионирование и контракты
Если фича — отдельный пакет:
- semver,
- deprecations,
- контрактные тесты entry point.

Это нужно, если фичи развиваются независимо.

## 7) Типичные ошибки
- фича тянет другую фичу (циклы),
- `Bundle.main` для ресурсов → ресурсы не находятся,
- строки локализации лежат в main bundle → модуль перестаёт быть автономным,
- публичные модели растекаются наружу → coupling.

## 8) Формулировка на собесе
“Я делаю фичу подключаемым модулем с entry point и минимальным public API. Все ресурсы и локализация живут внутри модуля и грузятся из его bundle. Зависимости вводятся через DI. В App composition root решается, включать фичу или нет, с fallback на отсутствие.”

**Самопроверка**
- Оспорено: “достаточно вынести в таргет” — без автономных ресурсов/локализации и без строгого public API фича всё равно будет зависеть от main и других частей.
- Неочевидно: большинство проблем “подключаемости” — это bundle/resources/localization и протекание типов, а не сам SPM.
- Источники, которые стоит освежить: SwiftPM resources (`Bundle.module`), локализация в пакетах/фреймворках, modular architecture entry points, семантика public/internal для ускорения сборки.

### Q167 (🔴): Как решать проблемы циклических зависимостей между модулями?

**Кратко**
- Циклы появляются, когда модули знают друг о друге и импортят реализации.
- Основные способы разорвать цикл:
  1) вынести **контракты** (протоколы/типы) в отдельный “верхний” модуль (Core/Contracts),
  2) зависеть **на абстракции**, а не на реализацию (DIP),
  3) общаться через **entry points** и **outputs**, а не через прямой импорт,
  4) поднять wiring в composition root (App),
  5) не превращать “Utils/Shared” в свалку.
- Контроль: rules + автоматические проверки dependency graph.

**Развёрнуто**
## 1) Откуда берутся циклы
Типичные причины:
- FeatureA вызывает FeatureB напрямую (import),
- общие типы лежат “не там” (в FeatureB, а нужны FeatureA),
- “Shared” модуль стал зависеть от фич,
- сервис-локатор позволяет скрыто тянуть зависимость назад,
- навигация размазана (FeatureA держит типы экранов FeatureB).

## 2) Dependency rule как основа
Нужно заранее определить направление:
- Features → Core
- App → Features
- Features ⛔️→ Features (напрямую)

Если это правило нарушается — цикл почти гарантирован.

## 3) Основные техники разрыва циклов
### A) Вынести контракты вверх
Если A нужен тип/протокол из B:
- перенести его в `Contracts`/`CoreDomain`.
Тогда:
- A зависит от Contracts,
- B зависит от Contracts,
цикл исчезает.

Важный нюанс:
- в Contracts класть минимум стабильных типов,
- иначе Contracts станет “вторым монолитом”.

### B) Абстракции вместо реализаций (DIP)
Если A использует сервис B:
- A зависит от `BProviding` (протокол),
- реализация в B или infra,
- wiring — в App.

### C) Entry points + outputs (межфичевое взаимодействие)
A не должен импортить VC/VM из B.
Вместо этого:
- App “даёт” A entry point B (как зависимость),
- A вызывает `BEntryPoint.start(...)`,
- результат получает через callback/output.

### D) Навигация наверх
Циклы часто порождает навигация.
Лечится:
- координатор (или router) на уровне App/flow,
- фичи не знают, какие другие фичи существуют.

### E) Разделить “Shared” по ответственности
Anti-pattern:
- `Shared` зависит от FeatureA и FeatureB.
Правильно:
- `CoreUI` (дизайн система),
- `CoreDomain` (контракты),
- `CoreInfra` (networking/storage/observability).

## 4) Практические “симптомы” и быстрые фиксы
Симптом:
- “нужно импортить модуль обратно, иначе не собрать”.
Фикс:
- найти, какой именно тип нужен, и вынести его в Contracts.

Симптом:
- “FeatureA знает про экран FeatureB”.
Фикс:
- заменить на entry point или routing event наружу.

## 5) Enforcement (иначе всё расползётся)
- запрет импортов feature→feature (линтер/скрипт),
- dependency graph check в CI,
- правила ревью: “нет новых публичных типов без причины”.

## 6) Формулировка на собесе
“Циклы решаю архитектурно: задаю dependency rule и держу контракты в верхнем модуле. Фичи общаются через entry points и outputs, wiring в composition root. Навигацию поднимаю наверх. Дополнительно ставлю проверки dependency graph в CI, чтобы циклы не возвращались.”

**Самопроверка**
- Оспорено: “цикл можно решить вынесением файлов” — циклы решаются только изменением направления зависимостей и расположения контрактов, а не перестановкой кода.
- Неочевидно: чаще всего цикл рождает навигация и протекание типов; entry points/outputs + contracts модуль — самый практичный разрыв.
- Источники: dependency inversion principle, modular architecture dependency rule, SPM target graphs и инструменты визуализации/проверки зависимостей.

### Q168 (🔴): Как построить слой авторизации/сессии так, чтобы он не ломал всю архитектуру (refresh token, logout, race conditions)?

**Кратко**
- Auth/Session — это отдельная подсистема с **SSOT** и чёткими границами.
- Компоненты:
  1) `SessionStore` (SSOT) — текущее состояние авторизации + публикация изменений,
  2) `TokenStore/SecureStorage` — Keychain,
  3) `AuthAPI` — login/refresh/logout,
  4) `AuthInterceptor` — добавляет токен и обрабатывает 401,
  5) `RefreshCoordinator` — дедуп refresh и защищает от гонок,
  6) `LogoutFlow` — атомарная очистка и сигнал наружу.
- Инварианты:
  - refresh всегда “один в полёте”,
  - после logout нет “старых” токенов в памяти и в запросах,
  - 401 не превращается в бесконечный цикл.

**Развёрнуто**
## 1) Где проекты чаще всего ломаются
- несколько запросов одновременно получили 401 → запустили 5 refresh → токены перетёрлись,
- refresh успел завершиться после logout → “воскресили” сессию,
- бесконечный цикл: запрос → 401 → refresh → снова 401 → refresh…,
- UI напрямую трогает токены или “переинициализирует” auth state.

Это всё — проблемы **конкурентности и ownership**.

## 2) Модель: SessionStore как SSOT
`SessionStore` держит:
- `state = authenticated(user) | unauthenticated | refreshing`,
- access token (обычно в памяти),
- сигналит подписчикам (UI/flows).

Правило:
- UI не решает “когда refresh” и не трогает токены.
UI реагирует на изменения state:
- показать login,
- закрыть защищённые экраны,
- перезапустить запросы (если нужно).

## 3) Refresh: “single flight” + дедуп
Нужен механизм:
- “если refresh уже идёт — все ждут тот же результат”.

Подход:
- `RefreshCoordinator` хранит in-flight task/promise:
  - если есть — вернуть её,
  - если нет — создать.

Критично:
- синхронизация (actor/serial queue/lock),
- аккуратная отмена при logout.

## 4) 401 обработка: interceptor + правила
Interceptor делает:
1) добавить access token в запрос,
2) если ответ 401:
   - проверить, можно ли refresh (есть refresh token, не в logout),
   - запустить `RefreshCoordinator.refresh()`,
   - повторить исходный запрос **один раз**,
3) если снова 401:
   - считаем токен невалидным → logout/session invalidation.

Важно:
- лимит повторов,
- различать 401 “token expired” vs 403/invalid scope,
- уважать cancellation (если upstream task отменили — не продолжаем refresh без нужды).

## 5) Logout как атомарная операция
Logout должен:
- пометить “logout in progress” (флаг/epoch),
- отменить refresh (если идёт),
- очистить:
  - in-memory tokens,
  - Keychain,
  - sensitive caches,
- перевести SessionStore в unauthenticated,
- оповестить приложение (flow) о необходимости закрыть защищённые экраны.

Важно: “epoch/version” подход:
- каждый refresh/response проверяет актуальность эпохи сессии,
- если эпоха поменялась (logout) — результат refresh игнорируется.

## 6) Race conditions: как их реально убить
### A) Actor/serial isolation
`SessionStore` и `RefreshCoordinator` лучше делать actor’ами или на serial queue.

### B) Session epoch
- увеличивается на logout,
- любой асинхронный результат проверяет epoch.

### C) In-flight request dedup + cancellation semantics
- если запросы коалесцируются, 401 обработка должна работать на “shared response” корректно.

## 7) Где место авторизации в архитектуре
- Domain: use cases “login/logout” (намерение).
- Data/Infra: реализация auth API, keychain, interceptor, refresh coordinator.
- UI: показывает flow (login screens) через coordinator, реагирует на SessionStore.

## 8) Формулировка на собесе
“Я строю auth как подсистему: SessionStore как SSOT, refresh через single-flight coordinator (actor), сетевой interceptor обрабатывает 401 и делает refresh с лимитом повторов. Logout атомарен: отменяет refresh, чистит in-memory и Keychain и повышает session epoch, чтобы результаты старых задач игнорировались. Так я избегаю гонок и бесконечных циклов.”

**Самопроверка**
- Оспорено: “достаточно просто сделать refresh в interceptor” — без single-flight и epoch легко получить гонки и “воскрешение” сессии после logout.
- Неочевидно: session epoch/версионирование — простой и мощный способ защититься от “устаревших” async результатов.
- Источники, которые стоит освежить: Swift Concurrency actors для изоляции состояния, паттерн single-flight/in-flight dedup, практики auth refresh (401 handling, retry limits), keychain + session lifecycle.

### Q169 (🔴): Как спроектировать sync engine: стратегия pull/push, мердж, дедупликация, backpressure, ограничения iOS background?

**Кратко**
- Sync engine — это отдельная подсистема, которая:
  - хранит локальный source of truth,
  - ведёт очередь изменений (outbox),
  - подтягивает изменения с сервера (inbox/pull),
  - мерджит с конфликт-резолюцией,
  - контролирует нагрузку (backpressure),
  - учитывает ограничения iOS background.
- Ключевая идея: **отделить пользовательские операции от сетевого исполнения** через журнал/очередь.

**Развёрнуто**
## 1) Компоненты sync engine
### A) Local store (SSOT)
- локальная БД/хранилище — “истина” для UI,
- UI не зависит от сети напрямую.

### B) Outbox (очередь локальных изменений)
- все мутации записываются как операции:
  - `create/update/delete`,
  - с payload и метаданными (timestamp, entityID, idempotency key).
- Sync потом “проталкивает” outbox на сервер.

### C) Pull (получение изменений)
- периодически/по триггеру запрашиваем изменения:
  - по cursor/версиям,
  - по “since token”.

### D) Merger/Conflict resolver
- применяет серверные изменения к local store,
- решает конфликты.

### E) Scheduler
- когда запускать sync:
  - app foreground,
  - connectivity changed,
  - background task,
  - push notification (silent push) — если используется.

### F) Observability
- логирование шагов,
- метрики времени/ошибок,
- correlation ids.

## 2) Push vs Pull стратегия
### Pull
Плюсы:
- проще,
- контролируемая нагрузка,
- прогнозируемое поведение.
Минусы:
- не realtime.

### Push (сервер инициирует)
В iOS чаще:
- silent push как триггер “сделай pull”.
Плюсы:
- быстрее доставка.
Минусы:
- ограничения и недоставка (APNs не гарантирует).

Реалистичная схема:
- push → триггер pull.

## 3) Дедуп и идемпотентность
### A) Idempotency keys
Каждая outbox операция имеет idempotency key:
- сервер при повторе не делает дубль.
Это критично из-за ретраев и перезапусков.

### B) Coalescing операций
Если пользователь сделал 10 update одной сущности:
- outbox может схлопнуть в одну (последнее состояние) или “patch merge”.

### C) Dedup incoming изменений
На pull:
- применять изменения ровно один раз (cursor/sequence),
- хранить last applied token.

## 4) Конфликты (самая болезненная часть)
Конфликт = локальные изменения и новые серверные изменения на одну сущность.

Стратегии:
- last-write-wins (простая, но иногда опасная),
- field-level merge,
- CRDT (редко на мобиле, дорого),
- “server wins” или “client wins” (по доменной семантике),
- ручное разрешение (для важных сущностей).

Важно:
- стратегия должна быть доменно-обоснованной.
Например:
- “заметка” можно field-merge,
- “баланс/деньги” — только сервер authoritative.

## 5) Backpressure и контроль нагрузки
Без контроля sync engine:
- может устроить шторм запросов,
- съедать батарею и трафик,
- приводить к throttling (429).

Механизмы:
- лимит параллельности (например, N операций одновременно),
- адаптивный backoff на ошибки/429,
- pause/resume по connectivity,
- batching операций,
- приоритеты (критичные мутации → быстрее, фоновые → позже),
- “budget” на background время.

## 6) Ограничения iOS background
Ограничения:
- app могут убить,
- время ограничено,
- фоновые сетевые операции должны быть устойчивыми к прерыванию.

Подходы:
- BGTaskScheduler для планирования,
- background URLSession (для крупных загрузок/выгрузок),
- минимизировать работу в фоне: чаще “поставить флаг/триггернуть”, чем делать большой sync,
- checkpoints: engine может продолжить после kill.

## 7) Инварианты надёжного sync
- операции в outbox не теряются (persisted),
- повторная отправка безопасна (idempotent),
- порядок применения определён (per entity ordering),
- engine возобновляем после перезапуска,
- UI всегда работает с local store.

## 8) Формулировка на собесе
“Я строю sync как отдельный engine: local store — SSOT, любые мутации пишутся в outbox как операции с idempotency keys. Sync scheduler запускает push/pull (часто push лишь триггер pull). Входящие изменения мерджатся с доменной стратегией конфликтов. Нагрузка контролируется backpressure: лимиты параллельности, батчинг, backoff. В фоне учитываю BGTaskScheduler и возможность прерывания: checkpoints и возобновление.”

**Самопроверка**
- Оспорено: “sync = просто периодически дернуть API” — без outbox, идемпотентности и backpressure система не выдержит реальных прерываний и ошибок.
- Неочевидно: конфликт-резолюция должна быть доменной, иначе “последний победил” может ломать смысл данных.
- Источники, которые стоит освежить: iOS BGTaskScheduler и ограничения background execution, идемпотентность и design outbox pattern, стратегии конфликтов (LWW vs merge), best practices backoff/throttling (429).

### Q170 (🔴): Как организовать state management на уровне приложения (auth, onboarding, paywall, connectivity) без глобального хаоса?

**Кратко**
- App-level state — это несколько “глобальных” доменов состояния, которые должны иметь:
  - **SSOT** (single source of truth),
  - **изоляцию** (actor/serial),
  - **явные входы/события**,
  - **предсказуемую навигацию** (flows).
- Я избегаю “глобального стора на всё” без границ.
- Обычно делаю:
  - отдельные stores: `SessionStore`, `ConnectivityStore`, `EntitlementsStore`, `OnboardingStore`,
  - `AppFlowCoordinator`, который решает, какой flow активен сейчас.

**Развёрнуто**
## 1) Почему “глобальный хаос” возникает
Если auth/onboarding/paywall/connectivity размазаны:
- каждый экран сам решает “куда перейти”,
- разные части по-разному интерпретируют состояние,
- много подписок на NotificationCenter,
- гонки: например, paywall показали во время logout,
- циклы навигации.

Это решается “архитектурой потоков” и SSOT.

## 2) Раздели глобальное состояние на домены
Пример доменов:
- Session/auth: authenticated/unauthenticated/refreshing,
- Onboarding: текущий шаг, завершён/нет,
- Entitlements/paywall: subscribed/trial/expired,
- Connectivity: online/offline/expensive,
- App lifecycle: foreground/background.

Каждый домен:
- имеет свой store/actor,
- публикует изменения как поток,
- имеет API для “намерений” (actions), а не прямые сеттеры.

## 3) SSOT и изоляция (важно для гонок)
Stores должны быть:
- actor или внутри serial queue,
- с чёткими инвариантами.

Пример инварианта:
- если session unauthenticated → paywall flow не стартует для защищённых фич (или наоборот, зависит от продукта).
Инварианты должны жить в одном месте.

## 4) “Кто решает, что показывать” — AppFlowCoordinator
Обычно нужен App-level flow orchestrator, который:
- слушает ключевые stores,
- вычисляет “текущий режим приложения”:
  - login flow,
  - onboarding flow,
  - main app,
  - paywall blocking flow (если продукт так устроен).
- обеспечивает, что активен ровно один главный flow.

Т.е. не VC решает навигацию, а coordinator.

## 5) Избегай мегастора: лучше композиция
Вместо:
- один гигантский `AppStore` со всем,
делай:
- маленькие domain stores,
- а AppCoordinator агрегирует их и принимает решения.

Это:
- снижает связность,
- улучшает тестируемость,
- позволяет менять домен независимо.

## 6) Модель событий: явная и типизированная
- Не полагаться на “всем отправим Notification”.
Лучше:
- typed outputs/streams,
- или event bus только для cross-cutting сигналов (logout, appActive), но с дисциплиной.

## 7) Тестирование app-state
Тестировать надо:
- состояние каждого store (state transitions),
- логику AppFlowCoordinator:
  - given states → expected active flow,
  - edge cases (connectivity drops during checkout).

## 8) Практичная формулировка на собесе
“Я делю app-level состояние на домены и делаю для каждого SSOT store с изоляцией (actor). Потоки (auth/onboarding/paywall) решаются на уровне AppFlowCoordinator, который слушает stores и активирует нужный flow. Это убирает навигацию из экранов и предотвращает гонки и циклы.”

**Самопроверка**
- Оспорено: “сделаем один глобальный singleton и всё” — так быстро появляется coupling и гонки; лучше несколько SSOT с явными границами и orchestration сверху.
- Неочевидно: самое важное — “кто владеет навигацией”; если она у VC, хаос неизбежен, даже при хороших сторах.
- Источники, которые стоит освежить: coordinator-based app flows, Swift actors для глобальных stores, patterns для app state decomposition, best practices вокруг NotificationCenter vs typed streams.

### Q171 (🔴): Как бы ты сделал систему “команд/операций” для сложных сценариев (редактор, загрузки, пайплайны), чтобы она была отменяемой и восстанавливаемой?

**Кратко**
- Нужна модель “команды” (command) с:
  - описанием действия,
  - возможностью отмены (undo) или компенсации (compensating action),
  - сериализацией для восстановления (persisted queue),
  - прогрессом и статусами,
  - изоляцией конкурентности.
- Архитектурно это похоже на:
  - `OperationQueue`/task pipeline + журнал операций,
  - или state machine + persisted commands,
  - с единым исполнителем (executor) и политиками retry/backoff.

**Развёрнуто**
## 1) Что значит “отменяемая и восстанавливаемая”
- Отмена: пользователь/система может остановить процесс, и система не должна оказаться в полусостоянии.
- Восстановление: после kill/crash/app restart можно продолжить или корректно завершить.

Это требует:
- персистентного представления текущего прогресса,
- идемпотентности действий,
- компенсирующих операций там, где “undo невозможно”.

## 2) Базовые сущности
### A) Command (описание)
- `id`, `type`, `payload`, `createdAt`,
- `state`:
  - queued/running/succeeded/failed/cancelled,
- `attempt` и метаданные policy (если нужно),
- `dependencies` (если есть граф).

Command должен быть сериализуемым (JSON/DB), чтобы пережить рестарт.

### B) Executor
Компонент, который:
- берёт команды из очереди,
- выполняет,
- обновляет статусы,
- диспатчит прогресс/события.

### C) Queue + persistence
- хранится в DB (Realm/CoreData/SQLite),
- операции “добавить/обновить/удалить” атомарны.

## 3) Отмена: два режима
### A) Cancellation (прекратить дальнейшее выполнение)
- для “чистых” операций (compute, upload) можно отменять и не коммитить.

### B) Compensation (если действие уже сделано)
Если операция уже повлияла на внешний мир:
- undo может быть невозможен.
Тогда нужна компенсирующая команда:
- “удалить созданный объект”,
- “откатить изменения”,
- или “пометить как отменённое”.

Это похоже на Saga pattern:
- цепочка шагов + компенсаторы.

## 4) Идемпотентность и дедуп
Восстановление означает повторы.
Чтобы не было дублей:
- команды должны быть идемпотентны,
- для серверных операций — idempotency keys,
- для локальных — проверка “уже применено” (version/marker).

## 5) Граф/пайплайны и зависимости
Для редактора/экспорта:
- шаги: render → encode → upload → publish.
Это можно выразить:
- как DAG зависимостей,
- или как state machine pipeline.

Executor:
- запускает только готовые команды,
- контролирует параллельность,
- ограничивает ресурсы.

## 6) Backpressure и ресурсные лимиты
Особенно важно для upload/render:
- ограничить параллельные тяжёлые операции,
- учитывать батарею/сеть/foreground.

Механизмы:
- QoS/priority,
- лимит параллельности,
- pause/resume при background,
- адаптивный backoff на ошибки.

## 7) UI и наблюдаемость
UI не должен “вручную” собирать состояние процесса.
UI подписывается на:
- состояние очереди/команд,
- прогресс отдельных команд.

Нужны:
- correlation id,
- логирование шага/ошибки,
- метрики длительности.

## 8) Как отвечать на собесе
“Я моделирую сложные сценарии как персистентную очередь команд. Команды сериализуемы и имеют статусы, прогресс и idempotency. Исполнитель (executor) выполняет команды с учётом зависимостей и лимитов, поддерживает cancellation и, когда нужно, компенсирующие действия (Saga). После рестарта executor поднимает очередь и продолжает/доделывает. UI подписывается на состояние, а не управляет шагами напрямую.”

**Самопроверка**
- Оспорено: “достаточно OperationQueue” — без persistence и идемпотентности ты не получишь восстановление после kill и безопасные повторы.
- Неочевидно: undo ≠ cancellation; если шаг уже затронул внешний мир, нужен компенсатор (Saga/compensating action).
- Источники, которые стоит освежить: Command pattern, Saga pattern, OperationQueue vs Swift tasks, idempotency keys, background upload (URLSession), persisted job queues.

### Q172 (🔴): Как проектировать архитектуру вокруг доменных событий (event-driven внутри приложения): гарантия доставки, порядок, дедупликация?

**Кратко**
- Доменные события полезны, когда:
  - есть независимые реакции на одно событие (analytics, кеш, уведомления, UI),
  - нужны слабые связи между фичами.
- Чтобы не получить хаос, нужны гарантии:
  1) где события публикуются (publisher),
  2) как доставляются (bus),
  3) какие гарантии порядка,
  4) как обеспечивается дедуп,
  5) где хранить события (in-memory vs persisted outbox),
  6) как наблюдать и дебажить.
- Лучший практический подход: **persisted outbox + подписчики** для важных событий.

**Развёрнуто**
## 1) Что такое доменное событие
Доменное событие — факт, который уже произошёл:
- `UserLoggedIn`
- `OrderPlaced`
- `DocumentSaved`

Важно:
- событие — не команда (“сделай”), а факт (“сделано”).

## 2) Почему event-driven легко превращается в спагетти
Если сделать “общий NotificationCenter на всё”:
- никто не знает, кто слушает,
- порядок неизвестен,
- события теряются,
- сложно тестировать и дебажить.

Поэтому нужен дизайн гарантий.

## 3) Уровни важности событий
### A) Best-effort (можно потерять)
Пример:
- analytics event.
Можно делать:
- in-memory bus.

### B) Must-deliver (нельзя терять)
Пример:
- “после покупки нужно обновить entitlement и кеш”.
Тут нужен:
- persisted outbox.

## 4) Гарантия доставки (delivery)
### In-memory bus
- быстро,
- но при crash/kill события теряются.

### Persisted outbox
Схема:
1) при изменении состояния записать событие в outbox (DB),
2) отдельный dispatcher читает outbox и доставляет подписчикам,
3) после успешной доставки помечает событие как обработанное.

Это даёт:
- at-least-once delivery.

## 5) Порядок (ordering)
Нужно определить требования:
- global ordering редко нужен и дорог.
Чаще нужно:
- ordering per aggregate/entity (например, по `documentId`).

Реализация:
- события имеют `sequence`/timestamp,
- dispatcher гарантирует порядок по ключу,
- параллельно можно обрабатывать разные ключи.

## 6) Дедупликация
Поскольку delivery часто at-least-once, подписчики должны быть идемпотентны.
Техники:
- event id + “processed ids” store,
- versioning per aggregate,
- idempotent side effects (например, upsert вместо insert).

## 7) Где это “живёт” в архитектуре
- Domain: определение событий как типов.
- Application layer: публикация событий (после успешной доменной операции).
- Infrastructure: bus/outbox/dispatcher, persistence, scheduling.
- Presentation: может слушать только “UI-friendly” события, но осторожно.

Важно:
- UI не должен быть единственным способом “обработать событие” (иначе событие теряется, если UI не открыт).

## 8) Тестирование
- unit тесты: при выполнении use case публикуется событие,
- integration: outbox dispatcher доставляет событие и отмечает обработанным,
- contract: подписчики идемпотентны.

## 9) Формулировка на собесе
“Я использую доменные события для слабой связности, но делю их на best-effort и must-deliver. Для must-deliver применяю persisted outbox: события пишутся в DB и доставляются диспетчером с at-least-once семантикой. Порядок обычно гарантируется per entity, а дедуп достигается eventId и идемпотентными подписчиками.”

**Самопроверка**
- Оспорено: “NotificationCenter достаточно” — он не даёт гарантий доставки/порядка/дедупа и плохо дебажится.
- Неочевидно: at-least-once требует идемпотентных подписчиков; иначе дедуп будет источником багов.
- Источники, которые стоит освежить: Domain Events, Outbox pattern, идемпотентность side effects, ordering per aggregate, практики event-driven внутри монолита.

### Q173 (🔴): Как бороться с архитектурной деградацией в долгоживущем проекте: правила, ревью-гейты, ADR, рефакторинг-стратегия?

**Кратко**
- Деградация = размывание границ, рост coupling, снижение тестируемости и скорости изменений.
- Борьба — это не “один рефакторинг”, а система:
  1) явные правила (dependency rule, layering),
  2) enforcement (линтер/CI checks),
  3) ADR (фиксируем решения и почему так),
  4) ownership и code review гейты,
  5) инкрементальные рефакторинги по стратегии,
  6) метрики (build time, циклы зависимостей, code hotspots).

**Развёрнуто**
## 1) Почему архитектура деградирует
- давление бизнеса: “быстрее фичу”,
- новые люди не знают правил,
- “временно” становится постоянным,
- отсутствуют гейты (любой может протащить зависимость куда угодно),
- нет времени на удаление флагов/экспериментов,
- нет наблюдаемости за “здоровьем” кода.

## 2) Правила (должны быть короткими и исполнимыми)
Примеры:
- Features не импортят Features.
- UI слой не импортит Data layer напрямую.
- Domain не знает про iOS/SDK.
- Все внешние SDK через адаптеры.
- Public API модулей минимален.

Если правил 50 — ими никто не пользуется.

## 3) Enforcement в CI (иначе правила — просто текст)
- dependency graph check (запрет циклов, запрет запрещённых импортов),
- lint rules (например, запрет `Bundle.main` в модулях),
- запрет “зависимостей назад” (core ← feature),
- проверка coverage на критичных слоях (не абсолютная, а по ключевым модулям),
- performance gates: время сборки/тестов, регрессии.

## 4) ADR: фиксируем решения и контекст
ADR (Architecture Decision Record) полезен, когда:
- решение влияет на многие фичи,
- есть tradeoffs и “почему так” важно помнить.

ADR должен быть:
- коротким (1–2 страницы),
- содержать:
  - контекст,
  - решение,
  - альтернативы,
  - последствия,
  - дату и owner.

Без ADR всё превращается в “мифы” и “кажется, мы так делали”.

## 5) Code review гейты и ownership
- Определить владельцев модулей/слоёв.
- Изменения в core/infra требуют ревью владельца.
- В PR шаблоне:
  - “нарушает ли это dependency rule?”,
  - “добавлены ли новые публичные API?”,
  - “как это тестируется?”.

## 6) Рефакторинг-стратегии (не big-bang)
### A) Strangler pattern
Постепенно оборачивать старые части новой архитектурой:
- новые фичи — по новым правилам,
- старые — мигрируют по мере касания.

### B) Hotspot-driven refactor
Не рефакторить всё.
Выбирать:
- места с частыми изменениями,
- высокий баг-рейт,
- “узкие горлышки” сборки.

### C) Expand → migrate → contract
Для API/моделей/схем:
- сначала расширяем,
- мигрируем,
- удаляем старое позже.

## 7) Метрики “здоровья архитектуры”
- время сборки и invalidation,
- количество циклов в графе,
- размеры модулей и public API,
- количество “God” объектов,
- частота конфликтов в merge,
- количество флагов без даты удаления.

Без метрик деградацию замечают слишком поздно.

## 8) Формулировка на собесе
“Я поддерживаю архитектуру системой: короткие правила и enforcement в CI, ownership и review гейты, ADR для ключевых решений, и инкрементальный рефакторинг (strangler/hotspots). Плюс метрики здоровья (build time, dependency cycles), чтобы деградацию ловить рано.”

**Самопроверка**
- Оспорено: “достаточно договориться на словах” — без CI гейтов и ownership правила неизбежно размоются под давлением сроков.
- Неочевидно: рефакторинг должен быть hotspot-driven и инкрементальным; big-bang почти всегда риск и остановка разработки.
- Источники, которые стоит освежить: ADR практики, Strangler pattern, hotspot analysis, modular enforcement в CI, code review governance.


### Q174 (🔴): Как архитектурно организовать наблюдаемость: трассировка запросов end-to-end, correlation IDs, feature metrics, privacy redaction?

**Кратко**
- Observability = logs + metrics + traces.
- Архитектурно:
  - единый `Observability` слой (facade),
  - correlation ID как сквозной контекст,
  - трассировка как “спаны” (request, decode, cache, UI render),
  - feature metrics — измеряем бизнес/UX (TTI, time-to-content),
  - privacy redaction — обязательный фильтр перед отправкой.
- Нельзя “логировать в UI где попало” — нужна политика и единый пайплайн.

**Развёрнуто**
## 1) Почему observability — часть архитектуры
Если логирование размазано:
- нет связи между событиями,
- трудно расследовать баги,
- метрики несопоставимы,
- есть риск утечки PII.

Поэтому observability — cross-cutting concern, как networking.

## 2) Компоненты observability слоя
### A) Logger
- структурированные логи (ключ-значение),
- уровни (debug/info/warn/error),
- контекст (correlation id, user/session id в редактированном виде).

### B) Metrics
- счётчики/тайминги:
  - TTI,
  - time-to-content,
  - latency requests,
  - error rate,
  - retry count,
  - cache hit ratio.

### C) Tracing
- spans:
  - “FetchFeed”,
  - “Decode JSON”,
  - “DB Write”,
  - “UI Render”.
- дерево спанов даёт “где время ушло”.

## 3) Correlation IDs: как сделать правильно
- Для каждого “пользовательского действия” (например, открытие экрана) генерируем root correlation id.
- Пробрасываем его:
  - через use case,
  - repository,
  - network request (в headers),
  - логи и метрики.
- В ответах сервера можно получать request id и связывать.

Технически:
- использовать Task-local storage (в Swift Concurrency) или явный context object.

## 4) Где вставлять instrumentation
### Network layer
- interceptor добавляет headers:
  - correlation id,
  - app version/build,
  - device info (без PII).
- логирует:
  - latency,
  - status,
  - retries,
  - size.

### Data layer
- cache hit/miss,
- DB read/write timing,
- sync events.

### UI/Presentation
- time-to-first-render,
- time-to-content,
- dropped frames (если есть),
- user interactions.

## 5) Feature metrics
Важно отделить:
- технические метрики (latency),
- продуктовые метрики (конверсия, completion rate).

Feature metrics должны жить:
- в доменных use cases или в application layer,
а не в VC,
чтобы логика измерения была стабильной и тестируемой.

## 6) Privacy redaction (must-have)
Нельзя логировать:
- email/phone,
- точные адреса,
- полные токены,
- contents документов/сообщений.

Подход:
- `Redactor`/policy:
  - whitelist полей,
  - masking (hashing),
  - truncate.

Идея:
- лучше “логов меньше, но безопасно”.

## 7) Fail-safe и деградация
- observability не должно ломать приложение:
  - логирование не должно падать,
  - отправка не блокирует main thread,
  - буферизация и отложенная отправка.

## 8) Формулировка на собесе
“Я выделяю observability как слой: Logger/Metrics/Tracing за фасадом. На входе формирую correlation id (обычно на user action) и пробрасываю его через use case → repo → network, добавляю в headers. Инструментирую latency/retries/cache hit и UX метрики (time-to-content). Обязательно делаю privacy redaction политикой перед отправкой, чтобы исключить PII. Всё асинхронно и fail-safe.”

**Самопроверка**
- Оспорено: “достаточно print/log в нужных местах” — без корреляции и политики это не расследуется и риск утечки PII высокий.
- Неочевидно: feature metrics лучше фиксировать в доменных сценариях, иначе измерение расползается по UI и становится нестабильным.
- Источники, которые стоит освежить: distributed tracing концепты (spans/correlation ids), Task-local context в Swift Concurrency, best practices privacy logging/redaction, metric naming и SLOs.

### Q175 (🔴): Как проектировать API так, чтобы минимизировать “existential trap” и взрыв generic’ов на границах слоёв (особенно при DI)?

**Кратко**
- “Existential trap” появляется, когда мы:
  - используем `any Protocol` там, где протокол имеет `Self/associatedtype`,
  - теряем оптимизации generics,
  - начинаем плодить type erasure и сложные generic сигнатуры.
- Практика:
  1) держать generics **внутри** слоя/модуля, а наружу отдавать **конкретный тип** или **не-generic фасад**,
  2) протоколы на границах делать “простыми”: без `associatedtype` если не нужно,
  3) применять type erasure точечно и на верхнем уровне,
  4) DI контейнеры не должны протекать generic’ами в бизнес-код,
  5) иногда лучше “конкретные протоколы-порты” вместо супер-абстрактных generic-комбинаторов.

**Развёрнуто**
## 1) Что именно ломается
### A) Протокол с associatedtype/Self
Нельзя хранить как `any P` без дополнительных приёмов:
- нужно generic контекст,
- или type erasure.

### B) Взрыв generic’ов
Если каждый слой принимает десяток generic параметров:
- сигнатуры становятся нечитаемыми,
- компиляция замедляется,
- API тяжело использовать.

### C) DI и existential trap
DI контейнеры часто возвращают “что угодно” и провоцируют:
- `any Protocol`,
- или огромные generic фабрики,
которые вытекают в фичи.

## 2) Основной принцип: “генерики внутрь, фасады наружу”
Например:
- в data layer можно использовать generic client/decoder,
- но наружу из репозитория возвращать:
  - конкретные доменные типы,
  - простой протокол `UserRepository`.

Так граница слоя остаётся чистой.

## 3) Проектирование протоколов на границах
Правила:
- на boundary протоколы должны быть:
  - минимальные,
  - без “избыточных” associatedtype,
  - ориентированные на сценарии/агрегаты, а не на общие “контейнеры”.

Вместо:
- `Repository<T>` с associatedtype,
часто лучше:
- `UserRepository`, `FeedRepository`.

Да, больше интерфейсов, но:
- проще DI,
- меньше generic шума,
- стабильнее границы.

## 4) Где применять type erasure
Type erasure — инструмент, но не базовый стиль.
Применять:
- при возврате из фабрик/DI,
- при хранении в коллекциях,
- при объединении разных реализаций под одним API.

Важно:
- сделать type erasure “на краю”, чтобы не расползалось.

## 5) Оpaque types (`some`) как компромисс
Если нужно скрыть конкретный тип, но сохранить generic оптимизации:
- `some Protocol` для return types (в ограниченных местах).

Но:
- `some` не решает хранение/передачу повсюду,
- это не “универсальный any”.

## 6) DI: не давать generic’ам протечь
Подходы:
- Composition root строит конкретные графы и отдаёт конкретные зависимости.
- DI контейнер, если используется, живёт в верхнем слое:
  - фичи получают уже “готовые” зависимости (протоколы без associatedtype).

Избегать:
- “сервис локатора”, который возвращает `Any`/`any` и маскирует зависимости.

## 7) Performance и компиляция
- меньше generic параметров в публичных сигнатурах → быстрее компиляция,
- меньше type erasure в горячих местах → лучше runtime.

Компромисс:
- держать типовую сложность там, где она даёт пользу (внутри модуля),
- и скрывать её на API границах.

## 8) Формулировка на собесе
“Я избегаю existential trap тем, что проектирую boundary протоколы простыми (без associatedtype, если не нужно) и держу generics внутри модулей. Если нужен polymorphism — использую type erasure точечно на краю (например, в DI/фабриках). В итоге API слоёв читаемое, DI не протекает generic’ами, а performance/компиляция остаются контролируемыми.”

**Самопроверка**
- Оспорено: “делаем один супер generic Repository<T> на всё” — это часто приводит к existential trap и взрыву generic API на границах, усложняет DI и компиляцию.
- Неочевидно: правильная архитектура — это компромисс между типовой абстракцией и стабильностью границ; generics нужно локализовать.
- Источники, которые стоит освежить: Swift existentials (`any`) vs generics, ограничения протоколов с associatedtype/Self, patterns type erasure (AnySequence), compile-time costs больших generic графов.

### Q176 (🔴): Как архитектурно обеспечить performance budgets: где ставить ограничения и как не допустить regressions (профайлинг в CI, перф-тесты)?

**Кратко**
- Performance budget — это контракт: “экран/фича должна укладываться в X”.
- Архитектурно:
  1) определить метрики (TTI, time-to-content, scrolling FPS, memory peak),
  2) поставить ownership и “гейты” в CI,
  3) встроить измерения в app (instrumentation),
  4) выделить “горячие” границы (data → UI) и стабилизировать их,
  5) не допускать “скрытых” регрессий через тесты и алерты.
- Главный принцип: измеряем автоматически, иначе это всегда будет “потом”.

**Развёрнуто**
## 1) Какие бюджеты реально полезны в iOS
- time-to-interactive (TTI),
- time-to-content (первый meaningful контент),
- scrolling performance (dropped frames),
- cold start / warm start,
- memory peak (особенно при списках и медиа),
- network latency + payload size,
- DB read/write time.

Важно: бюджеты должны быть конкретными и проверяемыми.

## 2) Где ставить границы в архитектуре
### A) Границы “data → presentation”
Самые частые регрессии:
- тяжёлые маппинги на main thread,
- неоптимальные diff/snapshot,
- повторные запросы и отсутствие кеша,
- лишние копии данных.

Поэтому:
- data layer должен отдавать готовые доменные модели,
- тяжёлые преобразования — в background,
- VM/Presentation — минимальные синхронные операции на main.

### B) Границы “UI rendering”
- избегать синхронных I/O на main,
- предвычислять layout/атрибуты,
- контролировать offscreen rendering,
- ограничить стоимость self-sizing.

Архитектурно:
- отделить “модель представления” (готовые размеры/строки) от raw данных.

## 3) Инструментация как часть продукта
Нужны системные точки измерения:
- start/end spans для use cases,
- экранные метрики:
  - `screenAppear → firstContent`,
- счётчики:
  - cache hits,
  - retries.

Это должно быть в общем слое observability, не в каждом VC.

## 4) CI-гейты и автоматические перф-тесты
### A) Microbenchmarks
- тесты на маппинг, сериализацию, вычисления.
Плюс: детерминировано.
Минус: не отражает UI/устройство.

### B) UI/perf tests
- запуск на реальном девайсе/симуляторе с одинаковыми условиями,
- измерение TTI/time-to-content.
Реальность:
- нужно бороться с шумом (variance):
  - несколько прогонов,
  - медиана,
  - “регрессия если хуже на N%”.

### C) Build/merge gates
- если регрессия превышает порог — PR блокируется или требует approval/perf waiver.

## 5) Профайлинг в релизном цикле
- периодический профайлинг “эталонных сценариев” (smoke perf suite),
- алерты по телеметрии продакшена (если собирается):
  - рост времени загрузки экрана,
  - рост memory peak.

## 6) Стратегия предотвращения регрессий
- определить критичные user journeys,
- закрепить бюджеты,
- автоматически измерять и хранить историю (trend),
- иметь процесс:
  - “перф регрессия — баг P0/P1”.

## 7) Компромиссы
- слишком жёсткие гейты могут тормозить разработку,
поэтому:
- начинай с нескольких ключевых метрик,
- постепенно расширяй suite,
- допускай “waiver” с обязательной задачей на исправление.

## 8) Формулировка на собесе
“Я задаю performance budgets как контракт для ключевых сценариев (TTI/time-to-content, scrolling, memory). Инструментирую их через общий observability слой и добавляю автоматические перф-тесты/бенчмарки в CI с порогами регрессии. Горячие границы оптимизируются архитектурно: тяжёлые маппинги и I/O уходят с main, данные кешируются и дедуплицируются, UI получает подготовленную модель. Так регрессии ловятся до релиза.”

**Самопроверка**
- Оспорено: “перф можно проверить руками перед релизом” — это не масштабируется; регрессии появляются постоянно и должны ловиться автоматически.
- Неочевидно: перф-гейты в CI требуют борьбы с шумом (variance) и процесса waiver, иначе команда начнёт обходить систему.
- Источники, которые стоит освежить: XCTest performance metrics, Xcode Instruments automation, практики perf regression testing, UIKit performance hotspots (diffable/self-sizing/offscreen).

### Q177 (🔴): Как проектировать архитектуру для multi-account / multi-tenant приложения (переключение аккаунтов, изоляция данных, кешей, сессий)?

**Кратко**
- Multi-account = несколько аккаунтов на устройстве, быстрое переключение.
- Архитектурные требования:
  1) данные и кеши строго **namespaced** по account/tenant,
  2) сессия и токены изолированы,
  3) фоновые задачи/синк не смешивают аккаунты,
  4) UI/flows корректно реагируют на переключение,
  5) безопасная очистка при logout/delete account.
- Обычно делаю `AccountContext` (контекст аккаунта) + `AccountScoped` зависимости.

**Развёрнуто**
## 1) Главные риски multi-account
- утечки данных между аккаунтами (кеш/БД/файлы),
- запросы уходят с неверным токеном,
- фоновые операции продолжают синк старого аккаунта,
- UI показывает данные “не того” аккаунта после переключения,
- сложно сделать безопасный logout.

Поэтому нужны строгие границы “scope”.

## 2) AccountContext как центральная идея
`AccountContext` включает:
- `accountId` / `tenantId`,
- `SessionStore` для этого аккаунта,
- ссылки на account-scoped репозитории/кеши/DB,
- возможно “корень” файлового пространства.

Приложение держит:
- `ActiveAccountStore` (SSOT): какой аккаунт активен сейчас.

Переключение аккаунта = смена active context.

## 3) Изоляция хранения и кешей (namespacing)
### A) DB
- отдельная БД на аккаунт (проще и безопаснее),
или:
- одна БД, но все сущности имеют `accountId` и все запросы фильтруются.

Практика:
- отдельная DB часто проще для гарантий и очистки,
- но требует миграций по нескольким хранилищам.

### B) Disk cache / файлы
- папки вида:
  - `/Documents/<accountId>/...`
- нельзя хранить “общий” файл без namespace.

### C) Memory cache
- ключи кеша включают accountId,
- при переключении аккаунта:
  - либо сбрасывать мем-кеш,
  - либо держать отдельные кеш-инстансы per account.

## 4) Networking и auth по аккаунтам
- каждый аккаунт имеет свой токен/refresh token,
- interceptor выбирает токен по active context,
- in-flight запросы старого аккаунта:
  - отменять при переключении,
  - или завершать в своём контексте, но не обновлять UI активного аккаунта.

Важно:
- session epoch/version per account, чтобы устаревшие результаты не “влезали”.

## 5) Background sync и задачи
- scheduler должен быть aware of account scope:
  - синк для активного аккаунта,
  - или по очереди для нескольких аккаунтов (если продукт требует).
- ограничения iOS в фоне → обычно синкаем только активный.

Важно:
- при logout аккаунта:
  - отменить его задачи,
  - удалить outbox/inflight, если есть.

## 6) UI и navigation flows
- главный flow зависит от active account:
  - если нет аккаунтов → onboarding/login,
  - если есть → main flow.
- переключение аккаунта:
  - сброс стека/переинициализация root,
  - или переключение контекста в coordinator.

Иначе легко получить “экран A показывает данные B”.

## 7) Тестирование и инварианты
Инварианты:
- запросы всегда используют токен активного аккаунта,
- кеш ключи всегда namespaced,
- UI подписан на active context и не держит “глобальные” singletons с данными.

Тесты:
- переключение аккаунта во время in-flight запросов,
- logout во время refresh,
- удаление аккаунта → отсутствие данных и токенов.

## 8) Формулировка на собесе
“Multi-account проектирую через AccountContext и active account SSOT. Все зависимости делаю account-scoped: DB, кеши, файлы, SessionStore. Ключи и пути namespaced по accountId. Networking берет токен из активного контекста; при переключении отменяю/изолирую in-flight и защищаюсь session epoch, чтобы результаты старого аккаунта не обновляли новый UI. Logout/удаление атомарно чистит scoped хранилища и отменяет фоновые задачи.”

**Самопроверка**
- Оспорено: “достаточно хранить accountId в модели” — если кеши/файлы/сетевые перехватчики не scoped, утечки неизбежны.
- Неочевидно: главное — scope зависимостей (инстансы) и управление in-flight задачами при переключении, иначе будут гонки и “перетекание” данных.
- Источники, которые стоит освежить: patterns для scoped DI (Account-scoped containers), iOS storage isolation, auth/session lifecycle per account, concurrency и cancellation при context switching.

### Q178 (🔴): Как бы ты спроектировал “плагинную” архитектуру фич (подключаемые пакеты/фреймворки) с минимальными связями и предсказуемой сборкой?

**Кратко**
- Плагинная архитектура = фичи поставляются как модули, которые приложение “подключает” через стабильные контракты.
- Архитектурная база:
  1) `FeatureContracts` (стабильные порты: entry points, модели, события),
  2) `FeatureModule` реализует контракт и экспортирует `register()`/`entryPoint`,
  3) `App` (composition root) выбирает, какие фичи включать (compile-time) и как связать (runtime),
  4) зависимости только Core/Contracts → Feature, а не наоборот.
- Предсказуемая сборка достигается:
  - ограничением public API,
  - запретом межфичевых импортов,
  - стабильным графом зависимостей,
  - минимизацией “умной” динамики.

**Развёрнуто**
## 1) Уточнение: что реально возможно на iOS
Полностью динамическая загрузка “плагинов” как на desktop ограничена:
- iOS сильно ограничивает динамическую подгрузку кода.
На практике “плагинность” обычно означает:
- compile-time подключаемые модули (SPM/frameworks),
- runtime включение/выключение через feature flags и registry.

## 2) Ключ: стабильные контракты и entry points
### A) Contracts module
Содержит:
- `FeatureEntryPoint` протоколы,
- доменные/нейтральные типы, которые нужны для коммуникации,
- возможно типизированные события/роуты.

Важно:
- contracts не знает про UIKit конкретных экранов,
- и не тянет тяжёлые зависимости.

### B) Feature module
Экспортирует наружу минимум:
- `public struct FeatureX: FeaturePlugin { ... }`
или:
- `public final class FeatureXEntryPoint: ...`

Внутри:
- всё internal.

## 3) Регистрация фичи: registry без God-object
### A) Явная регистрация в composition root
App собирает список фич:
- `let plugins: [FeaturePlugin] = [PaymentsPlugin(), ProfilePlugin(), ...]`

Плюсы:
- предсказуемо,
- легко трейсить зависимости,
- нет магии.

### B) Авто-регистрация (осторожно)
Через reflection/objc runtime — обычно плохо:
- сложнее дебаг,
- нестабильно,
- хуже предсказуемость сборки.

## 4) Коммуникация между фичами
Фичи не импортят друг друга.
Коммуникация только через:
- события (domain events),
- navigation requests (outputs),
- shared contracts (ports).

Например:
- FeatureA сообщает: `requestNavigation(.openProfile(userId))`,
а AppCoordinator решает, какая фича это обслужит.

## 5) Версионирование и совместимость
Если фичи развиваются независимо:
- semver для packages,
- contracts модуль — наиболее стабильный, меняется редко,
- изменения делаем через:
  - “expand then contract”,
  - deprecations,
  - default implementations.

## 6) Предсказуемая сборка и build performance
Чтобы “плагинность” не убила сборку:
- ограничить число публичных символов,
- минимизировать dependency fan-out,
- держать Core маленьким и стабильным,
- избегать крупных shared “utils”,
- не использовать heavy generics в публичных сигнатурах.

## 7) Примеры “плагинных” use cases
- white-label приложения (разные наборы фич),
- enterprise builds,
- A/B эксперименты на уровне модулей (частично),
- отделение ответственности между командами.

## 8) Формулировка на собесе
“Плагинную архитектуру на iOS я делаю как compile-time подключаемые фичи через SPM/frameworks, с runtime выбором через registry/flags. Основа — стабильный contracts модуль и entry points. Фичи не импортят фичи, коммуникация через events/outputs, wiring в composition root. Предсказуемость сборки достигается строгими границами, минимальным public API и контролем dependency graph.”

**Самопроверка**
- Оспорено: “можно просто динамически грузить код как на Android/desktop” — на iOS это ограничено; реальная “плагинность” чаще compile-time + runtime включение.
- Неочевидно: contracts модуль должен быть максимально стабильным; если он часто меняется, то вся независимость фич рушится.
- Источники, которые стоит освежить: ограничения iOS на dynamic code loading, SwiftPM modularization, patterns plugin/registry, API evolution в Swift packages (semver, deprecations), dependency graph enforcement.

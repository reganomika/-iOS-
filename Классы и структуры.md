## Классы и структуры

### Q1 (🟢): Можно ли использовать в структуре инициализатор?

**Кратко**
- Да, у `struct` могут быть **свои init** (включая несколько перегрузок).
- Если **не писать** ни одного своего `init`, компилятор даст **memberwise init** (по всем stored-полям) и дефолтный `init()` при наличии значений по умолчанию.
- Если **написать свой init**, memberwise может **исчезнуть** (поэтому часто делают init в extension или явно добавляют memberwise).
- Доступ memberwise init определяется наименее доступным stored-свойством: если хотя бы одно поле `private`, memberwise init тоже становится `private`.
- Можно делать **failable init** (`init?`) и `throws`.

**Развёрнуто**
В Swift `struct` — value type, но это никак не ограничивает инициализацию: структура может иметь пользовательские инициализаторы, convenience-подобные фабрики (через static funcs), failable/throwing init, инициализацию через generics и т.п.

Ключевые правила:

1) **Синтезируемые инициализаторы**
- **Memberwise initializer** (`init(a:b:...)`) синтезируется только если ты **не определил** пользовательский инициализатор в теле структуры.
- Его уровень доступа определяется наименее доступным stored-свойством:
  - если поле `private` — memberwise init тоже `private`,
  - если поле `internal` (дефолт) — memberwise init `internal`.
- **Default initializer** (`init()`) синтезируется, если **все stored** свойства имеют значения по умолчанию (или опционалы с `nil`) и нет пользовательских init.

2) **Что ломает синтез**
- Как только ты объявляешь **любой** свой `init` внутри `struct`, компилятор считает, что ты берёшь контроль на себя, и синтез memberwise пропадает.
- Типичный приём, если хочешь и свой init и memberwise: **явно написать memberwise** или вынести дополнительные init в `extension`.

3) **Доступ и инварианты**
- Инициализатор — место, где ты задаёшь **инварианты** структуры: валидируешь входные параметры, приводишь их к нормальной форме, запрещаешь невозможные состояния (например, отрицательная длина, пустой id и т.д.).
- Если может не получиться — `init?`, если нужен сигнал об ошибке — `init throws`.

4) **Этапы инициализации**
- До того как `self` полностью инициализирован (все stored свойства получили значения), нельзя обращаться к `self`/методам, которые читают `self` (компилятор это жёстко проверяет).
- Для `let`-свойств: они должны быть присвоены **ровно один раз** в init.

**Мини-примеры**
```swift
struct User {
    let id: String
    var name: String = "Anonymous"

    // Пользовательский init
    init(id: String, name: String? = nil) {
        self.id = id
        self.name = name ?? "Anonymous"
    }

    // Failable init
    init?(rawID: String) {
        guard !rawID.isEmpty else { return nil }
        self.id = rawID
    }
}

// Если нет пользовательских init — будет memberwise:
// User(id: "1", name: "Z")
```

**Самопроверка**
- Оспорено: "memberwise init всегда public" — нет, его уровень доступа определяется наименее доступным полем; `private` поле делает весь memberwise init `private`.
- Неочевидно: memberwise init исчезает при добавлении любого своего init в тело структуры (не в extension); это частая причина ошибок компиляции.
- Источники: Swift Language Guide (Initialization), Swift Evolution (memberwise initializer access control).


### Q2 (🟢): Что такое copy-on-write (CoW) и как он влияет на value-типы в Swift?

**Кратко**
- **Copy-on-write**: копия value-типа "дешёвая", пока данные **разделяют один буфер**; реальная копия происходит **только при мутации**.
- В стандартной библиотеке CoW используют `Array`, `Dictionary`, `Set`, `String`, `Data` (и похожие).
- CoW сохраняет **value semantics** (логически это копия), но оптимизирует память/скорость.
- Реальная копия буфера делается, когда он **не уникален** и ты пытаешься изменить данные.
- Одновременное **чтение** shared storage из нескольких потоков безопасно; data race возникает только при concurrent write или concurrent read+write без синхронизации.

**Развёрнуто**
CoW — это паттерн реализации value-типа, где "значение" хранит внутри ссылку на heap-буфер. Несколько экземпляров value-типа могут **разделять** один и тот же буфер, пока не начинается мутация. При попытке изменить данные выполняется проверка "уникальности" буфера; если буфер разделяемый — создаётся новый буфер, данные копируются, и мутация применяется уже к новой копии.

## Зачем это нужно
1) **Дешёвые копии value-типа**
- Присваивание/передача `Array`/`String` выглядит как копирование, но фактически часто копируется только "хедер" (несколько слов: pointer/length/capacity и т.п.), а не весь контент.

2) **Сохранение value semantics**
- Пользователь ожидает: "копия независима".
- CoW гарантирует это в момент мутации: изменения не "протекут" в другую копию.

3) **Производительность**
- CoW особенно выгоден для "read-mostly" сценариев: много чтения, мало изменений.

## Как это проявляется на практике
```swift
var a = Array(0..<1_000_000)
var b = a          // обычно копии буфера нет: a и b шарят storage
b[0] = 42          // при мутации b создаёт свою копию буфера (если storage был shared)
```

Для `String` аналогично:
```swift
var s1 = "hello"
var s2 = s1         // шарят storage (возможны разные оптимизации)
s2.append("!")      // при необходимости происходит copy-on-write
```

## Проверка уникальности и кастомный CoW
В кастомных value-типах CoW часто строят вокруг reference-хранилища:
- внутри `struct` хранится `final class Storage`,
- перед мутацией проверяется, уникален ли `Storage`.

```swift
final class Storage {
    var values: [Int]
    init(_ v: [Int]) { values = v }
    func copy() -> Storage { Storage(values) }
}

struct CoWBox {
    private var storage: Storage

    init(_ v: [Int]) { storage = Storage(v) }

    private mutating func ensureUnique() {
        if !isKnownUniquelyReferenced(&storage) {
            storage = storage.copy()
        }
    }

    mutating func append(_ x: Int) {
        ensureUnique()
        storage.values.append(x)
    }

    var values: [Int] { storage.values }
}
```

## Важные нюансы/ловушки
- CoW — **деталь реализации**, а не "фича языка": компилятор не делает CoW автоматически для любых `struct`.
- CoW не отменяет стоимость мутаций: первая мутация после шаринга может быть дорогой (полная копия буфера).
- "Копия" может происходить и по другим причинам (reallocation при росте capacity, переход в другую форму хранения и т.д.).
- **Потокобезопасность**: одновременное **чтение** shared CoW storage из нескольких потоков безопасно (read-only доступ). Data race возникает при concurrent write или concurrent read+write — тут CoW не защищает, нужна явная синхронизация.

**Самопроверка**
- Оспорено: "value-типы всегда копируются целиком при присваивании" — для CoW-контейнеров это чаще копия хедера до мутации.
- Неочевидно: чтение shared CoW storage из нескольких потоков безопасно, но любая запись без синхронизации — data race, CoW это не решает.
- Источники: Swift Standard Library docs (Array/String), материалы Swift.org/WWDC про value semantics и CoW, `isKnownUniquelyReferenced`.


### Q3 (🟠): Что быстрее: структура или класс?

**Кратко**
- Нельзя сказать “всегда”: зависит от операции (создание, копирование/передача, доступ, мутация, коллекции).
- `struct` часто быстрее из-за inline storage, cache locality и шансов на static dispatch/inlining.
- `class` часто медленнее из-за ARC (retain/release), heap allocation и indirection.
- `class` может быть быстрее, если value-тип большой и его часто копируют: передача ссылки дешевле копии.
- Правильный подход: профилировать (Time Profiler/Allocations), а не угадывать.

**Развёрнуто**
Сравнение “struct vs class” без контекста — ловушка. Нужно уточнить: что сравниваем (создание, чтение/запись полей, массовая обработка в цикле, работа в коллекциях, частота передач между функциями).

1) **Локальность данных**
- `Array<Struct>` хранит элементы подряд → меньше cache misses, быстрее итерации.
- `Array<Class>` хранит подряд только ссылки → объекты в heap, больше indirection.

```swift
struct Point { var x: Double; var y: Double }
final class PointRef { var x: Double = 0; var y: Double = 0 }

let a: [Point]     // inline, подряд
let b: [PointRef]  // подряд ссылки, объекты в heap
```

2) **Стоимость копирования**
- `struct` имеет value semantics: логически копируется при присваивании/передаче.
- Маленькие структуры обычно копируются дёшево.
- Большие — могут стать дорогими, особенно если их часто передают/возвращают.
- CoW помогает только типам, которые его реализуют (обычно стандартные коллекции), но не “любой структуре”.

3) **ARC overhead**
- `class` требует retain/release при присваивании/передаче/захвате → заметно в горячих местах.
- У `struct` ARC нет, но если внутри есть reference-поля, ARC будет работать для них.

4) **Dispatch и оптимизации**
- Value-типы чаще позволяют static dispatch, inlining, specialization.
- Классы чаще используют virtual dispatch (vtable), хотя иногда возможна devirtualization (например, `final` + whole-module optimizations).

5) **Практическая эвристика**
- Небольшие иммутабельные данные, активная обработка, хранение в коллекциях → чаще `struct`.
- Нужна identity, shared mutable state, граф объектов, делегаты/наблюдатели → чаще `class`.
- Если value-тип большой и постоянно копируется между слоями → класс (или redesign: CoW/indirection) может быть быстрее.

**Самопроверка**
- Оспорено: “struct всегда быстрее”.
- Неочевидно: без конкретного сценария сравнение бессмысленно — нужно мерить.
- Источники: Apple/WWDC по performance, Swift docs по value semantics/optimization, Instruments (Time Profiler/Allocations).

  
### Q4 (🟠): Почему размер структуры должен быть известен заранее?

**Кратко**
- `struct` — value type: компилятору нужен **точный размер и layout**, чтобы выделять память, копировать значение и вычислять смещения полей.
- `struct` может храниться **inline** (на стеке, внутри другой структуры, внутри массива), поэтому размер должен быть определим.
- Нельзя иметь `struct`, который содержит сам себя как stored property: это даёт **бесконечный размер**.
- “Переменный размер” делается через **индирекцию**: ссылки на heap (`class`/`Box`), `indirect enum`, указатели/буферы.
- У generic-структур размер известен после **специализации** под конкретный `T`.

**Развёрнуто**
Размер value-типа должен быть определим, потому что Swift активно использует **inline storage** и арифметику адресов.

1) **Выделение памяти**
- Локальные переменные могут лежать на стеке → размер кадра стека должен быть известен.
- Если структура — поле другой структуры/класса, её байты включаются в layout контейнера → без фиксированного размера контейнер тоже не собрать.

2) **Копирование и передача значений**
- Value semantics означают, что значение можно копировать/передавать “как есть”.
- Для этого компилятор должен знать, сколько байт копировать и какие шаги инициализации/уничтожения применить.

3) **Доступ к полям**
- `s.field` — это вычисление `base + offset`.
- Offset вычислим только при известном layout (размеры/выравнивания полей).

4) **Почему запрещена саморекурсия в stored property**
Такое невозможно, потому что размер становится бесконечным:
```swift
struct Node {
    var next: Node // ❌ бесконечный размер
}
```

5) **Как делать рекурсивные структуры правильно**
Нужна индирекция (указатель на heap):
```swift
final class Box<T> { var value: T; init(_ v: T) { value = v } }

struct Node {
    var next: Box<Node>? // ✅ фиксированный размер: optional-ссылка
}
```

Или `indirect enum`:
```swift
indirect enum List<T> {
    case end
    case node(T, List<T>)
}
```

6) **Что про “динамический размер” стандартных типов**
Типы вроде `Array/String/Data` логически переменного размера, но само значение обычно имеет **фиксированный размер** и содержит ссылки/счётчики на heap-буфер (детали layout — реализация).

7) **Generic-структуры**
```swift
struct Foo<T> { var x: T }

let a = Foo(x: 1)      // Foo<Int> — размер фиксирован
let b = Foo(x: "hi")   // Foo<String> — другой, но тоже фиксирован
```
Размер “плавает” между разными инстансами типа, но для конкретного `Foo<Int>` он известен.

**Самопроверка**
- Оспорено: идея “можно сделать value-типы с динамическим размером без потерь” — тогда пришлось бы ввести скрытую индирекцию и ухудшить свойства value-типов.
- Неочевидно: точный внутренний layout стандартных типов (`String`, `Array`) зависит от версии Swift/ABI, поэтому на собесе лучше говорить на уровне принципов.
- Источники: Swift Language Guide (Initialization, Memory/Types), `indirect enum` в документации Swift.


### Q5 (🟠): Когда лучше использовать класс, а когда структуру?

**Кратко**
- `struct` — когда важны **value semantics**: независимые копии, предсказуемость, отсутствие общей мутации.
- `class` — когда нужна **identity**: один объект, на который ссылаются многие, общий mutable state.
- `struct` часто лучше для моделей данных, DTO, конфигов, геометрии, “снимков” состояния.
- `class` часто лучше для объектов с жизненным циклом, наблюдением, делегатами, кэшами, контроллерами/сервисами.
- Если тип должен быть **shared** и часто мутироваться из разных мест — `class` (или `actor`) обычно естественнее.
- Если тип должен быть **потокобезопасным по умолчанию** — `struct` обычно проще, но не автоматически “thread-safe”.

**Развёрнуто**
Правильный критерий — не “быстрее/медленнее”, а **семантика** и **инварианты**.

## Когда выбирать `struct`
1) **Value semantics по смыслу**
- Экземпляр — это значение, а не сущность: координаты, размеры, конфигурации, параметры запроса, результат вычисления.
- Копия должна означать независимый объект: изменив копию, ты не влияешь на оригинал.

2) **Иммутабельность и предсказуемость**
- Иммутабельные `let`-структуры проще для reasoning, тестов и конкурентного кода.
- Меньше сюрпризов с разделяемым состоянием.

3) **Хранение в коллекциях**
- Массивы структур дают хорошую локальность данных.
- Многие стандартные контейнеры используют CoW → “копии” часто дешёвые до первой мутации.

## Когда выбирать `class`
1) **Нужна identity**
- Важно “кто” это, а не “какое значение”: объект-сущность, которую все разделяют (например, текущая сессия, соединение, менеджер ресурсов).
- Есть смысл сравнивать по ссылке (`===`).

2) **Разделяемое mutable state**
- Один объект меняется, и изменения должны быть видны всем держателям ссылок.
- Примеры: кэш, репозиторий, медиаплеер, менеджер загрузок, модель с подписчиками.

3) **Жизненный цикл и взаимодействие с Cocoa**
- UIKit/AppKit классо-ориентированы: `UIViewController`, `UIView`, `CALayer`, `Operation`, `URLSessionTask`.
- KVO/ObjC runtime/`@objc` часто предполагают классы.

## Типовые ориентиры (что “хорошо звучит” на собесе)
- **Модели данных**: `struct` (особенно если они иммутабельны и легко копируются).
- **Сервисы/менеджеры**: чаще `class`, но можно и `struct` при отсутствии состояния (как “namespace”) или при внедрении зависимостей.
- **Общий доступ из concurrency**: если состояние шарится — рассмотреть `actor` вместо `class` (или строгую синхронизацию).

## Антипаттерны/ловушки
- Делать `class` “на всякий случай” → легко получить неявные побочные эффекты и retain cycles.
- Делать огромные `struct` с частой мутацией из разных мест → можно получить дорогие копии и сложность reasoning.
- “Struct = thread-safe” — неверно: потокобезопасность зависит от мутаций и того, что внутри (reference-поля, глобальные синглтоны и т.п.).

**Самопроверка**
- Оспорено: критерий “выбираю по скорости” — выбирать надо по семантике (identity vs value).
- Неочевидно: граница между “модель” и “сущность” иногда размыта — тогда решает требование к shared state и жизненному циклу.
- Источники: Swift Language Guide (Structures and Classes), Swift Concurrency (actors), Apple docs по UIKit/ObjC runtime.


### Q6 (🟠): Работает ли ARC со структурами?

**Кратко**
- ARC управляет **только reference-типами** (объектами классов) и объектами, живущими в heap под управлением runtime.
- Сама `struct` — value type, её “жизненный цикл” не через retain/release.
- Но `struct` может **содержать ссылки** (например, `class`, closures) — для этих полей ARC **работает**.
- Поэтому “у структуры нет ARC” ≠ “внутри структуры нет ARC”.

**Развёрнуто**
ARC (Automatic Reference Counting) в Swift вставляет `retain/release` (и операции для `weak`) для **объектов**, которые имеют reference semantics и управляются runtime. Это в первую очередь экземпляры `class` (а также ObjC-объекты и некоторые runtime-обёртки).

## Что происходит со `struct`
- Экземпляр структуры — это **набор байт** (поля + выравнивания), который может лежать:
  - на стеке (локальная переменная),
  - inline внутри другого значения,
  - как часть объекта класса (stored property),
  - внутри буфера коллекции (`Array<Struct>`).
- Для самой структуры нет `retain/release` на “экземпляр структуры”, потому что она не является reference-объектом.

## Но ARC может быть задействован “через поля”
Если в структуре есть reference-типы, ARC будет работать для этих полей:
```swift
final class C { deinit { print("deinit") } }

struct S {
    var obj: C
}

do {
    var s = S(obj: C())
    // при копировании s (value semantics) копируется ссылка на C,
    // и ARC увеличит retain count у C, потому что появилась новая сильная ссылка
    let s2 = s
    _ = s2
}
// при выходе из scope ARC освободит C, когда счетчик станет 0
```

### Closure внутри struct
Closure тоже может удерживать объекты (включая `self`), и это снова ARC:
```swift
final class Owner { deinit { print("deinit") } }

struct Job {
    let run: () -> Void
}

do {
    let owner = Owner()
    let job = Job(run: { _ = owner }) // closure удерживает owner
    _ = job
}
```

## Частая ловушка на собесе
Фраза “ARC не работает со структурами” корректна только в узком смысле:
- ARC не управляет **самой структурой**.
Но если в структуре есть ссылки, ARC работает **для этих ссылок**.

## Практический вывод
- Выбирая `struct`, ты не “отключаешь ARC” автоматически: если внутри есть классы/closures, retain/release остаются.
- Если цель — снизить ARC overhead на горячем пути, важно смотреть на **состав полей** и на **частоту копирования** значения.

**Самопроверка**
- Оспорено: упрощение “struct = без ARC полностью”.
- Неочевидно: где физически хранится struct (stack/heap/inline) — это оптимизация компилятора, но не меняет семантику.
- Источники: Swift Language Guide (ARC), материалы Apple/WWDC по ARC/performance, практические профили (Instruments).

### Q7 (🟠): Какой тип диспетчеризации используют все value типы?

**Кратко**
- По умолчанию value-типы (`struct`, `enum`) используют **static dispatch** (прямой вызов) для большинства методов.
- Если value-тип участвует в протокольной абстракции через экзистенциал (`any P`), возможен вызов через **witness table** (динамика на уровне протокола).
- Если метод помечен `@objc`/использует ObjC runtime (редко и обычно не для value-типа), возможен message dispatch, но это не "типично для value-типов".

**Развёрнуто**
В Swift "диспетчеризация" — это то, **как выбирается реализация метода** во время выполнения.

## 1) Основной ответ: static dispatch
Для большинства методов у `struct`/`enum` компилятор знает точную реализацию на этапе компиляции, поэтому генерирует **прямой вызов** (static/direct dispatch). Это даёт:
- минимум накладных расходов на вызов,
- хорошие шансы на inlining и другие оптимизации.

```swift
struct Counter {
    var value: Int = 0
    mutating func inc() { value += 1 }
}

var c = Counter()
c.inc() // обычно direct/static dispatch
```

## 2) Когда появляется witness dispatch
Если value-тип используется "как протокол" через экзистенциал (`any P`), компилятор выбирает реализацию через **witness table**.

```swift
protocol P { func f() }

struct S: P {
    func f() { /* ... */ }
}

let p: any P = S()
p.f() // вызов через witness table (existential → witness table lookup)
```

Важно различать два случая:
- **`any P`** (экзистенциал) — всегда witness table dispatch на уровне вызова через протокольный тип.
- **`some P`** (opaque type) — компилятор знает конкретный тип и может использовать static dispatch или специализацию.

```swift
func callF(_ p: some P) {
    p.f() // компилятор знает конкретный тип → часто static dispatch или специализация
}

func callF2(_ p: any P) {
    p.f() // witness table lookup
}
```

Если вызов идёт через generic с известным конкретным типом (специализация), компилятор часто "разворачивает" вызов в прямой, но концептуально протокол даёт механизм witness.

## 3) Что не является "базовым" для value-типов
- **vtable dispatch** — характерен для классов (виртуальные методы).
- **ObjC message dispatch** — характерен для `@objc dynamic` и ObjC runtime.

## Формулировка, которая хорошо звучит на собесе
"Value-типы в Swift в основном используют static dispatch, а динамика появляется при вызовах через протоколы: через экзистенциал (`any P`) — witness table, через generic с ограничением (`some P`) — часто статический вызов или специализация."

**Самопроверка**
- Оспорено: упрощение "у value-типов всегда только static dispatch" — протоколы добавляют witness dispatch при использовании через экзистенциал.
- Неочевидно: `some P` и `any P` — это разные механизмы; `some P` позволяет компилятору сохранить static dispatch, `any P` требует witness table.
- Источники: Swift docs/Swift ABI материалы про witness tables, Apple/WWDC по performance и generics, Swift Evolution SE-0309 (any/some различие).

### Q8 (🟠): Как работает `mutating` в протоколах и методах структуры, и когда он нужен?

**Кратко**
- `mutating` нужен для методов value-типа, которые **меняют `self`** или его stored-поля.
- В `struct/enum` без `mutating` метод может менять только локальные переменные, но не состояние экземпляра.
- В протоколе `mutating` фиксирует контракт: “реализация может менять `self`” — важно для `struct/enum`.
- У классов `mutating` не нужен: ссылки позволяют менять состояние без замены `self`.
- `mutating` позволяет **переприсваивать `self`** целиком (часто в `enum`).

**Развёрнуто**
Swift защищает value semantics: если переменная объявлена как `let`, она иммутабельна, а методы не должны менять значение. Для `var`-экземпляров изменение допускается, но компилятор требует явного маркера `mutating`, чтобы отличать “читающие” методы от “изменяющих”.

## 1) `mutating` в `struct`
```swift
struct Counter {
    private(set) var value = 0

    mutating func inc() {
        value += 1
    }

    func peek() -> Int {
        value
    }
}

var c = Counter()
c.inc()        // ok
// let c2 = Counter(); c2.inc() // ошибка: нельзя мутировать let
```

Без `mutating` компилятор не разрешит менять stored properties:
```swift
struct Bad {
    var x = 0
    func inc() { x += 1 } // ❌ Cannot assign to property: 'self' is immutable
}
```

## 2) `mutating` и присваивание `self`
`mutating` разрешает заменить `self` целиком — это особенно полезно для `enum`:
```swift
enum State {
    case idle
    case loading
    case loaded(Int)

    mutating func setLoaded(_ value: Int) {
        self = .loaded(value)
    }
}
```

## 3) `mutating` в протоколах
Если протокол описывает метод, который может менять `self`, он должен быть `mutating`, иначе `struct/enum` не смогут корректно соответствовать протоколу.

```swift
protocol Resettable {
    mutating func reset()
}

struct S: Resettable {
    var x = 10
    mutating func reset() { x = 0 }
}

final class C: Resettable {
    var x = 10
    func reset() { x = 0 } // `mutating` не пишется, для class не нужно
}
```

Почему класс может реализовать `mutating`-требование без `mutating`?
- Для reference-типа “мутация” не означает замену `self`, а просто изменение объекта по ссылке; Swift разрешает так выполнять контракт протокола.

## 4) Что считается “мутацией”
`mutating` требуется, если метод:
- меняет stored property (`self.x = ...`)
- вызывает другой `mutating` метод
- меняет значение через `inout` доступ к `self`
- переприсваивает `self`

## 5) Типовые кейсы, где `mutating` важен
- state-машины на `enum`
- value-обёртки над буфером (CoW) — `ensureUnique()` перед изменениями
- математические типы (`normalize`, `rotate`, `clamp`) с in-place модификацией
- протокольные контракты (`Sequence`-подобные итераторы часто `mutating`)

**Самопроверка**
- Оспорено: “mutating — это про многопоточность” — нет, это про изменение value-типа и контракт изменения `self`.
- Неочевидно: в протоколах важно ставить `mutating` ровно там, где это часть контракта; лишний `mutating` усложняет использование через existential и generics.
- Источники: Swift Language Guide (Methods: Mutating Methods), Swift Programming Language (Protocols), примеры стандартной библиотеки (`IteratorProtocol`).

### Q9 (🟠): Чем отличаются stored и computed properties в `struct/class` и как это влияет на layout в памяти?

**Кратко**
- **Stored property** хранит значение “физически” в экземпляре → влияет на **размер/stride** и layout.
- **Computed property** не хранит значение → это **геттер/сеттер** (функции), обычно **не влияет** на размер экземпляра.
- `lazy` stored property хранится в экземпляре и инициализируется при первом доступе → влияет на размер и имеет накладные расходы.
- Влияние на performance: stored — быстрый доступ к памяти; computed — может делать вычисления, вызывать функции, иметь побочные эффекты.
- Computed property может использовать stored backing storage или внешнее состояние — это дизайн-решение.

**Развёрнуто**
## 1) Stored properties
Stored property — часть “памяти экземпляра”:

```swift
struct S {
    var a: Int
    var b: Double
}
```

Экземпляр `S` содержит байты для `a` и `b` (плюс выравнивание). Это напрямую определяет:
- `MemoryLayout<S>.size`
- `MemoryLayout<S>.stride`
- `MemoryLayout<S>.alignment`

У класса stored properties не лежат “в указателе”, а в памяти объекта на heap, но принцип тот же: stored поля увеличивают размер объекта.

## 2) Computed properties
Computed property — это синтаксический сахар над методами:

```swift
struct Rect {
    var w: Double
    var h: Double
    var area: Double { w * h }          // read-only computed
    var side: Double {
        get { w }
        set { w = newValue; h = newValue }
    }
}
```

- `area` и `side` не занимают места в экземпляре: у них нет хранения.
- Они компилируются в функции (геттер/сеттер), которые читают/пишут stored поля.

## 3) Backing storage и `private(set)`
Часто делают computed API поверх stored storage:
```swift
struct Person {
    private var _age: Int = 0
    var age: Int {
        get { _age }
        set { _age = max(0, newValue) }
    }
}
```
Размер экземпляра определяется `_age`, а не `age`.

## 4) `lazy` properties
`lazy` — это stored property с отложенной инициализацией:
- занимает место в экземпляре,
- хранит либо значение, либо состояние “не инициализировано”,
- при первом доступе выполняет инициализацию (может быть дорогой).

```swift
final class ImageHolder {
    lazy var image = loadHugeImage()
}
```

## 5) Нюансы про layout, которые стоит озвучить на senior
- Computed properties не влияют на layout, но **влияют на ABI/вызовы**: это код, а не данные.
- Stored properties влияют на layout и ABI: изменение stored полей (добавление/переупорядочивание) меняет размер/stride и может ломать бинарную совместимость (актуально для публичных библиотек).
- Внутренние оптимизации компилятора могут держать часть значений в регистрах/скрывать временные аллокации, но семантически stored = данные, computed = поведение.

## 6) Как быстро показать это на практике
```swift
struct A { var x: Int }
struct B { var x: Int; var y: Int { x } }

print(MemoryLayout<A>.size) // 8 на 64-bit
print(MemoryLayout<B>.size) // тоже 8: computed не добавил хранения
```

**Самопроверка**
- Оспорено: “property всегда занимает память” — computed не занимает, это функции.
- Неочевидно: детали ABI/stride/alignment зависят от платформы и типа полей; конкретные числа лучше демонстрировать через `MemoryLayout`.
- Источники: Swift Language Guide (Properties), Swift ABI/Library Evolution docs (для темы бинарной совместимости), `MemoryLayout` в стандартной библиотеке.

### Q11 (🔴): Можешь рассказать про TEXT и DATA сегменты памяти?

**Кратко**
- **TEXT (code) segment**: машинный код программы и часть read-only констант; как правило **read + execute**, без write.
- **DATA segment**: глобальные/статические переменные, инициализированные значения; обычно **read + write**.
- Рядом обычно обсуждают ещё: **BSS** (неинициализированные глобальные/статические — концепция C/C++; в Swift все глобальные обязаны иметь инициализатор), **Heap**, **Stack**, **MMAP/Shared libraries**.
- В iOS используются механизмы защиты: **W^X** (страница либо write, либо execute), ASLR, code signing.

**Развёрнуто**
Говоря "сегменты памяти", обычно имеют в виду **секции образа процесса**, загруженного из Mach-O (исполняемый файл/фреймворк). Реальный layout в памяти может отличаться, но концептуально деление такое.

## TEXT segment
TEXT-сегмент (в Mach-O это обычно `__TEXT`) содержит:
- **машинный код** функций,
- таблицы переходов, метаданные, иногда read-only константы,
- строки/литералы часто лежат в read-only секциях (например, `__cstring`), концептуально рядом с кодом.

Свойства:
- Обычно отображается в память как **read + execute** (RX).
- Нельзя писать в эти страницы (защита от модификации кода).
- Защищён code signing и политикой **W^X** (write xor execute).

## DATA segment
DATA-сегмент (обычно `__DATA`) содержит:
- **инициализированные глобальные и статические переменные**,
- некоторые runtime-структуры, таблицы, ссылки, lazy pointers (часть относится к динамическому линковщику),
- в ObjC/Swift runtime там могут быть части метаданных/таблиц (зависит от секции).

Свойства:
- Обычно **read + write** (RW).
- Данные меняются во время выполнения.

## BSS (важная оговорка для Swift)
BSS — концепция из C/C++: неинициализированные глобальные/статические переменные, которые не занимают места в файле, но при старте процесса заполняются нулями.

**В Swift** это понятие применяется ограниченно: все глобальные переменные в Swift **обязаны иметь инициализатор** (явный или implicit через тип с нулевым значением). Написать `var g: Int` без инициализатора на верхнем уровне файла — **ошибка компиляции**.

На уровне Mach-O секция BSS (`__BSS`) всё равно существует, но заполняется компилятором автоматически (Swift runtime инициализирует глобальные переменные лениво при первом обращении).

## Heap и Stack (для полноты картины на собесе)
- **Stack**: локальные переменные, кадры вызовов, часть временных значений; быстро, LIFO, ограничен по размеру.
- **Heap**: динамические аллокации (обычно объекты классов, буферы коллекций, ARC-managed объекты); гибко, но дороже.

## Пример "что куда попадает" (упрощённо)
```swift
var g1 = 10            // глобальная инициализированная переменная → DATA

struct S { static var x = 1 }  // статическая → DATA (инициализация ленивая в Swift)

func f() {
    let a = 1          // часто на stack/в регистрах (оптимизации)
    let obj = NSObject() // объект класса → heap, указатель может лежать на stack
}
```

## Практические выводы, которые ценят на уровне senior
- "Код" и "данные" разделены для безопасности: нельзя одновременно писать и исполнять (W^X).
- Глобальные/статические переменные живут долго и могут ухудшать тестируемость/конкурентность (shared state).
- Оптимизации/ABI могут менять детали, но концепт сегментов помогает понимать:
  - почему константы read-only,
  - почему модификация кода запрещена,
  - где искать утечки/рост памяти (heap), где переполнения (stack).
- В Swift глобальные переменные инициализируются **лениво** при первом обращении (thread-safe по умолчанию через dispatch_once-подобный механизм).

**Самопроверка**
- Оспорено: упрощение "все строки в DATA, а код только в TEXT" — в Mach-O много секций, но для собеса важен смысл RX vs RW.
- Оспорено: "BSS работает так же в Swift как в C" — в Swift нет "неинициализированных" глобальных переменных; BSS используется компилятором, но разработчик не может объявить глобальную без инициализатора.
- Неочевидно: точный набор секций (`__TEXT`, `__DATA`, `__DATA_CONST`, `__LINKEDIT`) зависит от бинаря и версии toolchain, детали лучше не утверждать без оговорок.
- Источники: Apple docs по Mach-O format, статьи/доки про dyld, материалы по iOS memory layout и memory protection (W^X, ASLR, code signing).

### Q11 (🔴) [NEW]: Какие гарантии даёт exclusivity enforcement в Swift и как оно связано с value semantics?

**Кратко**
- Swift требует **эксклюзивного доступа** к памяти для **write** и для **read+write**: нельзя одновременно писать и читать/писать один и тот же участок памяти.
- Это защищает от классов багов типа “двойной `inout` к одному и тому же”, aliasing при мутациях, некорректных interleaving при оптимизациях.
- Связь с value semantics: чтобы value-типы были предсказуемыми, компилятору нужны гарантии, что во время мутации нет конкурирующих доступов к тому же storage.
- Нарушение обычно ловится **на этапе компиляции**, а некоторые случаи — **в рантайме** (trap) при включённой динамической проверке.
- Это не “thread-safety”: exclusivity — про корректность доступа в одном потоке/контексте, а data race между потоками остаётся проблемой.

**Развёрнуто**
## 1) Что такое exclusivity
Exclusivity (Law of Exclusivity) — правило Swift: доступ к памяти должен быть
- **exclusive** для write,
- и не должен пересекаться с другим доступом к той же области памяти, если хотя бы один доступ — write.

Это особенно важно для:
- `inout` параметров,
- mutating методов,
- модификации элементов коллекций,
- свойств/подскриптов, которые возвращают `inout` доступ.

## 2) Типичный пример нарушения: overlapping `inout`
```swift
func swapInts(_ a: inout Int, _ b: inout Int) {
    let t = a
    a = b
    b = t
}

var x = 1
// swapInts(&x, &x) // ❌ overlapping access (компилятор не разрешит)
```

## 3) Пересечение доступа через свойства одного объекта
Классический кейс — передача двух `inout` к разным свойствам одного значения:
```swift
struct Pair { var a: Int; var b: Int }

func f(_ x: inout Int, _ y: inout Int) { x += 1; y += 1 }

var p = Pair(a: 1, b: 2)
// f(&p.a, &p.b) // в большинстве случаев OK: разные поля, непересекающиеся области
// но проблемы появляются, если доступ “размыт” через computed/subscript
```

Если свойство computed и доступ к нему может затрагивать общий storage, компилятор часто запрещает:
```swift
struct S {
    var arr = [1,2,3]
    subscript(i: Int) -> Int {
        get { arr[i] }
        set { arr[i] = newValue }
    }
}

func g(_ x: inout Int, _ y: inout Int) { x += 1; y += 1 }

var s = S()
// g(&s[0], &s[1]) // ❌ часто запрещено: overlapping access через subscript
```

## 4) Почему это связано с value semantics
Value-типы в Swift могут иметь общий backing storage (например, CoW-коллекции). Во время мутации важно, чтобы компилятор мог считать:
- “вот этот участок памяти сейчас меняется и никто другой к нему не обращается так, что увидит промежуточное состояние”.
Иначе оптимизации (inlining, reordering, elimination) могли бы менять наблюдаемое поведение или приводить к UB-подобным эффектам.

Exclusivity упрощает модель: мутация — это транзакция с эксклюзивным доступом.

## 5) Compile-time vs runtime enforcement
- Многие нарушения ловятся компилятором (особенно прямые `&x`/`&x`).
- Некоторые случаи зависят от пути выполнения/абстракции и могут ловиться рантайм-проверками (trap), если они активны.
- В релизе поведение зависит от настроек, но рассчитывать на “проскочит” нельзя: это логическая ошибка.

## 6) Что это НЕ гарантирует
- Не защищает от data races между потоками: два потока могут одновременно писать в одно место, и exclusivity не спасёт без синхронизации/actors.
- Не делает `Array`/`Dictionary` автоматически thread-safe.

**Самопроверка**
- Оспорено: “это просто запрет на два inout” — правило шире: любые перекрывающиеся доступы read/write.
- Неочевидно: конкретные примеры с subscript/computed могут по-разному приниматься компилятором в зависимости от возможности доказать непересечение; на собесе важно объяснить принцип и показать типовые кейсы.
- Источники: Swift Evolution proposals про exclusivity (Law of Exclusivity), Swift Language Guide про `inout`/mutating, материалы Swift.org/WWDC по memory safety.

### Q12 (🔴): Как проектировать value-типы, чтобы избегать лишних копий и retain/release (например, при работе с `Array`/`Data`)?

**Кратко**
- Делай value-типы **маленькими и "плоскими"**: избегай больших stored-полей и глубоких вложенностей, если они часто копируются.
- Опирайся на **CoW-типы** стандартной библиотеки (`Array`, `String`, `Data`) и не провоцируй лишние "уникализации" при мутациях.
- Минимизируй ARC внутри value-типа: меньше `class`-полей/closures на горячих путях, избегай лишних захватов.
- Используй **`inout`/mutating API** и "batching" изменений, чтобы не создавать промежуточные копии.
- Контролируй "copy boundaries": где именно происходят присваивания, возвраты из функций, захваты в замыканиях.

**Развёрнуто**
Цель — сохранить преимущества value semantics, но не платить лишним копированием памяти и ARC-трафиком.

## 1) Держать value-типы маленькими
Чем больше "сырого" stored-объёма (например, большие массивы как вложенные структуры без CoW, большие fixed-size буферы), тем дороже копии.
- "Модель-конфиг" с десятком `Int/String/Data` — нормально.
- "Монстр-структура" с огромными вложенными массивами и частой мутацией — кандидат на redesign.

## 2) Использовать CoW и не ломать его
`Array`/`Data`/`String` обычно CoW: копия дёшева до первой мутации. Но ты можешь случайно провоцировать копии:
- мутировать после шаринга в горячем цикле,
- по чуть-чуть мутировать, заставляя многократно проверять уникальность и перераспределять буфер.

Хороший приём — "batching":
```swift
func process(_ input: [Int]) -> [Int] {
    var out = input
    out.reserveCapacity(out.count)
    for i in out.indices {
        out[i] *= 2
    }
    return out
}
```
Здесь:
- `out` — одна логическая копия,
- мутации идут "in-place" и без лишних промежуточных массивов.

## 3) Избегать лишних временных значений
Плохой паттерн — создавать цепочки промежуточных копий:
```swift
let result = a.map(...).filter(...).sorted(...)
```
Иногда это ок, но на больших данных может породить много аллокаций.

Альтернативы:
- один проход,
- `lazy` последовательности (если нужны не все элементы и обработка каждого дорогая),
- `reserveCapacity` и ручное заполнение.

Важно: `lazy` в Swift не всегда быстрее eager-вычислений на небольших коллекциях из-за overhead замыканий. `lazy` выгоден когда обработка дорогая и нужен не весь результат, а не просто как способ "избежать временных массивов".

## 4) Осторожно с `Data`
`Data` часто используется как буфер и тоже CoW, но:
- некоторые API возвращают "view"/slice, а потом мутация может вызвать копию,
- преобразования типа `Data(bytes:)`/`Array(data)` могут создавать копии.

Правила:
- избегать частых `Data -> [UInt8] -> Data`,
- использовать `withUnsafeBytes`/`withUnsafeMutableBytes` для чтения/записи без лишних копий (но аккуратно с безопасностью).

```swift
data.withUnsafeBytes { raw in
    // читать без копии
}
```

## 5) Минимизировать ARC внутри value-типа
Если `struct` хранит `class`-поля, то при копировании структуры копируются ссылки → ARC делает retain/release.
- В горячем коде это может быть дороже, чем кажется.
Приёмы:
- хранить "сырые" value-данные вместо объектов,
- выносить тяжёлые reference-объекты наружу,
- не тащить closures как stored properties, если они часто копируются.

## 6) Контролировать мутацию через `inout` и API-дизайн
Передача value-типа по значению может создавать копии на границе функции.
Иногда выгоднее делать "редактор" через `inout`:
```swift
func normalize(_ data: inout [Int]) {
    for i in data.indices { data[i] = max(0, data[i]) }
}

var xs = [1, -2, 3]
normalize(&xs) // мутация in-place, без создания новых массивов
```

## 7) Когда нужна индирекция (и это нормально)
Если значение по смыслу value-type, но объём данных большой и часто копируется, можно применить CoW-обёртку:
- внутри `struct` хранить `final class Storage`,
- перед мутацией делать `isKnownUniquelyReferenced` и копировать storage только при необходимости.

Это даёт:
- value semantics с контролируемой стоимостью,
- но усложняет код и требует дисциплины (особенно для thread-safety).

## 8) Как проверять, что ты действительно избежал копий
- Профилировать: Allocations + Time Profiler.
- Считать аллокации, смотреть на "Copy"/"retain/release" hotspots.
- Писать микро-бенчмарки на критичных участках, но ориентироваться на реальные сценарии.

**Самопроверка**
- Оспорено: "CoW автоматически делает всё быстрым" — мутация после шаринга всё равно может быть дорогой, а цепочки преобразований могут плодить временные буферы.
- Оспорено: "`lazy` всегда быстрее eager" — нет: `lazy` выгоден при дорогой обработке и частичном потреблении результата; на небольших коллекциях overhead замыканий может перевесить.
- Неочевидно: точные моменты копирования у `String`/`Data` могут меняться; лучше мыслить в терминах "шаринг storage + копия при мутации/реаллокации".
- Источники: Swift stdlib docs (Array/Data/String), материалы Apple/WWDC по performance, `isKnownUniquelyReferenced`, Instruments (Allocations/Time Profiler).

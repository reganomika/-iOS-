## Q1 · Инициализаторы в структуре 🟢

**Суть.** У `struct` могут быть свои `init` (несколько, `init?`, `throws`). Если своих нет — компилятор синтезирует **memberwise** `init(...)` и `init()` (когда у всех полей есть значения по умолчанию).

- Любой свой `init` в теле структуры → memberwise-синтез **пропадает**. Чтобы оставить оба, вынеси свой init в `extension` или объяви memberwise явно.
- Внутри `init` нельзя обращаться к `self`, пока **все** stored-поля не присвоены; `let`-поля присваиваются ровно один раз.
- Доступность memberwise-init зависит от уровней доступа полей (`private`-поля делают его недоступным извне).

💬 *На собесе:* «Memberwise по умолчанию, но как только пишу свой init — синтез исчезает; чтобы сохранить оба, выношу init в extension. В init обязан полностью инициализировать self до первого обращения к нему.»

<details><summary>Подробно</summary>

`struct` — value type, но это не ограничивает инициализацию: пользовательские init, фабрики через `static func`, failable/throwing init, generics.

**Синтезируемые init:**
- *Memberwise* `init(a:b:...)` — только если ты **не** определил свой init в теле; параметры и доступность зависят от уровней доступа stored-полей.
- *Default* `init()` — если у всех stored-полей есть дефолты (или это optional с `nil`) и нет своих init.

**Этапы инициализации:** до полной инициализации `self` нельзя вызывать методы, читающие `self` (компилятор проверяет жёстко). Init — место, где задаются инварианты (валидация, нормализация); невозможное состояние → `init?` либо `init throws`.

```swift
struct User {
    let id: String
    var name: String = "Anonymous"

    init(id: String, name: String? = nil) {   // свой init → memberwise пропал
        self.id = id
        self.name = name ?? "Anonymous"
    }

    init?(rawID: String) {                      // failable; name возьмёт дефолт
        guard !rawID.isEmpty else { return nil }
        self.id = rawID
    }
}
```

*Источники:* Swift Language Guide — Initialization.

</details>

## Q2 · Copy-on-write (CoW) 🟢

**Суть.** Копия value-типа «дешёвая», пока экземпляры **делят один heap-буфер**; реальная копия буфера происходит **только при мутации не-уникального буфера** (проверка через `isKnownUniquelyReferenced`).

- CoW есть у стандартных `Array`, `Dictionary`, `Set`, `String`, `Data` — но это **деталь реализации**, не автомат для любой `struct`.
- Сохраняет value semantics (логически копия независима), оптимизируя память/скорость. Особенно выгоден для read-mostly.

⚠️ **Ловушка.** CoW **не** даёт thread-safety: одновременная мутация одного значения из разных потоков — всё равно data race. Первая мутация после шаринга может быть дорогой (полная копия буфера).

💬 *На собесе:* «CoW шарит storage между копиями и копирует по-настоящему только при мутации, когда буфер не уникален. Сохраняет value semantics, но не делает тип потокобезопасным.»

<details><summary>Подробно</summary>

Value «значение» хранит внутри ссылку на heap-буфер. Несколько экземпляров делят буфер, пока не начинается мутация; перед изменением проверяется уникальность — если буфер общий, создаётся новая копия, и мутация идёт уже в неё.

**Кастомный CoW** строят вокруг reference-хранилища:

```swift
final class Storage {
    var values: [Int]
    init(_ v: [Int]) { values = v }
    func copy() -> Storage { Storage(values) }
}

struct CoWBox {
    private var storage: Storage
    init(_ v: [Int]) { storage = Storage(v) }

    private mutating func ensureUnique() {
        if !isKnownUniquelyReferenced(&storage) { storage = storage.copy() }
    }
    mutating func append(_ x: Int) { ensureUnique(); storage.values.append(x) }
}
```

Копия может происходить и по другим причинам (реаллокация при росте capacity). Внутренний layout `String`/`Array` зависит от версии Swift/ABI — на собесе объясняй принцип, а не байты.

*Источники:* Swift stdlib docs (Array/String), `isKnownUniquelyReferenced`, WWDC по value semantics.

</details>

## Q3 · Что быстрее: структура или класс? 🟠

**Суть.** Универсального ответа нет — зависит от операции (создание, копирование, доступ, мутация, работа в коллекциях). Сравнение без контекста — ловушка.

- `struct` часто быстрее: inline storage, cache locality, шансы на static dispatch/inlining, нет ARC.
- `class` часто медленнее: ARC (retain/release), heap allocation, indirection, чаще virtual dispatch.
- Но `class` **может быть быстрее**, если value-тип большой и его часто копируют — передать ссылку дешевле копии.

💬 *На собесе:* «Уточню, что именно сравниваем. Обычно struct быстрее из-за локальности и отсутствия ARC, но большой часто копируемый value-тип может проигрывать классу. Правильный ответ — измерять в Instruments, а не угадывать.»

<details><summary>Подробно</summary>

- **Локальность:** `Array<Struct>` хранит элементы подряд (меньше cache misses); `Array<Class>` — подряд только ссылки, объекты разбросаны по heap.
- **Стоимость копий:** маленькие структуры копируются дёшево; большие — дорого при частой передаче. CoW спасает только типы, которые его реализуют.
- **ARC:** у класса retain/release при присваивании/передаче/захвате; у struct ARC нет, но работает для reference-полей внутри.
- **Dispatch:** value-типы чаще допускают static dispatch + inlining + specialization; классы — virtual dispatch (vtable), хотя `final` + WMO дают девиртуализацию.

**Эвристика:** маленькие иммутабельные данные в коллекциях → `struct`; identity / shared mutable state / граф объектов / делегаты → `class`.

*Источники:* WWDC по performance, Instruments (Time Profiler / Allocations).

</details>

## Q4 · Почему размер структуры должен быть известен заранее? 🟠

**Суть.** `struct` — value type, и компилятору нужен **точный размер и layout**, чтобы выделять память (часто inline/на стеке), копировать значение целиком и вычислять смещения полей (`base + offset`).

- Нельзя хранить `struct`, содержащую саму себя как stored property — это **бесконечный размер**.
- «Переменный размер» делается через **индирекцию**: ссылка на heap (`class`/`Box`), `indirect enum`.
- У generic-структур размер известен после **специализации** под конкретный `T`.

💬 *На собесе:* «Value-тип лежит inline, поэтому его размер должен быть определим — для аллокации, копирования и доступа к полям по offset. Рекурсию делаю через индирекцию: Box-ссылку или indirect enum.»

<details><summary>Подробно</summary>

Swift активно использует inline storage и арифметику адресов: локальные переменные на стеке (нужен размер кадра), поля контейнеров включаются в layout, доступ к полю = `base + offset`.

```swift
struct Node { var next: Node }        // ❌ бесконечный размер

final class Box<T> { var value: T; init(_ v: T) { value = v } }
struct Node2 { var next: Box<Node2>? }  // ✅ фиксированный размер (optional-ссылка)

indirect enum List<T> { case end; case node(T, List<T>) }  // ✅ через indirect
```

`Array`/`String`/`Data` логически переменного размера, но само значение фиксированного размера и содержит ссылки/счётчики на heap-буфер. Generic: `Foo<Int>` и `Foo<String>` имеют разные, но каждый — фиксированный размер.

*Источники:* Swift Language Guide — Initialization, `indirect enum`.

</details>

## Q5 · Когда лучше класс, а когда структура? 🟠

**Суть.** Критерий — **семантика и инварианты**, а не скорость. `struct` — когда нужны value semantics (независимые копии). `class` — когда нужна **identity** (один объект, на который ссылаются многие; общий mutable state).

- `struct`: модели данных, DTO, конфиги, геометрия, «снимки» состояния; иммутабельность → проще reasoning и конкурентность.
- `class`: жизненный цикл, делегаты/наблюдатели, кэши, сервисы, UIKit/Cocoa (`UIView`, `URLSessionTask`), KVO/`@objc`.
- Shared + часто мутируется из разных мест → `class` или **`actor`**.

⚠️ **Ловушка.** «struct = thread-safe» — неверно: потокобезопасность зависит от мутаций и содержимого (reference-поля, синглтоны).

💬 *На собесе:* «Выбираю по семантике: нужна независимая копия — struct, нужна общая идентичность и разделяемое состояние — class или actor. Класс "на всякий случай" ведёт к неявным сайд-эффектам и retain cycles.»

<details><summary>Подробно</summary>

**`struct` когда:** экземпляр — это значение, а не сущность (координаты, конфиг, результат вычисления); копия = независимый объект; иммутабельность для предсказуемости; хранение в коллекциях (локальность + CoW).

**`class` когда:** важна identity (сравнение по `===`), разделяемое mutable state видно всем держателям (кэш, репозиторий, плеер, модель с подписчиками); жизненный цикл и интеграция с Cocoa.

**Ориентиры:** модели → `struct`; сервисы/менеджеры → чаще `class` (или `struct`-namespace без состояния); shared state в concurrency → `actor`.

**Антипаттерны:** огромные `struct` с частой мутацией из разных мест (дорогие копии); `class` без необходимости (retain cycles).

*Источники:* Swift Language Guide — Structures and Classes; Swift Concurrency (actors).

</details>

## Q6 · Работает ли ARC со структурами? 🟠

**Суть.** ARC управляет **только reference-типами** (объектами классов в heap). У самой `struct` нет retain/release — её жизненный цикл не через ARC.

⚠️ **Ловушка (любят на собесе).** «ARC не работает со структурами» верно только про **саму структуру**. Если внутри есть reference-поля (`class`, замыкания) — для **этих полей** ARC работает: при копировании структуры копируются ссылки, и retain count объектов растёт.

- Выбор `struct` ≠ «отключил ARC»: если внутри классы/closures, retain/release остаются.
- Чтобы снизить ARC-overhead на горячем пути — смотри на **состав полей** и **частоту копирования**.

💬 *На собесе:* «ARC не управляет самой структурой, но работает для её reference-полей. Поэтому struct с class-полями всё равно платит за retain/release при копировании.»

<details><summary>Подробно</summary>

```swift
final class C { deinit { print("deinit") } }
struct S { var obj: C }

do {
    var s = S(obj: C())
    let s2 = s        // value-копия копирует ссылку на C → ARC: +1 retain
    _ = s2
}                     // выход из scope → ARC освободит C, когда счётчик = 0
```

Замыкание внутри структуры тоже удерживает захваченные объекты (это снова ARC). Где физически лежит struct (stack/heap/inline) — оптимизация компилятора, семантику не меняет.

*Источники:* Swift Language Guide — ARC; Instruments (Allocations).

</details>

## Q7 · Какой тип диспетчеризации у value-типов? 🟠

**Суть.** По умолчанию value-типы (`struct`, `enum`) используют **static (direct) dispatch** — компилятор знает точную реализацию, генерирует прямой вызов (минимум накладных, шанс на inlining).

- Через протокол (existential `any P` или generic-ограничение) появляется **witness table dispatch**.
- `vtable` — это про классы; ObjC message dispatch — про `@objc dynamic`. Для value-типов не базовое.

💬 *На собесе:* «Value-типы в основном на static dispatch, а динамика появляется при вызовах через протоколы — там работает witness table.»

<details><summary>Подробно</summary>

```swift
struct Counter { var value = 0; mutating func inc() { value += 1 } }
var c = Counter(); c.inc()          // static/direct dispatch

protocol P { func f() }
struct S: P { func f() {} }
let p: any P = S(); p.f()           // witness table (existential)
```

При вызове через generic с известным конкретным типом компилятор часто специализирует и «разворачивает» вызов в прямой (зависит от оптимизаций), но механизм протокола — witness.

*Источники:* Swift ABI / witness tables, WWDC по generics и performance.

</details>

## Q8 · Как работает `mutating` и когда он нужен? 🟠

**Суть.** `mutating` нужен методам value-типа (`struct`/`enum`), которые **меняют `self`** или его stored-поля. Без него метод не может изменить состояние экземпляра. В протоколе `mutating` фиксирует контракт «реализация может менять self».

- Позволяет **переприсвоить `self` целиком** — часто в `enum` (state-машины).
- Классам `mutating` не нужен: мутация по ссылке не меняет `self`. Поэтому `class` может реализовать `mutating`-требование протокола без слова `mutating`.
- Нельзя вызвать `mutating`-метод на `let`-экземпляре.

💬 *На собесе:* «mutating — про изменение value-типа, а не про потоки. Он отмечает методы, меняющие self, и нужен в протоколе, чтобы struct/enum могли его реализовать. Класс выполняет тот же контракт без mutating, потому что меняет объект по ссылке.»

<details><summary>Подробно</summary>

```swift
struct Counter {
    private(set) var value = 0
    mutating func inc() { value += 1 }   // без mutating — ошибка компиляции
}

enum State {
    case idle, loading, loaded(Int)
    mutating func setLoaded(_ v: Int) { self = .loaded(v) }   // переприсвоение self
}

protocol Resettable { mutating func reset() }
struct S: Resettable { var x = 10; mutating func reset() { x = 0 } }
final class C: Resettable { var x = 10; func reset() { x = 0 } } // без mutating
```

**Мутацией считается:** запись в stored property, вызов другого `mutating`, `inout`-доступ к `self`, переприсвоение `self`. Лишний `mutating` в протоколе усложняет использование через existential/generics — ставь только где это часть контракта.

*Источники:* Swift Language Guide — Methods (Mutating), Protocols; `IteratorProtocol`.

</details>

## Q9 · Stored vs computed properties и layout 🟠

**Суть.** **Stored** хранит значение физически в экземпляре → влияет на `size`/`stride`/`alignment`. **Computed** — это геттер/сеттер (код, не данные) → размер экземпляра **не** меняет.

- `lazy` stored — занимает место + инициализируется при первом доступе (может быть дорого).
- Stored-поля влияют на **ABI**: добавление/переупорядочивание меняет stride и ломает бинарную совместимость (важно для публичных библиотек). Computed — это код/вызовы, на layout не влияет.

💬 *На собесе:* «Stored — это память экземпляра, влияет на size/stride и ABI. Computed — функции поверх stored или внешнего состояния, места не занимают. lazy — stored с отложенной инициализацией.»

<details><summary>Подробно</summary>

```swift
struct Rect {
    var w, h: Double
    var area: Double { w * h }                    // computed read-only — 0 байт
    var side: Double { get { w } set { w = newValue; h = newValue } }
}

struct A { var x: Int }
struct B { var x: Int; var y: Int { x } }
MemoryLayout<A>.size   // 8 (64-bit)
MemoryLayout<B>.size   // тоже 8: computed не добавил хранения
```

Частый приём — computed API поверх stored backing (`_age` хранит, `age` валидирует в сеттере): размер определяет `_age`. У класса stored-поля лежат в объекте на heap, принцип тот же. Конкретные числа лучше показывать через `MemoryLayout`.

*Источники:* Swift Language Guide — Properties; Library Evolution (ABI); `MemoryLayout`.

</details>

## Q10 · Exclusivity enforcement (Law of Exclusivity) 🔴

**Суть.** Swift требует **эксклюзивного доступа** к памяти: нельзя пересекающиеся доступы к одной области, если хотя бы один из них — **write**. Защищает от aliasing-багов при мутациях (двойной `inout`, перекрытие через subscript).

- Касается `inout`-параметров, `mutating`-методов, модификации элементов коллекций, computed/subscript, возвращающих доступ.
- Ловится **на компиляции**, часть случаев — **рантайм-trap** при активной динамической проверке.
- Связь с value semantics: мутация трактуется как «транзакция» с эксклюзивным доступом — иначе оптимизации (reordering/inlining) могли бы менять наблюдаемое поведение.

⚠️ **Ловушка.** Это **не** thread-safety: exclusivity — про корректность в одном потоке/контексте; data race между потоками остаётся (нужны синхронизация/actors).

💬 *На собесе:* «Закон эксклюзивности запрещает перекрывающиеся доступы к памяти, если хоть один — запись. Это даёт компилятору право оптимизировать мутации, но это про один контекст, не про межпоточную безопасность.»

<details><summary>Подробно</summary>

```swift
func swapInts(_ a: inout Int, _ b: inout Int) { let t = a; a = b; b = t }
var x = 1
// swapInts(&x, &x)   // ❌ overlapping access — компилятор не разрешит

struct S {
    var arr = [1, 2, 3]
    subscript(i: Int) -> Int { get { arr[i] } set { arr[i] = newValue } }
}
func g(_ x: inout Int, _ y: inout Int) { x += 1; y += 1 }
var s = S()
// g(&s[0], &s[1])     // ❌ часто запрещено: overlapping через subscript
```

Конкретные случаи с computed/subscript принимаются по-разному в зависимости от того, может ли компилятор доказать непересечение. В релизе рассчитывать на «проскочит» нельзя — это логическая ошибка.

*Источники:* Swift Evolution — Law of Exclusivity; WWDC по memory safety.

</details>

## Q11 · TEXT и DATA сегменты памяти 🔴

**Суть.** Это секции образа процесса (из Mach-O). **TEXT** (`__TEXT`) — машинный код + read-only константы/литералы, отображается как **read+execute (RX)**. **DATA** (`__DATA`) — инициализированные глобальные/статические переменные, **read+write (RW)**.

- Рядом обычно спрашивают: **BSS** (неинициализированные глобальные/статические — в файле места не занимают, при старте обнуляются), **Heap**, **Stack**.
- Защиты iOS: **W^X** (страница либо write, либо execute), ASLR, code signing — поэтому код read-only и его нельзя модифицировать.

💬 *На собесе:* «TEXT — код и константы, read+execute; DATA — инициализированные глобальные/статические, read+write; BSS — неинициализированные, обнуляются при старте. Разделение кода и данных + W^X — это про безопасность.»

<details><summary>Подробно</summary>

- **Stack:** локальные переменные, кадры вызовов; быстро, LIFO, ограничен по размеру.
- **Heap:** динамические аллокации (объекты классов, буферы коллекций, ARC-managed); гибко, но дороже.

```swift
var g1 = 10                       // глобальная инициализированная → DATA
var g2: Int                       // глобальная без init → BSS
struct S { static var x = 1 }     // статическая → DATA/BSS
func f() {
    let a = 1                     // часто stack / регистры
    let obj = NSObject()          // объект → heap, указатель может лежать на stack
}
```

Практика для senior: глобальные/статические живут долго и ухудшают тестируемость/конкурентность (shared state). Точный набор секций (`__DATA_CONST`, `__LINKEDIT`…) зависит от toolchain — на собесе важен смысл RX vs RW.

*Источники:* Mach-O format, dyld, iOS memory protection (W^X, ASLR).

</details>

## Q12 · Проектирование value-типов без лишних копий и ARC 🔴

**Суть.** Сохранить value semantics, но не платить лишним копированием и ARC-трафиком: держать типы **маленькими и плоскими**, опираться на CoW стандартных типов и **не ломать его**, минимизировать reference-поля.

- **Batching** мутаций + `reserveCapacity` вместо цепочек промежуточных копий; `inout`/`mutating` API для in-place изменений.
- Меньше `class`-полей/closures на горячих путях (каждая копия struct = retain/release ссылок).
- Осторожно с `Data`: slices и конвертации `Data ↔ [UInt8]` плодят копии — используй `withUnsafeBytes`.
- Большой value-тип, который часто копируется → **CoW-обёртка** (`class Storage` + `isKnownUniquelyReferenced`).

💬 *На собесе:* «Держу value-типы маленькими, опираюсь на CoW и не провоцирую уникализацию в горячих циклах, мутирую через inout/batching, минимизирую class-поля. Если значение большое — оборачиваю в кастомный CoW. Проверяю всё через Allocations.»

<details><summary>Подробно</summary>

```swift
func process(_ input: [Int]) -> [Int] {     // batching: одна логическая копия
    var out = input
    out.reserveCapacity(out.count)
    for i in out.indices { out[i] *= 2 }     // in-place, без промежуточных массивов
    return out
}

func normalize(_ data: inout [Int]) {        // мутация in-place через inout
    for i in data.indices { data[i] = max(0, data[i]) }
}

data.withUnsafeBytes { raw in /* чтение без копии */ }
```

Цепочки `a.map(...).filter(...).sorted(...)` на больших данных плодят аллокации — иногда выгоднее один проход или `lazy`. CoW-обёртка даёт value semantics с контролируемой стоимостью, но требует дисциплины (и не решает thread-safety). Проверяй гипотезы профилировщиком (Allocations + Time Profiler), а не на глаз.

*Источники:* Swift stdlib (Array/Data/String), `isKnownUniquelyReferenced`, Instruments.

</details>

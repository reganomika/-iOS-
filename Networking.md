## Networking, кеширование, resiliency

### Q240 (🟢): Как устроен `URLSession`: какие основные сущности (task/request/response) и где чаще всего ошибаются?

**Кратко**
- `URLSession` — менеджер сетевых запросов.
- Ключевые сущности:
  - `URLRequest` (что отправляем),
  - `URLSessionTask` (`dataTask` / `uploadTask` / `downloadTask`),
  - `URLResponse`/`HTTPURLResponse` (что получили),
  - `URLSessionConfiguration` (политики: кеш, таймауты, прокси, куки),
  - делегаты (TLS, редиректы, прогресс, background).
- Частые ошибки: неправильные таймауты, утечки (retain циклы в делегатах/closures), игнорирование status codes, неправильная обработка cancellation/ретраев, отсутствие лимитов параллелизма.

**Развёрнуто**
## 1) Главная модель `URLSession`
`URLSession` — это:
- пул ресурсов (соединения, очереди),
- конфигурация поведения,
- фабрика задач (tasks).

Одна сессия = общий контекст:
- cookie storage,
- cache,
- connection pool,
- креденшелы,
- ограничения одновременных соединений.

Вывод:
- создавать сессию “на каждый запрос” — часто плохая идея: вы теряете переиспользование соединений и получаете лишние расходы.

## 2) `URLRequest`: входные параметры
Содержит:
- URL, method, headers,
- body (data/stream),
- cache policy (на уровне запроса),
- timeoutInterval (на уровне запроса).

Типовая ошибка:
- путать настройки `URLRequest.timeoutInterval` и таймауты `URLSessionConfiguration` (они работают на разных уровнях).

## 3) Tasks: какие бывают и когда что
### `dataTask`
- обычные запросы (JSON, небольшие ответы).
Важно:
- ответ приходит в памяти (или через streaming API, если нужно).

### `uploadTask`
- отправка данных/файлов.
Важно:
- есть варианты с `fromFile` и `from`, и background поддержка.

### `downloadTask`
- скачивание в файл.
Важно:
- поддерживает resume data для продолжения (не всегда надёжно, но базово есть).

## 4) `URLResponse` / `HTTPURLResponse`
- `URLResponse` — базовый тип.
- `HTTPURLResponse` — содержит status code и headers.

Типовая ошибка:
- считать “если error == nil, то успех”.
Реальность:
- `error == nil` означает, что транспортный уровень ок,
- но HTTP может быть 401/500 и это всё равно ошибка бизнес-уровня запроса.

## 5) Configuration: где чаще всего ломают
`URLSessionConfiguration` задаёт:
- `requestCachePolicy`, `urlCache`,
- `timeoutIntervalForRequest` и `timeoutIntervalForResource`,
- `waitsForConnectivity` (если включили),
- `allowsExpensiveNetworkAccess`/`allowsConstrainedNetworkAccess`,
- куки и credential storage.

Типовая ошибка:
- не думать про cache policy и потом “почему не обновляется/почему постоянно ходит в сеть”.
- включить `waitsForConnectivity` и получить “зависание” запросов без явной ошибки, если не продумали UX.

## 6) Делегаты vs completion handlers
### Completion handlers
- проще для большинства запросов.
Риск:
- capture `self` и держать объект дольше, чем ожидали.

### Delegates
Нужны для:
- TLS challenge / client cert,
- редиректов,
- background sessions,
- прогресса/стриминга.

Типовая ошибка:
- держать делегат сильной ссылкой → retain cycle:
  - `URLSession` удерживает делегат,
  - делегат удерживает `URLSession`.

## 7) Частые ошибки (которые реально спрашивают)
1) **Не проверяют status code** → считают 500 “успехом”.
2) **Смешивают retry и cancellation** → ретраят отменённые запросы или зацикливаются.
3) **Создают новую сессию на каждый запрос** → нет keep-alive, выше latency/энергия.
4) **Не ограничивают параллелизм** → лавина запросов, DDOS своего backend, рост памяти.
5) **Нет единых интерсепторов**:
   - токены/headers/логирование/ретраи размазаны по коду.
6) **Не различают error types**:
   - `URLError.timedOut` ≠ `notConnectedToInternet` ≠ `cancelled`.
7) **Логируют секреты** (Authorization header, tokens).

## 8) Как отвечать на собесе
“`URLSession` — это контекст с конфигурацией и пулом соединений. Мы создаём `URLRequest`, запускаем `URLSessionTask` (data/upload/download), получаем `HTTPURLResponse` и data. Важно проверять status code отдельно от transport error, грамотно настраивать конфигурацию (timeouts, cache), понимать разницу completion vs delegate, и избегать типовых ошибок: новая сессия на каждый запрос, отсутствие лимитов параллелизма, неправильные ретраи/кэнсел, и утечки через делегаты/closures.”

**Самопроверка**
- Оспорено: “error == nil значит успех” — HTTP status может быть ошибкой.
- Неочевидно: `waitsForConnectivity` и параллелизм могут влиять на UX (подвисания/лавины).
- Источники, которые стоит освежить: Apple URLSession docs (конфигурации/таймауты), особенности background sessions, URLError коды и правильная классификация ошибок.



### Q241 (🟢): В чём разница между `Cache-Control`, `ETag` и `Last-Modified` (в общих чертах)?

**Кратко**
- `Cache-Control` — правила кэширования (можно ли кэшировать, как долго, кому, можно ли использовать “устаревшее”).
- `ETag` — “версия” ресурса (идентификатор содержимого). Используется для **условных запросов**: `If-None-Match`.
- `Last-Modified` — время последнего изменения на сервере. Условный запрос: `If-Modified-Since`.
- В идеале:
  - `Cache-Control` задаёт TTL и политику,
  - `ETag/Last-Modified` позволяют валидировать кэш без скачивания тела (304 Not Modified).

**Развёрнуто**
## 1) Что именно решают эти механизмы
Есть 2 большие задачи:
1) **Freshness**: можно ли использовать кэш без сети?
2) **Validation**: если кэш есть, изменился ли ресурс на сервере?

`Cache-Control` больше про (1), `ETag/Last-Modified` про (2), но в реальности они часто работают вместе.

## 2) `Cache-Control`: политика и срок
Примеры директив:
- `max-age=60` → можно использовать кэш 60 секунд.
- `no-cache` → кэшировать можно, но перед использованием нужно **провалидировать** (условный запрос).
- `no-store` → не сохранять вообще (обычно для секретов/персональных данных).
- `private`/`public` → кто может кэшировать (браузер/прокси).
- `stale-while-revalidate` → можно отдать слегка устаревшее, пока обновляем в фоне (очень полезно для UX, если поддержано).

Типовая ошибка:
- путать `no-cache` и `no-store`.
`no-cache` ≠ “не кэшировать”. Это “не использовать без валидации”.

## 3) `ETag`: валидатор по содержимому
Сервер отдаёт `ETag: "abc123"`.
Клиент кэширует ответ и при следующем запросе отправляет:
- `If-None-Match: "abc123"`

Если ресурс не изменился:
- сервер отвечает `304 Not Modified` без тела,
- клиент использует локальный кэш.

Плюсы:
- точнее, чем время,
- хорошо работает при частых проверках.

Минусы/ловушки:
- ETag может быть слабым (`W/` weak ETag) — семантика зависит от сервера.
- если сервер неправильно реализовал ETag, кэширование будет странным.

## 4) `Last-Modified`: валидатор по времени
Сервер отдаёт:
- `Last-Modified: Tue, 01 Jan 2026 10:00:00 GMT`

Клиент отправляет:
- `If-Modified-Since: ...`

Если не изменилось:
- `304 Not Modified`.

Плюсы:
- просто, часто есть “по умолчанию”.

Минусы:
- точность времени,
- часы/округления,
- ресурс может измениться без изменения `Last-Modified` (ошибки на сервере),
- несколько изменений внутри одной секунды — потенциальные коллизии.

## 5) Как это сочетается в реальном дизайне кэша
- Для “списков/контента” часто:
  - короткий `max-age` + `ETag` для быстрой валидации.
- Для “секретного/персонального”:
  - `Cache-Control: no-store` (или вы на клиенте отключаете кэширование).
- Для UX:
  - `stale-while-revalidate` (или его клиентский аналог) даёт “быстро показать старое и обновить”.

## 6) Как отвечать на собесе
“`Cache-Control` задаёт правила кэширования и TTL. `ETag` и `Last-Modified` — валидаторы: клиент делает условный запрос через `If-None-Match` или `If-Modified-Since` и может получить `304`, не скачивая тело. `ETag` обычно точнее, `Last-Modified` проще, но менее надёжен.”

**Самопроверка**
- Оспорено: “no-cache = не кэшировать” — на самом деле требует валидации перед использованием.
- Неочевидно: кэширование — это договор клиента и сервера; без правильных заголовков сервером клиентский кэш часто будет “магически” работать плохо.
- Источники, которые стоит освежить: HTTP caching semantics (RFC 9111), документацию вашего backend/CDN по ETag/Cache-Control, поведение URLCache/NSURLRequest cache policies.


### Q242 (🟢): Что такое idempotency и почему она важна для повторов запросов?

**Кратко**
- **Idempotency**: повтор одного и того же запроса приводит к **тому же эффекту**, что и один запрос.
- Важно, потому что:
  - ретраи из-за таймаута/плохой сети могут отправить запрос повторно,
  - без идемпотентности можно получить двойные операции (двойной платеж, двойное списание, двойное создание).
- Решение: либо использовать идемпотентные методы (GET/PUT/DELETE по семантике), либо **идемпотентные ключи** для POST/мутаций.

**Развёрнуто**
## 1) Семантика: “одинаковый результат” vs “одинаковый эффект”
Важно различать:
- **idempotent**: эффект на сервере после N повторов тот же, что после 1.
- **safe**: не изменяет состояние (обычно GET/HEAD).

GET обычно safe и idempotent.
PUT/DELETE — обычно idempotent по смыслу (если корректно спроектированы).
POST — чаще всего **не idempotent** (создаёт новый ресурс, списывает деньги и т.д.).

## 2) Почему это критично именно для mobile
Мобильная сеть:
- нестабильна,
- запрос может таймаутиться,
- клиент может не знать, “дошёл ли запрос до сервера”.

Классический сценарий:
- клиент отправил POST “создать заказ”,
- связь оборвалась после того, как сервер уже создал заказ,
- клиент ретраит → заказ создаётся второй раз.

## 3) Как решают: idempotency keys
Для операций, где “повтор недопустим”:
- клиент генерирует `Idempotency-Key` (UUID),
- отправляет его вместе с запросом,
- сервер хранит соответствие:
  - key → результат операции (или факт выполнения),
- повтор с тем же key возвращает тот же результат, не выполняя операцию заново.

Это особенно важно для:
- платежей,
- создания заказов,
- любых мутаций, где дубль опасен.

## 4) Где тут ловушки (senior-уровень)
### A) Что считать “одинаковым запросом”
Идемпотентность обычно привязана к:
- endpoint,
- пользователю/сессии,
- полезной нагрузке.

Если key тот же, но body другой:
- сервер должен отклонять как ошибку (иначе можно “переписать” смысл).

### B) Время жизни ключа
Нужно TTL:
- держать ключи бесконечно дорого,
- но слишком маленький TTL может привести к повторным операциям позже.

### C) Ретраи не всегда безопасны
Даже при idempotency:
- ретраить нужно только на “retryable” ошибки (timeout, 502/503/504),
- и с backoff/jitter, чтобы не создать лавину.

## 5) Связь с UX
Идемпотентность позволяет:
- смело повторять запросы и восстанавливать операции,
- делать “at-least-once delivery” без двойного эффекта,
- строить оффлайн очереди (outbox).

## 6) Как отвечать на собесе
“Idempotency означает, что повтор запроса не меняет итоговый эффект. Это критично для ретраев на мобильной сети: без идемпотентности можно сделать двойные мутации. GET/PUT/DELETE обычно идемпотентны по семантике, а для POST используют idempotency key: один и тот же ключ гарантирует, что операция выполнится максимум один раз, а повтор вернёт тот же результат.”

**Самопроверка**
- Оспорено: “ретраить можно всё” — ретраи опасны для неидемпотентных мутаций без ключей.
- Неочевидно: идемпотентность — совместная ответственность клиента и сервера; клиентский key без серверной логики не решает ничего.
- Источники, которые стоит освежить: практики idempotency keys (payments), классификация retryable ошибок, дизайн PUT/POST/DELETE семантики в REST/GraphQL.



### Q243 (🟢): Что такое timeout’ы в networking (request/resource) и как их правильно выставлять?

**Кратко**
- В `URLSession` есть два основных таймаута:
  - `timeoutIntervalForRequest`: таймаут **на ожидание ответа/прогресса** для конкретного запроса (idle timeout).
  - `timeoutIntervalForResource`: таймаут **на весь ресурс целиком** (общий дедлайн на завершение, включая редиректы/повторы).
- Правильно выставлять:
  - request timeout — короткий, чтобы не “висеть” при проблемах,
  - resource timeout — длиннее, чтобы дать загрузкам завершиться,
  - отдельно настраивать для разных классов запросов (API vs upload/download).
- Важно не путать:
  - таймауты не равны “максимальное время сервера на обработку” — это клиентская политика.

**Развёрнуто**
## 1) Почему таймауты вообще нужны
Без таймаутов:
- запросы могут “зависать” при плохой сети,
- вы держите ресурсы (соединения, память),
- UX превращается в вечный спиннер.

Таймаут — это контролируемый дедлайн:
- после которого вы можете ретраить/показать ошибку/деградировать.

## 2) `timeoutIntervalForRequest`: idle timeout
Интуиция:
- “сколько мы готовы ждать, если нет прогресса”.

Это про:
- установление соединения,
- ожидание первого байта,
- паузы в передаче.

Если сеть “умирает”, этот таймаут сработает.

Типовая ловушка:
- “у меня большой download, ставлю request timeout 5 секунд” → он будет отваливаться при кратковременных паузах.

## 3) `timeoutIntervalForResource`: общий дедлайн
Интуиция:
- “сколько максимум готов тратить времени на ресурс целиком”.

Учитывает:
- редиректы,
- повторные попытки на уровне транспорта,
- длительные передачи.

Для больших ресурсов:
- resource timeout обычно значительно выше.

## 4) Как выставлять “правильно” (без магии, но с логикой)
Нельзя выбрать универсальное число для всего приложения.
Нужно делить по классам:

### A) Интерактивные API (кнопка → запрос)
- request timeout: относительно небольшой (чтобы UX не висел),
- resource timeout: умеренный.
И дополнительно:
- если request не критичен, лучше отменить и показать “try again”.

### B) Фоновые синки/предзагрузки
- можно позволить более длинные таймауты,
- но обязательно иметь circuit breaker/лимиты ретраев, чтобы не “пилить” батарею.

### C) Upload/Download файлов
- request timeout должен учитывать возможные паузы сети,
- resource timeout — достаточно большой, особенно в фоне.

## 5) Связь с ретраями и backoff
Важно:
- таймаут + ретраи без ограничений = бесконечная попытка.
Поэтому нужно:
- лимиты попыток,
- backoff/jitter,
- различать ошибки:
  - `timedOut` → retryable,
  - `cancelled` → не ретраить,
  - 4xx → обычно не ретраить.

## 6) Частые ошибки на собесе
1) “ставим таймаут 60 секунд всем запросам” → плохой UX.
2) “ставим таймаут 5 секунд всем запросам” → сломаете загрузки на мобильной сети.
3) “таймауты = защита от медленного бекенда” → частично, но сервер может отработать, а клиент уже отменил; нужна согласованная политика.
4) забывают про `waitsForConnectivity` → запрос может ждать сеть и таймауты/UX будут выглядеть иначе.

## 7) Как отвечать на собесе
“В `URLSession` есть request timeout (idle) и resource timeout (общий дедлайн). Я выставляю их по типам запросов: интерактивные — короче, фоновые и файловые — длиннее. Таймауты всегда идут вместе с политикой ретраев: ограничение попыток, backoff/jitter и классификация retryable ошибок, чтобы не получить бесконечные повторы и плохой UX.”

**Самопроверка**
- Оспорено: “один таймаут на всё” — разные типы запросов требуют разных дедлайнов.
- Неочевидно: таймауты должны сочетаться с retry policy, иначе вы просто “циклически таймаутитесь”.
- Источники, которые стоит освежить: `URLSessionConfiguration` timeouts, поведение при `waitsForConnectivity`, классификация `URLError` и best practices retry/backoff.



### Q244 (🟢): Чем отличается кэш в памяти от кэша на диске и когда что использовать?

**Кратко**
- **Memory cache**:
  - очень быстрый,
  - живёт пока процесс жив,
  - может быть сброшен системой при memory pressure.
- **Disk cache**:
  - медленнее,
  - переживает перезапуск приложения,
  - требует TTL/очистки и учёта места.
- Практика:
  - memory — для горячих данных (изображения, результаты списков, computed),
  - disk — для “дорого достать/часто нужно” и offline (кэш ответов, медиа, справочники),
  - лучше иметь layered cache: memory → disk → network.

**Развёрнуто**
## 1) Память (memory cache)
### Плюсы
- скорость (наносекунды/микросекунды),
- удобно для “горячих” данных,
- легко реализовать `NSCache`/Dictionary (с синхронизацией).

### Минусы
- не переживает перезапуск,
- ограничена объёмом RAM,
- может быть очищена системой:
  - memory pressure,
  - app goes to background и система чистит.

### Когда использовать
- изображения/preview,
- результаты, которые часто читаются в рамках сессии,
- “computed” данные (например, layout calculations, форматирование),
- дедуп запросов и in-flight операции.

## 2) Диск (disk cache)
### Плюсы
- сохраняется между запусками,
- подходит для offline и больших данных,
- можно хранить “дорого добываемые” результаты.

### Минусы
- latency выше (I/O),
- нужен формат хранения и миграции (если меняется структура),
- нужно управлять:
  - TTL,
  - максимальным размером,
  - политикой eviction,
  - очисткой на фоне.

### Когда использовать
- кэш HTTP ответов (через URLCache или свой),
- изображения/видео превью,
- справочники/конфиги/feature flags snapshot,
- offline-first хранение (часто уже ближе к локальной БД, но принцип тот же).

## 3) Layered cache: правильная “сеньорская” модель
Классическая цепочка:
1) **memory**: быстрый hit.
2) **disk**: если нет в memory.
3) **network**: если нет или устарело.

Ключевой момент:
- memory обычно наполняется из disk (read-through),
- disk обновляется из network (write-through).

## 4) Связь с TTL и invalidation (главная боль кэширования)
Кэш без политики устаревания = баги:
- пользователь видит старые данные,
- конфликт между списком и деталями,
- “почему после апдейта ничего не меняется”.

Нужно заранее определить:
- TTL (сколько можно показывать старое),
- условия invalidation:
  - после мутаций,
  - при смене аккаунта,
  - при смене региона/локали,
  - при app update,
  - при server-driven versioning.

## 5) Eviction: как “выкидывать”
### Memory
- `NSCache` сам умеет:
  - эвикшн по памяти,
  - необязательные лимиты count/cost.
Если Dictionary:
- вы обязаны сами придумать LRU/лимиты.

### Disk
- обычно:
  - max size + LRU,
  - TTL cleanup,
  - при необходимости: “pin” важных данных.

## 6) Частые ошибки на собесе/в жизни
1) “Диск — это как память, только медленнее” → нет, это другой жизненный цикл, нужны TTL/очистка.
2) “Кэш = правда” → кэш всегда может быть устаревшим; нужен источник истины и стратегия.
3) “Сохраним всё на диске” → вы получите бесконечный рост и проблемы с миграциями/корраптом.
4) “Память никогда не чистится” → система может выгрузить кэш в любой момент.

## 7) Как отвечать на собесе
“Memory cache быстрый, но живёт только в рамках процесса и может быть очищен системой; подходит для горячих данных. Disk cache медленнее, но переживает перезапуск и годится для offline/больших данных, требует TTL и политики очистки. Обычно делаю layered cache: memory → disk → network и заранее определяю invalidation/eviction.”

**Самопроверка**
- Оспорено: “кэш всегда надёжен” — кэш по определению может быть устаревшим и сбрасываться.
- Неочевидно: самая сложная часть — invalidation и согласованность нескольких кэшей.
- Источники, которые стоит освежить: URLCache/HTTP caching, `NSCache` поведение при memory pressure, практики LRU/TTL для disk cache и offline-first подходов.



### Q245 (🟠): Как спроектировать networking слой (client + endpoint/router + interceptors), чтобы его было легко тестировать и расширять?

**Кратко**
- Разделить обязанности:
  - **Transport** (`URLSession`/mock) — отправка запроса,
  - **Endpoint/Router** — сборка `URLRequest`,
  - **Client** — выполнение и decoding,
  - **Interceptors/Middleware** — cross-cutting (auth, retry, logging, cache).
- Всё за протоколами:
  - `HTTPClient`, `RequestBuilder`, `Interceptor`.
- Тестируемость:
  - подмена transport на stub,
  - тесты сборки `URLRequest`,
  - тесты decoding и маппинга ошибок,
  - детерминированные ретраи через “виртуальные часы”/инъекцию scheduler.

**Развёрнуто**
## 1) Проблема “URLSession везде”
Если UI/VM напрямую создаёт `URLRequest` и дергает `URLSession`:
- логика размазывается,
- auth headers/ретраи/логирование дублируются,
- тесты превращаются в интеграционные.

Сеньор подход — слой и контракты.

## 2) Минимальная модульная модель слоя
### A) Endpoint (описание запроса)
Содержит:
- path,
- method,
- query,
- headers (без auth),
- body,
- decoding strategy.

Важный принцип:
- Endpoint — это “данные”, а не “выполнение”.

### B) RequestBuilder / Router
Отвечает за:
- baseURL,
- кодирование query/body,
- добавление общих headers (Accept-Language, User-Agent),
- создание `URLRequest`.

Тестируемость:
- unit test “из endpoint получился правильный URLRequest”.

### C) Transport
Интерфейс:
- “выполни URLRequest и верни (data, response)”.

Реализации:
- `URLSessionTransport`,
- `MockTransport` для тестов,
- `ReplayTransport` для record/replay (полезно при flaky).

### D) HTTPClient
Отвечает за:
- выполнение,
- decoding,
- маппинг ошибок.

Ключ:
- клиент не должен знать про UI, только про доменные ошибки/DTO.

## 3) Interceptors / middleware
Это “обёртки” вокруг выполнения, которые добавляют политику:
- Auth (add token, handle 401),
- Retry policy,
- Logging (redaction),
- Metrics,
- Cache (read-through / validation),
- Request dedup (single-flight),
- Rate limiting.

Важно:
- интерсепторы должны быть компонуемыми и независимыми:
  - цепочка ответственности.

## 4) Ошибки: единая модель
Нужно унифицировать:
- transport errors (URLError),
- HTTP errors (status codes),
- decoding errors,
- domain errors (например, “invalid refresh token”).

Тогда верхние слои не будут парсить “всё подряд”.

## 5) Тестируемость: что и как тестировать
### A) Request building tests
- endpoint → URLRequest:
  - URL + query,
  - headers,
  - method,
  - body encoding.

### B) Client decoding tests
- given JSON → DTO/Domain,
- edge cases и missing fields.

### C) Error mapping tests
- 401 → `.unauthorized`,
- 409 → `.conflict`,
- timeouts → `.network(.timeout)`.

### D) Interceptor tests
- Auth interceptor добавил header,
- Retry interceptor делает backoff по “retryable” ошибкам,
- Cache interceptor отдаёт cached и потом обновляет.

Ключ:
- для ретраев нужна инъекция clock/scheduler, чтобы тесты были быстрыми.

## 6) Расширяемость (что меняется без боли)
Если дизайн нормальный:
- смена транспорта (REST → GraphQL/WebSocket) не трогает UI:
  - вы меняете transport/client за интерфейсом,
- добавили pinning/metrics — добавили interceptor,
- поменяли авторизацию — поменяли auth interceptor/session store.

## 7) Как отвечать на собесе
“Я выделяю endpoint как описание, builder/router как сборку `URLRequest`, transport как слой отправки (URLSession или mock), client как выполнение+decoding+error mapping. Cross-cutting вещи делаю интерсепторами (auth/retry/logging/cache/dedup). Всё за протоколами, поэтому запросы и интерсепторы легко тестировать отдельно.”

**Самопроверка**
- Оспорено: “достаточно одного NetworkManager со всем внутри” — это убивает тестируемость и расширяемость.
- Неочевидно: retry/cache/auth/dedup — это политики, их лучше композиционно навешивать, а не зашивать в client.
- Источники, которые стоит освежить: Apple URLSession patterns (delegate/interceptor идеи), примеры middleware chain, best practices error mapping и dependency inversion для networking.



### Q246 (🟠): Как реализовать retry с backoff/jitter и когда ретраи вредны?

**Кратко**
- Retry нужен только для **retryable** ошибок: временные сетевые сбои и 5xx (особенно 502/503/504), иногда 429.
- Нужны:
  - лимит попыток,
  - **exponential backoff**,
  - **jitter** (случайная “дрожь”), чтобы не синхронизировать клиентов,
  - уважение `Retry-After` (если сервер прислал).
- Ретраи вредны:
  - для неидемпотентных мутаций без idempotency key,
  - при 4xx (кроме 401/403 в контексте refresh flow, и 429),
  - при постоянной деградации сервера (нужен circuit breaker),
  - если вы ретраите сразу всем и без jitter → эффект “thundering herd”.

**Развёрнуто**
## 1) Главный принцип: retry policy — часть resiliency, а не “магический fix”
Retry улучшает успешность при transient сбоях,
но ухудшает ситуацию при перегрузке:
- увеличивает нагрузку,
- делает latency хуже,
- может усилить outage.

Поэтому retry всегда должен быть ограниченным и “вежливым”.

## 2) Что считать retryable
### Обычно retryable:
- `URLError.notConnectedToInternet` (иногда лучше ждать connectivity, а не ретраить),
- `URLError.networkConnectionLost`,
- `URLError.timedOut`,
- `URLError.cannotFindHost` / `cannotConnectToHost` (иногда),
- HTTP 502/503/504,
- HTTP 429 (если есть backoff и `Retry-After`).

### Обычно НЕ retryable:
- HTTP 400/401/403/404 (кроме особых флоу),
- HTTP 409 (конфликт) — нужен бизнес-мердж,
- HTTP 422 (валидация),
- decoding ошибки (это баг или контракт),
- cancellation (никогда не ретраить).

## 3) Exponential backoff
Базовая идея:
- задержка растёт экспоненциально: 0.5s → 1s → 2s → 4s…

Зачем:
- снизить давление на сеть/сервер,
- дать системе “выдохнуть”.

Но без jitter это плохо работает в масштабе.

## 4) Jitter: почему обязателен
Без jitter миллионы клиентов:
- падают одновременно,
- ретраят одновременно,
- снова падают → “волны”.

Jitter делает задержку случайной в рамках диапазона.
Подходы:
- full jitter: `sleep = random(0, base * 2^attempt)`
- equal jitter: `sleep = base * 2^(n-1) + random(0, base * 2^(n-1))`

Смысл:
- “размазать” ретраи по времени.

## 5) Лимиты: attempts, maxDelay, deadline
Нужны:
- `maxAttempts` (например 3–5),
- `maxDelay` (не бесконечно),
- общий deadline (resource timeout или отдельный).

Иначе:
- вы получаете вечные попытки и плохой UX.

## 6) Retry-After и 429
Если сервер прислал `Retry-After`:
- это сильнее вашей политики.
Игнорировать — значит усугублять rate limit и получать бан.

## 7) Retry и idempotency
Критично:
- ретраи мутаций допустимы только если:
  - операция идемпотентна (PUT/DELETE),
  - либо есть idempotency key (для POST),
  - иначе вы рискуете двойным эффектом.

## 8) Когда ретраи вредны (и что делать вместо)
### A) Сервер реально лежит/перегружен
Retry только усилит падение.
Нужно:
- circuit breaker (на клиенте можно адаптировать),
- деградация UX (показать cached/stale),
- приоритетность запросов (QoS).

### B) Ошибка логическая/валидационная
Retry бессмысленен:
- нужно исправлять данные или код.

### C) Слабая сеть и пользовательский интент
Если пользователь нажал “отмена”:
- отменить и не ретраить.
Иначе вы делаете “призрачные” операции.

## 9) Как отвечать на собесе
“Retry я делаю только для transient ошибок и 5xx/429. Политика: ограниченное число попыток, exponential backoff + jitter, уважение Retry-After. Ретраи опасны для неидемпотентных операций без idempotency keys и при 4xx/логических ошибках. При длительной деградации сервера лучше применять circuit breaker и деградацию на кэш.”

**Самопроверка**
- Оспорено: “добавим retry и всё станет стабильнее” — retry может усилить outage.
- Неочевидно: jitter — не косметика, а обязательный элемент, иначе клиенты синхронизируются.
- Источники, которые стоит освежить: паттерны backoff/jitter (AWS/GCP guidelines), классификация retryable ошибок, связь 429/Retry-After, design patterns circuit breaker.



### Q247 (🟠): Как сделать dedup/коалесинг одинаковых запросов (single-flight), чтобы не DDOS’ить свой backend?

**Кратко**
- **Dedup / single-flight**: если одновременно запрашивают один и тот же ресурс, выполняем **один** сетевой запрос, а результат раздаём всем подписчикам.
- Нужны:
  - ключ запроса (request key),
  - хранилище in-flight запросов,
  - корректная очистка при успехе/ошибке/отмене,
  - политика: какие запросы объединяем (обычно GET), а какие нельзя (мутации).
- Риски: неправильный ключ, гонки, смешивание разных auth/локалей, удержания памяти.

**Развёрнуто**
## 1) Зачем single-flight
Типичный кейс:
- на экране несколько компонентов просит `GET /profile`,
- при открытии и при pull-to-refresh,
- параллельно.

Без dedup:
- лавина одинаковых запросов,
- лишний расход сети/энергии,
- нагрузка на backend,
- “дергание” UI разными ответами.

Single-flight:
- один запрос, много потребителей.

## 2) Как выбрать ключ запроса
Это критично.
Ключ должен включать всё, что влияет на ответ:
- method + URL + query,
- нормализованные headers, которые меняют контент:
  - Authorization (или user/session),
  - Accept-Language/locale,
  - feature flags/AB (если они меняют контент),
  - любые cache-busting параметры.

Типовая ошибка:
- ключ только по URL → смешали ответы разных пользователей.

Практика:
- `RequestKey(method, url, query, userScope, localeScope, variantScope)`.

## 3) Структура реализации (концептуально)
Компоненты:
- `InFlightStore: [RequestKey: InFlightEntry]`
- `InFlightEntry` содержит:
  - task/publisher/continuation,
  - список ожидателей (callbacks/continuations),
  - счетчик/подписки для cancellation.

Алгоритм:
1) При запросе вычислить key.
2) Если entry есть → подписаться на результат.
3) Если нет → создать entry, запустить реальный запрос.
4) На completion:
   - всем ожидателям раздать result,
   - удалить entry.

Важно:
- удалять entry в `defer`, чтобы гарантировать очистку и при ошибке/отмене.

## 4) Cancellation: сложный момент
Вопрос:
- если один из потребителей отменил, отменяем ли запрос?

Обычно:
- отменяем запрос только если **все** потребители отменили,
- иначе продолжаем и раздаём остальным.

Для async/await:
- можно поддерживать ref-count:
  - каждый подписчик увеличивает count,
  - при cancel — уменьшает,
  - когда count == 0 → cancel task.

Типовая ошибка:
- отменили запрос из-за одного потребителя и “сломали” остальных.

## 5) Что можно и нельзя коалесить
### Можно
- GET запросы, которые читают состояние,
- “статичные” данные (справочники),
- конфиги.

### Осторожно/нельзя
- POST/PUT мутации:
  - разные body даже при одном URL,
  - разные side-effects,
  - нужна идемпотентность и отдельная логика.

Исключение:
- если мутация идемпотентна и ключ включает body/idempotency-key,
- но это уже “advanced” и требует строгих гарантий.

## 6) Взаимодействие с кэшем
Dedup хорошо комбинируется:
- сначала memory/disk cache hit,
- если miss → single-flight network,
- когда network вернул — обновить кэш.

Это снижает количество in-flight запросов и ускоряет UI.

## 7) Наблюдаемость
Полезно метрики:
- hit rate dedup (сколько запросов было объединено),
- среднее число подписчиков на один in-flight,
- ошибки.

Это помогает не гадать, а понимать пользу.

## 8) Как отвечать на собесе
“Я делаю single-flight для read-запросов: вычисляю ключ, учитывающий URL+query+контекст пользователя/локали, храню in-flight запрос в словаре и раздаю результат всем ожидающим. На completion очищаю запись. Для cancellation — ref-count: отменяю запрос только если отменились все потребители. Мутации обычно не коалесю без явной идемпотентности.”

**Самопроверка**
- Оспорено: “dedup = просто Dictionary по URL” — без учёта auth/контекста это смешивание данных и баги.
- Неочевидно: cancellation и ref-count — главный источник тонких багов.
- Источники, которые стоит освежить: single-flight паттерн (Go), реализации в async/await (Task sharing), Rx/Combine sharing (share/replay), и практики ключевания кэша/запросов.



### Q248 (🟠): Как организовать кэширование на клиенте: stale-while-revalidate, cache invalidation, ключи, TTL — стратегия?

**Кратко**
- Стратегия кэша = ответы на 4 вопроса:
  1) что кэшируем (какие endpoints/модели),
  2) где (memory/disk/URLCache/DB),
  3) как долго (TTL + условия invalidation),
  4) как обновляем (stale-while-revalidate, validation через ETag).
- **stale-while-revalidate**: быстро показываем кэш, параллельно обновляем в фоне, потом мягко обновляем UI.
- Самое сложное — **invalidation**: после мутаций, смены аккаунта, смены версии схемы, смены языка/региона.

**Развёрнуто**
## 1) “Кэширование” — это политика, а не storage
Можно иметь кэш-хранилище, но без политики это:
- рандомные баги,
- несогласованные данные,
- “почему не обновилось”.

Поэтому начинаем с правил.

## 2) Что кэшировать: выбираем кандидатов
Хорошие кандидаты:
- read-heavy endpoints (списки, каталоги),
- “дорого” по latency,
- данные, которые можно показывать слегка устаревшими.

Плохие кандидаты:
- персональные/секретные данные без явной пользы,
- быстро меняющиеся данные без валидации,
- мутации (POST/PUT) — это не про кэш, а про outbox/идемпотентность.

## 3) Ключи кэша: что считается “тем же самым”
Нужен `CacheKey`:
- endpoint + canonical query + (auth scope/tenant/account) + (locale/region, если влияет) + версионирование схемы.
Важно:
- нормализация query (сортировка),
- разделение по аккаунтам (кэш не должен протекать между пользователями).

## 4) TTL и freshness
У каждого типа данных:
- свой TTL.
Нельзя делать один TTL на всё:
- “профиль” может быть почти всегда свежий,
- “список рекомендаций” меняется чаще,
- “справочник стран” — редко.

Подходы:
- server-driven: Cache-Control, max-age.
- client-driven: TTL по типам данных (если сервер не помогает).

## 5) Invalidation: когда кэш нужно выбросить
Инвалидация по событиям:
- **после мутаций**:
  - обновили профиль → инвалидиируем `/me`, связанные списки,
  - удалили объект → обновляем соответствующие списки.
- **смена аккаунта/логаут**:
  - чистим персональные кэши.
- **смена локали/региона**:
  - если контент локализован.
- **обновление приложения/схемы**:
  - bump cache namespace/version.
- **по сигналу сервера** (если есть):
  - version hash, “config version”.

Ловушка:
- инвалидация “вручную и точечно” без системы → вы неизбежно забудете кейсы.
Нужно централизованное место, где описаны зависимости.

## 6) stale-while-revalidate (SWR): лучший UX паттерн
Алгоритм:
1) читаем кэш (memory/disk),
2) сразу возвращаем в UI (даже если stale),
3) параллельно делаем сетевой запрос,
4) если новые данные отличаются:
   - обновляем кэш,
   - эмитим обновление в UI.

Почему это работает:
- мгновенный контент,
- стабильный UI,
- сеть “догоняет”.

Где осторожно:
- если stale данные могут ввести в заблуждение (цены, баланс) → лучше строгая freshness/валидация.

## 7) Validation: ETag/Last-Modified
Чтобы не скачивать тело:
- хранить ETag,
- делать `If-None-Match`,
- получать 304 и подтверждать кэш.

Это снижает трафик и ускоряет обновление.

## 8) Консистентность: memory/disk/network
Нужны инварианты:
- memory всегда производный от disk (или наоборот, но единообразно),
- запись в кэш атомарна,
- обновление одного ключа не ломает другие.

Если у вас есть Single Source of Truth (например, DB/store):
- кэш можно делать вокруг него, а UI подписывать на store.

## 9) Как отвечать на собесе
“Я начинаю с политики: что кэшируем, где и на сколько. Для UX часто использую stale-while-revalidate: показываю кэш сразу и обновляю в фоне с мягким апдейтом UI. Ключи нормализую и разделяю по аккаунтам/локали. TTL и invalidation — самая важная часть: после мутаций, смены аккаунта, смены версии схемы. Если сервер поддерживает, использую ETag/304 для валидации.”

**Самопроверка**
- Оспорено: “кэширование — это просто URLCache” — без политики TTL/invalidation будут баги и несогласованность.
- Неочевидно: SWR улучшает UX, но может быть опасен для критичных данных (баланс/цены).
- Источники, которые стоит освежить: HTTP caching (ETag, Cache-Control), практики SWR, подходы к cache invalidation и dependency mapping, URLCache и кастомные кэши.


### Q249 (🟠): Как правильно реализовать upload/download (включая background tasks), прогресс и восстановление после падения?

**Кратко**
- Для больших файлов и надежности:
  - upload: `uploadTask(with:fromFile:)` (или stream), download: `downloadTask`,
  - background: `URLSessionConfiguration.background` + delegate,
  - прогресс: `URLSessionTaskDelegate`/KVO на `Progress`,
  - восстановление: resume data для download (частично) + свой persist состояния.
- Важно:
  - ограничить параллелизм,
  - учитывать энергопотребление и `allowsConstrained/Expensive`,
  - корректно обрабатывать cancel/pause/resume,
  - иметь серверную поддержку идемпотентности/чанков, если нужно “реально” возобновляемые upload.

**Развёрнуто**
## 1) DataTask vs Upload/Download task
### Upload
- `uploadTask` лучше, чем `dataTask` с body, потому что:
  - умеет работать с файлами,
  - поддерживает прогресс,
  - лучше подходит для фонового режима.

### Download
- `downloadTask` сохраняет в файл (временный URL), а не держит всё в памяти.

## 2) Background transfers: когда нужны и как мыслить
Background URLSession:
- позволяет системе продолжать передачу, когда приложение свернули/убили (в пределах возможностей iOS).

Ключевое:
- `URLSessionConfiguration.background(withIdentifier:)`
- делегатная модель:
  - `urlSession(_:downloadTask:didFinishDownloadingTo:)`
  - `urlSession(_:task:didCompleteWithError:)`
  - обработка `application(_:handleEventsForBackgroundURLSession:completionHandler:)`

Типовая ошибка:
- ожидать, что background session всегда завершит всё “любой ценой”.
iOS может:
- отложить,
- ограничить,
- отменить из-за условий.

## 3) Прогресс
### Download
- через делегат:
  - `didWriteData` даёт bytesWritten/totalBytesExpected
### Upload
- `urlSession(_:task:didSendBodyData:totalBytesSent:totalBytesExpectedToSend:)`

Также можно использовать `Progress`:
- но важно обновлять UI на main thread.

Ловушка:
- прогресс не всегда линейный (серверная обработка после upload и т.п.).

## 4) Восстановление после падения / перезапуска
### Download resume data
iOS может дать `resumeData` при cancel:
- `cancel(byProducingResumeData:)`
Потом:
- `downloadTask(withResumeData:)`

Ограничения:
- resume data не всегда валидна,
- зависит от сервера (range requests),
- может ломаться при смене URL/headers.

### Upload resume
Для upload “по-настоящему” resumable:
- нужна серверная поддержка:
  - chunked upload,
  - upload sessions,
  - range/offset,
  - idempotency keys.

Иначе вы сможете только “повторить с нуля”.

## 5) Persist состояния (без чего “resiliency” не получится)
Нужно хранить:
- идентификатор операции,
- путь к файлу,
- статус (queued/running/paused/completed),
- метаданные (endpoint, headers excluding secrets, checksum, size),
- для download: resumeData (если есть).

После перезапуска:
- восстановить очередь,
- попытаться продолжить,
- синхронизировать с сервером (если операция могла завершиться).

## 6) Очередь операций и лимиты
Нельзя запускать 20 upload одновременно:
- батарея,
- память,
- сеть,
- вероятность ошибок.

Нужны:
- лимит параллелизма,
- приоритеты,
- retry policy,
- network constraints:
  - Wi‑Fi only,
  - запрет на cellular, если надо,
  - учитывать Low Data Mode.

## 7) Безопасность и приватность
- не логировать пути/имена файлов с PII,
- временные файлы удалять,
- использовать Data Protection (если храните на диске),
- не держать access token в persisted metadata “как есть”:
  - лучше хранить ссылку на сессию и подставлять токен при старте.

## 8) Как отвечать на собесе
“Для больших transfer использую `uploadTask/fromFile` и `downloadTask`. Для фоновых — background `URLSession` с delegate и восстановлением через сохранённое состояние. Прогресс получаю через delegate callbacks. Download можно продолжать через resumeData (с оговорками), а для resumable upload обычно нужна серверная поддержка чанков/сессий. Обязательно ограничиваю параллелизм, учитываю сетевые ограничения и делаю корректную обработку cancel/pause/resume.”

**Самопроверка**
- Оспорено: “resume всегда работает” — resumeData нестабильна и зависит от сервера; нужен fallback.
- Неочевидно: resumable upload почти всегда требует протокола на сервере; клиент сам не “придумает” надёжное продолжение.
- Источники, которые стоит освежить: Apple docs по background URLSession, delegate callbacks, resumeData caveats, паттерны chunked/resumable upload.


### Q250 (🔴): Как построить resilient слой данных: circuit breaker, rate limiting, bulkheads — что можно адаптировать под iOS клиент?

**Кратко**
- Resiliency паттерны помогают не “добивать” систему, когда она деградирует.
- На iOS можно адаптировать:
  - **circuit breaker**: временно прекращать запросы к падающему сервису и быстро фейлить, а не ждать таймауты.
  - **rate limiting**: ограничивать частоту/параллелизм запросов (особенно фоновых) и уважать 429/Retry-After.
  - **bulkheads**: изолировать ресурсы — отдельные очереди/лимиты для разных типов трафика (UI критичный vs фон).
- Всё это должно работать вместе с кэшем/деградацией UX и observability.

**Развёрнуто**
## 1) Почему “просто retry” — недостаточно
Если сервер деградирует:
- ретраи увеличивают нагрузку,
- клиенты синхронизируются,
- latency растёт,
- батарея умирает.

Resiliency = “не усугубить” + “деградировать красиво”.

## 2) Circuit breaker на клиенте
### Идея
У сервиса есть состояния:
- **closed**: работаем нормально,
- **open**: быстро фейлим запросы (не ходим в сеть),
- **half-open**: периодически пробуем “тестовые” запросы, чтобы понять, восстановился ли сервер.

### Триггеры на iOS
- высокая доля 5xx,
- много timeouts,
- длительная latency выше порога,
- серия ошибок подряд.

### Что даёт
- мгновенная реакция вместо “висим по таймауту”,
- экономия батареи/трафика,
- защита backend от лавины.

### Как не сломать UX
Когда breaker открыт:
- отдавать stale cache (если можно),
- показывать понятную ошибку,
- не ретраить бесконечно, а дать “Try again”.

## 3) Rate limiting на клиенте
### Зачем
- чтобы не бомбить backend,
- чтобы не создавать конкуренцию за ресурсы (CPU/network) внутри приложения.

### Инструменты
- лимит параллелизма (например, “не больше N активных запросов”),
- токен-бакет (token bucket) на запросы в секунду,
- приоритеты запросов (UI vs background),
- уважение 429 и `Retry-After`.

Ловушка:
- rate limiting не заменяет дедуп (single-flight) — они дополняют друг друга.

## 4) Bulkheads: изоляция “отсеков”
### Идея
Разделить трафик и ресурсы:
- “критичный UI” (поиск, экран профиля),
- “фон” (prefetch, analytics, sync),
- “тяжёлые transfer” (upload/download).

Каждому отсеку:
- свой лимит параллелизма,
- своя retry policy,
- свой timeout budget.

Пример эффекта:
- фоновый sync не должен забивать очередь и ломать интерактивные запросы.

## 5) Как это выглядит архитектурно
Обычно это политика “вокруг” HTTP клиента:
- pipeline/interceptors:
  - rate limiter interceptor,
  - circuit breaker interceptor,
  - retry policy interceptor,
  - cache interceptor,
  - metrics interceptor.

Важно:
- политики должны быть конфигурируемыми (remote config/feature flags),
- но ключевые безопасные ограничения не должны быть “выключаемыми случайно”.

## 6) Деградация UX и fallback
Resiliency — это не только “не ходить в сеть”.
Это:
- показывать cached/stale данные,
- уметь работать в offline режиме,
- иметь screen states (loading/error/empty),
- избегать “спиннера навсегда”.

## 7) Как отвечать на собесе
“На клиенте я могу адаптировать circuit breaker, rate limiting и bulkheads как политики вокруг networking слоя. Circuit breaker быстро фейлит, когда сервис деградирует, вместо таймаутов и бесконечных ретраев. Rate limiting ограничивает параллелизм и уважает 429/Retry-After. Bulkheads разделяют очереди для UI-критичного трафика и фонового, чтобы они не мешали друг другу. Всё это работает вместе с кэшем и понятной деградацией UX.”

**Самопроверка**
- Оспорено: “достаточно retry” — при деградации retry усугубляет проблему.
- Неочевидно: bulkheads важны даже на клиенте: разные типы трафика конкурируют за сеть и CPU.
- Источники, которые стоит освежить: resiliency patterns (circuit breaker/bulkheads), практики 429/Retry-After, архитектура middleware/interceptors, подходы к QoS и лимитам параллелизма на iOS.



### Q251 (🔴): Как обеспечить consistency при нескольких источниках данных (memory cache / disk cache / network): инварианты и конфликт-стратегии?

**Кратко**
- Consistency между memory/disk/network достигается не “идеальной синхронизацией”, а **инвариантами**:
  - кто source of truth,
  - кто производный кэш,
  - где происходит запись,
  - как решаются гонки и порядок обновлений.
- Хорошие стратегии:
  - **Single Source of Truth** (SSOT) + подписки,
  - read-through/write-through layered cache,
  - versioning/ETag + атомарные апдейты,
  - дедуп обновлений и сериализация мутаций,
  - политика “last-write-wins” или доменный мердж.

**Развёрнуто**
## 1) Почему это сложно
При трёх источниках:
- UI читает memory,
- background обновляет disk,
- network приносит новые данные,
- параллельно пользователь делает мутацию.

Без инвариантов вы получите:
- “прыгающий” UI,
- устаревшие данные,
- запись старого поверх нового (race),
- несогласованные списки и детали.

## 2) Сначала выбрать “источник истины”
Варианты:
1) **DB/store как SSOT** (часто лучший для сложных приложений):
   - UI подписан на store,
   - network пишет в store,
   - кэши вокруг store.

2) **Disk как SSOT** (если нет DB, но есть файлы/кэш):
   - disk хранит последнее “правильное”,
   - memory — только ускоритель.

3) **Network как SSOT** (простые приложения):
   - но тогда offline/консистентность сложнее.

Сеньор мысль:
- если у вас сложные экраны/синк/оффлайн — делайте SSOT (DB или store).

## 3) Инварианты layered cache (простая, но строгая система)
Пример набора инвариантов:
- Memory кэш **всегда** производный от Disk/Store.
- Любая запись “новых данных” идёт **сначала** в Disk/Store, потом прогревает Memory.
- UI читает только Memory, но Memory может быть очищен в любой момент — значит, fallback на Disk обязателен.
- Обновления по одному ключу/объекту идут через одну “очередь” (сериализованы), чтобы не было гонок.

## 4) Версионирование данных
Чтобы не перезаписать новое старым:
- хранить “версию”:
  - `updatedAt`,
  - server revision,
  - ETag.

Правило:
- принимаем апдейт только если “новее”, либо делаем доменный мердж.

Ловушка:
- `Date()` на клиенте как версия — плохо для распределённых систем.

## 5) Конфликты: какие бывают и что делать
### A) Конфликт “сеть vs локальная мутация”
Например:
- пользователь изменил имя,
- в это время пришёл старый `/me`.

Стратегии:
- “локальная мутация побеждает” до подтверждения сервером (optimistic),
- или “сервер побеждает” и вы повторно применяете локальные изменения.

Выбор зависит от продукта.

### B) Конфликт “две сетевые загрузки”
Например:
- два запроса в разном порядке завершились.
Решение:
- single-flight,
- sequence number/epoch:
  - применяем только самый новый ответ.

### C) Конфликт “несогласованность списка и детали”
Например:
- список обновился, деталь нет.
Решения:
- единый store с нормализацией (entity store по id),
- списки хранят ids, детали по id, тогда обновления согласованы.

## 6) Сериализация мутаций и дедуп обновлений
Для мутаций:
- очередь outbox (в оффлайн случае),
- single-flight для refresh,
- actor/serial queue для состояния кэша.

Для обновлений:
- coalescing:
  - если пришло 10 апдейтов подряд — объединить и эмитить один.

## 7) Практический рецепт (простой, но рабочий)
- SSOT: store/DB.
- Network writes → store (transaction).
- Store changes → UI (diffable/observable).
- Memory cache: read-through (держит горячее).
- Disk cache/DB: TTL и invalidation.
- Concurrency: actor для “кэширующего слоя”.

## 8) Как отвечать на собесе
“Я решаю consistency через инварианты: выбираю SSOT (чаще DB/store), memory — производный кэш. Любые сетевые апдейты пишутся атомарно в SSOT и только потом прогревают memory. Конфликты решаю через versioning/ETag/sequence numbers и сериализацию обновлений (actor/очередь). Для списка+детали использую нормализацию по id, чтобы обновления были согласованными.”

**Самопроверка**
- Оспорено: “достаточно хранить кэш в двух местах” — без SSOT и инвариантов появятся гонки и несогласованность.
- Неочевидно: “порядок ответов” важнее, чем “порядок запросов”; нужен sequence/epoch или single-flight.
- Источники, которые стоит освежить: SSOT и нормализация entity store, подходы optimistic updates, паттерны concurrency (actors/serial queue), стратегии cache invalidation и versioning.



### Q252 (🔴): Как спроектировать offline-first outbox: очередь мутаций, идемпотентность, retries, дедупликация, порядок, конфликт-резолюция?

**Кратко**
- **Outbox** — локальная очередь изменений, которые нужно гарантированно доставить на сервер.
- Ключевые элементы:
  - персистентная очередь (DB),
  - идемпотентность (idempotency key / operation id),
  - сериализация или контролируемая параллельность,
  - retry policy (backoff+jitter, лимиты),
  - дедуп и коалесинг операций,
  - порядок и зависимости,
  - конфликт-резолюция (server wins / client wins / merge).
- “Offline-first” значит: UI работает от локального SSOT, а outbox синхронизирует с сервером.

**Развёрнуто**
## 1) Модель данных: что лежит в outbox
Запись “операция” обычно содержит:
- `operationId` (UUID) — идемпотентность,
- `type` (create/update/delete),
- `entityId`/scope,
- payload (минимальный diff),
- `createdAt`,
- `attemptCount`,
- `nextRetryAt`,
- зависимость (`dependsOnOperationId`) при необходимости,
- состояние (queued/inFlight/succeeded/failed/permanentFailed).

Важно:
- payload хранить аккуратно (без секретов),
- иметь версионирование схемы.

## 2) Идемпотентность — основа надёжности
Без неё:
- ретраи создадут дубли (двойные записи/платежи).

Поэтому:
- каждая операция имеет стабильный `operationId`,
- сервер должен принимать idempotency key и возвращать тот же результат на повтор.

Если сервер не поддерживает:
- вы не можете гарантировать exactly-once,
- максимум — best-effort + локальные дедуп механизмы, но это слабее.

## 3) Порядок и зависимости
Сценарии:
- create → потом update → потом delete,
- update одной сущности зависит от create другой.

Стратегии:
- per-entity сериализация:
  - для одного `entityId` операции идут строго по порядку,
- глобальная очередь с приоритетами и dependency graph,
- минимизация зависимостей через дизайн API (server-generated ids vs client-generated ids).

## 4) Дедуп и коалесинг
Пример:
- пользователь 10 раз подряд меняет имя.
Не надо отправлять 10 update.
Нужно:
- коалесить в один последний update (“last-write-wins” внутри outbox),
- либо батчить (если backend поддерживает).

Для delete:
- delete может “поглотить” предыдущие pending updates/creates.

## 5) Retry policy: когда и как повторять
- retry только на retryable ошибки:
  - timeouts,
  - 5xx,
  - 429 (с Retry-After),
  - сетевые потери.
- backoff+jitter,
- лимит попыток,
- dead-letter / permanentFailed после N попыток,
- circuit breaker при массовой деградации.

## 6) Конфликты: как решать
Конфликт — это когда локальное состояние расходится с сервером:
- два устройства изменили одно и то же,
- сервер отклонил update (409/412 precondition failed),
- локальная версия устарела.

Варианты:
1) **Server wins**:
   - принимаем сервер, локальное откатываем/показываем конфликт.
2) **Client wins**:
   - повторно применяем локальное изменение на свежей базе (опасно без мерджа).
3) **Merge**:
   - доменный мердж (например, объединить поля/список).

Ключ:
- конфликт-резолюция — часть домена, а не network слоя.

## 7) Архитектура offline-first: SSOT + sync engine
- UI читает из SSOT (DB/store) — это “правда” для пользователя.
- Мутации:
  1) применяются локально (optimistic) в транзакции,
  2) добавляют запись в outbox,
  3) sync engine отправляет и подтверждает.

Плюс:
- UX мгновенный.
Минус:
- нужно уметь откатывать/помечать “pending/failed”.

## 8) Состояния и UX
Каждая сущность может иметь:
- `syncState`: synced / pending / failed.
UI показывает:
- “отправляется…”,
- кнопку retry,
- конфликт.

Важно:
- не прятать ошибки бесконечными ретраями.

## 9) Наблюдаемость и отладка
Для сложных синков нужен:
- correlation IDs,
- лог операций (без PII),
- метрики (queue length, success rate, retry count),
- инструменты “force sync / clear queue” для поддержки.

## 10) Как отвечать на собесе
“Offline-first я строю через SSOT (локальная БД) и outbox. Мутации сначала фиксируются локально и добавляются в персистентную очередь с operationId/idempotency key. Sync engine отправляет их с ограниченной параллельностью, backoff+jitter и дедуп/коалесингом (особенно updates). Порядок обеспечивается per-entity, конфликты решаются доменной стратегией (server wins/client wins/merge) и отражаются в UI через syncState.”

**Самопроверка**
- Оспорено: “offline-first — это просто кэшировать GET” — без outbox мутации и надёжная доставка не решаются.
- Неочевидно: идемпотентность и конфликт-резолюция — обязательны, иначе получите дубли и “прыгающее” состояние.
- Источники, которые стоит освежить: outbox pattern, optimistic updates и conflict resolution, idempotency keys, background constraints iOS (BGTaskScheduler), стратегии дедуп/коалесинга операций.



### Q253 (🔴): Как сделать observability для networking: correlation IDs, распределённые трейсинг-идеи, метрики latency/error-rate, privacy redaction?

**Кратко**
- Observability = логи + метрики + трассировка, при этом **не нарушая приватность**.
- На клиенте нужно:
  - **correlation ID** (request id) и propagations в headers,
  - измерение latency по стадиям (dns/connect/ttfb/transfer),
  - error классификация (transport vs HTTP vs decoding vs domain),
  - метрики (success rate, p95 latency, retry count, queue length),
  - sampling + privacy redaction (не логировать токены/PII),
  - привязка к фичам/экрану (но без персональных данных).
- Должна быть возможность “собрать историю запроса” end-to-end.

**Развёрнуто**
## 1) Зачем это нужно (и что спрашивают на собесе)
Если нет observability:
- “иногда не работает” невозможно расследовать,
- вы не видите деградацию (рост p95 latency, рост 5xx),
- вы не понимаете эффект ретраев/кэша.

Senior ожидают:
- вы умеете измерять, а не угадывать.

## 2) Correlation IDs: основа трассировки
### Что это
- уникальный идентификатор запроса, который проходит:
  - клиент → backend → сервисы → логи.

### Как делать на клиенте
- генерировать `X-Request-ID` (UUID) на каждый запрос,
- или использовать формат traceparent (если backend поддерживает),
- прокидывать также:
  - “session id” (анонимный),
  - “feature id” (экран/фича) — без PII.

Важно:
- correlation ID должен быть доступен в ошибках/репортах (например, в Sentry breadcrumb), чтобы backend мог найти запрос.

## 3) Распределённая трассировка (идеи, даже если нет полноценного OpenTelemetry)
Если backend поддерживает:
- W3C Trace Context (`traceparent`, `tracestate`),
- OpenTelemetry.

На клиенте можно:
- создавать root span на запрос,
- добавлять атрибуты:
  - endpoint, method, status class, retry count,
  - cache hit/miss,
  - network type (wifi/cellular), но осторожно.

Если нет поддержки:
- хотя бы request-id + структурированные логи.

## 4) Метрики, которые реально нужны
### A) Latency
- средняя мало что значит — нужны перцентили:
  - p50/p90/p95/p99.
- измерять:
  - время запроса,
  - отдельно время decoding,
  - время “cache read”.

### B) Error rate
- разделять:
  - transport errors (URLError),
  - HTTP 4xx/5xx,
  - decoding,
  - domain errors.

### C) Retry metrics
- retry count,
- distribution backoff,
- % запросов, которые “успели” после retry.

### D) Cache metrics
- hit rate (memory/disk),
- stale served,
- revalidate success (304 rate).

### E) Queue metrics (если есть outbox/download queue)
- queue length,
- oldest pending age,
- success/fail ratio.

## 5) Privacy redaction: что нельзя логировать
Нельзя:
- Authorization header,
- access/refresh tokens,
- email/phone/name,
- raw request/response body (если там PII),
- файлы/пути с персональными данными.

Как делать правильно:
- редактирование (redaction) на уровне interceptor:
  - whitelist headers,
  - mask values,
  - для body — логировать только “структурную” информацию:
    - size, fields count, not raw.

Также:
- sampling: логируем 1–5% успешных запросов, но 100% ошибок (и то с редактированием).

## 6) Структурированные логи (важно для расследований)
Формат события:
- timestamp
- requestId
- endpoint (без query, если там PII)
- method
- statusCode
- durationMs
- errorCategory
- retryCount
- cachePolicy/hit
- networkType
- appVersion/build
- device model + iOS version (не персонально)

Такое можно агрегировать на сервере логов.

## 7) Интеграция с crash reporting
- добавлять breadcrumbs:
  - “request started/finished”,
  - requestId,
  - error category.
- связывать: crash → последняя сеть.

Важно:
- не спамить breadcrumbs, использовать sampling/агрегацию.

## 8) Как отвечать на собесе
“Я делаю observability через correlation IDs и структурированные события. Каждый запрос получает requestId и (если возможно) trace headers. Я собираю метрики latency по перцентилям, error-rate по категориям, метрики ретраев и cache hit rate. Всё логирование проходит через redaction: токены/PII не пишем, успешные запросы — sampling. В ошибках и репортах сохраняю requestId, чтобы backend мог найти цепочку событий.”

**Самопроверка**
- Оспорено: “достаточно print(error)” — без корреляции и метрик вы не отладите прод.
- Неочевидно: privacy redaction — обязательна, иначе observability становится утечкой данных.
- Источники, которые стоит освежить: W3C Trace Context/OpenTelemetry идеи, best practices structured logging, Apple privacy требования (особенно вокруг логирования), подходы к sampling и метрикам перцентилей.


### Q254 (🔴): Как проектировать безопасные и устойчивые политики refresh токенов + concurrency: single-flight refresh, очереди запросов, деградация UX?

**Кратко**
- Цель: **никогда не делать параллельные refresh** и не раздавать гоняющиеся токены по приложению.
- База:
  - централизованный `SessionStore` (единственное место, где живут токены),
  - **single-flight refresh** (один refresh на всех),
  - очередь/коалесинг запросов, которые пришли во время refresh,
  - чёткая классификация ошибок (expired vs revoked vs network),
  - защита от циклов (401 → refresh → 401 → refresh…),
  - безопасное хранение (Keychain) и redaction в логах.
- UX: деградация “мягко”:
  - при временной сети — показывать stale/cached, ретраи,
  - при revoked/invalid — быстрый logout + понятное сообщение.

**Развёрнуто**
## 1) Основная проблема: гонки refresh
Если несколько запросов получают 401 одновременно и каждый запускает refresh:
- вы делаете N refresh вместо 1,
- можете перезаписать токены в неправильном порядке,
- создаёте лишнюю нагрузку на backend,
- получаете “трепещущие” состояния авторизации (то работает, то нет).

Поэтому главное правило:
- **refresh должен быть single-flight**.

## 2) Архитектура: SessionStore как единая точка истины
Компонент `SessionStore` (лучше actor/serial queue) хранит:
- access token,
- refresh token,
- expiresAt (если есть),
- состояние refresh (idle/refreshing),
- ссылку на текущий in-flight refresh (Task/Continuation).

Инварианты:
- токены обновляются атомарно,
- access token никогда не читается “напрямую из разных мест” без синхронизации,
- все запросы берут токен через `SessionStore`.

## 3) Single-flight refresh: алгоритм
Сценарий A: запрос перед отправкой проверяет “почти истёк”:
1) если токен скоро истечёт → вызываем `ensureValidToken()`
2) `ensureValidToken()`:
   - если refresh уже идёт → await существующий
   - иначе запускает refresh и кэширует “in-flight” Task
3) после завершения refresh:
   - обновляем токены в Keychain (и в памяти),
   - завершаем in-flight,
   - все ожидающие продолжают.

Сценарий B: запрос получил 401:
1) проверить, что запрос был с “текущим” токеном (иначе мог прийти старый ответ)
2) если refresh уже идёт → дождаться
3) иначе запустить refresh single-flight
4) повторить оригинальный запрос **один раз** (с лимитом).

## 4) Очередь запросов на время refresh
Есть 2 подхода:

### Подход 1: “подвешиваем” запросы (gate)
- перед выполнением любой авторизованной операции:
  - await `ensureValidToken()`.
Плюсы:
- простая модель,
- меньше 401.
Минусы:
- можно увеличить latency, если refresh часто.

### Подход 2: “ретраим после 401”
- сначала пробуем, на 401 делаем refresh и ретрай.
Плюсы:
- меньше лишних refresh, если сервер терпим.
Минусы:
- всплеск 401 и ретраев при массовом истечении.

На практике часто делают гибрид:
- proactive refresh за X секунд до expiry + fallback на 401.

## 5) Защита от бесконечных циклов
Нужны ограничители:
- один ретрай после refresh на запрос (не бесконечно),
- если после refresh всё равно 401/403:
  - считаем refresh token невалидным/ревокнутым,
  - переходим в logout.

Также нужно различать:
- 401 из-за истёкшего access token,
- 401/403 из-за revoked refresh token / бан / смена пароля.

## 6) Ошибки и деградация UX
### A) Network down / timeout во время refresh
- не делать logout сразу,
- сохранять текущую сессию как “возможно валидна”,
- показывать offline UI / stale cache,
- повторять refresh по backoff (с лимитом) или по событию “сеть появилась”.

### B) Refresh token invalid/revoked
- быстрый переход в “unauthenticated” состояние,
- чистка токенов,
- показать понятный экран/баннер:
  - “Сессия истекла, войдите снова”.

### C) Сервер деградирует
- circuit breaker для refresh endpoint,
- не блокировать всё приложение бесконечно:
  - часть экранов может жить на кэше,
  - критичные действия отключить с объяснением.

## 7) Безопасность
- хранить refresh token в Keychain,
- минимизировать срок жизни access token,
- не логировать токены/headers,
- разделять окружения (prod/stage) и namespaces Keychain,
- при logout удалять токены и связанные персональные кэши.

## 8) Observability для refresh
Метрики:
- refresh success rate,
- среднее время refresh,
- количество “waiters” на single-flight,
- причины logout (revoked vs network).

Breadcrumbs (без секретов):
- refresh started/finished + requestId.

## 9) Как отвечать на собесе
“Я строю auth вокруг SessionStore (лучше actor), который единственный владеет токенами. Refresh делаю single-flight: если refresh уже идёт, все запросы await его результат. Запросы либо проходят через gate `ensureValidToken()`, либо на 401 запускают refresh и ретраят один раз. Обязательно есть защита от циклов и чёткая классификация ошибок: network — деградация и ретраи, revoked — logout. Токены в Keychain, в логах — redaction.”

**Самопроверка**
- Оспорено: “на 401 просто обновим токен” — без single-flight получите гонки и перезапись токенов.
- Неочевидно: нужно различать “временно нет сети” и “refresh token revoked”, иначе вы будете разлогинивать людей без причины.
- Источники, которые стоит освежить: best practices OAuth2 refresh flows, паттерн single-flight, подходы к gate vs retry-on-401, Apple Keychain + Data Protection, наблюдаемость auth событий.

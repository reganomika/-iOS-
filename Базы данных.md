## Базы данных в iOS

### Q179 (🟢): Когда в iOS вообще нужна “БД”, а когда хватит файлов/Keychain/UserDefaults?

**Кратко**
- **UserDefaults** — мелкие настройки/флаги, не данные предметной области.
- **Keychain** — секреты (токены, пароли, ключи).
- **Файлы** — большие бинарники (PDF/видео/кеши) и данные “как есть”.
- **БД (Core Data/Realm/SQLite)** — когда есть **много сущностей**, **связи**, **поиск/фильтры/сортировки**, **офлайн‑режим**, **инкрементальные обновления UI** и **целостность**.

**Развёрнуто**
## 1) Критерии выбора: данные vs настройки vs секреты vs контент
### UserDefaults
Подходит для:
- флагов UI (“показали онбординг”),
- пользовательских настроек (тема, сортировка),
- небольших значений (строки/числа/простые структуры).

Не подходит для:
- коллекций бизнес-данных,
- больших массивов/объектов,
- частых обновлений и сложных запросов.

Причина: нет нормальных запросов, нет транзакций, легко превратить в неуправляемую свалку.

### Keychain
Подходит для:
- access/refresh токенов,
- паролей/ключей,
- приватных идентификаторов, которые нельзя хранить в открытом виде.

Не подходит для:
- “обычных” данных приложения,
- больших объёмов,
- сложных выборок.

### Файловая система
Подходит для:
- контента: изображения, видео, PDF, аудио,
- кэшей ответов,
- экспортов/импортов,
- “как есть” файлы без сложных запросов.

Обычно в паре:
- метаданные о файлах — в БД,
- сами бинарники — на диске.

## 2) Когда нужна база данных
БД оправдана, если есть хотя бы 2–3 пункта:
- много объектов и они изменяются со временем,
- нужны выборки: фильтрация/сортировка/пагинация/поиск,
- есть связи (one-to-many, many-to-many),
- важно быстро строить экран из локальных данных,
- офлайн-first / синк / очередь операций,
- нужно гарантировать целостность (уникальность, каскадное удаление),
- нужен “reactive” UI (список обновляется на изменениях).

## 3) Core Data vs Realm в контексте “зачем БД”
### Core Data
Сильна в:
- интеграции с Apple экосистемой,
- графах сущностей/relationships,
- оптимизациях (faulting),
- NSFetchedResultsController (классика для таблиц).

### Realm
Сильна в:
- простоте модели (объекты “живые”),
- быстрых results/notifications,
- компактной интеграции без большого stack.

Но у обоих общий смысл:
- хранить **структурированные данные** и позволять их эффективно запрашивать.

## 4) Типичные ошибки выбора
- Пихать бизнес-данные в UserDefaults (“быстро и просто”) → потом невозможно мигрировать и делать запросы.
- Хранить токены в UserDefaults вместо Keychain → риск утечек.
- Хранить всё в файлах без метаданных → невозможно делать выборки и поддерживать целостность.
- Хранить большие бинарники прямо в БД без необходимости → память/размер/скорость страдают.

## 5) Хорошее правило большого пальца
- **Секреты → Keychain**
- **Настройки → UserDefaults**
- **Контент → файлы**
- **Модели и их связи/запросы → БД**
- **Файлы + БД** (часто лучший вариант): в БД лежат метаданные и индексы, на диске — бинарники.

**Самопроверка**
- Оспорено: “UserDefaults можно для всего, если данных немного” — это быстро деградирует из-за отсутствия запросов, транзакций и поддержки целостности.
- Неочевидно: граница “файлы vs БД” — обычно метаданные в БД, контент на диске; важно не хранить бинарники в БД без причины.
- Источники, которые стоит освежить: Apple docs по Data Protection/Keychain, рекомендации по хранению больших данных и кэшей, практики Core Data vs Realm по моделированию и наблюдению изменений.

### Q180 (🟢): Что такое Core Data и чем он отличается от SQLite (и почему Core Data — не “просто БД”)?

**Кратко**
- **SQLite** — конкретная реляционная БД/движок: таблицы, SQL, индексы.
- **Core Data** — **ORM/объектный граф + persistence framework**: управляет объектами, их связями, жизненным циклом, кэшированием, faulting, наблюдением изменений.
- Core Data **может** использовать SQLite как storage, но “Core Data = SQLite” неверно: Core Data добавляет слой объектного графа, контексты, правила сохранения и т.д.

**Развёрнуто**
## 1) Core Data: что это по сути
Core Data состоит из:
- **модели** (Entities, Attributes, Relationships),
- **контекстов** (`NSManagedObjectContext`) — “единица работы” и транзакционность,
- **persistent store coordinator / store** — физическое хранилище (часто SQLite),
- механизмов:
  - **faulting** (ленивая загрузка),
  - change tracking,
  - merge изменений между контекстами,
  - валидаций,
  - batch operations,
  - интеграции с UI (NFRController).

Core Data — это **менеджер объектного графа** + persistence.

## 2) SQLite: что это
SQLite:
- таблицы/строки/столбцы,
- SQL запросы,
- индексы,
- транзакции на уровне БД,
- полный контроль над схемой и запросами.

Ты пишешь:
- SQL,
- маппинг в модели,
- миграции руками.

## 3) Ключевые отличия (практика)
### Уровень абстракции
- SQLite: низкий уровень, “ты управляешь всем”.
- Core Data: высокий уровень — работаешь с объектами и связями.

### Объектный граф и связи
Core Data:
- relationships, inverse, delete rules,
- faulting для связей (lazy).
SQLite:
- foreign keys и join’ы — руками.

### Контексты и merge
Core Data:
- несколько контекстов, merge policies, propagation изменений.
SQLite:
- concurrency на уровне транзакций и собственных блокировок/очередей, всё вручную.

### Наблюдение изменений
Core Data:
- NSFetchedResultsController, notifications, Combine (через обвязку).
SQLite:
- нужно самому организовать.

### Производительность и контроль
- SQLite даёт полный контроль над запросами и индексами.
- Core Data может быть очень быстрой, но требует понимания:
  - faulting,
  - prefetching,
  - batching,
  - правил сохранения.

## 4) Почему “Core Data — не просто БД”
Потому что:
- это не движок хранения данных, а фреймворк управления объектами,
- storage может быть разным:
  - SQLite store,
  - binary store (исторически),
  - in-memory store (для тестов/preview),
- ценность Core Data — в работе с объектным графом и жизненным циклом объектов.

## 5) Когда Core Data предпочтительнее SQLite
- много связей и объектный граф — важен,
- нужен автоматический change tracking и удобное обновление UI,
- хочется меньше ручного SQL/маппинга,
- нужна интеграция с Apple стеком.

Когда SQLite предпочтительнее:
- очень специфичные запросы/индексы,
- нужен строгий контроль над SQL,
- хочется минимальной магии (но больше ручной работы).

## 6) Типичные когнитивные ловушки на собесе
- “Core Data = ORM над SQLite” — частично верно, но неполно: Core Data — ещё и object graph management, faulting, contexts.
- “Core Data медленная” — чаще проблема в неправильных fetch’ах/relationships и работе на main thread, а не в Core Data “по природе”.

**Самопроверка**
- Оспорено: “Core Data — просто SQLite с оболочкой” — Core Data даёт управление объектным графом, контексты, faulting и change tracking.
- Неочевидно: основная сложность Core Data — в контекстах и правильной настройке fetch/relationships, а не в “написать запрос”.
- Источники, которые стоит освежить: Apple Core Data Programming Guide, документация по NSManagedObjectContext/concurrency, материалы про faulting/prefetching и batch operations.

### Q181 (🟢): Что такое Realm и чем он принципиально отличается от Core Data по модели использования?

**Кратко**
- **Realm** — встроенная объектная база данных: хранишь и читаешь объекты напрямую, без отдельного контекста как в Core Data.
- Отличия по “модели мышления”:
  - Core Data: **object graph + contexts + save/merge**.
  - Realm: **live objects + write transactions + thread confinement**.
- Realm обычно проще стартовать, но требует строгой дисциплины по потокам и жизненному циклу “живых” объектов.

**Развёрнуто**
## 1) Realm: что это
Realm — объектная БД, где:
- модели наследуются от `Object`,
- выборки возвращают `Results<T>` (ленивые, “живые”),
- изменения выполняются в `write {}` транзакции,
- есть нотификации на изменения (наблюдение).

Важная характеристика:
- объекты и коллекции “живые”: они автоматически отражают изменения в БД (в рамках правил потоков).

## 2) Core Data vs Realm: отличия в ежедневной работе
### A) Жизненный цикл и “контекст”
Core Data:
- работаешь через `NSManagedObjectContext`,
- изменения живут в контексте до `save()`,
- нужно уметь merge между контекстами.

Realm:
- нет концепции “контекст как unit-of-work” в том же виде,
- изменения делаются через явные `write` транзакции,
- после commit данные сразу доступны (для того же realm/потока).

### B) Concurrency модель
Core Data:
- concurrency через contexts: main и background контексты,
- объекты нельзя “просто так” таскать между потоками (нужны objectID + refetch),
- merge policy и конфликты.

Realm:
- **thread confinement**:
  - `Realm`, `Object`, `Results` привязаны к потоку/очереди,
- чтобы передать данные:
  - копировать в value types,
  - или использовать `ThreadSafeReference`,
  - или freezing (если применимо).

### C) Наблюдение изменений
Core Data:
- NSFetchedResultsController (UITableView классика),
- notifications/Combine через обвязки.

Realm:
- нотификации на `Results` и объекты,
- удобно для реактивного UI.

### D) Модель и relationships
Core Data:
- declarative модель (xcdatamodeld),
- delete rules, inverse relationships, constraints.

Realm:
- relationships через ссылки, `List`,
- обратные связи через `LinkingObjects`,
- правила каскада/удаления чаще реализуются на уровне кода (зависит от модели).

## 3) Что проще/сложнее на практике
### Realm часто проще:
- быстро начать,
- меньше “стека” и конфигурации,
- удобные “живые” выборки.

### Realm часто сложнее:
- жёсткая дисциплина по потокам (объекты нельзя просто прокинуть),
- легко получить краши/неожиданное поведение из-за доступа к объекту с другого thread,
- нужно внимательно относиться к “долгоживущим” results/observations, чтобы не делать notification storm.

Core Data сложнее стартовать (контексты/мерджи), но:
- сильнее встроена в Apple стек,
- мощные инструменты для графов и batch операций,
- привычная экосистема.

## 4) Что сказать на собесе (суть отличий)
“Core Data — это object graph management с контекстами и save/merge, а Realm — объектная БД с live objects и транзакциями записи, но со строгим thread confinement. Выбор зависит от требований к экосистеме, команды и того, насколько комфортно контролировать concurrency модель.”

**Самопроверка**
- Оспорено: “Realm проще во всём” — она проще для CRUD старта, но concurrency и live objects часто дают сложные баги.
- Неочевидно: главная разница — не синтаксис CRUD, а модель конкурентности и жизненный цикл объектов (contexts vs live objects).
- Источники, которые стоит освежить: Realm docs про threading (`ThreadSafeReference`, freezing), Core Data concurrency и `NSManagedObjectID`, best practices для наблюдения изменений (notification storms).


### Q182 (🟢): Что такое сущность/объект в Core Data (Entity/NSManagedObject) и в Realm (Object) — в чём разница подходов?

**Кратко**
- **Core Data**: Entity — описание в модели; `NSManagedObject` — объект графа, живущий в контексте и имеющий жизненный цикл (faulting, save/rollback).
- **Realm**: `Object` — конкретный класс модели, который напрямую отображается в storage; изменения фиксируются внутри `write` транзакции.
- Главное отличие: **unit of work** и **контекст** в Core Data vs **live objects + транзакции** в Realm.

**Развёрнуто**
## 1) Core Data: Entity и NSManagedObject
### Entity
- задаётся в `.xcdatamodeld`,
- описывает:
  - атрибуты,
  - отношения,
  - индексы/constraints (возможности зависят от версии),
  - delete rules.

### NSManagedObject
- “живёт” внутри `NSManagedObjectContext`,
- может быть fault (ленивый placeholder),
- изменения копятся в контексте до `save()`:
  - можно `rollback()`,
  - можно merge изменения между контекстами.

Идея:
- Core Data управляет **object graph**, а не просто “таблицей”.

Ключевая деталь:
- переносить `NSManagedObject` между потоками нельзя; обычно передают `NSManagedObjectID` и re-fetch.

## 2) Realm: Object
- класс наследуется от `Object`,
- свойства определяют схему,
- объект “привязан” к конкретному `Realm` инстансу/потоку,
- любые изменения — внутри `realm.write { ... }`.

Realm объект:
- live: отражает изменения, сделанные в БД (с учётом thread rules),
- можно наблюдать изменения на `Results`/объектах.

Перенос между потоками:
- нельзя напрямую,
- используются:
  - value копия,
  - `ThreadSafeReference`,
  - freezing (когда применимо).

## 3) Подходы к “изменениям” и транзакциям
### Core Data
- контекст = unit-of-work:
  - можно массово изменить объекты,
  - затем `save()` одним коммитом.
- удобно для сложных “сессий редактирования”.

### Realm
- транзакция `write` = коммит:
  - изменения сразу становятся частью БД (после commit),
  - если нужно “сессия редактирования”, часто держат draft/value copy и потом применяют.

## 4) Ошибки и баги, которые следуют из различий
Core Data:
- забыли `save()` → “данные не сохранились”,
- неправильный merge policy → конфликты,
- слишком много объектов на main context → лаги.

Realm:
- доступ к объекту с неправильного thread → crash,
- долго держим Results/observations → notification storms,
- пишем часто мелкими транзакциями на главном потоке → лаги.

## 5) Как ответить на собесе
“В Core Data Entity — это описание в модели, а NSManagedObject — элемент объектного графа в контексте; изменения живут в контексте до save и есть механизм faulting/merge. В Realm модель — это Object-класс, который напрямую маппится на storage; изменения фиксируются через write транзакции, а объекты ‘живые’, но строго привязаны к потоку.”

**Самопроверка**
- Оспорено: “в Core Data объекты как в Realm” — в Core Data критична роль контекста (unit-of-work), в Realm — роль транзакций и thread confinement.
- Неочевидно: “редактирование в несколько шагов” проще в Core Data (контекст + rollback), а в Realm часто нужен draft/value model.
- Источники, которые стоит освежить: Core Data contexts/faulting/rollback, Realm threading и transactions, подходы к editable drafts (value models) поверх Realm.


### Q183 (🟢): Что такое миграция схемы и почему она неизбежна в приложениях с хранением данных?

**Кратко**
- **Миграция** — процесс перевода данных из старой схемы (модели) в новую при обновлении приложения.
- Она неизбежна, потому что:
  - продукт меняется (новые поля, связи, новые сущности),
  - появляются новые фичи и требования,
  - исправляются ошибки в модели.
- Без миграций приложение либо:
  - теряет данные,
  - либо не может открыть хранилище после апдейта.

**Развёрнуто**
## 1) Что именно “мигрирует”
Меняются:
- поля (добавили/удалили/переименовали),
- типы полей (Int → String и т.п.),
- отношения и delete rules,
- уникальные ограничения/индексы,
- структура хранения (разделили сущность на две, нормализовали).

Миграция должна:
- сохранить смысл данных,
- привести их к новой модели.

## 2) Почему миграция неизбежна (и где часто обманывают себя)
Иллюзия:
- “мы всё предусмотрим в первой версии”.
Реальность:
- данные и требования эволюционируют.
Любой persisted storage требует evolution-плана.

Даже “мелочь”:
- добавили `createdAt` — это миграция.

## 3) Core Data миграции (в общих чертах)
- lightweight migration:
  - работает для простых изменений (добавили поле, переименовали через mapping),
  - но ломается на сложных трансформациях.
- heavyweight migration:
  - custom mapping model и/или ручная логика преобразования,
  - нужна при “перестройке” сущностей и отношений.

Риск:
- если неправильно настроить, приложение не сможет загрузить store.

## 4) Realm миграции (в общих чертах)
- при увеличении `schemaVersion` задаёшь migration block:
  - для старых версий описываешь, как создать/заполнить новые поля,
  - как преобразовать структуру.

Риск:
- пропустить кейс для старой версии → крэши у пользователей, которые обновляются через несколько релизов.

## 5) Стратегия “безопасных миграций”
- всегда версионировать схему,
- тестировать апгрейд:
  - с N-1,
  - и “long jump” (например, N-5 → N),
- держать миграции идемпотентными (где возможно),
- избегать “удалить и пересоздать store” (кроме чисто кешей),
- для больших изменений — двухшаговый rollout:
  - сначала добавить новые поля/таблицы,
  - потом перенести данные,
  - потом удалить старое.

## 6) Типичные ошибки
- “Лёгкая миграция всегда сработает” — нет, сложные трансформации требуют кастома.
- “Пользователь обновляется всегда с предыдущей версии” — нет, есть long jump.
- “Проще удалить БД при ошибке” — это потеря данных и плохой UX (если не кеш).

## 7) Как ответить на собесе
“Миграция — это evolution схемы хранения. Она неизбежна, потому что модель данных меняется вместе с продуктом. В Core Data есть lightweight/heavyweight подходы, в Realm — migration block по schemaVersion. Безопасность достигается версионированием, тестами апгрейда через несколько версий и двухшаговыми миграциями для крупных изменений.”

**Самопроверка**
- Оспорено: “можно жить без миграций, если аккуратно” — изменения требований всё равно приведут к нужде в эволюции схемы.
- Неочевидно: long-jump апдейты (через несколько версий) — реальная причина большинства “миграционных” крашей у пользователей.
- Источники, которые стоит освежить: Core Data lightweight vs heavyweight migration, Realm migration best practices, стратегии двухшаговых миграций (expand/migrate/contract).


### Q184 (🟠): Как устроен Core Data stack: NSPersistentContainer, persistent store, context’ы — и какие контексты ты используешь в типичном приложении?

**Кратко**
- **NSPersistentContainer** — собирает stack: модель + coordinator + store, создаёт контексты.
- **Persistent store** — физическое хранилище (обычно SQLite).
- **NSManagedObjectContext** — unit-of-work: отслеживает изменения объектов и коммитит их через `save()`.
- Типичная схема:
  - `viewContext` (main) — чтение/наблюдение для UI,
  - background context(ы) — запись/импорт/тяжёлые операции,
  - merge изменений в `viewContext` (auto-merge или вручную).

**Развёрнуто**
## 1) Из чего состоит Core Data stack
### A) NSManagedObjectModel
- описание сущностей/атрибутов/relationships (xcdatamodeld),
- версии модели для миграций.

### B) NSPersistentStoreCoordinator (внутри контейнера)
- связывает модель с физическим store,
- маршрутизирует чтение/запись из контекстов в хранилище.

### C) NSPersistentStore (обычно SQLite)
- файл на диске,
- может быть:
  - SQLite store (прод),
  - in-memory store (тесты/preview).

### D) NSPersistentContainer
- удобная обёртка, которая:
  - грузит stores (`loadPersistentStores`),
  - даёт `viewContext`,
  - создаёт background контексты (`newBackgroundContext()`),
  - упрощает конфигурацию.

## 2) Роль NSManagedObjectContext (контекста)
Контекст:
- владеет объектами (managed objects) и их состоянием,
- отслеживает изменения (insert/update/delete),
- обеспечивает транзакционность:
  - `save()` коммитит изменения в store (через coordinator),
  - `rollback()` отменяет несохранённые изменения,
- определяет concurrency:
  - `.mainQueueConcurrencyType` или `.privateQueueConcurrencyType`.

Критично:
- `NSManagedObject` привязан к конкретному context и queue.

## 3) Типовая конфигурация контекстов в приложении
### Вариант A (самый частый): sibling contexts + merge
- `container.viewContext` (main):
  - UI чтение,
  - NSFetchedResultsController,
  - отображение списков.
- `container.newBackgroundContext()`:
  - импорт данных,
  - синк,
  - массовые записи,
  - тяжёлые операции.

Как “подружить”:
- включить авто-мердж:
  - `viewContext.automaticallyMergesChangesFromParent = true`
  - и/или слушать `NSManagedObjectContextDidSave` у background и мерджить в main.

Плюсы:
- просто,
- хорошо для большинства приложений.

### Вариант B: parent-child contexts (реже)
- child context на main для редактирования (draft):
  - можно rollback без записи в store,
- parent background context пишет в store.

Плюсы:
- удобно для сложных форм редактирования.
Минусы:
- сложнее понимать и отлаживать, возможны неожиданные мерджи и стоимость propagations.

## 4) Какие правила я обычно держу
- UI читает из `viewContext`, writes на main минимальны.
- Все тяжёлые записи/импорт/синк — на background context.
- Merge policy задаю явно (иначе конфликт может стать “магией”).
- Для long-running задач создаю отдельный background context, не переиспользую один на всё (уменьшает конфликтность и упрощает отмену).
- Не таскаю `NSManagedObject` между потоками:
  - передаю `NSManagedObjectID` и re-fetch в нужном контексте.

## 5) Типичные ошибки (и почему они происходят)
- Писать много на `viewContext` → лаги UI.
- Забыть merge → UI не видит изменений или видит “старые” данные.
- Делать один глобальный background context на всё → гонки и конфликт мерджей.
- Передавать `NSManagedObject` между потоками → crashes/undefined behavior.

## 6) Формулировка на собесе
“Core Data stack: container управляет моделью и store, контекст — unit-of-work. Я держу viewContext для UI и отдельные background contexts для записей/синка. Изменения мерджу в viewContext (auto merge или notifications). Объекты между потоками не передаю — только objectID.”

**Самопроверка**
- Оспорено: “достаточно одного viewContext” — это быстро приводит к лагам и сложным багам конкурентности.
- Неочевидно: sibling contexts + merge чаще проще и надёжнее, чем parent-child, если нет сильной причины для draft-редактирования.
- Источники, которые стоит освежить: Apple docs по NSPersistentContainer, NSManagedObjectContext concurrency, merge strategies и notifications, best practices “objectID across threads”.



### Q185 (🟠): Как устроена конкурентность: Core Data (main/background contexts, merge) vs Realm (thread confinement, freezing) — где чаще ошибаются?

**Кратко**
- **Core Data**:
  - изоляция через **контексты**,
  - `NSManagedObject` привязан к контексту/очереди,
  - фоновые записи требуют **merge** в `viewContext`.
- **Realm**:
  - изоляция через **thread confinement**: `Realm/Object/Results` привязаны к потоку,
  - передача между потоками через **ThreadSafeReference** или value-копии,
  - “живые” результаты могут генерировать много уведомлений.
- Самые частые ошибки:
  - таскать объекты между потоками,
  - писать на main thread тяжёлые транзакции,
  - неправильно мерджить/наблюдать изменения.

**Развёрнуто**
## 1) Core Data concurrency: модель и правила
### Контексты = единицы изоляции
- `viewContext` (main queue) для UI.
- `privateQueue` контексты для фона.

Жёсткое правило:
- обращаться к объектам контекста только на его очереди:
  - `context.perform { ... }` / `performAndWait`.

### Merge изменений
Если фон сохранил изменения:
- UI сам не “узнает”, пока не произойдёт merge в `viewContext`.

Способы:
- `viewContext.automaticallyMergesChangesFromParent = true` (для container),
- слушать `NSManagedObjectContextDidSave` и мерджить вручную.

### Где часто ломают
- создают background context, но не мерджат → UI “не обновляется”,
- делают `save()` на main после массовых изменений → фризы,
- передают `NSManagedObject` в другой поток → crashes,
- используют один shared background context на весь синк → гонки и конфликты.

Практика:
- передавать `NSManagedObjectID`, re-fetch в нужном контексте.

## 2) Realm concurrency: модель и правила
### Thread confinement
- `Realm`, `Object`, `Results` привязаны к потоку.
Запрещено:
- использовать их с другого потока.

### Передача данных между потоками
Варианты:
- value type копия (DTO),
- `ThreadSafeReference`:
  - создать reference,
  - на другом потоке `realm.resolve(ref)`.
- freezing:
  - “заморозить” объект/коллекцию для чтения в другом потоке (без live-обновлений).

### Где часто ломают
- “просто передали Realm объект” между потоками → crash,
- держат long-lived Results и подписки, и при массовых записях ловят notification storm,
- делают крупные write транзакции на main thread → лаги,
- в UI держат ссылку на объект, который удалили/изменили в другом месте → неожиданные состояния (если не контролировать).

## 3) Сравнение “типовых паттернов”
### Чтение для UI
- Core Data: `viewContext` + NSFetchedResultsController.
- Realm: `Results` + notifications/observations.

### Запись/импорт
- Core Data: background context, batch operations, затем merge.
- Realm: background thread realm, write транзакции, UI обновится через нотификации (при правильной подписке).

### Данные между слоями
И там, и там хорошая практика:
- на границе домена/презентации отдавать value types,
- не протаскивать “живые” managed objects/realm objects далеко.

## 4) Как выбирать стратегию и не утонуть
### Принцип: “Изоляция состояния”
- Core Data: изоляция = контекст.
- Realm: изоляция = thread (realm instance).

Нужно выбрать:
- где находится SSOT,
- кто владеет наблюдением изменений,
- как обеспечивается отмена/переинициализация при смене аккаунта/логауте.

## 5) Пример типового флоу (смысл, без конкретного кода)
- UI хочет обновить список:
  - Core Data: fetch + FRC; фон синк сохраняет → merge → UI обновился.
  - Realm: Results наблюдается; фон write commit → нотификация → UI обновился.

## 6) Формулировка на собесе
“Core Data конкурентность строится вокруг контекстов: объекты привязаны к контексту, фоновые записи требуют merge в viewContext, передавать нужно objectID. Realm строится вокруг thread confinement: realm/objects/results привязаны к потоку, для передачи — ThreadSafeReference или freezing/value copies. Частые ошибки — протаскивать объекты между потоками и делать тяжёлые записи на main.”

**Самопроверка**
- Оспорено: “в Realm проще, потому что нет контекстов” — вместо контекстов ты получаешь строгий thread confinement и проблемы с long-lived наблюдениями/notification storm.
- Неочевидно: у Core Data самая частая проблема — забытый merge; у Realm — попытка использовать объект с другого потока.
- Источники, которые стоит освежить: Apple docs по `perform`, merge notifications/policies; Realm threading (`ThreadSafeReference`, freezing) и best practices notifications.


### Q186 (🟠): Как проектировать отношения: Core Data (delete rules, inverse) vs Realm (List, LinkingObjects) — типичные ловушки?

**Кратко**
- **Core Data**:
  - relationships задаются в модели,
  - важны **inverse relationships** и **delete rules**,
  - ошибки = неверные каскады, orphan’ы и неожиданные удаления.
- **Realm**:
  - ссылки — это свойства `Object`, коллекции — `List`,
  - обратные связи — через `LinkingObjects`,
  - ошибки = ручное поддержание целостности и “забыли почистить ссылки”.
- Главная мысль: отношения — это всегда про **целостность** и **правила жизненного цикла**.

**Развёрнуто**
## 1) Core Data relationships: ключевые понятия
### Inverse relationship
- почти всегда должна быть задана,
- помогает Core Data:
  - поддерживать целостность графа,
  - корректно мерджить изменения,
  - оптимизировать faulting.

Ловушка:
- нет inverse → баги в графе, неожиданные поведения и сложный дебаг.

### Delete rules
Основные:
- **Cascade**: удаляя parent, удаляешь children.
- **Nullify**: удаляя parent, обнуляешь ссылку у children (если optional).
- **Deny**: запретить удаление, если есть связанные объекты.
- **No Action**: опасная зона — ответственность на тебе.

Типичная ловушка:
- поставить Cascade “на всякий случай” и случайно удалять большие куски данных.
Или наоборот:
- Nullify без бизнес-логики → появляются orphan’ы.

### Many-to-many
- Core Data умеет, но важно:
  - корректные inverse,
  - понимать, кто владеет жизненным циклом.

## 2) Realm relationships: как это устроено
### Links и Lists
- one-to-one/one-to-many:
  - ссылка: `var owner: Owner?`
  - коллекция: `let items = List<Item>()`

### Обратные связи
- не “inverse relationship” в модели, а:
  - `LinkingObjects(fromType: ..., property: ...)`
Это “view” на то, кто ссылается на объект.

### Удаление и целостность
Realm не будет “магически” делать каскады как Core Data.
Нужно явно:
- удалять детей,
- чистить ссылки,
- или проектировать так, чтобы orphan’ы были допустимы (редко).

Ловушка:
- удалить объект, на который кто-то ссылается → ссылки могут стать проблемой или логика начнёт ломаться (в зависимости от дизайна).

## 3) Типичные ловушки и как их избежать
### Ловушка 1: неправильная модель владения
Нужно ответить:
- кто “владелец” ребёнка?
- живёт ли ребёнок без родителя?

Если ребёнок не должен жить без родителя:
- Core Data: Cascade,
- Realm: вручную удалять детей в транзакции удаления родителя.

Если ребёнок может жить отдельно:
- Core Data: Nullify (и optional),
- Realm: отдельная сущность и ссылки обновляются логикой.

### Ловушка 2: циклы в графе и memory/perf
Большие графы отношений:
- Core Data: fault storms и неожиданные fetch cascades, если неправильно prefetch.
- Realm: большие “живые” коллекции и нотификации.

Решение:
- не таскать глубоко граф в UI,
- проектировать запросы и модели отображения.

### Ловушка 3: many-to-many без ограничений
Много связей + без delete правил/чистки:
- легко получить мусорные связи.

Решение:
- явная стратегия удаления и чистки,
- периодические “sanity checks” (если домен сложный).

## 4) Как отвечать на собесе
“В Core Data важно корректно задавать inverse relationships и delete rules, иначе появляются orphan’ы или неожиданные каскадные удаления. В Realm связи задаются через ссылки и List, а обратные — через LinkingObjects; каскады обычно нужно реализовывать вручную в write транзакциях. Поэтому сначала определяю модель владения и жизненный цикл сущностей, а уже потом выбираю delete rules/чистку.”

**Самопроверка**
- Оспорено: “delete rules — это просто галочки” — это фактически доменные правила жизненного цикла данных; ошибка приводит к потере данных или мусору.
- Неочевидно: Realm требует больше дисциплины в поддержании целостности, потому что многие каскады не “встроены” как в Core Data.
- Источники, которые стоит освежить: Core Data delete rules/inverse relationships, Realm LinkingObjects и best practices по каскадным удалениями и целостности ссылок.


### Q187 (🟠): Как организовать наблюдение изменений: NSFetchedResultsController / notifications / Combine в Core Data vs Realm Notifications/Results — tradeoffs?

**Кратко**
- Core Data:
  - **NSFetchedResultsController (FRC)** — лучший вариант для списков с секциями и анимациями в UIKit.
  - notifications/Combine — для более общего реагирования (но часто нужны доп. слои для диффов).
- Realm:
  - `Results` + **notifications** дают “живой” список, который сам обновляется.
  - Но легко получить **notification storm** и проблемы с потоками.
- Tradeoff:
  - FRC даёт стабильные диффы для UITableView,
  - Realm проще подписывать, но важна дисциплина по батчингу/потокам/жизненному циклу подписок.

**Развёрнуто**
## 1) Core Data: варианты наблюдения
### A) NSFetchedResultsController
Используется, когда:
- UIKit список (UITableView/UICollectionView),
- нужно:
  - sections,
  - granular updates (insert/delete/move/update),
  - корректные анимации без ручных diff.

Плюсы:
- “из коробки” даёт изменения для UI,
- хорошо сочетается с `viewContext`.

Минусы:
- специфичен к fetch request и контексту,
- для сложных UI (например, diffable) может потребоваться адаптер.

### B) Notifications (NSManagedObjectContextObjectsDidChange/DidSave)
Подходит, когда:
- не список,
- нужна реакция на сохранение/изменения.

Минусы:
- приходится самому решать:
  - что именно поменялось,
  - как обновлять UI (дифф/перестроение).

### C) Combine (через обёртки)
Combine сам по себе Core Data не “магически” делает реактивной.
Обычно:
- обёртка поверх notifications или FRC,
- или отдельный слой store, который публикует state.

## 2) Realm: наблюдение изменений
### A) Results + notifications
`Results` ленивый и “живой”:
- при коммите write транзакции подписчики получают изменения.

Плюсы:
- просто организовать реактивное обновление,
- изменения можно получать как “change set”.

Минусы:
- thread confinement:
  - наблюдать и использовать результаты нужно на корректном потоке,
- при частых массовых изменениях можно получить много уведомлений и лаги.

### B) Наблюдение отдельных объектов
Удобно для detail screen:
- объект “сам обновился” — UI может подтянуть новое.

Риск:
- если объект удалён/изменён, нужно корректно обработать состояние.

## 3) Сравнение по типичным кейсам
### UIKit список с анимациями
- Core Data: FRC часто самый надёжный путь.
- Realm: можно, но нужно аккуратно применять changeset (и следить за main thread обновлениями).

### SwiftUI
- Realm часто используют через wrapper/observed results,
- Core Data — через @FetchRequest.
Но если нужна сложная логика состояния, лучше:
- отдельный store/view model, а БД — только источник данных.

### Diffable Data Source
- Core Data:
  - FRC + адаптер в snapshot,
  - или вручную строить snapshot по fetch’у.
- Realm:
  - snapshot строить из Results,
  - изменения применять батчами.

## 4) Где чаще ошибаются
Core Data:
- наблюдают на фоне и обновляют UI не на main,
- забывают merge изменений в viewContext → FRC “не видит” обновления,
- делают fetch слишком широким → лишние обновления.

Realm:
- забывают invalidировать token (утечки),
- подписки живут дольше экрана,
- много мелких транзакций → много нотификаций,
- пытаются использовать Results/Objects на другом потоке.

## 5) Практические правила, которые показывают “senior уровень”
- Наблюдение должно быть связано с жизненным циклом экрана (token/observer cleanup).
- UI обновления — на main.
- Массовые изменения:
  - Core Data: batch updates + корректный merge,
  - Realm: батчить изменения в одну транзакцию, где возможно.
- На границе domain/presentation лучше отдавать value models, а не “живые” объекты БД.

## 6) Формулировка на собесе
“Для UIKit списков в Core Data я чаще использую NSFetchedResultsController — он даёт granular updates и секции. В Realm наблюдение строится вокруг live Results и notifications, но там важны thread confinement и контроль notification storm. Для более сложных UI (diffable/SwiftUI) часто делаю слой store/VM, а БД выступает источником данных.”

**Самопроверка**
- Оспорено: “Realm автоматически решит обновления UI” — без контроля транзакций и жизненного цикла подписок легко получить лаги и утечки.
- Неочевидно: FRC — сильный инструмент, но он привязан к UIKit-паттерну; для современных архитектур может понадобиться адаптация.
- Источники, которые стоит освежить: NSFetchedResultsController patterns, Core Data merge notifications, Realm change notifications и threading best practices, стратегии батчинга обновлений для diffable.


### Q188 (🟠): Как устроено кэширование и “живые” объекты: faulting в Core Data vs live objects в Realm — какие баги и утечки это провоцирует?

**Кратко**
- **Core Data faulting**:
  - объект может быть “пустой оболочкой” (fault) до обращения к данным,
  - это экономит память и ускоряет выборки,
  - но провоцирует неожиданные I/O и “fault storms”.
- **Realm live objects**:
  - выборки/объекты “живые” и обновляются при коммитах,
  - это удобно для реактивного UI,
  - но провоцирует “notification storms”, утечки токенов наблюдения и проблемы с долгоживущими ссылками.
- Общая мысль: оба механизма — это “ленивость + кэш”, и оба требуют дисциплины.

**Развёрнуто**
## 1) Core Data faulting: что это и зачем
### Что такое fault
Fault — это “placeholder” managed object:
- у него есть identity,
- но данные ещё не загружены.

Загрузка происходит:
- при доступе к свойствам,
- при проходе по отношениям.

Плюсы:
- экономия памяти,
- быстрые fetch’и больших графов (пока не трогаешь всё подряд).

### Баги/проблемы от faulting
1) **Fault storm**
- UI или бизнес-логика начинает массово “трогать” свойства/отношения,
- Core Data вынуждена подгружать множество объектов,
- результат — лаги/пики памяти/диск I/O.

2) **N+1 запросы через relationships**
- пробежались по списку и для каждого item залезли в relationship → каскад подгрузок.

3) **Неожиданный I/O на main thread**
- обращение к свойству в UI может вызвать обращение к store.

### Как это лечить
- `fetchBatchSize`,
- `relationshipKeyPathsForPrefetching` (prefetch),
- проектировать fetch так, чтобы UI не “вытягивал” граф глубже нужного,
- не делать тяжёлые обходы графов на main.

## 2) Realm live objects: что это и зачем
### Что значит “live”
`Results` и объекты:
- отражают актуальное состояние БД,
- после commit транзакции подписчики получают обновления.

Плюсы:
- удобно для UI,
- меньше ручной синхронизации данных.

### Баги/проблемы от live objects
1) **Notification storms**
- много мелких write транзакций,
- много подписок,
- частые пересчёты UI → лаги.

2) **Утечки наблюдений**
- забыли invalidate notification token,
- подписка живёт дольше экрана,
- удерживает объекты/замыкания → memory leak.

3) **Долгоживущие ссылки**
- UI держит ссылку на объект/Results, который часто меняется:
  - неожиданные апдейты,
  - race-like эффекты в логике (не data race, но “данные поменялись под ногами”).

4) **Thread confinement ошибки**
- объект “живой”, но привязан к потоку → краш при неправильном доступе.

### Как это лечить
- батчить изменения (одна транзакция вместо 100),
- минимизировать число подписок,
- чётко привязать жизненный цикл token к экрану,
- в presentation слое использовать value snapshots, если нужен стабильный “снимок” состояния,
- для передачи между потоками использовать ThreadSafeReference/freezing/value copies.

## 3) Как сравнить подходы (в двух словах)
- Core Data:
  - лениво грузит данные из store,
  - проблемы чаще про **неожиданные fetch’и** и **N+1**.
- Realm:
  - данные “живые” и пушатся изменениями,
  - проблемы чаще про **частоту обновлений** и **жизненный цикл подписок**.

## 4) Как объяснить на собесе
“Faulting в Core Data экономит память, но если в UI начать трогать глубоко relationships — получишь fault storms и I/O на main; лечится batching/prefetch и аккуратным fetch-дизайном. В Realm объекты live: удобно, но при частых мелких транзакциях и множестве подписок получаются notification storms и утечки токенов; лечится батчингом, правильным lifecycle и иногда value snapshots.”

**Самопроверка**
- Оспорено: “faulting/live — это всегда плюс” — это плюс только при дисциплине; иначе это источник скрытых лагов и утечек.
- Неочевидно: самые тяжёлые баги обычно не в “самой БД”, а в неправильном паттерне доступа (UI провоцирует I/O или подписки провоцируют шторм).
- Источники, которые стоит освежить: Core Data fetchBatchSize/prefetch/faulting docs, Realm notifications/token lifecycle, практики batching writes и построения UI snapshots.


### Q189 (🔴): Как обеспечить консистентность данных при конкурентных изменениях: конфликты, merge policies, версионирование, last-write-wins vs доменные правила? (Core Data + Realm)

**Кратко**
- Консистентность = **чёткие правила**, кто может писать, как решать конфликты и как не терять смысл данных.
- Типовые стратегии:
  1) **один writer** (serial queue / actor / single write context),
  2) optimistic concurrency: **versioning + conflict resolution**,
  3) deterministic merge: **доменные правила** вместо “кто последний — тот прав”.
- Core Data: merge policies + constraints + правильная модель контекстов.
- Realm: write транзакции + сериализация writes + доменные версии/идемпотентность на уровне модели/синка.

**Развёрнуто**
## 1) Сначала прояснить: “какая конкурентность”?
Есть два разных мира:
1) **Локальная конкурентность** (внутри устройства):
- UI и background синк пишут одновременно.
2) **Распределённая конкурентность** (локально vs сервер/другие устройства):
- офлайн-изменения, конфликт при синке.

Обе требуют стратегии, но инструменты разные.

## 2) Базовый приём: Single-writer
Самый практичный способ избежать хаоса:
- все записи идут через один “канал”:
  - serial queue,
  - actor,
  - “writer context”.

Плюсы:
- проще reasoning,
- меньше конфликтов,
- легче тестировать.

Минусы:
- нужна архитектура очереди/операций и приоритизация.

## 3) Core Data: локальные конфликты и merge policies
### A) Почему вообще возникают конфликты
- два контекста изменили один и тот же объект,
- затем оба попытались сохранить/мерджить.

### B) Merge policies (идея)
Политики определяют, “чья версия победит”:
- store-trump (store выигрывает),
- object-trump (in-memory выигрывает),
- и другие варианты.

Проблема last-write-wins:
- может терять данные (перетирание изменений).

### C) Лучшие практики для Core Data
- минимизировать параллельные writers:
  - один background writer context,
  - viewContext — в основном чтение.
- при конфликтах:
  - не “сваливаться” в last-write-wins,
  - по возможности применять доменные правила:
    - например, “объединить коллекции”, “суммировать счётчики”, “выбрать max(updatedAt)”.

### D) Constraints и уникальность
- использовать уникальные constraints там, где это важно,
- обрабатывать conflicts как доменные события (“уже существует”).

## 4) Realm: что даёт модель транзакций (и что не даёт)
Realm write транзакции:
- атомарны внутри одного realm instance,
- но **не решают автоматически** конфликты бизнес-значений.

Локально:
- чаще решается “single writer”:
  - все writes на одной очереди/actor,
  - UI отправляет intents/commands.

При синке:
- нужны версии/операции:
  - `updatedAt`,
  - `version`,
  - или CRDT/операционный подход (если очень сложно).

## 5) Версионирование и optimistic concurrency
### Зачем
Чтобы не перетирать изменения “вслепую”.

Типовой механизм:
- у сущности есть `version` (int) или `etag`.
- при сохранении:
  - если версия на стороне хранилища/сервера изменилась — конфликт.

Дальше:
- применяем conflict resolution:
  - last-write-wins (простое, но опасное),
  - merge по полям,
  - доменная логика (например, “статус можно только повышать по уровню”).

## 6) Доменные правила vs last-write-wins
Last-write-wins годится для:
- неважных данных (например, lastOpenedAt),
- кешей,
- некоторых UI-настроек.

Доменные правила нужны для:
- денег/заказов/энтitlements,
- счетчиков/инвентаря,
- любых данных, где “перетёрли” = “потеряли смысл”.

Пример:
- два изменения списка:
  - LWW удалит одно из них,
  - доменная логика объединит операции (add/remove) в правильном порядке.

## 7) Архитектурный вывод
Консистентность обеспечивается не “настроечкой БД”, а:
- дизайном write-path:
  - intents → serial обработчик → транзакция,
- явными правилами конфликтов,
- идемпотентностью операций,
- тестированием конфликтных сценариев.

## 8) Формулировка на собесе
“Я стараюсь избегать локальных конфликтов через single-writer подход (actor/serial queue или writer context). В Core Data — правильная схема контекстов и merge policies; в Realm — write транзакции, но с сериализацией writer’а. Если конфликты всё же возможны (особенно при синке), добавляю версии/updatedAt и применяю доменные conflict rules вместо last-write-wins для критичных данных.”

**Самопроверка**
- Оспорено: “merge policy решит всё” — merge policy часто просто выбирает победителя, но не сохраняет смысл доменных данных.
- Неочевидно: single-writer сильно упрощает локальную консистентность, но для distributed sync всё равно нужен versioning/операции.
- Источники, которые стоит освежить: Core Data merge policies и constraints, patterns single-writer (actor/queue), optimistic concurrency (version/etag), conflict resolution стратегии (field merge, domain rules, CRDT основы для сложных кейсов).



### Q190 (🔴): Как делать безопасные миграции: Core Data lightweight/heavyweight vs Realm migration blocks — как избежать потери данных и “неподдерживаемых” схем?

**Кратко**
- Безопасная миграция = **версионирование + обратная совместимость по пути обновления + тестирование long-jump**.
- Core Data:
  - **lightweight** — простые изменения (добавили поля/отношения, переименования через mapping),
  - **heavyweight** — сложные трансформации (split/merge сущностей, изменение структуры данных).
- Realm:
  - `schemaVersion` + migration block с явной логикой преобразования.
- Главные правила:
  1) миграции должны работать для апдейта через несколько версий,
  2) данные не удалять “потому что не получилось” (если это не кеш),
  3) для больших изменений — двухшаговая стратегия (expand → migrate → contract).

**Развёрнуто**
## 1) Что значит “безопасная миграция”
- Пользователь обновляется с версии N-k, не только с N-1.
- Миграция:
  - не падает,
  - не теряет данные,
  - не делает приложение непригодным (например, бесконечный краш на старте).

Безопасность = инженерный процесс, а не “галочка”.

## 2) Core Data: lightweight migration
### Когда работает
- добавили optional attribute,
- добавили новую entity,
- добавили relationship,
- простое переименование (если настроен mapping).

### Почему перестаёт хватать
- нужно преобразовать данные (тип/формат),
- нужно объединить/разделить сущности,
- нужно пересчитать поля по правилам,
- нужно изменить кардинальность отношений так, что “старые данные” не ложатся.

### Практика
- включить автоматическую миграцию (где уместно),
- но иметь план B, если lightweight не справится.

## 3) Core Data: heavyweight migration
### Когда нужна
- “структурные” изменения модели с трансформацией данных:
  - split entity на две,
  - merge нескольких сущностей,
  - изменение ключевых relationships,
  - перерасчёт и нормализация.

### Риски
- сложнее поддерживать,
- ошибки проявляются у пользователей long-jump апдейтов.

### Как уменьшить риск
- минимизировать объём преобразований за релиз,
- делать двухшаговые релизы:
  1) добавить новые поля/таблицы (expand),
  2) заполнить их (migrate),
  3) удалить старые позже (contract).

## 4) Realm: migration blocks
Realm требует:
- `schemaVersion` увеличивать при каждом изменении схемы,
- migration block описывает преобразования:
  - для каждой версии/диапазона версий.

Риск:
- забыть обработать древнюю версию → краш у пользователя, который обновился “сильно позже”.

Практика:
- писать миграции так, чтобы они были совместимы “цепочкой”:
  - `if oldSchemaVersion < 5 { ... }`
  - `if oldSchemaVersion < 8 { ... }`

## 5) Типичные техники предотвращения потери данных
- использовать значения по умолчанию,
- делать новые поля optional на первом шаге, а обязательными — позже,
- переносить данные в новые структуры, а старые поля удалять только в следующем релизе,
- при проблемах — “fail closed”:
  - лучше показывать ошибку и предложить восстановление/саппорт, чем silently wipe.

Если данные — кеш:
- можно безопасно пересоздавать store, но это должно быть осознанно и отдельно от “данных пользователя”.

## 6) Тестирование миграций
Обязательные тесты:
- апдейт N-1 → N,
- апдейт N-5 → N (long-jump),
- большие базы (stress),
- миграции + последующие операции чтения/записи.

Техника:
- хранить “golden” базы прошлых версий в тестовых ресурсах и прогонять апгрейд.

## 7) Операционные детали (что часто забывают)
- миграция может занять время → нужен план UX:
  - показать прогресс/лоадер,
  - не делать это на main thread,
  - не блокировать UI без обратной связи.
- хранение backup перед крупной миграцией (в некоторых сценариях).

## 8) Формулировка на собесе
“Для безопасных миграций я версионирую схему и обязательно тестирую long-jump апдейты. В Core Data использую lightweight, пока изменения простые, а для трансформаций делаю heavyweight или двухшаговую миграцию (expand/migrate/contract). В Realm — schemaVersion и migration block с обработкой диапазонов версий. Данные пользователя не вайплю при ошибках (если это не кеш).”

**Самопроверка**
- Оспорено: “lightweight всегда спасёт” — при реальных эволюциях модели почти всегда наступает момент, когда нужна явная трансформация.
- Неочевидно: двухшаговые миграции — самый практичный способ снижать риски больших изменений, особенно при большом числе пользователей и долгих апдейтах.
- Источники, которые стоит освежить: Core Data migration (lightweight/heavyweight, mapping models), Realm migration docs, стратегии expand/migrate/contract, техники тестирования миграций с “golden stores”.


### Q191 (🔴): Как проектировать offline-first + sync поверх локальной БД: outbox, идемпотентность, конфликт-резолюция, дедуп — и как это ложится на Core Data/Realm?

**Кратко**
- Offline-first = локальная БД — **источник правды**, сервер — синхронизатор.
- Архитектурный минимум:
  1) **Local store** (Core Data/Realm),
  2) **Outbox** (очередь локальных операций),
  3) **Sync engine** (push/pull),
  4) **Idempotency** (операции можно повторять без вреда),
  5) **Conflict resolution** (доменные правила),
  6) **Dedup** (по operationId, entityVersion, server ids).
- Core Data/Realm — это реализация local store; сложность синка живёт поверх них.

**Развёрнуто**
## 1) Сразу исправим предпосылку: “синк = просто загрузить/выгрузить”
Нет. Реальный синк — это:
- нестабильная сеть,
- повторы,
- частичные успехи,
- конкурентные изменения,
- ограничения iOS background.

Поэтому дизайн должен быть:
- повторяемым (идемпотентным),
- восстанавливаемым,
- наблюдаемым.

## 2) Модель данных для синка
Нужно хранить (минимально):
- `serverId` (если есть),
- `localId`,
- `updatedAt` или `version`,
- `syncState` (synced/pending/failed),
- иногда `deletedAt` (tombstone) вместо физического удаления.

### Tombstones
Удаление офлайн:
- если просто удалить запись, сервер может не узнать.
Решение:
- tombstone (пометка удаления) или outbox operation “delete”.

## 3) Outbox pattern: ядро offline-first
Outbox — таблица/коллекция операций:
- create/update/delete,
- payload (что менять),
- `operationId` (UUID),
- `createdAt`, `retryCount`, `state`,
- зависимость от других операций (если нужно).

Почему outbox важен:
- операции можно повторять после падения приложения,
- можно гарантировать порядок (там, где нужно),
- можно делать backoff и дедуп.

Где хранить:
- в той же БД (Core Data entity / Realm Object).

## 4) Idempotency и дедуп
### Идемпотентность
Операция должна безопасно выполняться повторно:
- сетевой слой отправляет `Idempotency-Key`/operationId,
- сервер возвращает тот же результат при повторе,
- локально мы отмечаем operation как applied.

### Dedup
Нужен на 2 уровнях:
- **операции**: не применять одну и ту же дважды,
- **данные**: не создавать дубль сущности при повторном create.

Техники:
- unique constraints по `serverId`,
- сопоставление `localId ↔ serverId`,
- operation log с “appliedOperationIds”.

## 5) Conflict resolution: где живёт и как устроить
Конфликт = два источника изменили одну сущность.

Стратегии:
- last-write-wins (быстро, но теряет смысл),
- merge по полям,
- доменная стратегия (“статус можно только повышать”, “количество = сумма дельт”).

Важно:
- конфликт-резолюция должна быть детерминированной.
Где жить:
- в sync engine / domain layer, не в UI.

## 6) Pull vs Push и порядок
Обычно:
- push outbox (локальные операции),
- pull изменения с сервера (delta),
- применить pull, возможно создав новые outbox операции/resolve conflicts.

Порядок важен:
- если pull применить до push — можно потерять локальные изменения или сложнее резолвить.
Но “правильный” порядок зависит от домена.

## 7) Ограничения iOS (background)
- фон ограничен по времени,
- network может быть прерван,
- sync должен уметь:
  - паузиться,
  - продолжаться,
  - быть “chunked”.

Практика:
- синк небольшими батчами,
- сохранять прогресс (cursor/lastSyncToken),
- экспоненциальный backoff,
- уважать battery/network conditions.

## 8) Как это ложится на Core Data vs Realm
### Core Data
- local store = entities + контексты (writer context),
- outbox entity живёт рядом,
- применять pull удобно batch-операциями,
- важно правильно делать merge, чтобы UI обновлялся.

### Realm
- local store = live objects,
- outbox = realm objects,
- writes через транзакции,
- важно батчить, иначе notification storm.

Главное:
- синк дизайн одинаковый, различается техника commits/наблюдения.

## 9) Формулировка на собесе
“Offline-first строю через local store как SSOT и outbox. Любое локальное изменение записываю как доменную операцию в outbox и применяю локально, затем sync engine пушит outbox с idempotency keys и ретраями, а pull подтягивает дельты. Конфликты решаю доменными правилами на уровне sync engine. Dedup делаю по operationId и unique constraints по serverId. Core Data/Realm — это реализация local store; важнее архитектура writer-path и батчинг.”

**Самопроверка**
- Оспорено: “синк — это просто ‘отправить изменения’” — без outbox/идемпотентности/дедупа получишь дубли и потерю данных при повторах.
- Неочевидно: tombstones и операция delete — критичны для офлайн удаления, иначе удаление теряется.
- Источники, которые стоит освежить: Outbox pattern, idempotency keys на API, стратегии conflict resolution (LWW vs domain merge), iOS background execution (BGTaskScheduler), Core Data batch operations и Realm write batching.


### Q192 (🔴): Как расследовать и чинить performance проблемы: Core Data (fault storms, fetch tuning, batch updates) vs Realm (large Results, notification storms, memory spikes)?

**Кратко**
- Сначала измеряем: где время/память (Instruments).
- Core Data:
  - проблемы часто из-за fetch’ей и отношений: **fault storms**, **N+1**, отсутствие batching/prefetch,
  - лечится: `fetchBatchSize`, `prefetch`, `propertiesToFetch`, batch operations, перенос работы с main.
- Realm:
  - проблемы часто из-за “живости”: **large Results**, **notification storms**, большие write транзакции и память,
  - лечится: батчинг транзакций, сокращение подписок, snapshot/value models, ограничение объёма данных в UI.
- Главная цель: минимизировать работу на main и объём данных, который “видит” UI.

**Развёрнуто**
## 1) Диагностика: порядок действий, чтобы не гадать
### Шаг 1: воспроизведение и сценарий
- один конкретный экран/флоу,
- фиксируем входные данные (размер базы, количество записей).

### Шаг 2: инструменты
- Time Profiler,
- Allocations / Leaks,
- Core Animation (FPS),
- для Core Data:
  - включить SQL debug/logging (в dev),
  - смотреть частоту fetch’ей,
- для Realm:
  - смотреть частоту write транзакций и уведомлений, объём коллекций.

### Шаг 3: классификация проблемы
- CPU bound (тяжёлые вычисления/маппинги),
- I/O bound (подгрузки из store),
- main-thread bound (всё происходит на main),
- memory bound (пики памяти, удержания, утечки).

## 2) Core Data: типовые причины и фиксы
### A) Fault storms / N+1
Симптомы:
- скролл лагает,
- CPU/I/O всплески при отображении списка,
- много маленьких fetch’ей.

Причины:
- для каждого cell трогаем relationship или computed, который вызывает fetch,
- отсутствие prefetch.

Фиксы:
- `fetchBatchSize`,
- `relationshipKeyPathsForPrefetching`,
- строить view models из ограниченного набора полей (не тянуть весь граф).

### B) Fetch tuning
Инструменты:
- `fetchLimit`, `fetchOffset` (пагинация),
- `propertiesToFetch` / `resultType` (когда уместно),
- корректные индексы/constraints (по полям фильтра).

### C) Сохранения и merge
Симптомы:
- фризы на `save()`/merge,
- лаги после синка.

Фиксы:
- писать на background context,
- batch updates/deletes, где можно,
- контролировать merge в viewContext (не мерджить огромные изменения на main одним куском, если можно chunk).

## 3) Realm: типовые причины и фиксы
### A) Large Results и тяжёлый UI
Симптомы:
- список тяжёлый уже при построении snapshot,
- память растёт при пролистывании.

Причины:
- results без limit/filter,
- UI строит snapshot из тысяч объектов сразу,
- много связанных объектов подтягивается “по пути”.

Фиксы:
- строгие query (filter/sort/limit),
- пагинация/инкрементальная подгрузка,
- превращать в lightweight view models для UI.

### B) Notification storms
Симптомы:
- после синка UI начинает дергаться,
- частые перерисовки, spike CPU.

Причины:
- много мелких write транзакций,
- много подписок (каждая даёт обновления),
- подписки живут дольше нужного.

Фиксы:
- батчить write транзакции (одна транзакция на батч),
- уменьшить число подписок,
- подписываться на “верхний” Results, а не на каждый элемент,
- корректно инвалидировать token при уходе экрана.

### C) Memory spikes
Причины:
- большие транзакции на main,
- удержание объектов/Results в долгоживущих структурах,
- построение массивов из больших results.

Фиксы:
- работать потоково (chunk),
- не материализовать всё в массив, если не надо,
- сбрасывать references, использовать автопулы на импортах (где применимо).

## 4) Общая архитектурная профилактика
- Single-writer path (actor/serial queue) для записей и синка.
- UI слой получает “готовые” данные (view models), а не живой граф.
- Синк и тяжёлые маппинги — не на main.
- Пагинация и ограничения выборок по умолчанию.
- Наблюдение привязано к lifecycle экрана.

## 5) Как отвечать на собесе
“Я начинаю с измерений в Instruments и фиксирую сценарий. В Core Data чаще лечу fault storms и N+1 через batching и prefetch, а также выношу save/merge на фон. В Realm борюсь с large Results и notification storms: батчу транзакции, сокращаю подписки, строю UI snapshot из ограниченного набора данных. В обоих случаях цель — минимизировать работу на main и объём данных, который обновляет UI.”

**Самопроверка**
- Оспорено: “проблема в Core Data/Realm как технологии” — чаще проблема в паттернах доступа (UI провоцирует I/O или шторм уведомлений).
- Неочевидно: оптимизация обычно требует ограничивать объём данных (limit/filter/pagination) и менять границы ответственности (view models vs live objects).
- Источники, которые стоит освежить: Instruments workflows, Core Data fetch tuning (batching/prefetch), Realm notifications best practices, общие принципы performance для scrolling UI.


### Q193 (🔴): Как решать безопасность локальных данных: Data Protection, Keychain, шифрование Realm, угроз-модель, wipe/logout, бэкапы — что реально защищает и от чего?

**Кратко**
- Сначала определить **угроз-модель**: от кого защищаемся (случайный доступ, украденный телефон, джейлбрейк, forensic, бэкапы).
- Инструменты iOS:
  - **Data Protection** (классы защиты файлов) — защита данных “на диске” при заблокированном устройстве.
  - **Keychain** — хранение секретов с доступом по политикам (биометрия, whenUnlocked и т.п.).
  - **Realm encryption** — шифрование файла Realm (ключ хранить в Keychain).
- Важно:
  - шифрование ≠ защита от всего,
  - на джейлбрейке/скомпрометированном устройстве гарантий почти нет,
  - нужен безопасный wipe при logout и продуманная политика бэкапов.

**Развёрнуто**
## 1) Угроз-модель (без неё разговор бессмысленный)
Типовые угрозы:
1) Потерян/украден телефон, устройство заблокировано.
2) Доступ к резервной копии (iTunes/iCloud backup).
3) Устройство разблокировано (злоумышленник получил доступ к UI).
4) Jailbreak/рут (компрометированная ОС).
5) Логи/аналитика/крэш-репорты утекли с PII.

Разные угрозы → разные меры.

## 2) Data Protection: что даёт
Data Protection — это про шифрование данных на диске ключами, связанными с passcode и состоянием блокировки.
Практика:
- файлы в Documents/Library могут иметь protection class.
Основные классы (смысл):
- **Complete**: доступ только когда устройство разблокировано.
- **UntilFirstUserAuthentication**: доступ после первого разблокирования после ребута.
- **None**: доступ всегда.

Что защищает:
- от чтения файлов с заблокированного устройства (при корректном passcode/secure enclave сценарии).

Что не защищает:
- от доступа, когда устройство уже разблокировано,
- от логических утечек (экспорт, шаринг),
- от джейлбрейка/forensic высокого уровня (частично).

## 3) Keychain: где он обязателен
Keychain хранит:
- токены, refresh токены,
- ключи шифрования,
- приватные идентификаторы.

Плюсы:
- защищён OS-level политиками,
- можно настраивать доступ:
  - whenUnlocked / afterFirstUnlock,
  - require biometry, etc.

Ошибка:
- хранить токены в UserDefaults или в файле.

## 4) Шифрование Realm (и что с Core Data)
### Realm encryption
- Realm поддерживает шифрование файла ключом.
Ключ:
- должен храниться в Keychain,
- генерируется один раз,
- нельзя логировать/экспортировать.

Что даёт:
- даже если файл Realm вытащили, без ключа он бесполезен.

Что не даёт:
- если злоумышленник получил ключ (компрометированное устройство) — защита падает.

### Core Data
Core Data поверх SQLite можно защищать:
- Data Protection на уровне файла store,
- или применять шифрование SQLite через сторонние решения (например, SQLCipher), но это усложняет поддержку.
Часто:
- Data Protection + минимизация PII + правильные политики бэкапа.

## 5) Бэкапы и политика хранения
Опасность:
- данные могут попасть в iCloud/iTunes backup.

Решения:
- для чувствительных данных:
  - не хранить их в бэкапируемых местах,
  - использовать “do not backup” атрибут для кешей/временных данных,
  - хранить секреты только в Keychain (он ведёт себя иначе, но нужно понимать синк-ключейн и политики).

Важно:
- “не бэкапить” подходит для кешей и данных, которые можно восстановить,
- для пользовательских данных нужно оценить UX/требования.

## 6) Wipe/logout: что означает “удалить данные”
Logout должен быть атомарным:
- удалить токены из Keychain,
- остановить синк/фоновые операции,
- удалить/очистить локальные БД и кэши (account-scoped),
- удалить файлы пользователя (если бизнес-логика требует),
- сбросить in-memory caches.

Ловушка:
- стерли токен, но оставили БД → пользователь сменил аккаунт и видит чужие данные.

## 7) Практики “не светить PII”
- минимизировать PII в локальном сторе,
- редактировать/маскировать логи,
- в аналитике и crash reports — privacy redaction,
- не хранить лишнего (data minimization).

## 8) Честный ответ про “абсолютную безопасность”
Если устройство скомпрометировано (jailbreak/рут):
- гарантировать безопасность почти невозможно.
Можно:
- усложнить атаку (encryption keys in Keychain, anti-tamper, jailbreak detection),
- но это не серебряная пуля.

## 9) Формулировка на собесе
“Я начинаю с угроз-модели. Секреты и ключи — в Keychain. Файлы и stores защищаю Data Protection классами; для Realm можно включить file encryption, а ключ хранить в Keychain. Продумываю политику бэкапов: кеши исключаю, чувствительные данные минимизирую. Logout/wipe — атомарно: токены, scoped storage, файлы, остановка фоновых задач. Понимаю, что на джейлбрейке абсолютной защиты нет.”

**Самопроверка**
- Оспорено: “шифрование БД решает всё” — без угроз-модели и управления ключами это ложное чувство безопасности.
- Неочевидно: главный риск часто не “вытаскивание файла БД”, а бэкапы, логи и неправильный logout/switch-account.
- Источники, которые стоит освежить: Apple docs по Data Protection и File Protection attributes, Keychain item accessibility, Realm encryption docs, iOS backup exclusion attributes, практики privacy redaction.

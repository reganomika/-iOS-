## Многопоточность

### Q47 (🟢): Что такое race condition?

**Кратко**
- Race condition — баг, когда результат зависит от **недетерминированного порядка** выполнения нескольких потоков/задач.
- Часто проявляется при доступе к общему состоянию без синхронизации: иногда “работает”, иногда ломается.
- Не равно data race: race condition шире (может быть и без одновременной записи в память), а data race — конкретно про небезопасные конкурентные обращения к одним и тем же данным.

**Развёрнуто**
Race condition — это ситуация, когда корректность логики зависит от того, “кто успел первым”. Поскольку планировщик, очереди и задержки не детерминированы, поведение становится нестабильным.

## 1) Типичный пример
Есть общий счётчик и две задачи, которые его увеличивают:

```swift
final class Counter {
    var value = 0
}

let counter = Counter()
let queue = DispatchQueue.global(qos: .userInitiated)

for _ in 0..<1_000 {
    queue.async {
        counter.value += 1 // ❌ небезопасно без синхронизации
    }
}
```

Ожидание: `value == 1000`. Реальность: часто меньше, иногда совпадает. Итог зависит от гонки между задачами.

Почему так:
- `counter.value += 1` не атомарно: это read → add → write.
- Две задачи могут прочитать одно и то же старое значение и записать одинаковый результат.

## 2) Race condition vs data race
- **Data race**: конкурентный доступ к одной области памяти, где хотя бы одна операция — запись, и нет синхронизации → undefined/неопределённое поведение.
- **Race condition**: логическая гонка, когда порядок событий важен. Она может быть:
  - data race (часто),
  - или “высокоуровневая” гонка (например, “запрос A пришёл позже запроса B и перезатёр UI”, даже если доступ к памяти синхронизирован).

## 3) Как предотвращать
- Делать общий state неизменяемым (immutable) или изолировать (actor).
- Защитить доступ:
  - serial queue,
  - locks (`NSLock`, `os_unfair_lock`),
  - atomic operations,
  - акторы (structured concurrency).
- Для UI: обновлять состояние на `MainActor`/main queue, чтобы избежать гонок между потоками.

## 4) Как поймать
- Thread Sanitizer (TSAN) — лучший для data races.
- Инварианты + стресс-тесты + искусственные задержки (`usleep`, `Task.sleep`) для воспроизведения.

**Самопроверка**
- Оспорено: “race condition = data race” — data race частный случай; race condition шире.
- Неочевидно: “иногда работает” не значит “нет бага” — гонки часто маскируются в debug/на быстрых девайсах.
- Источники: материалы Apple по Thread Sanitizer, docs по Swift Concurrency/actors, базовые определения race/data race в CS.

### Q48 (🟢): Что такое дедлок?

**Кратко**
- Дедлок (deadlock) — состояние, когда несколько потоков/задач **навсегда ждут друг друга**, и прогресс невозможен.
- Классика: взаимная блокировка двух locks или синхронный вызов на очередь, которая уже занята текущей задачей.
- Отличие от race condition: при дедлоке система “застывает”, при гонке результат просто становится недетерминированным.

**Развёрнуто**
Дедлок — частный случай проблем синхронизации, когда возникает цикл ожиданий: каждый участник ждёт ресурс, который удерживает другой.

## 1) Пример с двумя locks (AB/BA)
```swift
let lockA = NSLock()
let lockB = NSLock()

DispatchQueue.global().async {
    lockA.lock()
    Thread.sleep(forTimeInterval: 0.1)
    lockB.lock()              // ждёт B
    lockB.unlock()
    lockA.unlock()
}

DispatchQueue.global().async {
    lockB.lock()
    Thread.sleep(forTimeInterval: 0.1)
    lockA.lock()              // ждёт A
    lockA.unlock()
    lockB.unlock()
}
```
Если первая задача удерживает A и ждёт B, а вторая удерживает B и ждёт A — обе ждут бесконечно.

## 2) Классический GCD-дедлок: sync на ту же serial queue
```swift
let serial = DispatchQueue(label: "serial")

serial.async {
    serial.sync {
        print("never")
    }
}
```
Внешний блок занял serial queue. Внутренний `sync` ждёт, пока очередь выполнит вложенный блок — но она не может, потому что занята внешним. Получаем дедлок.

Особый случай — main queue:
```swift
DispatchQueue.main.async {
    DispatchQueue.main.sync {  // ❌ дедлок
        print("never")
    }
}
```
(Если это выполняется уже на main thread/выполняющемся блоке main queue.)

## 3) Условия дедлока (интервью-уровень)
Часто вспоминают “4 Coffman conditions”:
1) взаимное исключение (ресурс не делится),
2) hold and wait (держим один ресурс и ждём другой),
3) no preemption (нельзя отнять ресурс принудительно),
4) circular wait (циклическое ожидание).
Если все четыре выполнены — дедлок возможен.

## 4) Как предотвращать
- Единый порядок захвата locks (всегда A→B, никогда B→A).
- Минимизировать время удержания lock.
- Избегать `dispatchSync` на той же serial queue/main queue.
- Использовать higher-level примитивы: serial queue вместо нескольких locks, actors вместо ручной синхронизации.
- Таймауты/tryLock (не лечат причину, но помогают не зависать навсегда).

## 5) Как диагностировать
- Признак: приложение “висит”, CPU может быть низким, main thread занят.
- Инструменты:
  - Xcode Debugger: пауза и просмотр backtrace всех потоков,
  - Instruments: Time Profiler + thread states, System Trace,
  - Main Thread Checker (частично),
  - логирование “lock acquired/released” вокруг критических секций.

**Самопроверка**
- Оспорено: “дедлок только про locks” — нет, дедлок возможен и на очередях (sync), и на семафорах, и на ожидании ресурсов.
- Неочевидно: наличие дедлока может проявляться как “иногда зависает” из-за гонки по времени; воспроизводимость часто улучшается искусственными задержками.
- Источники: определения deadlock (Coffman conditions), документация Apple по GCD, практики отладки hangs в Xcode/Instruments.

### Q49 (🟢): Что такое livelock?

**Кратко**
- Livelock — ситуация, когда потоки/задачи **не заблокированы**, активно “работают”, но **прогресс не происходит**.
- В отличие от deadlock: при livelock участники не ждут навсегда, а постоянно реагируют друг на друга, “уступая” или повторяя попытки.
- Часто возникает при агрессивных retry/backoff без случайности или при симметричном поведении двух акторов.

**Развёрнуто**
Livelock — это “все бегают, но никто не приходит”. Система тратит CPU/ресурсы, но остаётся в той же логической точке.

## 1) Интуитивный пример (аналогия)
Два человека пытаются разойтись в коридоре:
- оба одновременно шаг влево → снова мешают,
- оба шаг вправо → снова мешают,
и так бесконечно.
Они не “застряли” как в deadlock, они двигаются, но не продвигаются.

## 2) Пример в коде: симметричные tryLock + “уступи”
```swift
let lockA = NSLock()
let lockB = NSLock()

func worker() {
    while true {
        if lockA.try() {
            if lockB.try() {
                // сделали работу
                lockB.unlock()
                lockA.unlock()
                break
            } else {
                lockA.unlock()
                // "вежливо уступили" и сразу пробуем снова
            }
        }
    }
}
```

Если два потока выполняют одинаковую логику синхронно и постоянно “уступают” одновременно, они могут бесконечно мешать друг другу. Это livelock.

## 3) Чем отличается от starvation
- Livelock: активное взаимное “мешание” участников, они постоянно предпринимают действия.
- Starvation: один участник долго не получает ресурс из-за приоритета/схемы планирования, даже если другие продвигаются.

## 4) Как предотвращать
- Добавлять **jitter** (случайность) в backoff/retry:
  - экспоненциальный backoff + случайная составляющая.
- Разрывать симметрию:
  - фиксированный порядок захвата ресурсов,
  - разные стратегии для разных участников.
- Использовать примитивы более высокого уровня:
  - serial queue/actor вместо tryLock-loop.

## 5) Диагностика
- Признак: CPU может быть высоким, логика “крутится”, но результат не достигается.
- Наблюдение потоков/стеков покажет повторяющиеся участки кода (retry loops).
- Time Profiler отлично показывает “горячие” циклы без прогресса.

**Самопроверка**
- Оспорено: “если не deadlock, то всё ок” — livelock тоже критическая проблема: прогресс = 0 при активной нагрузке.
- Неочевидно: livelock часто маскируется под “периодические подвисания” и лечится не блокировками, а разрывом симметрии (jitter/backoff).
- Источники: базовые определения livelock/deadlock/starvation, практики backoff/jitter, профилирование Time Profiler.

### Q50 (🟢): Что такое starvation?

**Кратко**
- Starvation — ситуация, когда поток/задача **долго не получает** нужный ресурс/время CPU и практически не продвигается, пока другие продолжают работать.
- Причины: приоритеты, несправедливые locks, постоянная конкуренция, “вечно занятая” очередь, неправильная QoS/priority.
- Отличается от deadlock: прогресс в системе есть, но **не у голодающего** участника.

**Развёрнуто**
Starvation — это проблема справедливости (fairness). Система не “зависла”, но некоторые участники оказываются вытесненными почти бесконечно.

## 1) Типовой сценарий
Есть общий lock/ресурс, и более приоритетные/часто запускающиеся задачи постоянно забирают его, не оставляя шанса другим.

Примерно так:
- Высокоприоритетная задача часто просыпается и коротко держит lock.
- Низкоприоритетная пытается взять lock, но каждый раз её опережают.

## 2) Где встречается в iOS
- QoS/приоритеты: `.userInteractive` задачи могут вытеснять `.background`.
- OperationQueue с зависимостями и ограничением concurrency: низкоприоритетные операции могут ждать очень долго.
- Несправедливые примитивы синхронизации (unfair locks), активные spin loops.
- Приоритетная инверсия может выглядеть как starvation (и наоборот), если низкий приоритет держит ресурс, нужный высокому.

## 3) Starvation vs livelock vs deadlock
- Deadlock: никто не может продолжить (или важные участники замерли навсегда из-за цикла ожиданий).
- Livelock: все активны, но прогресса нет из-за взаимного “мешания”.
- Starvation: прогресс есть, но конкретный участник практически не получает ресурсов.

## 4) Как предотвращать
- Правильный QoS/priority: не ставить всё в `.userInteractive`.
- Ограничивать “агрессивных” производителей работы (throttling).
- Справедливые механизмы: иногда лучше serial queue, иногда fair lock.
- Уменьшать время удержания lock, разделять ресурсы, снижать contention.
- Backoff/jitter для конкурентных попыток.

## 5) Диагностика
- Симптом: часть задач “никогда не завершается” или завершается аномально долго при нагрузке.
- Инструменты:
  - Instruments (System Trace) для планирования/CPU,
  - Time Profiler для выявления горячих мест,
  - логирование времени ожидания lock/очередей,
  - `os_signpost` для измерений.

**Самопроверка**
- Оспорено: “если нет дедлока, значит нет проблем” — starvation может быть не менее критичной, особенно для фоновых задач и пайплайнов.
- Неочевидно: иногда starvation — это следствие design choice (например, всегда предпочитать UI), но если оно влияет на UX (зависшая синхронизация/сохранение), нужно менять приоритеты и архитектуру.
- Источники: определения starvation/fairness, Apple docs про QoS и планирование, Instruments System Trace/Time Profiler.

### Q51 (🟢): Что такое `MainActor` и зачем он нужен, если уже есть main queue?

**Кратко**
- `MainActor` — это **актор** в Swift Concurrency, который изолирует выполнение кода на “главном” исполнителе (обычно main thread) и даёт **compile-time гарантии** для доступа к UI/состоянию.
- Main queue (`DispatchQueue.main`) — это GCD очередь: она гарантирует порядок выполнения блоков, но **не даёт типовых/компиляторных гарантий** и не интегрирована с `await`/actor isolation так же глубоко.
- `MainActor` нужен, чтобы:
  - безопасно обновлять UI в async/await коде,
  - получать предупреждения/ошибки компилятора при доступе к main-isolated состоянию с не-main контекста,
  - корректно и удобно “перепрыгивать” на main с помощью `await`.
- В одном приложении main queue и `MainActor` сосуществуют; `MainActor` часто маппится на main queue, но семантика — про **изоляцию данных**, а не только “куда отправить блок”.

**Развёрнуто**
## 1) Главная разница: model-level гарантии vs runtime scheduling
### Main queue (GCD)
- Это очередь задач.
- Ты вручную решаешь, что надо диспатчить на main:
```swift
DispatchQueue.main.async {
    self.label.text = "Hi"
}
```
- Компилятор не мешает тебе менять UI с background thread (может поймать Main Thread Checker в рантайме, но это не строгая гарантия).

### `MainActor`
- Это часть модели structured concurrency и actor isolation.
- Помечая код `@MainActor`, ты говоришь: “этот код и это состояние доступны только через MainActor”.

```swift
@MainActor
final class ViewModel {
    var title: String = ""
    func updateUIState(_ t: String) { title = t }
}
```

Если из background Task попробовать:
```swift
func work(vm: ViewModel) async {
    vm.title = "X" // ❌ компилятор запретит: main-actor isolated
}
```

Правильно:
```swift
await MainActor.run {
    vm.title = "X"
}
```
или если `vm` уже `@MainActor`, просто `await vm.updateUIState("X")`.

## 2) Почему это важно именно с async/await
Когда ты делаешь `await`, выполнение может продолжиться на другом executor. С GCD легко ошибиться:
- часть кода до `await` на main,
- после `await` уже не на main,
и ты внезапно обновляешь UI не там.

`MainActor` делает это явно и проверяемо компилятором.

## 3) Relationship с main thread / main queue
- В большинстве iOS приложений `MainActor` исполняется на main thread.
- Но корректнее думать так: `MainActor` гарантирует **serialization и изоляцию** для main-isolated кода.
- Как именно он маппится на конкретный scheduler — деталь реализации, но для практики UI = `@MainActor`.

## 4) Типовые шаблоны
### Пометить UI слой
```swift
@MainActor
final class MyViewController: UIViewController {
    func render() { /* UI */ }
}
```

### Переключиться на main внутри фоновой работы
```swift
Task.detached {
    let data = await load()
    await MainActor.run {
        self.render(data)
    }
}
```

## 5) Подводные камни (внутри ответа, без “вне блока”)
- `@MainActor` не “ускоряет”, он ограничивает параллелизм (всё сериализуется на main).
- `Task.detached` игнорирует actor context → легко потерять main isolation, если не использовать `await MainActor.run`.
- Не стоит помечать `@MainActor` тяжёлую работу (парсинг/декодинг), иначе нагрузишь main.

**Самопроверка**
- Оспорено: “MainActor = просто sugar над DispatchQueue.main” — нет, это модель изоляции данных + интеграция с компилятором/structured concurrency.
- Неочевидно: точное соответствие MainActor ↔ main queue может меняться, но практический контракт для iOS UI стабилен: UI должен быть на main/MainActor.
- Источники: Swift Concurrency docs (Actors, Global Actors, MainActor), Apple docs/WWDC по migration to async/await, правила UIKit “main thread only”.

### Q52 (🟠): Чем отличается параллельность от конкурентности?

**Кратко**
- **Конкурентность (concurrency)** — это про *структуру* выполнения: несколько задач “продвигаются” во времени, их выполнение **перемежается** (interleaving). Может быть и на одном ядре.
- **Параллельность (parallelism)** — это про *физику* выполнения: несколько задач реально исполняются **одновременно** на разных ядрах/исполнителях.
- Конкурентность — средство управлять многими задачами, параллельность — средство ускорить выполнение за счёт одновременности.

**Развёрнуто**
## 1) Конкурентность
Если у тебя есть две задачи A и B, конкурентная система может выполнять так:
- кусочек A,
- кусочек B,
- снова A,
- снова B,
быстро переключаясь. На одном ядре это даёт иллюзию одновременности.

Это важно для:
- I/O ожиданий (сеть, диск),
- UI responsiveness,
- обслуживания множества задач.

## 2) Параллельность
Параллельность означает:
- A выполняется на ядре 1,
- B выполняется на ядре 2,
реально одновременно.

Это важно для:
- CPU-bound задач (кодирование/декодирование, обработка изображений, ML),
- сокращения общего wall-clock времени.

## 3) Связь и частые ошибки
- Можно иметь concurrency без parallelism (один core, много задач, переключения).
- Можно иметь parallelism без “сложной” concurrency (одна большая задача разложена на несколько потоков).
- Concurrency повышает риск гонок/дедлоков, если есть общий state.
- Parallelism без контроля может ухудшить производительность из-за contention/overhead.

## 4) Привязка к iOS инструментам
- GCD/OperationQueue дают concurrency и (при наличии ядер) parallelism.
- Swift structured concurrency тоже: `async let`, TaskGroup создают конкурентные задачи; реальные параллельные исполнения зависят от executor/планировщика и ресурсов.

**Самопроверка**
- Оспорено: “это одно и то же” — нет: concurrency про организацию, parallelism про одновременное исполнение.
- Неочевидно: concurrency не гарантирует ускорение; если задача CPU-bound и всё на одном executor/ядре, времени меньше не станет.
- Источники: базовые определения CS, материалы Apple про GCD/Queues и Swift Concurrency.

### Q53 (🟠): Чем отличается синхронное и асинхронное выполнение?

**Кратко**
- **Синхронно (sync)** — вызывающий поток/задача **ждёт завершения** работы, прежде чем продолжить.
- **Асинхронно (async)** — вызывающий **не ждёт**, работа выполняется позже/параллельно, а результат приходит через callback/await/notification.
- Это про *ожидание* и *временную связь*, а не обязательно про потоки: sync/async можно выполнять и на одной очереди, и на разных.

**Развёрнуто**
## 1) Синхронное выполнение
Синхронный вызов блокирует текущий поток до завершения операции:

```swift
let serial = DispatchQueue(label: "serial")

serial.sync {
    // текущий поток ждёт, пока блок выполнится
}
```

Плюсы:
- линейный, простой поток управления,
- легко писать “сверху вниз”.

Минусы:
- блокировки → риск подвисаний (особенно на main thread),
- дедлоки при неправильном использовании (`sync` на занятую serial queue).

## 2) Асинхронное выполнение
Асинхронный вызов планирует работу и сразу возвращает управление:

```swift
serial.async {
    // выполнится позже
}
print("я выполнюсь сразу")
```

Плюсы:
- не блокирует вызывающий поток,
- позволяет держать UI отзывчивым,
- удобна для I/O ожиданий.

Минусы:
- сложнее reasoning: порядок выполнения не гарантирован между независимыми задачами,
- нужны синхронизация/изоляция данных,
- появляются гонки, отмена, обработка ошибок.

## 3) Важно: sync/async ≠ serial/concurrent
- sync/async — поведение вызова (ждём/не ждём).
- serial/concurrent — свойства очереди (сколько задач она выполняет одновременно).
Можно:
- `serial.async` (часто),
- `concurrent.sync` (редко нужно, но возможно),
- `concurrent.async` (параллельная обработка).

## 4) Важно: async не гарантирует “в другом потоке”
`DispatchQueue.main.async` — это async, но всё равно выполнится на main thread.
`await` — это async стиль, но продолжение может оказаться на другом executor’е.

## 5) Swift async/await — это асинхронность без callback адa
С `async/await` ты пишешь линейно, но выполнение не блокирует поток:

```swift
func load() async throws -> Data { ... }

Task {
    let data = try await load() // поток не блокируется, задача приостанавливается
    await MainActor.run { /* update UI */ }
}
```

**Самопроверка**
- Оспорено: “async = другой поток” — нет, async значит “не ждать”; где исполнится — зависит от executor/queue.
- Неочевидно: `await` не блокирует поток, но может “разорвать” контекст выполнения; после await нельзя молча считать, что ты всё ещё на main.
- Источники: Apple docs по GCD (sync/async), Swift Concurrency docs (async/await, Task scheduling).

### Q54 (🟠): Чем отличается многопоточность от мультипроцессности?

**Кратко**
- **Многопоточность (multithreading)**: несколько потоков **внутри одного процесса**, общий адресный пространство (общая память) → быстрое взаимодействие, но риск data races.
- **Мультипроцессность (multiprocessing)**: несколько **процессов** с раздельной памятью → лучше изоляция и безопасность, но дороже обмен данными (IPC).
- В iOS приложение обычно один процесс; многопоточность — повседневная реальность (GCD, OperationQueue, Swift Concurrency executors).

**Развёрнуто**
## 1) Процесс vs поток
### Процесс
- отдельное адресное пространство (виртуальная память),
- свои ресурсы: дескрипторы, sandbox, права,
- краш процесса обычно не валит другие процессы (изолированность).

### Поток
- “линия исполнения” внутри процесса,
- все потоки процесса делят heap/глобальные данные,
- у каждого потока свой stack.

## 2) Последствия для синхронизации
Многопоточность:
- общий state доступен напрямую,
- нужны locks/actors/queues/атомики,
- легко получить data races/дедлоки.

Мультипроцессность:
- нет общего heap → меньше гонок на памяти,
- но нужно IPC:
  - XPC, sockets, shared containers, file-based обмен, etc.
- обмен дороже и требует сериализации/копирования/мэппинга.

## 3) Производительность и масштабирование
- Потоки легче процессов: дешевле создавать, переключать (обычно), проще обмениваться данными.
- Процессы тяжелее: отдельные адресные пространства, больше overhead.

Но:
- процессы могут давать лучшую устойчивость и sandbox изоляцию,
- для CPU-heavy задач параллельность возможна и там, и там, но IPC/координация разные.

## 4) Практика iOS
- UI всегда в одном процессе, main thread.
- Фоновые работы делаются через:
  - GCD/OperationQueue (потоки),
  - Swift Concurrency (таски на executors).
- Реальная мультипроцессность в iOS чаще встречается через:
  - расширения (extensions) — отдельные процессы,
  - XPC-сервисы (в macOS чаще, в iOS ограниченно),
  - system daemons.

**Самопроверка**
- Оспорено: “потоки = процессы” — нет: процессы изолируют память, потоки её разделяют.
- Неочевидно: “мультипроцессность безопаснее” — да по memory isolation, но она усложняет архитектуру и обмен данными; в iOS чаще выбирают потоки/таски.
- Источники: базовые определения OS (process/thread), Apple docs по concurrency (GCD/OperationQueue) и про app extensions (процессы).

### Q55 (🟠): Как работает GCD?

**Кратко**
- GCD (Grand Central Dispatch) — низкоуровневый механизм Apple для конкурентности: ты отправляешь блоки работы на **dispatch queues**, а система сама маппит их на **пул потоков**.
- Ключевые идеи:
  - очереди бывают serial и concurrent,
  - `async` не блокирует вызывающий поток, `sync` блокирует,
  - QoS задаёт приоритет выполнения,
  - есть dispatch groups, semaphores, barriers и work items.
- GCD обеспечивает эффективное планирование, уменьшает необходимость создавать/управлять потоками вручную.

**Развёрнуто**
## 1) Базовая модель: queue → tasks → threads
В GCD ты почти никогда не создаёшь `Thread` напрямую. Ты создаёшь задачи (blocks) и отправляешь их на очередь:

```swift
let q = DispatchQueue(label: "com.app.serial")
q.async {
    // работа
}
```

Система:
- ставит блок в очередь,
- выбирает поток из пула (или создаёт при необходимости),
- выполняет блок, соблюдая правила очереди.

## 2) Serial vs Concurrent (как это влияет на исполнение)
- **Serial queue**: выполняет задачи по одной, строго по порядку.
- **Concurrent queue**: может выполнять несколько задач одновременно (если есть ресурсы), но порядок старта/завершения может отличаться.

Важно: гарантии про порядок относятся к очереди, не к потокам.

## 3) `async` vs `sync`
- `async`: кладёт блок в очередь и возвращает управление сразу.
- `sync`: кладёт блок и **ждёт** его завершения.

```swift
DispatchQueue.global().sync {
    // текущий поток ждёт здесь
}
```

Риск: дедлок при `sync` на текущую serial queue (или на main queue, если ты уже на main).

## 4) QoS (приоритеты)
GCD планирует выполнение на основе QoS:
- `.userInteractive`, `.userInitiated`, `.utility`, `.background`, `.default`.
Это влияет на:
- приоритет CPU,
- энергопотребление,
- scheduling fairness.

## 5) Встроенные примитивы координации
- `DispatchGroup`: дождаться набора задач.
- `DispatchSemaphore`: ограничить параллелизм или синхронизировать ресурсы.
- `DispatchWorkItem`: управляемая задача (cancel/notify).
- `barrier`: эксклюзивная запись на concurrent queue (для “read-many/write-one”).
- `DispatchSource`: события (таймеры, файлы, сигналы).

## 6) “Под капотом” (интервью-уровень, без лишней магии)
- GCD управляет пулом worker threads.
- Очереди — это структуры данных, где хранятся блоки.
- Планировщик решает:
  - какой блок выполнить,
  - на каком потоке,
  - с каким приоритетом,
  - с учётом зависимости/состояния очереди и нагрузки системы.
- Конкретное число потоков не фиксировано и адаптируется системой.

## 7) Как правильно думать про GCD
- Мы проектируем **очереди и правила доступа к данным**, а не “ручное распределение по потокам”.
- Главный способ сделать код безопасным — изолировать state на serial queue, либо использовать более высокие абстракции (actors, OperationQueue).

**Самопроверка**
- Оспорено: “GCD = набор потоков” — это в первую очередь модель очередей и планирования задач; потоки — деталь исполнения.
- Неочевидно: точная политика планировщика и количество потоков зависят от ОС/нагрузки; нельзя делать предположения “всегда 4 потока”.
- Источники: Apple docs по Dispatch (GCD), материалы WWDC по concurrency/performance.

### Q56 (🟠): Что такое serial и concurrent queues?

**Кратко**
- **Serial queue** выполняет задачи **по одной** и **в порядке добавления** (FIFO для старта).
- **Concurrent queue** может выполнять **несколько задач одновременно**; порядок старта обычно FIFO, но завершение недетерминировано.
- Очередь — не поток: одна и та же очередь может исполняться на разных потоках; важны её гарантии по порядку/одновременности.

**Развёрнуто**
## 1) Serial queue
Гарантия:
- в каждый момент времени выполняется максимум **одна** задача из этой очереди.
- Это делает serial queue удобным механизмом синхронизации состояния (“изоляция вместо locks”).

```swift
let serial = DispatchQueue(label: "com.app.serial")

serial.async { print("A") }
serial.async { print("B") }
// A и B не выполнятся одновременно
```

Использование:
- защита общего mutable state без locks,
- последовательные операции, где порядок важен.

Подводный камень:
- `sync` на ту же serial queue из выполняющейся задачи → дедлок.

## 2) Concurrent queue
Гарантия:
- задачи из очереди могут выполняться параллельно (если есть ресурсы).
- Удобно для независимых работ (например, обработка элементов массива).

```swift
let concurrent = DispatchQueue(label: "com.app.concurrent", attributes: .concurrent)

for i in 0..<5 {
    concurrent.async {
        print(i)
    }
}
```

Использование:
- параллельные вычисления,
- read-heavy доступ к данным с barrier для записи.

## 3) Порядок и потоки
Важно:
- Очереди упорядочивают задачи, но не “привязаны” к одному потоку.
- На serial queue блоки могут выполняться в разных потоках, но всё равно строго последовательно.
- На concurrent queue блоки могут стартовать в порядке постановки, но завершаться в любом порядке.

## 4) Как выбирать
- Нужна последовательность/защита state → serial queue.
- Нужна параллельность для независимых задач → concurrent queue.
- Нужен “много читателей / один писатель” → concurrent queue + barrier.

**Самопроверка**
- Оспорено: “serial queue = один поток” — нет, это гарантия последовательности, а не выделенный thread.
- Неочевидно: FIFO порядок относится к постановке/старту, но реальное расписание может влиять на наблюдаемый порядок логов, особенно между разными очередями.
- Источники: Apple docs по DispatchQueue (serial/concurrent), материалы о thread pools и планировании GCD.

### Q57 (🟠): Что такое QoS и зачем он нужен?

**Кратко**
- QoS (Quality of Service) — это “класс важности” задачи: влияет на **приоритет планирования**, энергопотребление и отзывчивость.
- В GCD/OperationQueue QoS помогает системе решать, **какие задачи выполнять раньше**, какие — в фоне.
- Неправильный QoS может привести к:
  - лагам UI (если важное на low QoS),
  - прожору батареи (если всё на high QoS),
  - priority inversion (высокий ждёт низкий).

**Развёрнуто**
## 1) Зачем QoS вообще нужен
На устройстве ограниченные ресурсы: CPU, энерго-бюджет, термальный режим. QoS позволяет ОС:
- приоритизировать задачи, влияющие на UX (скролл, анимации),
- откладывать фоновые работы (индексация, синхронизация),
- уменьшать конкуренцию за CPU и избегать лишних пробуждений.

## 2) Основные классы QoS (практический смысл)
(Названия могут встречаться в GCD и `QualityOfService` у OperationQueue.)

- **userInteractive**: критично для UI, должно быть “прямо сейчас” (анимации, обработка жестов).
- **userInitiated**: пользователь инициировал действие и ждёт результата (загрузка контента для текущего экрана).
- **utility**: длительные, но важные задачи (download, парсинг больших данных), не критично мгновенно.
- **background**: фоновые задачи, пользователь прямо сейчас не ждёт (prefetch, cleanup).
- **default/unspecified**: когда не указали явно.

## 3) QoS inheritance (наследование)
В GCD QoS часто “наследуется”:
- очередь может иметь QoS,
- работа может подняться/опуститься в зависимости от контекста,
- waiting (например, синхронное ожидание) может влиять на effective QoS, чтобы уменьшать priority inversion.

Суть: QoS — не “жёсткий приоритет потока”, а сигнал планировщику.

## 4) Связь с priority inversion
Если низкий QoS держит ресурс (lock), который нужен высокому QoS:
- высокий ждёт низкого,
- система может попытаться “пробустить” низкого (priority boosting), но это не всегда спасает.
Правильнее — не допускать долгих critical sections и корректно выбирать QoS.

## 5) Как выбирать на практике (эвристика)
- Всё, что напрямую влияет на UI responsiveness → `.userInteractive`.
- Действие по кнопке, результат нужен “сейчас” → `.userInitiated`.
- Загрузка/обработка, где допустимо подождать → `.utility`.
- Периодическая/отложенная работа → `.background`.

## 6) Пример
```swift
DispatchQueue.global(qos: .userInitiated).async {
    // подготовили данные для текущего экрана
}

DispatchQueue.global(qos: .background).async {
    // очистка кэша
}
```

**Самопроверка**
- Оспорено: “QoS — это просто приоритет очереди и всё” — это больше: сигнал планировщику про важность/энергию и взаимодействие с другими задачами (inheritance/boosting).
- Неочевидно: приоритетные эффекты зависят от системы; нельзя гарантировать, что high QoS “всегда выполнится первым”, но в среднем планировщик будет отдавать ему больше ресурсов.
- Источники: Apple docs по QoS (Dispatch/OperationQueue), материалы о priority inversion и priority boosting.

### Q58 (🟠): Что такое work item и для чего он нужен?

**Кратко**
- `DispatchWorkItem` — обёртка над задачей для GCD, которую можно:
  - запускать (`async`/`sync`),
  - отменять (`cancel()`),
  - получать уведомление о завершении (`notify`),
  - переиспользовать/передавать как объект.
- Полезен, когда нужно управлять жизненным циклом задачи, а не просто “бросить блок в очередь”.

**Развёрнуто**
## 1) Что даёт WorkItem поверх обычного closure
Обычный `queue.async { ... }` — “fire-and-forget”.
`DispatchWorkItem` позволяет:
- сохранить ссылку на работу,
- отменить её до старта или кооперативно в процессе,
- повесить callback на завершение.

```swift
let item = DispatchWorkItem {
    print("work")
}

DispatchQueue.global().async(execute: item)

item.notify(queue: .main) {
    print("done")
}
```

## 2) Отмена: важный нюанс
`cancel()`:
- помечает work item как отменённый,
- но **не убивает** уже выполняющийся код насильно.

Чтобы отмена имела эффект, код должен проверять `isCancelled`:

```swift
let item = DispatchWorkItem {
    for i in 0..<1_000_000 {
        if item.isCancelled { return }
        _ = i * i
    }
}
```

(На практике удобнее захватить `item` через внешний var или использовать другие паттерны; смысл — отмена кооперативная.)

## 3) Debounce / отмена предыдущих работ
Очень типовой use case: “если пользователь быстро вводит текст, отменяй старую работу и запускай новую”.

```swift
final class SearchDebouncer {
    private let queue = DispatchQueue(label: "search")
    private var pending: DispatchWorkItem?

    func schedule(_ block: @escaping () -> Void) {
        pending?.cancel()
        let item = DispatchWorkItem(block: block)
        pending = item
        queue.asyncAfter(deadline: .now() + 0.3, execute: item)
    }
}
```

## 4) Группы и зависимости
WorkItem можно:
- добавлять в `DispatchGroup`,
- использовать `notify` как лёгкую форму “continuation”.

## 5) Когда НЕ нужен
- Если просто надо выполнить блок на очереди без управления — обычный `async` проще.
- Для сложных зависимостей часто удобнее `Operation`/`OperationQueue`, а в Swift Concurrency — `Task`/`TaskGroup`.

**Самопроверка**
- Оспорено: “cancel() гарантированно остановит выполнение” — нет, отмена кооперативная; если работа уже выполняется и не проверяет флаг, она продолжит.
- Неочевидно: `DispatchWorkItem` — это GCD-уровень; в structured concurrency отмена (`Task.cancel()`) более встроенная, но тоже требует кооперации.
- Источники: Apple docs по DispatchWorkItem, примеры debounce/throttle на GCD, сравнение с Operation/Task.

### Q59 (🟠): Что такое `dispatch group` и когда его использовать?

**Кратко**
- `DispatchGroup` — механизм GCD, чтобы:
  - отслеживать набор асинхронных задач,
  - получить событие “всё завершилось” (`notify`),
  - или дождаться завершения синхронно (`wait`).
- Нужен, когда запускаешь **несколько независимых async работ** и хочешь сделать действие после их завершения (fan-out → fan-in).

**Развёрнуто**
## 1) Базовые способы использования
### A) `async(group:)` — самый простой
```swift
let group = DispatchGroup()
let q = DispatchQueue.global(qos: .userInitiated)

q.async(group: group) { /* task 1 */ }
q.async(group: group) { /* task 2 */ }

group.notify(queue: .main) {
    // оба завершились
}
```

### B) Ручной `enter/leave` (когда работа “внутри” другого async API)
Полезно, если у тебя completion-based API:

```swift
let group = DispatchGroup()

group.enter()
api.fetchA { result in
    defer { group.leave() }
    // обработка A
}

group.enter()
api.fetchB { result in
    defer { group.leave() }
    // обработка B
}

group.notify(queue: .main) {
    // оба запроса завершились
}
```

Критично: `enter` и `leave` должны быть сбалансированы, иначе:
- если забыть `leave` → `notify` никогда не сработает,
- если сделать лишний `leave` → краш/некорректное состояние.

## 2) Когда использовать
- Параллельные независимые запросы: загрузить профиль + настройки + фичефлаги.
- Параллельная обработка набора элементов, а потом агрегация результатов.
- Когда нужен “join” для группы задач без сложных зависимостей.

## 3) Когда НЕ использовать (или быть осторожным)
- Если нужен результат каждой задачи с типобезопасностью и отменой — в Swift Concurrency чаще лучше `async let` или `TaskGroup`.
- `group.wait()` на main thread — плохая идея (может подвесить UI).
- `enter/leave` легко ошибиться при множественных путях выхода/ошибках → использовать `defer`.

## 4) Аналог в Swift Concurrency
- `async let` для фиксированного набора задач.
- `withTaskGroup` для динамического числа задач.
Но group остаётся актуальным для legacy callback/GCD кода.

**Самопроверка**
- Оспорено: “DispatchGroup нужен для сериализации” — нет, он для координации завершения набора задач.
- Неочевидно: `wait` может приводить к deadlock/лагам, если вызвать на неподходящей очереди; чаще предпочтительнее `notify`.
- Источники: Apple docs по DispatchGroup, best practices по notify vs wait, Swift Concurrency structured equivalents.

### Q60 (🟠): Что такое barrier и когда он нужен?

**Кратко**
- `barrier` — специальная задача для **concurrent queue**, которая выполняется **эксклюзивно**:
  - все задачи, поставленные **до** barrier, должны завершиться,
  - задачи **после** barrier начнутся только после завершения barrier.
- Главный use case: паттерн “много читателей / один писатель” для общего состояния без locks.

**Развёрнуто**
## 1) Как работает barrier на concurrent queue
Barrier имеет смысл только на **собственной** concurrent queue (созданной тобой с `.concurrent`), а не на глобальных очередях (там гарантии могут не выполняться как ожидаешь).

```swift
final class ThreadSafeStore {
    private var dict: [String: Int] = [:]
    private let q = DispatchQueue(label: "store", attributes: .concurrent)

    func get(_ key: String) -> Int? {
        q.sync { dict[key] }             // читатели могут параллелиться
    }

    func set(_ key: String, _ value: Int) {
        q.async(flags: .barrier) {       // писатель — эксклюзивно
            self.dict[key] = value
        }
    }
}
```

Что гарантируется:
- несколько `get` могут выполняться одновременно,
- `set` блокирует конкурентное выполнение других `get/set` на этой очереди на время записи.

## 2) Когда barrier нужен
- Есть общий mutable state (например, словарь/кэш),
- чтений много, записей мало,
- хочется избежать большого числа locks и уменьшить contention.

## 3) Когда barrier НЕ помогает
- Если обращения к состоянию происходят **мимо** этой очереди (прямой доступ к `dict` из других мест) — потокобезопасности нет.
- Если очередь не concurrent — barrier бессмысленен.
- Если используешь global concurrent queue — barrier не даёт ожидаемой эксклюзивности для “всех задач в системе”, он работает в рамках данной очереди.

## 4) Barrier vs lock
- Barrier хорош, когда ты централизуешь доступ через одну очередь.
- Lock хорош, когда изолировать доступ через очередь сложно или нужно защищать маленькие критические секции в разных местах.
- В Swift Concurrency часто лучше actor, если модель данных подходит (изолированное состояние + async доступ).

## 5) Синхронный barrier
Есть и `sync(flags: .barrier)` — он блокирует вызывающий поток до завершения записи.
Использовать аккуратно, не на main, если запись может быть тяжёлой.

**Самопроверка**
- Оспорено: “barrier делает thread-safe всю программу” — нет, он обеспечивает эксклюзивность только в рамках конкретной concurrent queue и только при дисциплине доступа.
- Неочевидно: многие думают, что barrier работает на глобальных очередях “как lock” — это опасная ошибка; правильный паттерн — своя concurrent queue.
- Источники: Apple docs по DispatchQueue barrier flags, практики реализации read-write locks через GCD, сравнение с locks/actors.

### Q61 (🟠): Что такое semaphore и когда он нужен?

**Кратко**
- Semaphore — счётчик, который ограничивает доступ к ресурсу:
  - `wait()` уменьшает счётчик (или блокирует, если счётчик 0),
  - `signal()` увеличивает счётчик и будит ожидающих.
- В GCD это `DispatchSemaphore`.
- Используют для:
  - ограничения параллелизма (например, максимум N одновременных задач),
  - синхронизации “подожди, пока случится событие” (но осторожно, можно легко подвесить main),
  - защиты небольших критических секций (реже; чаще для этого берут locks/queues/actors).

**Развёрнуто**
## 1) Базовая модель
Semaphore хранит целое значение `count`.
- Если `count > 0`, `wait()` проходит и уменьшает `count`.
- Если `count == 0`, `wait()` блокируется до `signal()`.

## 2) Ограничение параллелизма (типовой use case)
Например, скачивать не более 4 файлов одновременно:

```swift
let sem = DispatchSemaphore(value: 4)
let q = DispatchQueue.global(qos: .utility)

for url in urls {
    q.async {
        sem.wait()
        defer { sem.signal() }

        // download(url)
    }
}
```

## 3) “Сделай async → sync” (опасный, но часто спрашивают)
Иногда используют семафор, чтобы дождаться completion:
```swift
let sem = DispatchSemaphore(value: 0)

api.fetch { _ in
    sem.signal()
}

sem.wait() // ❌ если вызвать на main — повиснет UI, возможен deadlock
```

Почему это плохо:
- блокирует поток,
- может привести к дедлоку, если completion должен выполниться на этом же потоке/очереди.

Правильнее:
- использовать `await`,
- или callback/notify,
- или `DispatchGroup`.

## 4) Semaphore vs Mutex (интуитивно)
- Semaphore — про “N разрешений” (resource permits).
- Mutex — про “только один владелец” (mutual exclusion).
Mutex можно считать частным случаем семафора с `value = 1`, но в реальности у них разные свойства и типичные применения.

## 5) Частые ошибки
- Забыли `signal()` → вечная блокировка (deadlock).
- `wait()` на main thread.
- Смешивание семафоров с очередями без понимания, где выполняется completion.

**Самопроверка**
- Оспорено: “семафор нужен, чтобы сделать async синхронным” — это анти-паттерн для UI кода; основная сила семафора — ограничение параллелизма.
- Неочевидно: `DispatchSemaphore` блокирует поток, а не “приостанавливает задачу” как `await`; для Swift Concurrency лучше structured подход.
- Источники: Apple docs по DispatchSemaphore, типовые паттерны ограничителя параллелизма, сравнение с locks/actors.

### Q62 (🟠): Чем отличается semaphore от mutex?

**Кратко**
- **Mutex** (mutual exclusion) — “замок” для критической секции: **только один** владелец в момент времени.
- **Semaphore** — счётчик “разрешений”: одновременно могут войти **до N** владельцев (N ≥ 1).
- Mutex обычно используется для защиты **shared mutable state**, semaphore — чаще для **ограничения параллелизма** или координации событий.
- Mutex обычно имеет понятие “владельца” (lock/unlock парой), у семафора “владельца” в классическом смысле нет (это просто счётчик).

**Развёрнуто**
## 1) Идея mutex
Mutex гарантирует взаимное исключение:
- один поток “вошёл” в критическую секцию,
- остальные ждут, пока он выйдет.

Пример в Swift через `NSLock` (это mutex-подобный интерфейс):
```swift
final class SafeCounter {
    private var value = 0
    private let lock = NSLock()

    func inc() {
        lock.lock()
        value += 1
        lock.unlock()
    }
}
```

## 2) Идея semaphore
Semaphore — это “пул разрешений”.
- `value = 1` → поведение похоже на mutex,
- `value = N` → до N параллельных “входов”.

Ограничение параллелизма:
```swift
let sem = DispatchSemaphore(value: 3)
DispatchQueue.global().async {
    sem.wait()
    defer { sem.signal() }
    // максимум 3 таких блоков одновременно
}
```

## 3) Отличия по типичным рискам
### Mutex
- Риск: deadlock при неправильном порядке/непарных lock/unlock.
- Риск: priority inversion, если низкий держит lock долго.

### Semaphore
- Риск: “утечки разрешений”:
  - забыли `signal()` → все ждут навсегда,
  - лишний `signal()` → счётчик “раздувается”, семантика ломается.
- Частый анти-паттерн: блокировать main thread, ожидая async completion.

## 4) Как выбирать
- Нужно защитить shared mutable state → mutex/serial queue/actor.
- Нужно ограничить число одновременных работ (pool) → semaphore.
- Нужна типобезопасность и структурированная отмена → Swift Concurrency (TaskGroup/actors) чаще лучше, чем ручные примитивы.

## 5) Важно для собеса
Фраза, которая показывает понимание:
- “Mutex — эксклюзивный доступ. Semaphore — доступ по разрешениям (permits). Mutex обычно имеет строгую ownership дисциплину, semaphore — счётчик и координация.”

**Самопроверка**
- Оспорено: “semaphore = mutex” — только в частном случае семафора с `value = 1`, но семантика и применение шире.
- Неочевидно: многие mutex/locks на практике тоже реализуются через более низкие примитивы (futex/unfair lock), но на собесе важны контракт и сценарии применения.
- Источники: базовые определения OS sync primitives, Apple docs (DispatchSemaphore, NSLock), материалы про priority inversion.

### Q63 (🟠): Что такое `NSLock`?

**Кратко**
- `NSLock` — простой mutex-подобный lock из Foundation для взаимного исключения в многопоточном коде.
- Используется для защиты критических секций (shared mutable state).
- Блокирует поток, если lock уже захвачен другим потоком.
- Не является рекурсивным: повторный `lock()` тем же потоком приведёт к дедлоку (используй `NSRecursiveLock`, если это нужно).

**Развёрнуто**
## 1) Базовый контракт
`NSLock` предоставляет:
- `lock()` — захват (может блокировать),
- `unlock()` — освобождение,
- `try()` — попытка без блокировки,
- `lock(before:)` — попытка с таймаутом.

```swift
final class SafeBox<T> {
    private var value: T
    private let lock = NSLock()

    init(_ value: T) { self.value = value }

    func read() -> T {
        lock.lock()
        defer { lock.unlock() }
        return value
    }

    func write(_ newValue: T) {
        lock.lock()
        defer { lock.unlock() }
        value = newValue
    }
}
```

## 2) Зачем `defer` почти обязателен
Главная ошибка — забыть `unlock()` на одном из путей выхода (ранний return, throw, error path).
`defer` делает unlock гарантированным.

## 3) Ограничения и типовые проблемы
- **Не рекурсивный**: если функция, взявшая lock, вызывает другую, которая пытается взять тот же lock — дедлок.
- Может приводить к **priority inversion** (низкоприоритетный поток держит lock, высокий ждёт).
- Lock снижает параллелизм: чем дольше критическая секция, тем хуже масштабирование.

## 4) Когда `NSLock` — нормальный выбор
- Небольшая критическая секция.
- Нужно синхронизировать доступ из разных мест, где неудобно централизовать через одну очередь.
- Нет возможности/желания переписать на actor/serial queue.

## 5) Когда лучше другое
- “Много читателей / один писатель” → concurrent queue + barrier или rw-lock подход.
- Асинхронный мир Swift Concurrency → actor/isolated state.
- Рекурсия/реентрантность → `NSRecursiveLock`.

**Самопроверка**
- Оспорено: “NSLock безопасен сам по себе” — он даёт mutual exclusion, но не решает архитектурные проблемы (кто владеет состоянием), и легко получить дедлок/инверсию приоритетов.
- Неочевидно: внутренняя реализация lock может быть `os_unfair_lock`-подобной и меняться; на собесе важен контракт и последствия.
- Источники: Apple docs по NSLock/NSLocking, практики использования `defer`, материалы про priority inversion.

### Q64 (🟠): Что такое `NSRecursiveLock`?

**Кратко**
- `NSRecursiveLock` — lock, который может быть **захвачен одним и тем же потоком несколько раз** без дедлока.
- Внутри ведёт счётчик захватов: надо сделать столько же `unlock()`, сколько было `lock()`.
- Нужен, когда код может повторно входить в защищённую секцию из того же потока (рекурсия/реентрантные вызовы).
- Минус: часто скрывает проблемы дизайна и обычно медленнее/сложнее для reasoning, чем обычный lock.

**Развёрнуто**
## 1) Проблема обычного lock
Обычный mutex (`NSLock`) не позволяет повторно захватить lock тем же потоком:
- поток уже владеет lock,
- повторный `lock()` будет ждать освобождения,
- но освобождения не будет (поток ждёт сам себя) → self-deadlock.

## 2) Что делает `NSRecursiveLock`
Он разрешает повторный вход:
- если текущий поток уже владеет lock, он увеличивает счётчик и продолжает.

```swift
final class RecursiveSafeCounter {
    private var value = 0
    private let lock = NSRecursiveLock()

    func inc(times: Int) {
        lock.lock()
        defer { lock.unlock() }

        value += 1
        if times > 1 {
            inc(times: times - 1) // ✅ повторный вход с тем же потоком
        }
    }
}
```

## 3) Важный инвариант: баланс lock/unlock
Если захватили lock N раз, нужно N раз вызвать `unlock()`, иначе lock “останется захваченным”.

Поэтому `defer` всё ещё полезен, но аккуратно в рекурсивных сценариях (каждый уровень должен освобождать).

## 4) Когда реально нужен
- Рекурсивные алгоритмы, которые защищают общие данные.
- Реентрантные вызовы, когда публичный метод вызывает внутренний, который тоже требует синхронизации.
- Legacy API, где трудно гарантировать “единственную точку входа”.

## 5) Когда лучше не использовать
- Если можно перепроектировать так, чтобы lock брался в одном месте (явная граница критической секции).
- Если проблема — неправильная архитектура владения состоянием: recursive lock маскирует, но не лечит.

## 6) Альтернативы
- Централизация доступа через serial queue (часто проще для reasoning).
- Actor в Swift Concurrency (если подходит модель async изоляции).
- Разделение состояния на независимые части, чтобы уменьшить необходимость в реентрантности.

**Самопроверка**
- Оспорено: “NSRecursiveLock всегда лучше NSLock, потому что безопаснее” — он решает конкретный сценарий, но усложняет reasoning и может скрывать архитектурные ошибки.
- Неочевидно: recursive lock не спасает от deadlock’ов между потоками; он только позволяет повторный захват одним потоком.
- Источники: Apple docs по NSRecursiveLock, практики синхронизации (reentrancy/recursion), сравнение с serial queue/actors.

### Q65 (🟠): Что такое spinlock? Почему его не любят?

**Кратко**
- Spinlock — lock, который при занятости **не блокирует поток**, а **крутится в цикле** (busy-wait), пока не освободится.
- Плюс: очень быстрый, если ожидание короткое и contention минимален.
- Минусы: жрёт CPU, плохо для энергии и производительности, опасен при priority inversion; на iOS исторически `OSSpinLock` признан проблемным и заменён на `os_unfair_lock`.
- Не любят, потому что в реальных условиях (preemption, разные QoS, длительные секции) он часто делает хуже.

**Развёрнуто**
## 1) Как работает spinlock
Идея: если ожидание “почти ноль”, то дешевле активно ждать, чем:
- парковать поток,
- потом будить,
- делать системные переключения контекста.

Псевдокод:
- пока флаг “занято” → крутимся,
- как освободилось → захватываем.

## 2) Почему это может быть плохо
### A) Busy-wait = расход CPU и батареи
Пока поток крутится, он:
- занимает CPU,
- мешает другим задачам,
- увеличивает нагрев и энергопотребление.

### B) Priority inversion становится хуже
Классический сценарий:
- Низкоприоритетный поток удерживает lock.
- Высокоприоритетный поток пытается взять spinlock и начинает крутиться.
- Но он крутится на CPU и может **вытеснять** низкоприоритетный поток, который должен освободить lock.
Итог: высокий тратит CPU, низкий не получает времени → прогресс задерживается сильнее (парадоксально).

Это одна из причин, почему `OSSpinLock` считался проблемным.

### C) Preemption и длительные critical sections
Если секция оказалась дольше “пары инструкций”, spin превращается в “жечь CPU просто так”.

## 3) Что вместо spinlock в Apple экосистеме
- `os_unfair_lock` — “unfair” lock, который при contention паркует поток, а не крутится (и уменьшает проблему priority inversion относительно spin-подхода).
- Более высокие уровни: serial queue, barrier, actors.

## 4) Когда spinlock теоретически уместен
- Очень короткие критические секции,
- крайне редкий contention,
- жёстко контролируемая среда (высокоуровневый код почти никогда).

В приложенческом iOS коде это почти не оправдано.

**Самопроверка**
- Оспорено: “spinlock быстрее, значит лучше” — быстрее только в узком окне условий; иначе ухудшает CPU/энергию и может усилить priority inversion.
- Неочевидно: термин “spinlock” часто смешивают с “unfair lock”; важно: spin крутится, unfair обычно паркует.
- Источники: материалы Apple/сообщества о проблемах `OSSpinLock`, документация по `os_unfair_lock`, базовые OS sync primitive объяснения.

### Q66 (🟠): Что такое atomic operations?

**Кратко**
- Atomic operation — операция, которая выполняется как **неделимая**: другие потоки не видят “промежуточных” состояний.
- Атомарность обычно означает:
  - отсутствие torn reads/writes,
  - корректные read-modify-write (например, `fetch_add`) без гонок.
- Но атомарность ≠ отсутствие логических гонок: можно атомарно инкрементировать счётчик и всё равно иметь race condition на уровне бизнес-логики.
- Важна **memory ordering**: атомики часто задают барьеры видимости (acquire/release/seq_cst).

**Развёрнуто**
## 1) Что решают атомики
Классический data race пример:
- два потока делают `x += 1`,
- это read → add → write,
- без атомарности обновления теряются.

Атомик даёт операцию “увеличь и верни старое/новое значение” как единый шаг.

## 2) Что атомики НЕ решают
- Если нужно обновить несколько переменных согласованно, атомик на одной переменной не даст консистентности.
- Атомики не заменяют критические секции, когда нужны инварианты:

Пример: два поля должны меняться вместе (balance, version). Атомики по отдельности могут дать наблюдение “половинчатого” состояния.

## 3) Memory ordering (интервью-уровень)
Атомики важны не только “чтобы два потока не записали одновременно”, но и чтобы:
- гарантировать, что записи до атомика станут видимы другим потокам после атомика (release),
- и что чтения после атомика увидят актуальные данные (acquire).

Без правильного ordering можно получить ситуации, когда значения “не видны” из-за переупорядочивания (reordering) и кэшей CPU.

## 4) Где используются в iOS/Swift
- Низкоуровневые runtime/lock реализации.
- Счётчики, флаги состояния, one-time init.
- Ограничители параллелизма/lock-free структуры (но это уже сложно и редко нужно в app-коде).

В Swift стандартная библиотека исторически не давала “простых атомиков” из коробки; часто используют:
- `OSAtomic` (устарело),
- `stdatomic`/C++ атомики через bridging (редко),
- сторонние реализации,
- либо уходят на actors/locks/queues.

## 5) Практический критерий выбора
- Нужен простой счётчик/флаг и есть понимание ordering → атомик может быть хорош.
- Нужен согласованный state и инварианты → lock/serial queue/actor.
- Нужна типобезопасная изоляция в async мире → actor.

**Самопроверка**
- Оспорено: “atomic = thread-safe” — атомарность одной операции не делает всю структуру данных потокобезопасной.
- Неочевидно: memory ordering — ключевой компонент атомиков; без него легко сделать “атомарно, но неправильно”.
- Источники: базовые материалы по атомикам и memory model, Apple/clang docs по atomics, обсуждения Swift concurrency vs атомики.

### Q67 (🟠): Что такое thread-safe?

**Кратко**
- Thread-safe означает: код/тип/операция работает корректно при одновременном доступе из нескольких потоков/задач, без гонок и повреждения состояния.
- Thread-safe не равно “всегда параллельно” — наоборот, часто thread-safety достигается **сериализацией** (locks, serial queue, actor).
- Важно определить *что именно* считается корректностью: атомарность операции? консистентность инвариантов? отсутствие data races? прогресс без дедлоков?

**Развёрнуто**
## 1) Что включает понятие thread-safe
Обычно ожидают как минимум:
- нет data races (небезопасных конкурентных чтений/записей),
- сохранены инварианты (состояние не ломается),
- нет UB/коррапции памяти.

Но на собесе хорошо уточнять:
- thread-safe для каких операций?
- “в любой момент времени” или только при определённом протоколе использования?

Например, тип может быть thread-safe для чтения, но не для записи.

## 2) Основные техники достижения thread-safety
### A) Иммутабельность
- неизменяемые значения безопасны по определению,
- copy-on-write даёт value semantics, но мутация требует изоляции.

### B) Сериализация доступа
- serial queue:
  - все операции над state выполняются в одной очереди → упорядочены.
- actor (Swift Concurrency):
  - изоляция состояния и доступ через `await`, один поток исполнения логически.

### C) Locks
- `NSLock`, `os_unfair_lock`, `pthread_mutex`:
  - защищают критические секции.
Минус: риск дедлоков и priority inversion.

### D) Атомики
- подходят для простых флагов/счётчиков,
- требуют понимания memory ordering.

## 3) Частые ловушки
- “Thread-safe метод” внутри объекта не делает объект thread-safe целиком, если есть другие методы/поля, которые обходят синхронизацию.
- “Atomic property” (в терминах ObjC) не гарантирует инварианты между несколькими полями.
- Thread-safe не гарантирует отсутствие starvation или fairness; это отдельные свойства.

## 4) Как формулировать на собесе
Хорошая формулировка:
- “Thread-safe — когда параллельные вызовы не приводят к data races и оставляют состояние консистентным; обычно достигается сериализацией или синхронизацией доступа.”

**Самопроверка**
- Оспорено: “thread-safe = без locks” — thread-safety часто достигается locks/очередями/акторами; отсутствие locks не цель сама по себе.
- Неочевидно: разные уровни гарантий (lock-free, wait-free, progress guarantees) — это отдельная тема; для iOS обычно достаточно корректности + отсутствие гонок.
- Источники: определения thread-safety и memory model, Apple docs по concurrency primitives, Swift Concurrency (actors).

### Q68 (🟠): Что такое data race?

**Кратко**
- Data race — когда два (или больше) потока/задачи **конкурентно** обращаются к одной области памяти, и:
  - хотя бы один доступ — **запись**,
  - и нет достаточной синхронизации/изоляции.
- Следствие — **неопределённое поведение**: потеря обновлений, чтение “рваных” значений, коррапция состояния, редкие краши.
- Data race — частный случай race condition, но более “низкоуровневый” и опасный.

**Развёрнуто**
## 1) Формальное ядро определения
Чтобы назвать ситуацию data race, нужны три вещи:
1) общий участок памяти (shared location),
2) конкуренция (параллельное или перекрывающееся во времени выполнение),
3) конфликтующий доступ (write/write или read/write),
4) отсутствие synchronizes-with (locks, atomics, actor isolation, serial queue).

Если все выполнено — это data race.

## 2) Пример: “потерянные инкременты”
```swift
final class Counter {
    var value = 0
}

let c = Counter()
let q = DispatchQueue.global(qos: .userInitiated)

for _ in 0..<10_000 {
    q.async {
        c.value += 1 // ❌ read-modify-write без синхронизации
    }
}
```
Итоговое значение недетерминировано и обычно меньше 10_000.

## 3) Пример: “рваное” состояние (инварианты ломаются)
```swift
final class State {
    var a = 0
    var b = 0 // хотим инвариант: b всегда == a
}
```
Если один поток пишет `a` и `b`, а другой читает, можно увидеть `a` уже новое, а `b` ещё старое — логическая неконсистентность. Даже если каждый set “атомарен” сам по себе, инвариант может ломаться без общей критической секции.

## 4) Как избегать
- Swift Concurrency: actor/`@MainActor` для UI state.
- Serial queue: все операции над state через одну очередь.
- Locks: `NSLock` и т.п. вокруг критических секций.
- Atomics: для простых флагов/счётчиков (с корректным ordering).

## 5) Как находить
- Thread Sanitizer (TSAN) — №1 инструмент для data races:
  - находит конфликтующие обращения,
  - даёт стек-трейсы мест чтения/записи.
- Стресс-тесты, нагрузка, рандомные задержки (чтобы чаще воспроизводилось).
- Инварианты и assertions.

**Самопроверка**
- Оспорено: “data race просто даёт неправильный результат” — может быть гораздо хуже: редкие краши и коррапция памяти.
- Неочевидно: отсутствие воспроизведения не означает отсутствия data race; он может проявляться только на реальных девайсах/релизной оптимизации.
- Источники: определения data race из memory model, Apple docs по Thread Sanitizer, материалы Swift Concurrency (actor isolation).

### Q69 (🟠): Что такое priority inversion?

**Кратко**
- Priority inversion — когда **высокоприоритетная** задача вынуждена ждать **низкоприоритетную**, потому что та удерживает нужный ресурс (lock/очередь/семафор), а средние по приоритету задачи ещё и вытесняют низкую.
- Итог: система ведёт себя так, будто приоритеты “перевернулись” — высокий не получает CPU/ресурс, хотя должен.
- Лечится:
  - уменьшением времени удержания lock,
  - избеганием блокировок между разными QoS,
  - priority inheritance/boosting (частично делает ОС),
  - правильным выбором примитивов (не spinlock) и архитектуры.

**Развёрнуто**
## 1) Классический сценарий (High waits Low, while Medium runs)
- **Low** захватил lock и пошёл выполнять работу.
- **High** попытался взять lock и заблокировался.
- **Medium** получает CPU (потому что он не блокирован) и вытесняет Low.
- Low не может продолжить и отпустить lock → High ждёт ещё дольше.
Получаем “инверсию”: High фактически страдает из-за Low и Medium.

## 2) Почему это важно в iOS
- QoS влияет на планирование.
- Если `.userInteractive` поток/задача ждёт ресурс, удерживаемый `.background`, UI может лагать/фризить.
- Это может выглядеть как случайные подфризы, “непонятные” задержки, особенно под нагрузкой.

## 3) Где возникает
- Locks (`NSLock`, mutex) при смешивании разного QoS.
- Serial queue как “ресурс”: если low-QoS задача заняла очередь, high-QoS задача в этой же очереди ждёт.
- Семафоры и любые блокирующие ожидания.
- Spinlock усугубляет, потому что высокий может “крутиться” и мешать низкому отпустить lock.

## 4) Как предотвращать (практически)
- Делать критические секции минимальными:
  - не держать lock во время I/O, ожиданий, `await`.
- Не смешивать high/low QoS в одном lock/очереди без необходимости:
  - разделять ресурсы,
  - не выполнять heavy background работу под тем же lock, который нужен UI.
- Использовать более подходящие механизмы:
  - actor/serial queue, если это упрощает изоляцию,
  - `os_unfair_lock` (системный механизм обычно умеет лучше взаимодействовать с планировщиком, чем spin).

## 5) Диагностика
- Симптом: high-priority путь (UI) “ждёт” и периодически фризит, хотя CPU вроде доступен.
- Инструменты:
  - Instruments: System Trace (sched, QoS, thread states),
  - Time Profiler + анализ stack’ов “Blocked on lock”,
  - логирование времени ожидания lock/очереди (`os_signpost`).

**Самопроверка**
- Оспорено: “priority inversion — это просто когда low блокирует high” — ключевой элемент часто в том, что **medium вытесняет low**, усугубляя задержку.
- Неочевидно: ОС может делать priority boosting, но на это нельзя полностью полагаться; архитектура и короткие критические секции важнее.
- Источники: материалы OS scheduling, Apple QoS docs, инструменты Instruments System Trace и практики анализа lock contention.

### Q70 (🟠): Как работает `OperationQueue`?

**Кратко**
- `OperationQueue` — высокоуровневая абстракция над concurrent execution, построенная вокруг объектов `Operation`.
- Даёт:
  - зависимости (`addDependency`),
  - отмену (`cancel`),
  - приоритеты (`queuePriority`), QoS,
  - ограничение параллелизма (`maxConcurrentOperationCount`),
  - KVO-состояния (`isExecuting/isFinished/isCancelled`),
  - возможность объединять операции в граф.
- По сути, это scheduler для `Operation`-объектов, который сам распределяет их на потоки и учитывает зависимости/приоритеты.

**Развёрнуто**
## 1) Базовая модель
Ты создаёшь `Operation` (часто `BlockOperation` или кастомный subclass) и добавляешь в очередь:

```swift
let queue = OperationQueue()
queue.maxConcurrentOperationCount = 4

let op1 = BlockOperation { /* work 1 */ }
let op2 = BlockOperation { /* work 2 */ }
op2.addDependency(op1)

queue.addOperations([op1, op2], waitUntilFinished: false)
```

Очередь:
- не запускает `op2`, пока не завершится `op1`,
- может выполнять независимые операции параллельно.

## 2) Состояния и жизненный цикл
`Operation` имеет состояния:
- готова (`isReady`) — все зависимости завершены,
- выполняется (`isExecuting`),
- завершена (`isFinished`),
- отменена (`isCancelled`).

Для кастомных async операций нужно корректно управлять KVO для `isExecuting/isFinished` (или использовать более новые паттерны/обёртки), иначе очередь не поймёт, что операция “всё ещё работает”.

## 3) Отмена: кооперативная
`cancel()`:
- ставит флаг,
- очередь может не стартовать отменённую операцию,
- если операция уже выполняется — она должна проверять `isCancelled` и корректно завершаться.

## 4) Приоритеты и QoS
- `qualityOfService` — для планирования системой.
- `queuePriority` — относительный приоритет внутри очереди.
Важно: это не “жёсткие гарантии”, а сигналы планировщику.

## 5) Почему это удобно
- Можно строить pipeline: download → parse → persist → UI update.
- Удобно ограничивать concurrency.
- Удобно отменять пачки операций (например, при уходе с экрана).
- Лучше тестируемость и управляемость, чем “россыпь async блоков”.

## 6) Типовые подводные камни
- Сложность правильной реализации async `Operation` subclass.
- Легко забыть выставить `isFinished` → очередь “повиснет”.
- Слишком много мелких операций → overhead.

**Самопроверка**
- Оспорено: “OperationQueue — это просто удобный GCD” — она добавляет граф зависимостей, состояние, отмену и приоритеты на уровне объектов.
- Неочевидно: cancellation не “убивает” выполнение; нужна кооперативная поддержка внутри операции.
- Источники: Apple docs по Operation/OperationQueue, best practices async Operation, сравнение с GCD и Swift Concurrency.

### Q71 (🟠): Чем отличается `OperationQueue` от GCD?

**Кратко**
- GCD — низкоуровневая модель “очереди + блоки”; быстро, просто, но управление зависимостями/отменой/состоянием — на тебе.
- `OperationQueue` — более высокий уровень: “очередь + объекты Operation”, где есть:
  - зависимости,
  - отмена,
  - приоритеты,
  - наблюдаемое состояние,
  - ограничение concurrency,
  - композиция в граф.
- По производительности GCD обычно легче (меньше overhead), `OperationQueue` удобнее для сложных пайплайнов.

**Развёрнуто**
## 1) Абстракция и модель программирования
### GCD
- Отправляешь closures на очереди:
```swift
DispatchQueue.global().async { /* work */ }
```
- Зависимости/координацию строишь вручную:
  - groups, semaphores, barriers,
  - цепочки callback’ов,
  - собственные state machines.

### OperationQueue
- Отправляешь `Operation`-объекты:
```swift
let q = OperationQueue()
q.addOperation(BlockOperation { /* work */ })
```
- Зависимости встроены:
```swift
op2.addDependency(op1)
```

## 2) Отмена
- GCD: “отмена” closures почти отсутствует (кроме `DispatchWorkItem`, но это ограниченно и кооперативно).
- OperationQueue: `cancel()` — часть модели, операции могут проверять `isCancelled`, очередь может не стартовать отменённые.

## 3) Состояние и наблюдаемость
- GCD: нет встроенного `isExecuting/isFinished`.
- Operation: есть состояния, можно KVO-наблюдать, можно строить сложные графы.

## 4) Приоритеты
- GCD: QoS на очереди/задаче.
- OperationQueue: QoS + `queuePriority` (внутри очереди).

## 5) Ограничение параллелизма
- GCD: делается через semaphores или собственные очереди/пулы.
- OperationQueue: `maxConcurrentOperationCount` из коробки.

## 6) Когда что выбирать
### Выбирай GCD, если:
- задача простая,
- нужна минимальная обвязка,
- нужно “быстро диспатчнуть” и всё.

### Выбирай OperationQueue, если:
- есть pipeline и зависимости,
- нужно массово отменять задачи (например, при уходе с экрана),
- нужна управляемость и тестируемость,
- важна приоритизация внутри набора задач.

## 7) В 202x мире: Swift Concurrency
- Для нового кода structured concurrency часто замещает и GCD, и OperationQueue:
  - `TaskGroup` вместо групп,
  - `actors` вместо locks/serial queues,
  - cancellation встроена.
Но OperationQueue остаётся полезной для legacy, интеграций и сложных dependency-graph’ов.

**Самопроверка**
- Оспорено: “OperationQueue — просто обёртка над GCD без смысла” — смысл в графе зависимостей, состоянии и отмене.
- Неочевидно: выбор зависит от требований к управлению; GCD быстрее в простых случаях, OperationQueue лучше масштабируется по сложности проекта.
- Источники: Apple docs OperationQueue vs Dispatch, примеры pipeline, Swift Concurrency migration материалы.

### Q72 (🟠): Что такое async/await в Swift?

**Кратко**
- `async/await` — синтаксис и модель для асинхронного кода, позволяющая писать его “как синхронный”, но без блокировки потока.
- `await` **приостанавливает** текущую задачу (task) до результата, освобождая поток для других работ.
- Это часть Swift Concurrency: вместе с `Task`, `actors`, cancellation, structured concurrency.
- Ключевое отличие от GCD: ты работаешь не с потоками/очередями напрямую, а с задачами и исполнителями (executors).

**Развёрнуто**
## 1) Что означает `async`
`async` у функции значит:
- она может приостанавливать выполнение,
- её можно вызывать только из async контекста или через `Task`.

```swift
func loadData() async throws -> Data {
    // ...
    return Data()
}
```

## 2) Что делает `await`
`await` — точка приостановки:
- задача может “уснуть”, пока ждёт I/O или другой async результат,
- поток при этом не блокируется.

```swift
Task {
    do {
        let data = try await loadData()
        await MainActor.run {
            // обновление UI
        }
    } catch {
        // обработка ошибки
    }
}
```

Ключевая мысль для собеса:
- `await` не означает “выполнится в другом потоке”.
- `await` означает “задача может быть приостановлена и продолжена позже, возможно на другом executor’е”.

## 3) Почему это лучше callback-ов во многих случаях
- Линейный код: проще читать и поддерживать.
- Обработка ошибок через `throw/try/catch`, а не через “error в completion”.
- Structured concurrency: дочерние задачи живут в рамках родительской области, легче управлять временем жизни и отменой.

## 4) Важные детали поведения
- После `await` ты **не обязан** оставаться на том же потоке/очереди.
  - Поэтому UI обновления — через `@MainActor`/`MainActor.run`.
- `async` функции должны быть reentrant-safe и учитывать cancellation (если это долгие операции).
- Cancellation кооперативная: задаче нужно проверять `Task.isCancelled` или использовать `try await` точки, которые бросают `CancellationError`.

## 5) Bridging с legacy completion APIs
Старые completion-based API можно оборачивать в async через continuations:
- `withCheckedContinuation`
- `withCheckedThrowingContinuation`
(на собесе достаточно сказать идею; детали — отдельный вопрос)

**Самопроверка**
- Оспорено: “async/await = запустить в бэкграунде” — нет; это про асинхронность и приостановку задач, а не гарантированную смену потока.
- Неочевидно: после `await` меняется контекст исполнения; нужно явно контролировать UI слой (MainActor).
- Источники: Swift Concurrency docs (The Swift Programming Language), материалы WWDC про async/await и structured concurrency.

### Q73 (🟠): Что такое `Task` и `TaskGroup`?

**Кратко**
- `Task` — единица асинхронной работы в Swift Concurrency. Запускает async код и поддерживает:
  - приоритет,
  - отмену,
  - локальные значения (`TaskLocal`),
  - structured lifetimes (если не `detached`).
- `TaskGroup` — механизм structured concurrency для запуска **динамического числа** дочерних задач и ожидания их результатов (fan-out/fan-in) с управляемой отменой.
- Аналогии:
  - `Task {}` — как “запустить асинхронную работу”.
  - `withTaskGroup` — как “запустить много работ и собрать результаты”.

**Развёрнуто**
## 1) `Task`
### `Task { }` (structured)
Создаёт задачу, связанную с текущим контекстом (priority, cancellation, actor context могут наследоваться):

```swift
Task {
    let data = try await load()
    await MainActor.run { /* UI */ }
}
```

### `Task.detached { }` (unstructured)
Не наследует actor context и часть настроек:

```swift
Task.detached {
    // не на MainActor даже если вызвали с него
}
```

Важно: detached часто источник ошибок (потеря MainActor, неожиданное удержание, неконтролируемый lifetime).

## 2) `TaskGroup`
### Зачем нужен
Когда у тебя переменное число задач, и ты хочешь:
- запустить их параллельно,
- дождаться всех,
- собрать результаты,
- корректно отменить всё при ошибке/выходе.

Пример:
```swift
func loadAll(urls: [URL]) async throws -> [Data] {
    try await withThrowingTaskGroup(of: Data.self) { group in
        for url in urls {
            group.addTask {
                try await fetch(url)
            }
        }

        var result: [Data] = []
        result.reserveCapacity(urls.count)

        for try await data in group {
            result.append(data)
        }

        return result
    }
}
```

## 3) Почему это “structured”
TaskGroup живёт строго внутри блока `withTaskGroup`:
- по выходу из блока runtime гарантирует, что дочерние задачи завершены/отменены.
Это дисциплина времени жизни, которая уменьшает “висячие” фоновые задачи.

## 4) Ошибки и отмена в TaskGroup
- `withThrowingTaskGroup`: первая ошибка может привести к отмене остальных задач (кооперативно).
- Дочерние задачи должны быть cancellation-friendly, иначе они продолжат работать.

## 5) Когда выбирать что
- Один фоновой кусок работы → `Task {}`.
- Несколько фиксированных параллельных операций → `async let`.
- Динамическое количество параллельных операций → `TaskGroup`.
- Нужно полностью развязать от текущего контекста (редко) → `Task.detached`.

**Самопроверка**
- Оспорено: “TaskGroup — это просто как DispatchGroup” — похоже по цели, но TaskGroup даёт structured lifetime, типизированные результаты и встроенную отмену/ошибки.
- Неочевидно: `Task.detached` — не “лучше”, а более опасный инструмент; часто лучше оставаться в structured модели.
- Источники: Swift Concurrency docs (Tasks, Task Groups), WWDC про structured concurrency, сравнения с DispatchGroup/OperationQueue.

### Q74 (🟠): Что такое cancellation и как оно работает?

**Кратко**
- Cancellation в Swift Concurrency — **кооперативная**: `Task.cancel()` ставит флаг отмены, но задача остановится только если:
  - проверяет `Task.isCancelled`,
  - вызывает `try Task.checkCancellation()`,
  - или попадает в `await`, которое бросает `CancellationError` (например, `Task.sleep`).
- Отмена распространяется по task tree (structured concurrency): отмена родителя обычно отменяет детей.
- Cancellation ≠ прекращение потока: это сигнал и договор, а не принудительное убийство.

**Развёрнуто**
## 1) Что именно делает `cancel()`
Когда ты вызываешь `task.cancel()`:
- у задачи выставляется “cancelled” флаг,
- многие async API начинают быстрее завершаться/бросать `CancellationError`,
- дочерние задачи (в structured контексте) получают отмену.

Но если задача:
- не проверяет флаг,
- не имеет cancellation points,
она может продолжать выполняться и удерживать ресурсы.

## 2) Как правильно писать cancellation-friendly код
### A) Проверять флаг в циклах
```swift
func work() async {
    while !Task.isCancelled {
        // часть работы
        await Task.yield() // даём шанс планировщику
    }
}
```

### B) Принудительная проверка
```swift
func work() async throws {
    try Task.checkCancellation()
    // ...
}
```

### C) Использовать await-точки, которые бросают CancellationError
```swift
try await Task.sleep(nanoseconds: 1_000_000_000) // бросит при отмене
```

## 3) Отмена и structured concurrency
- Если ты внутри `Task {}` создаёшь дочерние задачи (`async let`, TaskGroup), они связаны временем жизни и отменой.
- Отмена родителя сигналит детям:
  - это помогает автоматически “собирать” хвосты.

## 4) Отмена и resource cleanup
Отмена — не исключение “внезапно в любой строке”, она проявляется в точках проверки/await.
Поэтому важно:
- использовать `defer` для освобождения ресурсов,
- аккуратно обрабатывать `CancellationError`:

```swift
do {
    try await work()
} catch is CancellationError {
    // нормально: задача отменена
}
```

## 5) Типовые ошибки
- Думать, что `cancel()` сразу остановит выполнение.
- Игнорировать отмену в долгих циклах/парсинге/CPU-heavy задачах.
- Хранить task в объекте и не отменять при уходе со сцены → “висячие” задачи.

**Самопроверка**
- Оспорено: “cancellation — это убийство” — нет, это кооперативный сигнал; корректность зависит от кода.
- Неочевидно: многие API сами являются cancellation points (sleep, некоторые async I/O), но CPU-bound код должен добавлять проверки вручную.
- Источники: Swift Concurrency docs (Cancellation), WWDC материалы по structured concurrency и cancellation, примеры Task.sleep/checkCancellation.

### Q75 (🟠): Чем отличается `Task {}` от `DispatchQueue.async`, и как они взаимодействуют в одном приложении?

**Кратко**
- `DispatchQueue.async` (GCD) — планирует **closure** на конкретной очереди (serial/concurrent) с заданным QoS; ты явно управляешь “куда отправить”.
- `Task {}` (Swift Concurrency) — создаёт **задачу** в модели structured concurrency; она исполняется на executor’ах Swift Concurrency и интегрирована с:
  - `await`,
  - cancellation,
  - priorities,
  - actor isolation (`MainActor`).
- В одном приложении они легко смешиваются:
  - можно вызывать GCD из Task,
  - можно оборачивать callback-based API в async через continuations,
  - `MainActor` чаще всего соответствует main thread, но это разные уровни абстракции.

**Развёрнуто**
## 1) Модель выполнения: очереди vs задачи
### GCD
Ты выбираешь очередь:
```swift
DispatchQueue.global(qos: .utility).async {
    // работа
}
```
- Очередь определяет порядок/конкурентность.
- Отмена и зависимости — вручную (WorkItem/Group/Semaphore).

### Task
Ты создаёшь задачу:
```swift
Task {
    let data = try await load()
}
```
- Где и как она выполнится — решает Swift runtime (executors).
- Есть structured lifetime: дочерние задачи “живут” в рамках родителя (если не detached).
- Есть cancellation/priority inheritance.

## 2) Потоки и блокировки
- GCD `async` — не блокирует вызывающий поток.
- `Task` при `await` **приостанавливается**, не блокируя поток.
Разница:
- GCD работает на уровне потоков/очередей.
- Task работает на уровне задач/continuations, позволяя экономить потоки при ожидании I/O.

## 3) Отмена
- В GCD “голые” closures не отменяются (кроме WorkItem, и то кооперативно).
- В Task cancellation встроена (`Task.cancel()`), но тоже кооперативная и лучше интегрирована с async API.

## 4) Взаимодействие в одном приложении
### A) Вызвать GCD из Task (например, CPU-heavy work)
```swift
func compute() async -> Int {
    await withCheckedContinuation { cont in
        DispatchQueue.global(qos: .userInitiated).async {
            let result = heavy()
            cont.resume(returning: result)
        }
    }
}
```
(Идея: оборачиваем блок в continuation. На практике ещё важно учитывать отмену.)

### B) Обернуть callback-based API в async
Если API вызывает completion на main или background, continuations позволяют интегрировать его в `await`.

### C) UI обновления
В Task после `await` ты не обязан быть на main:
```swift
Task {
    let model = try await load()
    await MainActor.run { render(model) }
}
```
С GCD это выглядело бы как `DispatchQueue.main.async`.

## 5) Как выбирать
- Новый код с async I/O, отменой, structured lifetimes → Task/async/await.
- Низкоуровневый контроль очередей, barrier, группы, интеграция со старым кодом → GCD.
Часто гибрид: внешняя модель — Swift Concurrency, внутри отдельных мест — GCD для CPU-bound распараллеливания.

**Самопроверка**
- Оспорено: “Task просто обёртка над DispatchQueue” — это другой runtime и модель (structured concurrency, actors, cancellation).
- Неочевидно: смешивание моделей без дисциплины приводит к неожиданным удержаниям/приоритетам; при переходе через continuations нужно учитывать cancellation и context (MainActor).
- Источники: Swift Concurrency docs (Tasks, Executors, MainActor), Apple docs по GCD, материалы WWDC про миграцию от GCD к async/await.

### Q76 (🟠): Как работает structured concurrency: task tree, cancellation, priority inheritance?

**Кратко**
- Structured concurrency — дисциплина, где асинхронные задачи образуют **дерево (task tree)**:
  - дочерние задачи создаются внутри области (scope) родителя,
  - родитель не “выходит” из scope, пока дети не завершены/отменены.
- Это даёт:
  - управляемый lifetime (нет “висячих” задач),
  - автоматическое распространение cancellation,
  - наследование приоритета (priority inheritance) и контекста (в т.ч. actor context).
- Инструменты: `async let`, `withTaskGroup/withThrowingTaskGroup`, `Task {}` (structured), в отличие от `Task.detached` (unstructured).

**Развёрнуто**
## 1) Task tree: дерево задач
Когда внутри задачи ты создаёшь дочерние задачи через structured механизмы:
- они становятся детьми текущей задачи,
- runtime знает об этой связи.

Пример с `async let`:
```swift
func load() async throws -> (A, B) {
    async let a = fetchA()
    async let b = fetchB()
    return try await (a, b)
}
```

Пока функция `load` не завершится, она обязана дождаться `a` и `b` (или они будут отменены при ошибке/выходе). Это и есть “структурированность”.

## 2) Cancellation propagation
Если родительская задача отменена:
- cancellation сигналится детям.
Если в `withThrowingTaskGroup` одна задача бросила ошибку:
- остальные задачи обычно отменяются (кооперативно), чтобы не тратить ресурсы.

Важно: отмена — сигнал. Дети должны быть cancellation-friendly.

## 3) Priority inheritance
В structured модели приоритет чаще “наследуется”:
- если пользовательский action запустил high-priority задачу, её дети обычно получают близкий приоритет,
- это помогает избегать ситуаций, где high-level задача ждёт результата low-priority дочерней.

Это похоже на идею борьбы с priority inversion на уровне задач.

## 4) Контекст выполнения (actor context)
Если ты внутри `@MainActor` контекста создаёшь structured task, она может наследовать этот контекст:
- удобно для UI: не потерять main isolation случайно.
`Task.detached` контекст не наследует.

## 5) Чем отличается от unstructured concurrency
### Structured
- `async let`, TaskGroup, `Task {}` внутри контекста:
  - lifetime ограничен scope,
  - есть propagation cancellation/priority/context.

### Unstructured
- `Task.detached`:
  - не “привязан” к родителю,
  - живёт сам по себе,
  - легко получить утечки времени жизни, неожиданные удержания, потерю MainActor.

## 6) Почему structured concurrency важна
- Упрощает reasoning: видно, где создаются задачи и когда они завершаются.
- Уменьшает баги: меньше “забытых” фоновых задач.
- Делает отмену и обработку ошибок системными, а не “вручную по колбэкам”.

**Самопроверка**
- Оспорено: “структурированность — это просто стиль кода” — нет, это runtime-гарантии времени жизни и связей задач (task tree).
- Неочевидно: priority inheritance не абсолютен (влияние зависит от runtime/OS), но концептуально помогает предотвращать ожидание “низких” задач “высокими”.
- Источники: Swift Concurrency docs (Structured Concurrency, Task groups), WWDC сессии про task tree/cancellation/priority, материалы про global actors и inheritance.

### Q77 (🔴): Что такое actor?

**Кратко**
- `actor` в Swift — reference-тип, который обеспечивает **изоляцию своего состояния**: в один момент времени к mutable state actor’а имеет доступ только один “исполнитель” (логически сериализовано).
- Внешний доступ к actor’у обычно требует `await` (потому что обращение может приостанавливать), чтобы обеспечить безопасность от data races.
- Actor — основной инструмент Swift Concurrency для thread-safety без ручных locks/queues.

**Развёрнуто**
## 1) Что именно гарантирует actor
- Внутри actor’а его методы и доступ к его stored properties исполняются так, что конкурентные обращения не приводят к одновременной мутации состояния.
- Это устраняет data races на его изолированном состоянии.

Пример:
```swift
actor Counter {
    private var value = 0

    func inc() {
        value += 1
    }

    func get() -> Int { value }
}
```

Использование:
```swift
let c = Counter()

Task {
    await c.inc()
    let v = await c.get()
    print(v)
}
```

## 2) Почему нужен `await`
Если два разных task обращаются к actor’у:
- они “очередятся” на actor’овом executor’е,
- поэтому вызов может приостанавливать до своей очереди.

Поэтому:
- actor методы из внешнего контекста — `await`,
- если метод помечен `nonisolated`, он не требует await, но и не имеет доступа к изолированному состоянию.

## 3) reentrancy: важная тонкость
Actor не гарантирует, что метод будет “монолитно” держать эксклюзивный доступ между await-точками.

Если внутри actor метода есть `await`, actor может:
- “отпустить” исполнение,
- обработать другие входящие сообщения,
- потом продолжить.

Пример тонкости:
```swift
actor Store {
    private var items: [Int] = []

    func addAfterDelay(_ x: Int) async {
        await Task.yield()
        items.append(x)
    }
}
```

Если логика требует инвариантов “между await-точками”, нужно:
- избегать await внутри критической части,
- или копировать состояние локально до await,
- или перестраивать дизайн.

## 4) Actor vs serial queue/locks
- Actor даёт compile-time модель изоляции и хорошо сочетается с async/await.
- Serial queue/locks — runtime-уровень; компилятор не гарантирует, что ты всегда обращаешься к state правильно.
- Actor проще для reasoning в async коде, но требует `await` и меняет API.

## 5) `MainActor` как частный случай
`@MainActor` — global actor для UI:
- всё помеченное `@MainActor` изолировано так, будто находится “в одном actor’е” на main executor’е.

## 6) Что actor не решает автоматически
- Не делает твою логику правильной: можно получить race condition на уровне событий/порядка (логические гонки).
- Не решает проблемы долгих операций внутри actor:
  - если ты делаешь heavy CPU внутри actor, ты блокируешь доступ к его состоянию.
- Не защищает внешние reference-типы, которые actor хранит и отдаёт наружу (можно “вынести” небезопасный объект наружу).

**Самопроверка**
- Оспорено: “actor = lock” — actor ближе к модели “очередь сообщений + изоляция + compile-time ограничения”, и имеет reentrancy нюансы.
- Неочевидно: reentrancy между await-точками — частый источник багов; важно уметь объяснить, что actor сериализует доступ, но не делает метод “атомарным” сквозь await.
- Источники: Swift Concurrency docs (Actors), WWDC про actor isolation и reentrancy, материалы про MainActor/global actors.

### Q78 (🔴): Как избежать data races при доступе к общему состоянию: actor, locks, serial queue, атомики — критерии выбора?

**Кратко**
- Выбор инструмента зависит от:
  - **модели данных** (есть ли общий mutable state),
  - **async/await контекста**,
  - частоты чтений/записей,
  - требований к latency/throughput,
  - сложности инвариантов,
  - необходимости fairness/приоритетов/отмены.
- Базовая эвристика:
  - UI и UI-state → `@MainActor`.
  - Изолированный state в async мире → `actor`.
  - Простая синхронизация в sync мире → serial queue или `NSLock`.
  - Read-heavy, write-rare → concurrent queue + barrier или rw-lock.
  - Простые флаги/счётчики → атомики.
- Самое важное: инструмент работает только при **дисциплине доступа** (все пути к state должны идти через один механизм).

**Развёрнуто**
## 1) Сначала классифицируй проблему
### A) Есть ли общий mutable state?
- Нет → лучше сделать immutable/value semantics и забыть о синхронизации.
- Да → нужно изолировать доступ.

### B) Контекст исполнения
- Ты в structured concurrency (async/await) → actor’ы естественнее.
- Ты в legacy sync/GCD мире → queues/locks проще интегрировать.

### C) Инварианты
- Один счётчик/флаг → атомик может быть достаточен.
- Несколько связанных полей → нужен механизм “атомарности группы” (lock/queue/actor).

## 2) Actor: когда лучший выбор
Выбирай `actor`, если:
- state должен быть доступен из многих async задач,
- ты хочешь compile-time защиту от data races,
- API может быть async.

Плюсы:
- изоляция по умолчанию,
- cancellation/await-интеграция,
- меньше ручных ошибок с locks.

Минусы:
- `await` в API,
- reentrancy нюансы (между await-точками),
- heavy CPU внутри actor блокирует доступ.

## 3) Serial queue: когда проще всего
Выбирай serial queue, если:
- код в основном sync/closure-based,
- ты хочешь “одну линию исполнения” для state,
- API может быть sync (`queue.sync`) или async (`queue.async`).

Плюсы:
- простой reasoning,
- удобно внедрять без переписывания API на async.

Минусы:
- риск дедлока (особенно `sync`),
- нет compile-time гарантий: можно случайно обойти очередь и сломать всё.

## 4) Locks (NSLock/os_unfair_lock): когда нужен локальный замок
Выбирай locks, если:
- критическая секция маленькая,
- доступ к state происходит из многих мест, и не хочешь прокидывать очередь,
- важно sync API и минимальный overhead.

Плюсы:
- очень точечная защита,
- быстрые для маленьких секций.

Минусы:
- дедлоки, priority inversion,
- сложнее maintainability: легко забыть lock или держать слишком долго,
- сложно комбинировать с `await` (нельзя держать lock через await).

## 5) Concurrent queue + barrier: read-many/write-one
Выбирай этот подход, если:
- чтений много, записей мало,
- хочешь параллелить чтения.

Плюсы:
- высокая пропускная способность на чтениях.

Минусы:
- дисциплина доступа обязана быть строгой,
- записи async barrier могут усложнить консистентность (нужны sync/barrier или callbacks).

## 6) Atomics: для простых примитивов
Выбирай атомики, если:
- нужен флаг/счётчик/once-init,
- ты понимаешь memory ordering,
- нет сложных инвариантов.

Плюсы:
- минимум overhead,
- без блокировок.

Минусы:
- легко сделать “атомарно, но неправильно”,
- не подходит для сложных структур.

## 7) Быстрый чек-лист выбора (интервью)
- Нужен async API и безопасность компилятором → actor.
- Нужно сохранить sync API → serial queue или lock.
- Read-heavy → barrier.
- Только счётчик/флаг → атомик.
- UI → MainActor.

**Самопроверка**
- Оспорено: “есть один правильный инструмент” — нет; выбор зависит от API-границ и инвариантов.
- Неочевидно: часто лучший фикс — убрать общий mutable state, а не “прикрутить lock”.
- Источники: Swift Concurrency (actors, MainActor), Apple docs по GCD/locks/barriers, материалы по atomics и memory ordering.

### Q79 (🔴): Как диагностировать подвисания/дедлоки/priority inversion: признаки и инструменты?

**Кратко**
- Признаки:
  - **Hang/UI freeze**: main thread занят или ждёт ресурс.
  - **Deadlock**: потоки “взаимно ждут” (locks/queues/semaphores), прогресс = 0.
  - **Priority inversion**: high-QoS ждёт low-QoS, иногда при участии medium-QoS, проявляется как “периодические фризы”.
- Инструменты:
  - Xcode Pause/Debug Navigator → backtraces всех потоков.
  - **Instruments**: Time Profiler, System Trace, Thread States/Lock Contention, Points of Interest.
  - Thread Sanitizer (для data races, иногда помогает косвенно).
  - `os_signpost`/`Logger` для точечной телеметрии.
  - Memory Graph — не для дедлоков, но помогает, если “зависание” из-за удержаний/тасков.

**Развёрнуто**
## 1) Сначала классифицируй “подвисание”
### A) UI freeze (main thread blocked)
Чаще всего причина:
- sync ожидание на main (`DispatchQueue.sync`, `semaphore.wait`, `group.wait`),
- долгий CPU на main (парсинг, layout, image decode),
- ожидание lock, который держит background,
- долгий I/O на main.

### B) Deadlock
Признак:
- несколько потоков в состояниях ожидания, образуют цикл зависимостей (locks/queues/semaphores).
Обычно воспроизводится “всегда” при определённом сценарии, но иногда зависит от таймингов.

### C) Priority inversion
Признак:
- high-QoS поток/задача блокирован на lock/очереди,
- low-QoS держит ресурс долго,
- medium-QoS активно исполняется и вытесняет low → high ждёт ещё дольше.

## 2) Быстрая диагностика в Xcode (самый быстрый шаг)
### “Pause” в момент зависания
1) Во время фриза нажать Pause в Xcode.
2) Открыть Debug Navigator → Threads.
3) Посмотреть:
- main thread: что делает? (в lock? в `dispatch_sync`? в ожидании семафора?)
- другие потоки: кто держит lock? кто ждёт?

Если видишь:
- `dispatch_sync` на main → вероятный дедлок/блокировка.
- `semaphore_wait_trap` → кто-то ждёт семафор.
- `pthread_mutex_lock`/`os_unfair_lock_lock` → ожидание lock.

## 3) Instruments: что и когда включать
### Time Profiler
Используй когда:
- подвисание из-за CPU работы.
Смотри “горячие” стеки, особенно на main.

### System Trace
Используй когда:
- подозрение на scheduling/QoS/priority inversion,
- нужно увидеть thread states, preemption, QoS, wakeups.
Это самый информативный для “почему high ждёт low”.

### Points of Interest / os_signpost
Добавь метки вокруг подозрительных участков:
- начало/конец операций,
- ожидания,
- захват/освобождение ресурсов.
Позволяет точно сопоставлять задержки со стек-трейсами.

### Lock Contention (если доступен в профайле)
Позволяет увидеть:
- какие locks самые конфликтные,
- кто держит долго,
- кто ждёт.

## 4) Типовые паттерны, которые ловят hang/deadlock
- `DispatchQueue.main.sync` из main контекста.
- `group.wait()` или `semaphore.wait()` на main.
- Захват нескольких locks в разном порядке (A→B и B→A).
- Держать lock через I/O/await.
- Один общий serial queue для разных QoS задач (UI и фон) → UI ждёт фон.

## 5) Практическая стратегия локализации
- Сделать repro шаги и “узкий” сценарий.
- Поставить `os_signpost` вокруг ключевых этапов.
- Если hang:
  - Pause → посмотреть стеки.
- Если периодические фризы:
  - System Trace + signposts → увидеть зависимость QoS/ресурсов.
- Если дедлок редкий:
  - добавить искусственные задержки, увеличить параллелизм, чтобы “вытащить” тайминги наружу.

**Самопроверка**
- Оспорено: “Time Profiler решит всё” — он ловит CPU, но дедлоки/priority inversion часто требуют System Trace и анализа thread states/locks.
- Неочевидно: многие “подвисания” — это не deadlock, а просто блокировка main на ожидании (wait/sync) или тяжёлой работе; классификация экономит часы.
- Источники: Apple Instruments docs (Time Profiler/System Trace/Points of Interest), практики отладки hangs в Xcode, материалы про QoS и priority inversion.
